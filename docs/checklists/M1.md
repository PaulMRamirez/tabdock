# M1 checklist

Run on 2 October 2026 in a Claude Code cloud session (Linux, Node 22.22, headless Chromium 141 with the MCP-B polyfill, plus Chrome for Testing 154 and 156 for native WebMCP). What the sandbox could check is ticked with its evidence; what needs the owner's own laptop is left open with steps.

## Done in the sandbox

- [x] **A1.1** End to end with the sim page: pair by code, operator approves, `list_pages`, `list_page_tools`, `call_page_tool` returns the handler's result under the untrusted header. `tests/e2e/test/pairing.test.ts`, in `pnpm test`, on all three runtime profiles (`runtimes.test.ts`).
- [x] **A1.2, scripted with Claude Code itself.** `pnpm --filter @tabdock/e2e check:claude-code:m1` ran Claude Code 2.1.287 against the relay as an HTTP MCP server with an `Authorization: Bearer` header, the demo page in headless Chromium with the real adapter. Claude paired with the code from the page, the script approved, and Claude called `get_view` and `add_item`; the page's activity strip recorded both, and the relay's audit named the client `claude-code 2.1.287` (the script asserts the client name).
- [x] **A1.2 in a real browser, scripted.** `tests/e2e/specs/tabdock-relay.spec.ts` pairs, approves with a real mouse click on the widget's Allow as driver button inside its closed shadow root, lists and calls tools, and denies `clear_board` from the widget.
- [x] **A1.3** A reload inside the resume window keeps the page id, attachment and roster; past the window the page is gone. `tests/e2e/test/resume.test.ts` with the sim page, and `page.reload()` in the Playwright spec.
- [x] **A1.4** A wrong code and an expired code each return `pairing_expired`; a denial returns `denied_by_operator`; silence ends in `timeout` and no attachment. `tests/e2e/test/pairing.test.ts`.
- [x] **Native WebMCP.** `tabdock-relay.spec.ts` and `demo-page.spec.ts` also pass on Chrome for Testing 154 (string input) and 156 (object input) through `CHROMIUM_EXECUTABLE`, so the adapter's input detection works on both sides of the Chrome 155 change.
- [x] Section 9 requirements M1 can prove, each with tests in `packages/relay/test` or `tests/e2e/test`: S1, S2, S3, S4, S10, S11, S12, S13, the relay and adapter halves of S5, S6's prompt and deny-on-silence, S7's relay audit, S8's revoke, and S9's frame and result caps. The S9 limits on users, call rate and queue depth arrive in M2.

## For the owner, on a laptop (about fifteen minutes)

- [ ] **A1.2 interactively.** Follow "Try it by hand" in `docs/tour/01-walking-skeleton.md`: make a token, `pnpm dev`, open the printed URL in Chrome, add the relay to Claude Code with the printed `claude mcp add` line, ask Claude to pair with the code in the Tabdock widget and click Allow as driver. Then ask it to add an item, try `clear_board` and Deny, and reload the tab. Note your Claude Code version and anything that felt slow or unclear in the widget.
- [ ] **Native WebMCP in your own Chrome, optional.** With `chrome://flags/#enable-webmcp-testing` on in Chrome 155 or later, repeat the pairing and a call. The sandbox already proved this headless; this confirms it with a real profile and a visible tab.
