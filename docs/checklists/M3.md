# M3 checklist

Run on 3 October 2026 in a Claude Code cloud session (Linux, Node 22.22, headless Chromium 141 with the MCP-B polyfill). The sandbox cannot open a real tunnel or reach WorkOS or a phone (its proxy refuses tunnel edges, WebSocket upgrades and non-443 ports; `docs/notes/verified.md`), so the public path was tested against `oauth2-mock-server` and an https stand-in for the public URL, and every item that needs the real tunnel, provider or phone is left open below with steps.

## Done in the sandbox

- [x] **The relay as a resource server.** A valid token works on both protocol eras; expired, wrong audience or issuer, unsigned, unknown-key and no-expiry tokens are refused; no or a malformed header gets a 401 with `resource_metadata`; an account off the allowlist gets a 403; unreachable provider keys give a 503; a provider whose metadata does not match is refused at startup; and the client SDK's whole OAuth flow goes from the first 401 to a tool call. `packages/relay/test/oauth.test.ts`.
- [x] **Public URL mode.** An http or pathful public URL is refused, the Host allowlist takes the public host and loopback names only, dev tokens are refused everywhere, and `/page` takes only sockets made on this machine. `packages/relay/test/public-mode.test.ts` and `config.test.ts`; `pnpm dev:public` names every missing setting and never prints a secret (`tests/e2e/test/dev-public.test.ts`).
- [x] **QR pairing at `/pair`.** The nonce is 128 bits, in the fragment, single use, dies with its code (on expiry, use, a typed code or the page sleeping), and unknown, used and malformed nonces answer alike; a preview spends nothing; a claim without a session, from another origin or by a non-member is refused before the nonce is read; approve, deny and silence each reach the phone; limits count per user and per page; no nonce, code, cookie, sign-in value or token reaches a log line. `packages/relay/test/pair.test.ts` and `pairing.test.ts`. A phone-sized Chromium goes from the QR URL through mock sign-in, Join and the operator's click to a first call: `tests/e2e/specs/pair.spec.ts`.
- [x] **The widget's QR code.** Drawn as one SVG path under a Trusted Types CSP, identical to the library's matrix, redrawn for each pairing, absent for a URL that is not https, and never logged; it fits at phone width. `packages/adapter/test/qr.test.ts` and the QR tests in `tests/e2e/specs/widget.spec.ts`.
- [x] **Spike tooling.** The flag is off by default and refused in production; the marker tool comes and goes from the relay's terminal and reaches 2025 sessions as `list_changed` and 2026-07-28 clients through `subscriptions/listen`; call timings and pairing milestones are logged without tokens. `packages/relay/test/spike.test.ts`, `tests/e2e/test/spike-latency.test.ts`. `pnpm spike:soak --quick` froze and thawed the demo page three times, and each time it resumed the same page with its attachment and a working call (`tests/e2e/specs/soak.spec.ts` in CI).
- [x] **Claude Code.** `pnpm --filter @tabdock/e2e check:claude-code:m3` signs Claude Code 2.1.288 in through the relay's 401 and metadata (CIMD client id, S256, `resource` equal to the connector URL) against an https stand-in, and it shows Connected. It needs the installed CLI, so it is not in CI.
- [x] **Demo.** `pnpm demo:m3` passes from a clean `git archive` export after `pnpm install --frozen-lockfile`.

## For the owner

### 1. Accounts and settings (laptop, about 30 minutes)

- [ ] **ngrok.** Create a free account and install the agent with your authtoken. The free plan gives one development domain on `ngrok-free.app` or `ngrok-free.dev`, assigned to you and fixed; its `https://` origin is `TABDOCK_PUBLIC_URL`. Run `ngrok http 127.0.0.1:8787 --url https://<your domain> --inspect=false`: the last flag turns off the local inspector, which would show whole requests with their bearer tokens (ADR 0016). Leave full capture off in the ngrok dashboard (Settings, Observability; off by default).
- [ ] **WorkOS.** Create an AuthKit environment. Under Connect, Configuration, in the MCP Auth card, choose Manage and turn on Client ID Metadata Document (off by default) and Dynamic Client Registration. In the MCP resource indicators card, choose Edit MCP resources, add `<public URL>/mcp` exactly, and use its menu to Set as default, so a client that sends no `resource` still gets that audience. Under Connect, Applications, create an OAuth application, first-party and confidential (the default), with the redirect URI `<public URL>/pair/callback`; its client id and a secret (shown once) go in `.env`. Each person's user ID (`user_...`, the `sub`) is in the address of their page under Users. `TABDOCK_OAUTH_ISSUER` is your AuthKit domain exactly as the `issuer` in its metadata.
- [ ] **`.env`.** Run `pnpm dev:public` once with nothing set: it lists the six settings it needs (`TABDOCK_PUBLIC_URL`, `TABDOCK_OAUTH_ISSUER`, `TABDOCK_OAUTH_USERS`, `TABDOCK_PAIR_CLIENT_ID`, `TABDOCK_PAIR_CLIENT_SECRET`, `TABDOCK_ALLOWED_ORIGINS`), and once the public URL is in, the Resource Indicator and redirect URI to enter at WorkOS. Add `TABDOCK_SPIKE=1` for the measurements. `.env.example` describes each.

### 2. First run through the tunnel

- [ ] Start `pnpm dev:public` and ngrok. From the laptop, `curl -i -X POST <public URL>/mcp` should give a 401 whose `WWW-Authenticate` names `<public URL>/.well-known/oauth-protected-resource/mcp`, and that URL should return JSON naming your AuthKit issuer. If either fails, check that ngrok passes the public `Host` unchanged.
- [ ] Open `<public URL>/pair` in the laptop's browser and click Visit on ngrok's warning page (a cookie keeps it away for 7 days): the page should then say "No pairing link here".
- [ ] **Claude's sign-in sends no scope**, since the relay's metadata lists none (WorkOS's own MCP server does the same). If claude.ai reports a scope error at sign-in in step 3, tell me.
- [ ] **Streamed responses.** In step 3, the first tool call from Claude on the web should answer within a few seconds. If calls hang until a timeout, note it here: the 2025-era leg would then answer with plain JSON (M3 plan). The relay sends a keepalive on open streams every 15 s, well inside ngrok's 5-minute idle limit.

### 3. Claude on the phone (A3.1)

- [ ] On claude.ai on the laptop, add a custom connector with the connector URL `pnpm dev:public` prints (`<public URL>/mcp`), and sign in with an account listed in `TABDOCK_OAUTH_USERS`. A connector cannot be edited later, so check the URL first.
- [ ] Open `http://127.0.0.1:5173/` (the demo board) on the laptop. In the Claude app on the phone, with the connector enabled, ask Claude to pair with the code the widget shows, allow it on the laptop, and ask for the board's view and to add an item. Note the client name the roster shows.
- [ ] Ask from the phone again after the laptop's screen has been locked for a minute, and note whether the call works.

### 4. QR pairing from the phone (A3.2)

- [ ] On the phone, open the public URL once first and click Visit on ngrok's warning page, so the cookie keeps it from sitting between the QR link and `/pair`. Later, try one scan in a private tab without that cookie and note whether `/pair` still finds the link after the warning page.
- [ ] Scan the widget's QR code off the laptop screen with the phone's camera, in light and in the page's dark mode, and note whether it reads first time.
- [ ] On the phone, `/pair` should show the board's origin, title and the same code as the widget, then sign you in, come back, and join on Join. The page keeps the link in `sessionStorage` across the sign-in; note it if the page lost it on the way back. If sign-in fails, the relay logs `pair sign-in failed` with the provider's reason; send it to me. WorkOS's reference says PKCE works only for apps made through dynamic registration, while the relay always sends it, so this is the step to watch.
- [ ] Allow it on the laptop; the phone should say you joined. Then ask Claude on the phone to list pages and call `get_view`.

### 5. Measurements (A3.3), with `TABDOCK_SPIKE=1`

- [ ] **Round trip.** On the laptop, `pnpm spike:latency --public --code <code>`; open the sign-in URL it prints, approve the pairing on the page, and paste its table into `docs/notes/spike.md`.
- [ ] **Tool list changes.** In a Claude chat on the phone that has used the board, type `add` in the relay's terminal, ask Claude in the same chat which tools it has, then start a new chat and ask again. Record the relay's `spike: tools/list` and `spike: client opened a stream` lines and both answers in `spike.md`; type `remove` afterwards.
- [ ] **Tab survival.** Run `pnpm spike:soak` (60 minutes) once. Then leave the demo board in a background tab for an hour with Energy Saver off, then on with `?busy` added to the demo URL, and once across laptop sleep; after each, ask Claude for the view and watch the relay's `page asleep` and `page connected` lines. Fill the tab survival table.
- [ ] **Scan to first call.** Pair once by QR and once by code, call a tool, and copy the `spike: pairing milestone` lines' timings into the table.

### 6. The go or no-go note (A3.4)

- [ ] Fill the gate table at the end of `docs/notes/spike.md` (conversational latency, fixed tools on mobile, an hour of background survival) and write the verdict in a few sentences.
