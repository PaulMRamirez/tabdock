# M4 checklist

Started on 3 October 2026, before the hosted code exists. This first half is the setup you can do now, in order: local mode on your laptop, then the reference deployment, starting with the GitHub `production` environment so that every value has a home the moment a page shows it, then Fly.io, WorkOS production and Pages. The second half lists what waits for the M4 pull request to merge, and the sandbox results join at the end of the milestone. `docs/deploy.md` explains each account and setting in more depth, including how to rotate it. Every dashboard name, command and limit below was checked against Fly's, WorkOS's and GitHub's documentation on 3 October.

(C) marks a step that needs a computer; everything else works in a phone browser. No value enters the repository, an issue, a pull request, a chat or a notes app: each one goes from the page that shows it straight into a secret of the GitHub `production` environment. Placeholders: `<domain>` is your personal domain, `<app>` the Fly app name you choose, `<user>` your GitHub user name, `<authkit domain>` your WorkOS production environment's sign-in domain.

## Setup you can do now

### 1. Local mode (laptop, about 5 minutes)

Available once local mode lands on the `m4-cloud` branch, as its own commit ahead of the rest of M4; I will say when. Until the pull request merges, run it from that branch.

1. [ ] (C) Update your checkout to that commit and run `pnpm install`.
2. [ ] (C) Move your M3 settings aside: `mv .env .env.m3`. Any of them turns local mode off, since explicit settings win (ADR 0022). Git ignores `.env.*`, and `pnpm dev:public` needs the file back under its old name.
3. [ ] (C) Inside the checkout, remove the M1-era entry: `claude mcp remove tabdock --scope local`. It holds an old dev token in the scope that belongs to this directory, and the name `tabdock` is kept for the hosted relay. If Claude Code says there is no such server, move on.
4. [ ] (C) Run `pnpm relay`. The banner says the relay serves this computer only, names the token file and whether it was just created, and prints a `claude mcp add ... tabdock-local` command for your shell. It never prints the token.
5. [ ] (C) In a second terminal, paste that command as printed. It reads the token from the file, so neither your shell history nor the screen ever holds it.
6. [ ] (C) Check with `claude mcp list`: `tabdock-local` should show `✔ Connected`. Never use `claude mcp get` for this; it prints the stored header, token and all. Note your Claude Code version here, and send me any refusal the relay printed (each names its fix, never the file's contents).

### 2. The GitHub `production` environment (about 10 minutes)

This comes first because two values in later sections are shown only once, and each must go straight from its page into this environment.

1. [ ] In the repository's Settings, open Environments, choose New environment, name it `production` and choose Configure environment. (On the free plan this needs a public repository, which this one is.)
2. [ ] Tick Required reviewers and add yourself. Leave Prevent self-review off: you are the only reviewer and you start the deploys, so with it on nobody could approve. Save protection rules.
3. [ ] Untick Allow administrators to bypass configured protection rules and save, so every deploy waits for an explicit Approve, even one started under your account.
4. [ ] Under Deployment branches choose Selected branches and tags, then Add deployment branch or tag rule, Ref type Branch, name `main`, Add rule.
5. [ ] Protect `main` itself, since step 4 is only as strong as the branch. In the repository's Settings open Rulesets (under Rules), then New ruleset, New branch ruleset. Name it `main`, set Enforcement status to Active and leave the Bypass list empty. Under Target branches choose Add a target, then Include default branch. Under Branch protections keep Restrict deletions and Block force pushes ticked (the default), tick Require a pull request before merging with Required approvals left at 0, and choose Create. Every change to `main`, the deploy workflow included, then arrives as a pull request you can see.
6. [ ] Under Environment secrets, choose Add secret for the two values you know already. Never Add variable: GitHub prints variables unmasked in logs. Never repository secrets either: every workflow can read those without your approval.
   - `TABDOCK_PUBLIC_URL`: `https://relay.<domain>`, with no path and no trailing slash.
   - `TABDOCK_ALLOWED_ORIGINS`: `https://demo.<domain>`.

### 3. Fly.io (about 20 minutes)

1. [ ] Create an account at fly.io and add a card on your organization's Billing page. There is no free tier; the trial lasts 2 Machine hours or 7 days, and a card (or at least $25 of credit) keeps the app running after it.
2. [ ] (C) Install flyctl (`brew install flyctl`, or `curl -L https://fly.io/install.sh | sh`, or on Windows `pwsh -Command "iwr https://fly.io/install.ps1 -useb | iex"`) and run `fly auth login`.
3. [ ] If you keep or plan other apps in your `personal` organization, create an organization for Tabdock alone (in the dashboard, or (C) `fly orgs create <org>`) and use it in place of `personal` below: a deploy token can reach its organization's private network. Fly bills each organization separately, so the new one needs its card too.
4. [ ] (C) Pick `<app>`: unique across Fly, public as `<app>.fly.dev` (where the relay answers 403 to all but its health check), saying nothing about an employer, and not a word the deploy log prints anyway, such as plain `tabdock`, since GitHub hides a secret's value wherever a log shows it; a few random characters on the end do it. Then `fly apps create <app> --org personal`, and add the environment secret `FLY_APP` with the value `<app>`.
5. [ ] (C) Create the audit volume: `fly volumes create tabdock_audit --app <app> --region iad --size 1`. The name must be `tabdock_audit`, the one `deploy/fly/fly.toml` will mount. Volumes are encrypted at rest and snapshotted daily (kept 5 days) by default. One volume means a short outage on every deploy and on a host failure, the trade ADR 0019 accepts, so if flyctl warns about a single volume, go ahead.
6. [ ] (C) Give the app its addresses now, so DNS and the certificate can come before the first deploy: `fly ips allocate-v6 --app <app>` and `fly ips allocate-v4 --shared --app <app>`. A first deploy would allocate both itself, but it waits for the merge. Always pass `--shared`: without it Fly allocates a dedicated IPv4 at $2 a month. `fly ips list --app <app>` should show one IPv6 and one shared IPv4.
7. [ ] Add the certificate: in the dashboard open the app, then Certificates, and add `relay.<domain>` (or (C) `fly certs add relay.<domain> --app <app>`). Fly then shows several alternative DNS setups, not one list to copy.
8. [ ] At your DNS provider, create only these three of the records Fly shows, each set to DNS only, never proxied: the `A` record for `relay` (the shared IPv4), the `AAAA` record for `relay` (the IPv6) and the `_acme-challenge.relay` CNAME, which lets Fly issue the certificate before anything runs. Skip the alternative CNAME for `relay` itself and the `_fly-ownership` TXT record. (C) `fly certs setup relay.<domain> --app <app>` lists the same values. `docs/deploy.md` (DNS) says why each choice matters.
9. [ ] Check that the certificate page shows it issued once DNS resolves; (C) `fly certs check relay.<domain> --app <app>` checks again.
10. [ ] Make the deploy token: open the app, then Tokens, and create a token named `github-production` with an expiry of about a year if the form offers one (or (C) `fly tokens create deploy --app <app> --name github-production --expiry 8760h`; the default lifetime is 20 years). Copy all of it, including the leading `FlyV1` and the space after it, and add it at once as the environment secret `FLY_API_TOKEN`; keep no other copy. It can manage this app and, as Fly documents, open WireGuard tunnels into the organization's private network, and it can deploy code that reads every secret, which is why it sits behind your approval.

### 4. WorkOS production (about 20 minutes)

Nothing carries over from the M3 staging environment: production has its own issuer, users and applications, so every value below is new. If the dashboard is awkward in a phone browser, note it here.

1. [ ] Switch the dashboard to the Production environment, then add a card under Settings, Billing, Payment information; production stays locked without one. AuthKit costs $0 below a million monthly users as long as SSO, a custom domain and Radar stay off, so leave all three off.
2. [ ] Under Authentication: keep Email + Password on (the default); turn on Magic Auth, the six-digit code sent by email (valid 10 minutes), which is off until you enable it; and leave Sign up on, so invitees can make accounts. Email verification is always on.
3. [ ] Under Connect, Configuration: in the MCP Auth card choose Manage and turn on Client ID Metadata Document (off by default) and Dynamic Client Registration. In the MCP resource indicators card add `https://relay.<domain>/mcp` exactly, with no trailing slash, then choose Set as default from its "..." menu, so a client that sends no `resource` still gets a token for the relay.
4. [ ] Under Authentication, Features, JWT Template, paste exactly this and save (ADR 0020):

   ```
   { "urn:tabdock:email": {{ user.email }}, "urn:tabdock:email_verified": {{ user.email_verified }} }
   ```

   It renders into every access token the environment issues, Claude's included. The relay reads only these two claims; without them a guest shows as an unverified account.

5. [ ] Under Connect, Applications, create an OAuth application named `tabdock-pair`: first-party, confidential (leave Public off), with the redirect URI `https://relay.<domain>/pair/callback`. Add its client ID (`client_...`) as the environment secret `TABDOCK_PAIR_CLIENT_ID`. Then create a secret for it; WorkOS shows it once, so add it at once as `TABDOCK_PAIR_CLIENT_SECRET`.
6. [ ] Find the environment's AuthKit domain (a random name under `authkit.app`), open `https://<authkit domain>/.well-known/oauth-authorization-server` and copy its `issuer` value exactly into the environment secret `TABDOCK_OAUTH_ISSUER`. The same page should list `S256` under `code_challenge_methods_supported` and have a `registration_endpoint`.
7. [ ] Sign up once, to get your user ID. Open this address, with your two values filled in:

   `https://<authkit domain>/oauth2/authorize?response_type=code&client_id=<pair client id>&redirect_uri=https%3A%2F%2Frelay.<domain>%2Fpair%2Fcallback&scope=openid%20email&nonce=signup&state=signup`

   Choose sign up, use your personal email and enter the code WorkOS sends. The browser then fails to reach `relay.<domain>`, which is expected before the first deploy; the account exists. If the page offers no way to sign up, tell me before trying anything else.

8. [ ] In the dashboard open Users, then your user, and copy its ID (`user_...`, also in the page address): that is your `sub`. Add the environment secret `TABDOCK_OAUTH_USERS` as `<your user ID>=<short id>:<Your Name>`, where the short id is 1 to 64 letters, digits, `_` or `-` and does not start with `g_`, and the name is optional and has no comma.

### 5. Check the environment (2 minutes)

1. [ ] In the `production` environment, Environment secrets should list exactly these eight, and Environment variables none: `TABDOCK_PUBLIC_URL`, `TABDOCK_ALLOWED_ORIGINS`, `FLY_APP`, `FLY_API_TOKEN`, `TABDOCK_PAIR_CLIENT_ID`, `TABDOCK_PAIR_CLIENT_SECRET`, `TABDOCK_OAUTH_ISSUER` and `TABDOCK_OAUTH_USERS`. The other hosted settings name nothing of yours and go in `deploy/fly/fly.toml` with the code (`docs/deploy.md`, Settings in the repository).

### 6. GitHub Pages for the demo (about 10 minutes, plus DNS time)

The order matters: a custom domain that points at Pages without being verified and claimed can be taken over (ADR 0021).

1. [ ] In your profile's Settings (not the repository's), open Pages, choose Add a domain and enter `<domain>` itself. Create the TXT record it shows (`_github-pages-challenge-<user>.<domain>`), wait for DNS, then choose Verify. Keep that record for good: verifying `<domain>` also protects `demo.<domain>`, and removing the record undoes it.
2. [ ] Check your DNS zone for wildcard (`*`) records and delete any. GitHub warns that a wildcard allows a takeover even of a verified domain.
3. [ ] In the repository's Settings, open Pages and under Build and deployment set Source to GitHub Actions. Then enter `demo.<domain>` under Custom domain and Save. GitHub asks for the domain here before the DNS record exists; with an Actions source no `CNAME` file is needed.
4. [ ] At your DNS provider, add a CNAME record from `demo` to `<user>.github.io` (no repository name), DNS only.
5. [ ] Tick Enforce HTTPS once Pages offers it. GitHub says that can take up to 24 hours, and it may wait for the first publish after the merge; if so, leave it, and item 2 below brings it back.
6. [ ] If your zone has CAA records, make sure they allow `letsencrypt.org`, which issues both Fly's and GitHub's certificates.

Your zone should now hold, besides anything you had before: `A` and `AAAA` records for `relay`, the `_acme-challenge.relay` CNAME, a `demo` CNAME, the `_github-pages-challenge-<user>` TXT record, and no wildcard.

## After the merge

GitHub runs a dispatched workflow only when its file is on the default branch, so everything here waits for the M4 pull request to merge. I will expand each item into steps then.

1. [ ] **Image.** After CI publishes the first image to GHCR, open the package, then Package settings, and change its visibility to Public (a first publish is private, and Fly pulls it anonymously).
2. [ ] **First deploy.** Approve it in the GitHub app (Review deployments, Approve and deploy). Approve only a run on `main` that you started or I told you about, whose commit is a merge you reviewed; reject any other, and never ask a session to approve for you. I then check `/healthz`, the 401 challenge and the metadata from the sandbox, and the Pages publish of the demo. If Enforce HTTPS was not offered before, tick it now in the repository's Pages settings, and check that `http://demo.<domain>` redirects to `https://`.
3. [ ] **Proxy range.** I open a pull request that narrows `TABDOCK_TRUSTED_PROXY_CIDR` in `deploy/fly/fly.toml` to the range holding the proxy address the relay logged on its first request; merge it, then approve one more deploy.
4. [ ] **Connector.** On claude.ai on the web, remove the ngrok connector, add `https://relay.<domain>/mcp` and sign in with your production account.
5. [ ] **Phone and Claude Code.** Check that the connector appears in the Claude app on the phone. (C) Add the hosted relay to Claude Code as `tabdock`, replacing any older `tabdock` entry, sign in, and check with `claude mcp list`; this settles whether WorkOS production accepts Claude Code's `localhost` redirect.
6. [ ] **A4.2 with a second account.** Hold the operator tab on `https://demo.<domain>/?relay=wss://relay.<domain>/page&invites=all` (the demo's parameter names are confirmed when its changes land; `invites=all` lets the page offer control invites, which pages refuse by default). Pair from Claude on the web and call a tool from the phone; a second account joins by a watch invite (reads, refused a write) and by a control invite (approved, writes); Revoke all ends both. Then record the token-shape log line and what the checklist asks for at that point.
7. [ ] **Client list.** If the record shows both hosted Claude and Claude Code signing in through client ID metadata documents, turn Dynamic Client Registration off at WorkOS (Connect, Configuration, MCP Auth) and, in the same step, merge the pull request I open that sets `TABDOCK_OAUTH_CLIENT_IDS` in `fly.toml` to the URLs seen; then approve a deploy.
