## 7. Implications for M3

The resource-server half needs nothing new: an `oauth` plugin can call `verifyBearerToken` with `expectedResource` and `resourceMetadataUrl`, serve PRM with `oauthMetadataResponse`, and replace the `realm="tabdock"` challenge at relay.ts:159, which Claude cannot follow (H). `AuthPlugin` (auth.ts:9) returns only `User | null`, so it needs a way to emit the challenge (M). An OAuth `sub` may fail `IdSchema` (`^[A-Za-z0-9_-]{1,64}$`, protocol page-link.ts:12), so the plugin must map it (M). The SDK offers no token verifier: for IdP JWTs the choice is `jose` 6.2.12 (MIT, panva, 0 dependencies, 169.8 M downloads last week, already in the lockfile through the client devDependency, needs approval as a runtime dependency) or hono's `verifyWithJwks` with own key caching (no approval) (H for facts). The AS half has no maintained SDK answer. If the IdP issues audience-bound tokens and supports DCR or CIMD with PKCE, the relay stays a pure resource server. Otherwise the relay must be its own AS, minting relay-audience tokens after an upstream sign-in, with per-client consent; that needs an AS library and an upstream client library (`openid-client` 6.8.8 or `oauth4webapi` 3.8.8, MIT, panva, about 17 M downloads each last week), both owner decisions, and `server-legacy` is not a fit since it is deprecated, Express-bound and lacks CIMD (M).
