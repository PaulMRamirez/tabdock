Consequences for the build:

1. A quick tunnel's hostname changes each run, and a connector's auth settings cannot change after adding (claude.com/docs/connectors/custom/add-unlisted.md:207), so every restart means re-adding the connector and new OAuth metadata URLs. Prefer a stable hostname. H.
2. SSE risk: the relay's 2025-era session leg builds `WebStandardStreamableHTTPServerTransport` without `enableJsonResponse` (`packages/relay/src/sessions.ts:169-180`), whose default is SSE (`@modelcontextprotocol/server` 2.3.0 `dist/index.d.mts:526`); the 2026-07-28 leg uses `auto`, JSON unless a notification precedes the result, and `subscriptions/listen` is always SSE (`createMcpHandler-D4NN8WsG.d.mts:3694, 3950-3962`). Claude's OAuth support lists the 2025 auth specs only (claude.com/docs/connectors/building.md:43), so hosted Claude likely takes the SSE leg. On a quick tunnel, set `enableJsonResponse: true` or avoid it. Facts H, behaviour untested.
3. Claude rejects hostnames with no public `A` record, any non-routable address, or CGNAT `100.64.0.0/10`, and WAF or bot rules can block it (claude.com/docs/connectors/building/troubleshooting.md:22-55). The relay's `Host` check must admit the tunnel hostname (testing.md:27). H.
4. Timeouts fit: call deadline 45 s and pair wait 50 s (`packages/protocol/src/constants.ts:41,44`), under Cloudflare's 125 s and Claude's 240 s. H.
5. All tunnelled traffic reaches the relay from loopback ("requests to the origin are made internally between cloudflared and the origin", tunnels FAQ), so per-address limits collapse into one bucket in M3 (backlog M4 item). H.

**Sandbox:** cannot test the public path. GitHub release downloads return 403 (repository not enabled for this session), but `cloudflared` 2026.9.3 installed from `pkg.cloudflare.com`. The tunnel edge `region1.v2.argotunnel.com` failed the TLS handshake through the proxy, and `/root/.ccr/README.md` lists WebSocket upgrades, non-443 ports and certificate-pinned clients (ngrok) as unsupported; `connect.ngrok-agent.com` was unreachable. Starting a quick tunnel was refused by the session's permission policy ("External Ingress Tunnel"). Tailscale needs the owner's account; not attempted. Public-path checks go in `docs/checklists/M3.md`. H.

## 2. QR flow at `/pair`

**Library facts (H):** `qrcode-generator` 2.0.4, MIT, sole maintainer kazuhikoarase, no `dependencies` (0 transitive), 4,376,069 downloads 25 Sep to 1 Oct 2026, published 7 Aug 2025 and nothing since (`npm view`; api.npmjs.org). ESM default export (`dist/qrcode.mjs:2235`). API: `qrcode(typeNumber 0=auto, 'L'|'M'|'Q'|'H')`, `addData`, `make`, `getModuleCount`, `isDark`, `createSvgTag({cellSize, margin, scalable})`, `createDataURL`, `renderTo2dContext` (`dist/qrcode.d.ts:30-51`). Default margin is 4 cells (`qrcode.mjs:507`). `stringToBytes` keeps only the low byte (`qrcode.mjs:735-742`), so URLs must be ASCII. A default import typechecks under the repo's NodeNext plus `verbatimModuleSyntax` with TypeScript 6.0.3. Minified 20.9 KB, 7.6 KB gzip (esbuild).

**Size (H, probe):** an 89-character quick-tunnel URL with a 22-character nonce is version 6 at level M (41 modules); a 62-character Funnel URL is version 4 (33 modules).

**Rendering in the closed shadow root (H, probe `shadowqr.mjs`):** under `require-trusted-types-for 'script'` plus `img-src 'self'`, `innerHTML = createSvgTag()` threw `TypeError ... requires 'TrustedHTML'` and the `createDataURL` image was blocked; an SVG built with `createElementNS` from `isDark()` (one `<path>`, `shape-rendering="crispEdges"`, white background, 4-module quiet zone) and the canvas both rendered. Build the SVG with DOM calls; the adapter runs on pages whose CSP it does not control.

**Nonce flow (design; RFC sources H, design M):**

1. Mint the nonce with the ticket: 128 random bits from `node:crypto`, base64url, single use, 120 s, bound to `pageId`, separate from the code; compare in constant time or look up by hash.
2. QR encodes `https://<public>/pair#<nonce>`. A fragment is "separated from the rest of the URI prior to a dereference" (RFC 3986 section 3.5), so it never reaches relay or tunnel logs (S11). Page script reads `location.hash`, clears it with `history.replaceState`, keeps it in `sessionStorage` through sign-in.
3. `GET /pair` is static and consumes nothing; send `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `frame-ancestors 'none'`.
4. Sign-in uses the same identity provider as the `oauth` plugin, so the browser user and Claude's token map to one `userId`. Session cookie `__Host-` (Secure, no Domain, Path=/), HttpOnly, `SameSite=Lax`, which survives the provider's top-level GET redirect but not cross-site POSTs (MDN Set-Cookie, 1 Sep 2026).
5. Before claiming, show the page's origin (from the WebSocket `Origin` header), title and current pairing code to match against the widget: RFC 8628 sections 3.3.1 and 5.4 recommend this against remote phishing when a QR skips typing. As built, the preview works before sign-in too, so the phone shows what it would join first; it shows only what the QR's own widget already shows.
6. `POST /pair/claim` (session cookie, `Origin` checked): consume atomically, rotate the ticket and push `pairing`, create an `AttachRequest` with `via: 'qr'`; rate limit per user and per page, never per address (ADR 0016, since every tunnelled caller shares one); one generic error for unknown, used or expired.
7. Operator approves on the page (60 s, default deny); the phone polls status rather than holding SSE.

The nonce alone yields nothing; nonce plus session yields only a pending request.

## 3. Spike measurements (A3.3)

**Latency (design, M):** a script on `@modelcontextprotocol/client` 2.3.0 against the public URL: 5 warm-up calls, then 50 sequential `call_page_tool get_view`, timed with `performance.now()`; nearest-rank p50 is the 25th and p95 the 48th sorted value. Log relay timestamps (request in, `invoke` out, `result` in, response out) to split tunnel from page time; hosted Claude's latency includes model time, so only the relay split is measurable for it. How the script authenticates through the `oauth` plugin is open.

**Tool list refresh (L):** no Claude doc covers `list_changed` or mid-chat refresh (claude.com connector docs grepped). A vendor help page says "A chat that's already open keeps the tool list it started with" (eden.so/help/eden-mcp/refreshing-tools, 28 Sep 2026; secondary). Test: a spike flag adds a marker tool on demand and sends `list_changed` on sessions with a GET stream; the relay logs every `tools/list` and `GET /mcp` from Claude; ask in the same chat, then a new one. Manual.

**Web Lock and Energy Saver (M to H):** in Chromium main, `kHoldingWebLock` is a cannot-freeze reason set when a frame "holds at least one Web Lock" (`frame_node.h:216-217`, `freezing_policy.cc:813-815`), kept for every freezing type (`freezing_policy.cc:366-378`); only IndexedDB has a "blocking" variant. The string "holding Web Lock" is in the CfT 154, 155 and 156 binaries. The blog's "Hold a Web Lock or an IndexedDB connection that blocks operations outside the group" is ambiguous; chromestatus ties "blocks" to IndexedDB. So the adapter's uncontested lock should exempt the tab; confirm at `chrome://discards`. Energy Saver freezes only CPU-intensive groups hidden and silent over 5 minutes (about 10% of background tabs; developer.chrome.com/blog/freezing-on-energy-saver; chromestatus 5158599457767424), so also test a CPU-busy variant. Infinite-tabs freezing is off by default (`components/performance_manager/features.cc:215`).

**Memory Saver (H):** a Web Lock does not protect from discarding; a pinned tab does (`chrome/browser/performance_manager/policies/discard_eligibility_policy.cc`). A discard reloads the page, and attachments survive only inside the 10-minute resume window. Pin the tab for the spike and log `document.wasDiscarded`.

**Freezing drops the socket (H):** Blink fails open WebSockets on `kFrozen` (`dom_websocket.cc:601-622`; `DisconnectWebSocketOnBFCache` is `stable`, `runtime_enabled_features.json5:2483`). Probe: the page saw close 1006 at resume and the server saw 1001 only then; during a 40 s freeze the network stack answered 200 protocol pings while the page answered 0 app pings. The relay's JSON `ping` (`hub.ts:853-864`) detects this; protocol `ws.ping()` would not.

**Timers (H):** hidden over 5 minutes, chain count 5 or more, silent 30 s and no WebRTC gives one wake-up per minute; WebSockets are not an exemption (developer.chrome.com/blog/timer-throttling-in-chrome-88). Backoff and the 2 s poll can stretch to 60 s.

**Headless versus manual (H, probes):** `Page.setWebLifecycleState` (experimental, `frozen`/`active`; `Page.pdl:1245`) over raw CDP hid the page, fired `freeze`, stopped timers and fired `resume`; the page stays hidden afterwards, which allows a 60-minute hidden soak. Through Playwright (`launch` or `connectOverCDP`) the same call succeeded but froze nothing, because Playwright enables `Emulation.setFocusEmulationEnabled` for every page it controls, which keeps the page visible and focused; a raw CDP session that enables focus emulation itself stops freezing too (found while building the soak, 3 October 2026, Playwright Chromium 141.0.7390.37). On that build a 3 s freeze did not drop the WebSocket, while freezes past the relay's 30 s idle timeout were dropped 20 to 30 s in and the adapter resumed the same page about 0.9 s after the thaw. No CDP command sets visibility (`Page.pdl`, `Emulation.pdl`, `Target.pdl`). CDP froze a page holding a lock, so it bypasses Chrome's policy: headless tests adapter recovery, not the exemption. Energy Saver, Memory Saver, laptop sleep (relay, tunnel and tab suspend together), network changes and the phone are manual. Time from scan to first call comes from relay timestamps (nonce issued, claim, approval, first call).
