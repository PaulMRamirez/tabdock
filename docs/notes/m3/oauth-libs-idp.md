## 2. The three shapes

**(a) Relay is its own AS** and delegates sign-in upstream: it mints relay-audience tokens, serves DCR or CIMD, shows per-client consent, holds keys and grants; the upstream needs one HTTPS callback. Most code and attack surface. (M)

**(b) Relay is a pure resource server**; its PRM names an AS that already does DCR or CIMD, S256 and audience binding. Relay code: PRM, `verifyBearerToken`, a JWT check. Least code; needs an IdP account. (M)

**(c) Hosted gateway.** Cloudflare Access "Managed OAuth" makes Access the AS (DCR, redirect allowlist, localhost and loopback toggles), gives clients opaque tokens and hands the origin a `Cf-Access-Jwt-Assertion` JWT to verify; it needs a named Cloudflare Tunnel on a domain in the account (oauthlib/src/cf-managed-oauth.md:17-23, 85-87, 199-221, 298; H). Quick tunnels need no account but change hostname every run and do not support SSE (developers.cloudflare.com trycloudflare page; H). Zero Trust free for 50 users: secondary sites only (L).

Using Google or GitHub directly as Claude's AS through "Use your own OAuth client" fails the audience rule: their access tokens are opaque and bound to the client, not the relay; Google's token endpoint takes only secret-based auth (discovery document fetched today; H). GitHub metadata could not be fetched (session proxy returns 403 for github.com; unverified). Rejected (M).

## 6. Recommendation

**Shape (b) with WorkOS AuthKit; the relay stays a pure resource server.** It is the only provider verified today to offer everything Claude needs together: CIMD and DCR, S256 with `none` in its metadata (oauthlib/src/workos-as-meta.md:20-35), and `aud` set to the relay's URL. The relay adds no AS code: the SDK's `verifyBearerToken({ expectedResource })` over a `jose` verifier, one runtime dependency to approve (no transitive packages, already in the lockfile); hono's `verifyWithJwks` plus our own key cache avoids even that. Setup is dashboard toggles, and staging's default Google and GitHub credentials spare the owner a Google Cloud project or GitHub app. It is free, and a later IdP swap changes only issuer, JWKS URL and audience. The plugin must still allowlist the two users' `sub` (whether AuthKit sign-up can be closed is unverified), map `sub` onto `IdSchema`, and run on a stable hostname, since the Resource Indicator and PRM `resource` must equal the connector URL.

**Fallback: shape (a) with `oidc-provider` 9.12.2 plus `openid-client` 6.8.8 and a GitHub OAuth app upstream.** Self-contained and certified, with stable DCR and RFC 8707; it costs about 38 new packages (koa tree), a `@types` dev dependency, relay-held signing keys, a per-client consent page and the loopback catch above. Either way a CI test AS (`oidc-provider`, or `oauth2-mock-server` 9.2.0, MIT, 2 dependencies, 255 k weekly) needs the owner's nod as a dev dependency.
