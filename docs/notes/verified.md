## Consequences for the build

M0 needs three things now. The `executeTool`, `getTools` and annotation rows are handled by ADR 0001 (detect the input form per page, parse string schemas, treat results as text) and ADR 0002 (consequential tools without the hint), both awaiting the owner. Every MCP-B reference stays pinned to exactly 5.1.0, with `embed.js` served from `node_modules`, because 6.0 flips the input form and an `@latest` URL would break the demo when 6.0 is promoted. Two scaffold fixes follow from the tooling rows: `engines.node` becomes `>=22.18`, and `allowBuilds` replaces `onlyBuiltDependencies`. The e2e client at 2.2.0 works and can stay for M0.

Later milestones: M1 can use the v2 SDK, which meets the section 7 condition; pin server, client and core together (2.3.0 today) with the node adapter at 2.1.1. `/mcp` must not require a browser `Origin`, since hosted Claude sends none; S1 and S2 cover `/page`. `pair_page` waiting 60 s collides with Claude Code's 60 s timer, so cap it near 50 s or send progress (ADR), and set `_meta["anthropic/maxResultSizeChars"]` so large results stay inline. M2 attribution cannot rely on `clientInfo`; older clients need the SDK's sessionful legacy branch (ADR). M3's request-header connector may be missing on the owner's account: check the Add custom connector dialog for "Request headers" before M3, or bring a minimal OAuth plugin forward (ADR). M5's `list_changed` plan needs an ADR, as 2026-07-28 sends it only over `subscriptions/listen` and hosted Claude documents none of it. One short ADR should refresh SPEC section 3 with these rows.
