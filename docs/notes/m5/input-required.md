# Confirming consequential calls in the caller's client

Checked on 5 October 2026 against the MCP pages and `schema.ts` for 2025-06-18, 2025-11-25 and 2026-07-28, the `@modelcontextprotocol/server`, `client` and `core` 2.3.0 tarballs (still `latest`; the server changelog on main tops at 2.3.0), Claude Code 2.1.289's changelog and docs, Claude's connector docs, and a live probe: a scratch server on the SDK, driven by the SDK client and by Claude Code 2.1.289 on both revisions.

## What the wire does

On 2026-07-28 a server may answer `tools/call` (or `prompts/get`, `resources/read`, nothing else) with `resultType: "input_required"`, carrying `inputRequests` (server-chosen keys mapped to embedded `elicitation/create`, `sampling/createMessage` or `roots/list` requests) and an opaque `requestState`, at least one of the two. The client retries the same request under a new JSON-RPC id with `inputResponses` (bare results under the same keys) and `requestState` echoed byte for byte. The server must treat `requestState` as attacker controlled, protect its integrity when it affects authorization, and should bind it to the principal, a short expiry and a digest of the request; the spec warns that this is not single use, which the server must enforce itself. A server must not request a capability the request's `io.modelcontextprotocol/clientCapabilities` omits, and must not assume the client answers or retries; there is no round limit. An answer is `accept` (with `content`), `decline` or `cancel`. Form mode takes a flat object of primitives and must never ask for secrets; `elicitation: {}` means form only. The 2025 revisions push `elicitation/create` during the call, declared in `initialize`; 2025-11-25 adds URL mode, which 2026-07-28 keeps without `elicitationId`. Both later revisions say servers MUST bind elicitations to the client and user identity.

## What the SDK and clients do

SDK 2.3.0 offers `inputRequired()` with `inputRequired.elicit()`, `inputResponse()`, `ctx.mcpReq.inputResponses` and `ctx.mcpReq.requestState()`, and `createRequestStateCodec` (HMAC-SHA256, signed not encrypted, TTL, a `bind` callback) whose `verify` plugs into `requestState.verify` and fails as `-32602 Invalid or expired requestState`. An elicitation the client did not declare becomes `-32021` on 2026-07-28. On a sessionful 2025 connection a default-on legacy shim turns the same return into real `elicitation/create` legs and re-enters the handler; an undeclared capability or a leg timeout becomes an `isError` result in the SDK's words. `ctx.mcpReq.elicitInput` still works on 2025 connections. The SDK client fulfils `input_required` through its `elicitation/create` handler, up to 10 rounds. The probe showed all of this, decline and cancel included.

Claude Code 2.1.289 declares `elicitation: {form: {}, url: {}}` on both revisions and answers a form inside `input_required` correctly. Two findings matter for trust: headless `claude -p` without a hook answered `cancel` at once, and an `Elicitation` hook answered `accept` with no dialog. A client confirmation proves only that the account's client said yes, not that a person did. Claude's connector docs list tools, prompts and resources and never mention elicitation, so hosted Claude is unverified.

## Who confirms

(A) Keep only the page prompt, ignoring the M5 item. (B) Ask the caller by default wherever the client supports it; this weakens S6, since a page that never chose it would lose its operator's prompt to something an agent can answer. (C) Let a page opt in to confirmation in its members' own clients, with the page prompt as the fallback everywhere else. (D) Ask both, doubling prompts for little gain. I recommend C. It sits strictly between `confirm` and `allow`, which pages can already choose, and it serves the phone case: an operator away from the laptop confirms on the phone instead of letting the page time out. A gap the fact check found in these options: Claude Code honours `_meta['anthropic/requiresUserInteraction']: true` on a tool, which forces its own permission prompt on every call in every permission mode, `bypassPermissions` included, and denies the call in `dontAsk` (code.claude.com/docs/en/mcp, "Require approval for a specific tool"). It binds one client only and the relay never sees the answer, so D2 weighed it and did not take it.

Concretely, `policy.confirmVia: 'page' | 'client'`, default `'page'`, set in `attach()` or `data-confirm-via`, matters only when `consequential` is `'confirm'`; `deny` still refuses and `allow` still runs. The relay asks the caller only when hello said `client`, the tool is consequential, the caller is a member driver, and the request declares form elicitation (the 2026-07-28 envelope, or the 2025 session's `initialize`). Otherwise, and always for invitees, the call goes out unconfirmed and the page prompts, timeout meaning deny; the relay never provokes `-32021`. The relay cannot repeat ADR 0002's classification, so the adapter marks such tools `consequential: true` in the `tools` frame; a wrong flag fails safe both ways (a page prompt, or one spare question in the client).

## Binding a confirmation to one call

On 2026-07-28 the first round runs every check that precedes dispatch (access, rate, tool, role, arguments), then stores a record under a random 128-bit id: user, page, MCP tool name, page tool, a SHA-256 digest of canonical-JSON arguments, client name, expiry 120 s out, at most four pending per user. It returns `input_required` with one boolean field `confirm` (default false) and a `requestState` from the SDK codec with a per-process 256-bit key, payload only the id, bound to user id, OAuth client id and method. The message is relay text: tool name, page id, the origin's host without scheme, arguments capped at 500 characters, never page titles or descriptions (S10). On the retry the codec checks MAC, expiry and binding; the handler deletes the record first (single use), requires the same user, page, tools and digest, and dispatches only on `accept` with `confirm === true`. Anything else returns a new error, `not_confirmed`, and the page never hears of it. A restart voids pending confirmations, failing closed.

On the 2025 leg I recommend `ctx.mcpReq.elicitInput` inside the request, with the same 120 s timer and the client's signal, and `inputRequired.legacyShim: false`: the shim would answer our timeouts without an error code and skip our audit line. The open request is the binding there, and 120 s plus the 45 s call deadline stays under hosted Claude's 240 s.

## How the page learns it

The invoke frame gains `confirmation?: { by: 'client', confirmationId, at }`. The adapter skips its prompt only when its own `attach()` policy says `client`, the tool is consequential by its own rule, the caller id is a member's and its own grants say driver; otherwise it prompts, so a crafted frame cannot bypass S6. A confirmed write no longer holds the write queue while someone decides. The activity log shows "confirmed in <client> by <name>".

## Audit

A confirmed call's record gains `confirmedBy: 'client'`; a refusal records `not_confirmed` within the refusal budget, and an expiry sweep writes one for a retry that never came. Asking writes nothing, and arguments and their digest are never logged (S7). The format stays at version 1, since 0.1.0 is unreleased.

## SPEC and ADR changes

One ADR (0025 if still free; it became ADR 0026) changes sections 3 (new rows), 5 (`confirmVia`), 6 (the tool flag and invoke field), 7 (`not_confirmed` and the flow), 8 (option and data attribute), 9 (S6 adds: "A page may opt in to confirmation in its members' own MCP clients where the client declares form elicitation; otherwise, and always for invitees, the page prompts; a declined, dismissed or expired client confirmation means deny"; ADR 0026 words it for member drivers and keeps invitees, observers and invite-made attachments on the page prompt) and 10 (A5 tests for accept, decline, cancel, expiry, replay, another user, changed arguments, and page prompts for no capability, invitees and `'page'` pages, on both revisions). `docs/checklists/M5.md` adds hosted Claude's declared capabilities, read from a relay log line on the reference deployment, and Claude Code's real dialog.
