# The tour on Pages, the demo's relay URL and the 0.1.0 README (M5 research)

Checked on 5 October 2026 against the Pages actions' sources at their SHAs, docs.github.com, the CSP3 draft, chromestatus, Claude's connector and Claude Code docs, `npm view` and tarballs, and probes in `/tmp/m5-pages`: curl against live Pages sites, Playwright's Chromium 141, a local-mode relay and Claude Code 2.1.289.

## Where things stand

The Pages publish is the last job of `deploy.yml`, after a relay deploy and its approval, and builds `apps/demo` alone. Its pins, `upload-pages-artifact` v5.0.0 (`fc324d35`) and `deploy-pages` v5.0.1 (`368f8252`), are still the newest tags. Nothing is live: the repository has no Deploy run and no deployment. The static `index.html` loads `/main.js` by absolute path and carries no CSP; the dev server's `frame-ancestors` header cannot travel, so the board's refusal to link inside a frame is the only framing defence. The relay comes only from `?relay=`, dialled at once, with no form.

## What Pages does

`upload-pages-artifact` tars one directory and `deploy-pages` posts one artifact per deployment, so demo and tour must be built into one directory in one job; a tour-only publish would drop the demo. Limits: 1 GB a site, 10 minutes a deploy, 100 GB a month (soft). With an Actions source the custom domain lives in settings and a `CNAME` file is ignored; domain verification and no wildcard record still guard against takeover; Enforce HTTPS may take 24 hours to appear. Pages sends no CSP or `X-Frame-Options`, only `cache-control: max-age=600`, and CSP3 says a `<meta>` policy ignores `frame-ancestors`.

## Rendering the tour

**(a) A build script with `marked`, Mermaid rendered to SVG at build time.** With every request aborted, Chromium rendered all seven Mermaid blocks in the repo in 30 to 470 ms each, 26 to 50 KB, with no script and, under `htmlLabels: false`, no `foreignObject`; `marked` turns a fence into `pre code.language-mermaid`, easy to swap for an `<img>`. Cost: two dev dependencies outside the pre-approved list, `marked` 18.0.14 (MIT, no dependencies) and `mermaid` 12.1.0 (MIT, 117 packages and about 200 MB in a scratch install, no install scripts), of which only the self-contained `dist/mermaid.min.js` (5.5 MB) is loaded. **(b) `jekyll-build-pages` v1.0.13**: no npm packages, but it runs its image by mutable tag, so a SHA pin no longer fixes what runs, and it does not render Mermaid. **(c) Mermaid at runtime from jsDelivr with SRI**: 1.57 MB gzipped per reader and `style-src 'unsafe-inline'`. Worse, tour pages share the demo's origin, which the relay's allowlist vouches for, and in one tab the `sessionStorage` holding the adapter's resume token and grants. No S-rule's wording breaks, but S2's origin check would vouch for code the project does not ship. **(d) `beautiful-mermaid` 1.1.3** needs no browser, but its SVGs import Google Fonts and labels overlap lines. **(e) GitHub's Markdown API** needs a token and network at build time and leaves Mermaid open.

**Recommendation: (a).** A private workspace package, `apps/site`, whose `pnpm site:build` writes `apps/site/dist`: the demo's static build at the root, each `docs/tour/*.md` as `tour/NN-title.html` plus an index, diagrams as `tour/img/NN-k.svg` behind `<img>` (`securityLevel: 'strict'`, `htmlLabels: false`, network aborted), PNGs copied, tour `.md` links rewritten to `.html` and other repo paths to GitHub at the release tag. Tour pages carry no script, a `tour.css`, a no-referrer meta and `default-src 'none'; img-src 'self'; style-src 'self'; base-uri 'none'; form-action 'none'`; wide diagrams scroll sideways. The build fails if a tour page holds `<script` or `on*=` or lacks the policy, or an SVG holds a script or an outside URL.

**Publishing.** A new `pages.yml`, dispatched on `main` only: a build job (`contents: read`) and a deploy job (`pages: write`, `id-token: write`, `github-pages` environment limited to `main`, as GitHub recommends), pinned as above. The Pages job leaves `deploy.yml`, so a tour fix needs no relay deploy; an ADR amends ADR 0021's note. CI runs `pnpm site:build` after its Playwright install. `index.html` loads `./main.js`, so a `<user>.github.io` fallback works too. The demo stays at `/` (M4's URLs and origin list unchanged), the tour at `/tour/`, each linking the other.

## The demo's relay URL

The board already takes the relay from visitors and refuses anything but `ws:` and `wss:`, credentials in the URL, `ws:` off loopback on an https page, and any frame. Against a hostile relay the adapter still holds S4 to S6 (its own grant record, the least role, prompts denied on timeout). What it lacks is the visitor's knowledge: a crafted link dials a relay nobody chose, which then shows names of its own making in attach prompts and a QR to any https host. Recommended: without `?relay`, a Connect form that navigates to `?relay=`; with one, a bar reading "Connect to <host>" (from `URL.host`, so IDNs show as punycode) that dials only after a trusted click, remembered for this tab in `sessionStorage` per relay URL so a reload reconnects; only the dev bundle's `?e2e` hook skips it. Also refuse a relay URL with a query or fragment (S11 keeps credentials out of URLs).

The static build alone (the dev server's `?mcpb` frames) gains `default-src 'none'; script-src 'self'; style-src 'self' 'sha256-<inline style>'; img-src 'self'; connect-src wss: ws:; worker-src blob:; base-uri 'none'; form-action 'none'`. Under it, with loopback hosts named, the board registered six tools, linked to a local-mode relay, drew its widget and ran `?busy` with no violation; `ws://[::1]:*` was blocked, since CSP's host grammar has no IPv6 literal, hence `ws:`, which costs nothing: Chromium refused `ws:` to a non-loopback host from https and allowed 127.0.0.1, localhost and [::1]. From Chrome 147 (stable is 154) Local Network Access prompts before a public site opens a loopback WebSocket (chromestatus; not probed), so the README's local path uses `pnpm dev`. None of this weakens S1 to S14.

## The 0.1.0 README, about 650 words

1. **Tabdock**, three sentences: WebMCP tools on a live page, a relay with one stable URL, several clients and people per page, the tab approving each.
2. **Try it**: tour and demo, linked from the repository's About website field, keeping the owner's domain out of committed files as M4 did.
3. **Local mode with Claude Code**: `pnpm install`, `pnpm dev`, paste the printed `claude mcp add` line, check with `claude mcp list` (never `claude mcp get`: 2.1.289 still prints the header), open the board link, ask Claude to pair with the widget's code, approve.
4. **Claude on the web, desktop and phone**: a public URL through a tunnel (`pnpm dev:public`) or a host (`docs/deploy.md`); add `https://<relay>/mcp` under Customize, Connectors, + Add, Add custom connector (Free plans allow one), and sign in. Claude Code to a hosted relay: `claude mcp add --transport http --scope user tabdock https://<relay>/mcp`, then `/mcp` or `claude mcp login tabdock`.
5. **Your own page**: SPEC section 8's `attach()` snippet.
6. **Security in brief**: the tab approves every attachment or mints the invite; roles are checked in relay and page; consequential tools prompt; the relay sees plaintext, so run your own; origins allowlisted, secrets never logged, calls audited. Link the threat model.
7. **Architecture**: a top-to-bottom Mermaid flowchart (clients to relay, the adapter dialling out, `document.modelContext`, the person at the tab), which GitHub renders; its draft rendered here.
8. **Docs**: tour, deploy guide, threat model, SPEC, ADRs, and the full command list moved to a new `docs/develop.md`.
9. **Status and licence**: 0.1.0, automated against S1 to S14, manual checks in `docs/checklists/`, WebMCP's status from `mcp-b.md`; Apache-2.0.
