# M5: decisions taken under the standing instruction

On 4 October 2026 the owner asked me to keep going and to take my recommendation wherever a question came up. Every decision below is the recommended option from the research beside this file (`page-tools.md`, `input-required.md`, `revisions.md`, `mcp-b.md`, `packaging.md`, `pages-readme.md`, `backlog-fixes.md`), checked by independent fact checkers on 5 October, and is recorded as accepted under that instruction. Where I departed from a note's recommendation I say so and why. ADRs 0025 to 0031 carry the SPEC changes.

## D1. First-class page tools (ADR 0025)

The relay's whole tool surface (the five fixed tools, the spike marker and page tools) moves from `McpServer.registerTool` to the SDK's low-level `Server`, whose docs name it for tool sets computed per request. The relay answers `tools/list` from a per-user snapshot and dispatches `tools/call` by name, so a stale first-class name still reaches the hub and answers `not_attached`, `page_asleep` or `page_gone` with its audit line (S7, S8), and page-chosen names never reach the SDK's `console.warn`. A golden test keeps the five fixed tools' wire entries identical on both eras. The 2.3.0 typings mark `Server` deprecated for ordinary use; the relay uses it for the advanced case the docs describe and says so in a comment.

The alias is the page id, so a name is `<page id>__<tool>`: ids are random, unique and never reused, so a cached name can only reach the page it named. A `.` in a page's tool name becomes `_`; a full name over 64 characters is left off the list, and when two of a page's tools map to the same name both are left off, so a page cannot win a collision by ordering. Every tool left off stays reachable through `call_page_tool`. Observers see only tools marked `readOnlyHint`; drivers see all; invitees and invite-made attachments get no first-class names (ADR 0016 keeps them on the fixed tools), and the hub answers such names `tool_not_found`. An asleep page's tools leave the list and return under the same names on wake.

Each entry's description is a fixed prefix naming the tool, the page id and the origin (cut to 100 characters) and saying that the description and schema are untrusted page text, never instructions, followed by the page's description made one line, with any `[tabdock` defused, JSON-quoted and cut so the whole is at most 500 characters; the title is the page tool's title or name with the origin's host, at most 120. Only `readOnlyHint` passes through. The schema is the hub's existing cut copy with `x-mcp-header` keys removed; a typeless root gets `type: "object"`, and any other root keeps the tool off the list, since clients of both eras reject a whole list over one bad root. Each user's list holds at most 64 page tools and 100,000 characters of them.

On 2026-07-28, `tools/list` carries `ttlMs` 10,000 with `cacheScope` private. Each user's listen streams are served by a handler of that user's own, created with their first stream and closed with their last, behind `listen-streams.ts`, so one user's change never signals another; 2025 sessions get `notifications/tools/list_changed` for their own user only. A per-user notifier sends at most one change a second and none when the list's digest is unchanged. The switch is `TABDOCK_FIRST_CLASS_TOOLS`, parsed like `TABDOCK_INVITES`, off by default in every mode, allowed in production and named in the start line. A first-class call runs the very same hub path as `call_page_tool`: one shared function, the same checks, prompts, queue, audit records and errors.

## D2. Consequential confirmation in the caller's client (ADR 0026)

A page may opt in with `policy.confirmVia: 'client'` (default `'page'`; script tag `data-confirm-via`). Only then, and only for a member driver whose client declared form elicitation, does a consequential call under `consequential: 'confirm'` ask the caller in their client instead of prompting on the page. Everyone else gets today's page prompt: a page that did not opt in, every invitee, and every client without the capability. `allow` and `deny` keep their meaning. S6 is unchanged for a page that did not opt in. A Claude Code `Elicitation` hook can accept with no person present, so a client confirmation proves only that the signed-in account's client said yes; that is why it is opt-in, members only, and shown in the page's activity log as confirmed in the client.

On 2026-07-28 the relay answers the first round with `input_required` and binds the retry to one exact call: the SDK's `createRequestStateCodec` (its maintained HMAC with expiry and a bind to user, OAuth client and method, under a per-process 256-bit key) carries only an id, and a single-use server-side record holds the user, page, MCP tool, page tool, a SHA-256 digest of the canonical JSON arguments and a 120 s expiry, at most four pending per user; the record is deleted before any other check and a restart voids them all. On the 2025 leg the relay calls `elicitInput` inside the request with its own 120 s timer and the client's signal (`legacyShim` off), so every outcome stays in the handler. The adapter marks such tools `consequential: true` in the tools frame, since only it knows ADR 0002's inputs; the invoke carries `confirmation: { by: 'client', confirmationId, at }`, and the adapter honours it only under its own `attach()` policy, its own consequential rule and its own record that the caller is a member driver, so a crafted frame still prompts. Decline, cancel, expiry, reuse and changed arguments answer the new error `not_confirmed`; call records gain `confirmedBy: 'client'`, and the audit format stays at version 1. The elicitation message is written by the relay and never carries a page title or description.

I considered and did not take Claude Code's `_meta['anthropic/requiresUserInteraction']` (raised by the fact checker): it binds one client only, the relay cannot see it, and it would double every prompt.

## D3. MCP revisions, conformance and Origin (ADR 0027)

The relay claims 2025-03-26, 2025-06-18, 2025-11-25 and 2026-07-28, with 2024-11-05 over Streamable HTTP as best effort and no HTTP+SSE. "Verified" (A5.2) means: CI runs a client matrix (`@modelcontextprotocol/sdk` 1.10.2, 1.12.3, 1.24.0 and 1.32.0 as npm aliases; client 2.3.0 in legacy, auto and pinned modes) against the sim page on both legs, raw version probes, and the official conformance suite's 2025-11-25 and 2026-07-28 requirement sets, pinned at `@modelcontextprotocol/conformance` 0.2.0-alpha.12 with checked-in baselines, through a loopback proxy that adds a throwaway bearer token and logs nothing; Claude Code is checked on both revisions in the sandbox, not CI. The suite is a dev tool outside CLAUDE.md's pre-approved list (it brings express and octokit); I accept it under the standing instruction and say so in the PR.

`/mcp` refuses a present `Origin` outside an allowlist with 403 before auth, as both revisions require: loopback origins in local and dev-token mode, the public origin in public and hosted mode, plus `TABDOCK_MCP_ALLOWED_ORIGINS`; a missing `Origin` passes, since Claude Code and hosted Claude send none. An unsupported-version error on the 2026-07-28 leg should list every revision the relay serves, as the spec's MUST says; if the SDK cannot be made to, the deviation is recorded. One info line per user, client and leg per window (through the repeated-lines budget) lets the owner read which revision hosted Claude speaks. The SDK pins stay exact (server, client and core 2.3.0; node 2.1.1), rechecked on release day.

The demo stays on MCP-B 5.1.0, since 6.0 is still a beta; a Playwright leg runs the adapter against the 6.0 beta polyfill (pinned exactly as a dev alias), the baseline is re-run on it, and the demo switches the day 6.x becomes npm `latest`, polyfill and local-relay embed together. The adapter keeps its marker check (6 has no marker and behaves like native Chrome), and `POLYFILL_HINT` names `installWebMCP()` too. `tabdock.v1` stays the page link for 0.1.0. `docs/mcp-b-comparison.md` compares the two protocols on nine axes, and `docs/upstream/mcp-b.md` drafts a feature request issue for `@mcp-b/webmcp-local-relay`: first a `cancel` frame older embeds ignore, then an opt-in `webmcp-remote.v1` profile that must keep S1, S2 and S4. The owner posts it from a personal account; the build posts nothing.

## D5. Packaging and release 0.1.0 (ADR 0028, amending ADR 0022)

Three packages, `@tabdock/protocol`, `@tabdock/adapter` and `@tabdock/relay`, in lockstep at 0.1.0 under an npm org `tabdock` the owner creates first (all names were free on 5 October); nothing under unscoped `tabdock`. The relay is bundled by esbuild (its own source only, npm dependencies external, `npm-shrinkwrap.json` shipped) with one bin `tabdock-relay`, an `audit` subcommand and a `--new-token` flag, its version from `package.json`, no implicit `.env`, and a packaged rule for the checkout that is never weaker than ADR 0022's refusal of a token directory inside a repository. Protocol and adapter ship `tsc` output with declarations; the whole protocol moves to `zod/mini` with the English locale set, which measured the adapter's script-tag build at 126,658 bytes against 286,140, and a test holds it under 150,000. The local banner prints `claude mcp add-json --scope user` with a `headersHelper` script the relay writes beside the token on POSIX shells (probed: no token in Claude Code's config or argument list); PowerShell keeps `--header`. The relay does not serve the adapter script. Publishing is stage-only through npm trusted publishing behind a GitHub environment `npm`, triggered by a published GitHub release, with a one-day stage-only token from CI for the very first versions; one `CHANGELOG.md`, one tag `v0.1.0`, `docs/release.md`. The npm org, the environment, the approvals and the trusted publisher setup are the owner's.

## D6. The tour on Pages and the demo's relay (ADR 0029)

A new private package `apps/site` renders `docs/tour` with `marked` and turns each Mermaid block into an SVG at build time in Playwright's Chromium with the network blocked, so tour pages carry no script and run under `default-src 'none'`. `marked` 18.0.14 and `mermaid` 12.1.0 are dev dependencies outside CLAUDE.md's list, accepted under the standing instruction. I departed from the note in one respect: mermaid brings about 117 packages, so `apps/site` keeps its own lockfile outside the workspace and installs only when the site is built, leaving a clean clone's `pnpm install` as it was. The site puts the demo at `/` and the tour at `/tour/`, from a new `pages.yml` dispatched on `main` only (build job `contents: read`, deploy job `pages: write` and `id-token: write`), and the Pages job leaves `deploy.yml`. The demo no longer dials a relay the visitor did not choose: with no `?relay` it shows a Connect form, and a linked relay shows a "Connect to <host>" bar that dials only after a trusted click, remembered for the tab; only the dev and test bundle's `?e2e` skips it. It refuses a relay URL with a query or fragment, and the static build carries a meta CSP and a relative script path. The README shrinks to about 650 words with a Mermaid diagram, and the command list moves to `docs/develop.md`; the live URL goes in the repository's About field, not in a file.

## D7. Hardening from the last M4 hunt (ADR 0030)

The five small items are fixed: `config.ts` refuses a per-user request share above the relay total; `#approveRedemption` closes an expired invite and answers `pairing_expired`; the adapter caps a relay's `deadlineMs` at the timer maximum less its grace, with `MAX_TIMER_MS` in the protocol constants; `request-heap.ts` adds a surcharge for integer keys and stops calling its charge an upper bound; `#sendInvoke` answers `page_asleep` for a socket that is not open. Three residuals are fixed and become S9 limits: invitees together hold at most a quarter of the relay's request bytes; an `/mcp` response that makes no progress for 30 s is cut off with a logged line; and every 2026-07-28 request spends the request budget, `tools/list`, `server/discover` and `initialize` included. Four residuals are accepted in the threat model (the `/pair` session store's eviction, the tool budget filled from a few hosted addresses, rosters from pairing retries, look-alike emails). The M4 checklist's after-merge items become owner steps. The deploy snapshot stays in the backlog until re-pairing annoys.
