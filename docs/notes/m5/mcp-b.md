# MCP-B: the 6.0 re-check, a protocol comparison and an upstream proposal (M5 research)

Checked on 5 October 2026 against `npm view`, tarballs unpacked in `/tmp/m5-mcpb`, a live probe of both polyfills in Playwright's Chromium 141, which has no native WebMCP (`/tmp/m5-mcpb/live/probe.mjs`), the WebMCP draft of 2 October, chromestatus, chromiumdash and MCP-B's repository files. Issue and Discussions facts come from rendered GitHub pages, since the API was closed to this session.

## MCP-B 6.0: still a beta, and better for Tabdock

`latest` is still 5.1.0 for `@mcp-b/global`, `webmcp-polyfill`, `transports`, `webmcp-local-relay`, `webmcp-ts-sdk` and `webmcp-types`; `beta` is the `6.0.0-beta.20261001010549` build of 1 October, with nothing published since. GitHub has no 6.0 release, `CHANGELOG.md` on main stops at 5.1.0, and the `@6` CDN URLs printed in 6.x's own READMEs still return 404 (`@beta` works). 6.0 is not stable.

What changed matters. `@mcp-b/webmcp-polyfill` 6 is no longer MCP-B's own runtime: it vendors the WebML Community Group's polyfill (webmachinelearning/webmcp-polyfill at `439c6c3`, MIT, not on npm) plus a declarative forms layer, and exports only `installWebMCP()`; `initializeWebMCPPolyfill`, which `apps/demo/src/main.ts` imports, is gone. The probe, run against 5.1.0 and 6 side by side, confirmed that on 6: `executeTool` takes an object (a string throws `TypeError: inputObject must be an object`; omitted input runs with `{}`); `consequentialHint` survives, and a tool given any annotations reports all four as booleans; there is no `__isWebMCPPolyfill` marker; the handler receives `{ signal }` and saw the caller's abort at 100 ms; unregistering a tool mid-run no longer rejects the call (it resolved when the handler ended, at 301 ms); and a handler error, a vanished tool and a handler returning `undefined` all give a fixed `UnknownError: Tool execution failed`. Results are now `JSON.stringify`d, as the draft prescribes, so a handler's `plain text` arrives as `"plain text"` with quotes, unlike 5.1.0 and the Chrome 153 to 156 baseline.

For the adapter this is good news. It tries an object first, so input detection needs nothing. Without the marker it treats 6 as native Chrome, which is now right: aborts reach handlers, and ADR 0012's "Tool unregistered" hold cannot happen on 6 (it stays for 5.x pages). `POLYFILL_HINT` in `packages/adapter/src/core.ts` should name `installWebMCP()` too, and ADR 0001's notes should record that on 6, as on native, a write's slot frees when the abort lands, so a handler that ignores its signal can overlap the next write; ADR 0001 already accepts this, and no S rule changes.

The draft also adds `toolactivated` and `toolcancel` events (the 6 polyfill fires them only for declarative forms). Chromestatus lists the origin trial as M149 to M156; the extension to M162 was approved by API Owners on 28 September (corrected by the fact checkers: the Intent to Extend Experiment gate shows an API owner's approval at 23:57 UTC), though the trial stage's listed range still reads M149 to M156. Stable is 154.0.8037.97 on Linux (154.0.8037.98 on Windows), M155 ships 6 October, Beta is 156.0.8078.4.

## The two page links compared

|                    | MCP-B local relay (6.0 beta; 5.1 alike unless noted)                                                                                                                                                                                                                                                                                                             | Tabdock                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |

| Who dials          | Page to `ws://127.0.0.1`, scanning ports 9333 to 9348 for a `server-hello`, caching the port                                                                                                                                                                                                                                                                     | Page to one configured `ws` or `wss` URL                                                    |
| Trust, auth        | None. `--widget-origin` defaults to `*`; an Origin-less socket is judged by its claimed `hello.origin`; any header-less local process may join over `webmcp-relay.v1` and call every tool; MCP side is stdio                                                                                                                                                     | Origin header only (S1), allowlist (S2), signed-in users, pairing (S3)                      |
| Users, approval    | One implicit user; extra MCP clients start extra relays that join the first; no approval, roles or prompts                                                                                                                                                                                                                                                       | Attachments approved on the page, roles, consequential prompts, one write at a time, revoke |

| Results, errors    | The page builds the `CallToolResult`; the SDK's `fromJsonSchema` checks arguments; of WebMCP's four hints only `readOnlyHint` survives: `consequentialHint`, `untrustedContentHint` and `debugging` are dropped (the SDK's `ToolSchema` strips them, probed), while MCP's own hints such as `destructiveHint` pass; `input_required` and task-only tools refused | Page returns text; relay checks arguments off-thread, labels, caps, coded errors            |

| Lifetime           | Tools vanish with the socket; ping 15 s, dead at 25 s; retries, then a probe every 2 min; invoke timeout 65 s; no cancel frame                                                                                                                                                                                                                                   | 10 minute resume window, `cancel`, close codes, Web Lock                                    |

The shapes rhyme (hello, full tool list replacement, invoke and result, ping), so a proposal is plausible; the gaps are exactly Tabdock's security work. Chrome 147 and later also prompt before a public page opens a loopback WebSocket (Local Network Access), one more reason a public page wants a public relay.

## Upstream proposal

Route: MCP-B is MIT. CONTRIBUTING tracks enhancements as issues (the feature form needs a package, problem and solution; blank issues are off), sends questions to Discussions, and has no RFC process; pull requests need Conventional Commits with a package scope, a changeset and their AI contribution and testing standards. Issue 158, "webmcp-server-relay", has sat open with no reply since 11 March. It is the feature form filed against `@mcp-b/transports`, with a one-line problem and a one-line solution asking about "webmcp server replay" (sic), labelled enhancement and triage, so it is weak evidence of demand for a server relay (made precise by the fact checkers).

What to propose: an opt-in remote profile for `@mcp-b/webmcp-local-relay` on a separate subprotocol, `webmcp-remote.v1`, reusing `webmcp.v1` frames and adding only what a public relay needs: `cancel`, an explicit `data-relay-url` (wss, no scan), a Streamable HTTP MCP endpoint behind an auth hook, pairing with an on-page approval before `hello/accepted`, a `caller` on `invoke`, and a resume token. Local mode keeps its defaults. The profile must refuse Origin-less sockets, require an explicit allowlist and never expose `webmcp-relay.v1` off loopback; a remote mode with the local defaults would break S1, S2 and S4, and Tabdock should not support one.

Smallest first step: one issue asking for a relay to browser `{type: "cancel", callId}` sent on MCP cancellation and invoke timeout, with the embed passing an `AbortSignal` to `executeTool`. It helps local users today (a timed-out call keeps running in the page), is backward compatible (the 6 widget ignores unknown types), and is the first frame remote mode needs. A second small issue could carry WebMCP hints in `_meta`.

Open questions for the maintainers: this package or a new one; where consent UI lives, given their widget is hidden; tab suffixes or a page prefix for names; whether `webmcp.v1` will be versioned when page payloads change; and whether they would adopt Tabdock's attach frames as the profile or prefer Tabdock to speak theirs.

## Recommendations

Demo: stay on 5.1.0, since the backlog moves it only once 6.0 is stable, but add a Playwright leg on the 6.0 beta (pinned exactly as a dev alias) running the revoke, cancellation and consequential specs (ADR 0031 takes the call, cancel and consequential specs), and switch the demo as soon as 6.x is `latest`: the `installWebMCP` import plus both MCP-B pins, the vendored embed included, because embed and runtime must share a major. Wire protocol: keep `tabdock.v1` for 0.1.0. Upstream: draft the first issue in `docs/upstream/mcp-b.md` for the owner to post from his personal account; nothing is posted by the build.
