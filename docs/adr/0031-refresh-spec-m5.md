## Context

SPEC section 3 records facts checked on 2 and 3 October and asks that each be re-verified before use. On 5 October the M5 research re-checked the ones M5 builds on against the npm registry, both revisions' MCP pages, the SDK tarballs, chromestatus and chromiumdash, Claude's and Claude Code's docs, and live probes: Claude Code 2.1.289 run headless through a recording proxy, both MCP-B polyfills in Playwright's Chromium 141, Chrome for Testing 154, and a local-mode relay. Independent fact checkers then re-ran the claims. Most rows hold; some have moved, and several facts M5 depends on are missing.

MCP-B 6.0 is still a beta, and 6 changes what the adapter meets. `latest` is 5.1.0 for all six `@mcp-b` packages and `beta` is the build of 1 October, with no GitHub release, no changelog entry and `@6` CDN URLs that 404. Its polyfill now vendors the WebML Community Group's polyfill and exports only `installWebMCP()`, so `initializeWebMCPPolyfill`, which the demo imports and calls (`apps/demo/src/main.ts:1` and `:25`), is gone. On 6, `executeTool` takes only an object, `consequentialHint` survives, there is no `__isWebMCPPolyfill` marker, handlers receive the caller's signal, unregistering a tool mid-call no longer rejects the call, every failure reads `UnknownError: Tool execution failed`, and results are serialized as JSON, so a plain string arrives quoted. The repository pins 5.1.0 throughout: the polyfill in `apps/demo/package.json`, and the local relay whose embed the demo serves (`apps/demo/scripts/server.ts:16-30`) there and in `tests/e2e/package.json`. The adapter recognises 5.x by `POLYFILL_MARKER` (`packages/adapter/src/core.ts:549`), which gates ADR 0001's wait for a running write and ADR 0012's hold after "Tool unregistered", and its `POLYFILL_HINT` (line 562) names only `initializeWebMCPPolyfill()`. MCP-B's local relay has no `cancel` frame, accepts any page origin by default and asks nobody before a page's tools are served, which is why D4's upstream draft starts where it does.

The fact checkers corrected two notes in ways section 3 must carry, and both notes now carry the corrections. `mcp-b.md` said the WebMCP origin trial's extension to M162 was requested and not shown as granted; chromestatus shows the API Owners gate for the Intent to Extend Experiment approved at 23:57 UTC on 28 September 2026, though the trial stage's own range still reads M149 to M156. `revisions.md` said headless Claude Code opened no notification stream; in two runs `claude -p` opened `subscriptions/listen` right after `server/discover`, and under `MCP_PROTOCOL_NEGOTIATION=legacy` a GET stream on its session, which the recording proxy missed because the relay holds a GET stream's response headers. ## Decision

**MCP-B (D4).** The demo stays on MCP-B 5.1.0 while 6.0 is a beta. A Playwright leg runs the adapter against the 6.0 beta polyfill, pinned exactly as a dev alias in `tests/e2e`, through its call, cancel and consequential specs, and the WebMCP baseline (`docs/notes/baseline.md`) is re-run on it. The day 6.x becomes npm `latest`, the demo moves in one change: the `installWebMCP()` import and both pins, the polyfill and the local relay whose embed the demo vendors, since embed and runtime must share a major. The adapter keeps its marker check. 6 has no marker and behaves like native Chrome, so the adapter treating it as native is now right: aborts reach handlers, ADR 0012's hold stays for 5.x pages and cannot arise on 6, and, as on native, a write's slot frees when its abort lands, so a handler that ignores its signal can overlap the next write, which ADR 0001 already accepts. Input detection needs nothing, since the adapter tries an object first. `POLYFILL_HINT` names `installWebMCP()` beside `initializeWebMCPPolyfill()`. The adapter and relay forward a result's text as the runtime gives it (ADR 0001; `resultText` in `packages/adapter/src/core.ts:911`, `callResult` in `packages/relay/src/mcp.ts:258`), so on 6 a client sees a plain string quoted, and the 6 leg's specs expect that. The page link stays `tabdock.v1` for 0.1.0.

`docs/mcp-b-comparison.md` compares MCP-B's local relay with Tabdock on nine axes: transport and framing, who dials, trust and auth, users and approval, naming and listing, results and errors, untrusted content, lifetime, and versioning. `docs/upstream/mcp-b.md` drafts a feature request for `@mcp-b/webmcp-local-relay` in the form MCP-B's CONTRIBUTING asks for (package, problem, solution). Its first step is a relay to browser `{type: "cancel", callId}` frame, sent on MCP cancellation and invoke timeout, with the embed passing an `AbortSignal` to `executeTool`: it helps local users today, and older embeds ignore a type they do not know. Its second is an opt-in remote profile on a subprotocol of its own, `webmcp-remote.v1`, which must refuse sockets without an `Origin` header, require an explicit origin allowlist, never expose `webmcp-relay.v1` off loopback, and hold `hello/accepted` until an approval on the page, so S1, S2 and S4 hold there as here; a remote mode with the local defaults would break all three, and Tabdock would not support one. The draft cites issue 158 for what it is. The owner posts it from a personal account; the build posts nothing. D4 changes no SPEC requirement: section 2's Upstream row already says to propose a remote relay mode, and section 3 carries the facts.

## Consequences

The spec's facts match what M5 builds on as of 5 October, and M5 has a yardstick: CLAUDE.md's definition of done now has six numbered tests, their manual parts in `docs/checklists/M5.md`. These facts age fast. Chrome 155 reaches Stable the day after this record, MCP-B 6 may become `latest` at any time, and a new SDK may follow; `docs/release.md` rechecks the SDK pins on release day (ADRs 0027 and 0028), and when the demo moves to MCP-B 6 a later record refreshes the MCP-B row, since notes cannot change SPEC. The rows on hosted Claude stay partly blind: which revision it speaks, whether it sends `Origin` and whether it declares form elicitation are read off the reference deployment by the owner, and until then first-class tools and client confirmation fall back safely for it, to `call_page_tool` and to the page prompt.

A5.2's Claude Code half runs in the sandbox rather than in CI, since it needs a signed-in CLI and spends model calls, so a regression in Claude Code between runs shows only when it is run again. A5.4 runs on a beta pinned exactly, so a new beta build is a deliberate bump. A5.5 leaves publishing to the owner, so the first release is the test of `publish.yml`. Once 0.1.0 is on npm the name sticks in practice, which section 12 now says. Until MCP-B answers the draft, `tabdock.v1` and MCP-B's `webmcp.v1` stay apart and a Tabdock page needs Tabdock's adapter. On MCP-B 6 a plain-text result reaches clients quoted, a visible change from 5.1.0 that the demo's move will show; unwrapping it would be a change to ADR 0001's rule and needs its own record.
