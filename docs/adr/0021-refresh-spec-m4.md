# 0021: Refresh SPEC sections 3, 10, 11 and 12 for M4

Status: Accepted by the owner, 3 October 2026. Changes SPEC sections 3, 10, 11 (its second paragraph, which ADR 0022 splits off) and 12.

## Context

SPEC section 3 lacks facts M4 builds on, checked on 3 October (`docs/notes/verified.md`, rows marked M4). Section 11 says only "a small container host from M4"; the owner has chosen Fly.io and a subdomain of a personal domain for the project's reference deployment (D1 and D2 in `docs/notes/m4/m4-decisions.md`), and ADR 0022 asks that SPEC name what a host must do rather than which host to use. Section 12 leaves open where a public demo lives and section 10 publishes it only at the M5 release, but the owner chose to publish `apps/demo` on GitHub Pages in M4 (D6), so A4.2 can run from any device with a browser. The demo already takes its relay as `?relay=wss://...` and has a static build, which leaves out MCP-B's vendored widget because a static host cannot send `frame-ancestors` (`apps/demo/scripts/server.ts`).

## Decision

**Demo.** As part of the reference deployment, M4 publishes `apps/demo` on GitHub Pages, under the custom domain `demo.<domain>` unless the owner picks `<user>.github.io` before the origin list is staged; the custom domain gives the demo an origin of its own, so the relay's origin list names only it, while `<user>.github.io` would cover every project site under the account, as section 10 already warns. A custom domain on the origin list is guarded against takeover: the owner verifies `<domain>` for GitHub Pages in the account's settings before creating the `demo` record, creates no wildcard record, and when retiring the demo removes its origin from `TABDOCK_ALLOWED_ORIGINS` before removing the record or the Pages site. Since Pages cannot forbid framing, the static build refuses to attach inside a frame. The relay is never hosted on Pages, and the `docs/tour` explainers still go up at the M5 release.

## Consequences

The spec's facts match what M4 builds on, and its open items shrink to two. SPEC requires only what a host and a provider must do; Fly.io, WorkOS and the owner's domain appear only in section 3's facts and where SPEC names the reference deployment as an example (sections 4, 7 and 11), never as a requirement, so someone running their own relay follows sections 7 and 11, not the owner's accounts. The demo goes public one milestone early; any page session it opens is bounded by the origin list and the per-address and total caps, and minting invites still needs a member attached. Two residual risks join the threat model: any site can frame the published demo and try to trick its operator into a click, narrowed by the refusal to attach in a frame; and a custom domain left pointing at Pages after the site goes could be taken over, which the guard above prevents while it is followed. No design changes beyond those ADRs 0017 to 0020 and 0022 record.
