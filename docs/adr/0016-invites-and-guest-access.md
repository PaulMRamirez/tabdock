# 0016: Invites and guest access

Status: Accepted by the owner, 3 October 2026. Changes SPEC sections 2, 5 to 10 and 12, and ADR 0013's 403 for unknown accounts once invites are on. Built in M4 (invites) and after M5 (agent tokens); M3 lays the groundwork.

## Context

From M3 only accounts the owner lists in `TABDOCK_OAUTH_USERS` can attach (ADR 0013): sharing a page means learning a friend's `sub`, editing `.env`, restarting the relay and reading out a code that lives 120 s. The owner asked whether access without OAuth ever makes sense, and how invites made in the widget could ease sharing. A design panel (security, ease and client-constraint lenses, a judge and a red team; notes kept in the session) settled it. Binding facts: Claude's connectors take OAuth or no auth and cannot be edited once added; Free allows one custom connector; hosted Claude treats a 403 as final and its traffic carries no per-user identity; Claude Code takes a URL and headers.

## Decision

**Anonymous means no account, never no identity.** Without sign-in the only identity is a credential the operator minted on one page. Relay-wide unauthenticated `/mcp`, code pairing without sign-in and anonymous drivers are never allowed: attachments, attribution (S7), revocation (S8) and S13 all key on a user. The ease comes from signed-in invites.

**Invites (M4).** The operator mints an invite in the widget: a label, Can watch or Can control, a lifetime (15 minutes, 1 hour by default, or while the page is open) and, for watch invites only, a number of uses. The adapter draws a 128-bit secret, keeps its own record (stored beside the grants under ADR 0011's key) and sends the relay only its hash and terms. The link `<public URL>/i#<secret>` shows once, as a QR code and text; the fragment keeps the secret out of logs. A watch invite is approval given in advance, as `autoApprove: 'observer'` already is, narrowed to whoever holds the link: it attaches as observer with a notice. A control invite is never approved in advance: redeeming it raises the usual prompt naming the account beside the label, and it is spent only on approval; one prompt may be pending per invite, and three refusals or timeouts burn it. The relay forwards the presented secret with the attach request, and the adapter honours an invite-made attachment only when that secret matches its own record, never above the invite's role. Invite-made attachments end with the page session, on revoke, or 24 hours after redemption, use at most the page's user limit minus two seats, and stay on the five fixed tools (never M5's first-class tools).

**Who may mint.** A page may mint invites only while one of the owner's allowlisted users is attached to it; the relay records that user as the sponsor, `/i` and `pair_page` say "shared by <sponsor>", and the invites and the attachments they made end when no sponsor is left, since from M4 a script can open a page session claiming any allowed origin. A page sets `policy.invites` to `off`, `watch` or `all`; the default is `watch`, so control invites need a page that opts in. The control handle gains `invite()`.

**Revoke closes doors.** `revoke('*')` also cancels every live invite and agent token. Revoking someone who joined by invite bars that account from that invite, a multi-use invite's Revoke defaults to "and close this link", and a redemption never clears a revoke.

**Invitees.** With invites on, the `oauth` plugin admits a valid token whose `sub` is not on the allowlist as an invitee instead of a 403, through the one mapping M3 builds, which returns the account's kind. An invitee sees only the pages it holds, may hold one session until it has an attachment, and has its own small pool, evicted first when full. `pair_page` and `/pair/claim` answer an invitee's pairing code with a new error, `invite_required`, so a code seen on a shared screen cannot summon prompts from strangers. Invitees redeem at `/i`, which previews the page (its title marked as written by the page) and the sponsor, signs the browser in as `/pair` does, and claims only when the person clicks Join; `pair_page` also takes a single-use link. Prompts, the roster and the activity log show an invitee's verified email, or "unverified account" with a short id, and an "invited" badge, and refuse a display name that copies a member's. On `/mcp`, pairing and redemption are limited per user, per invite and per page, never per address.

**No-account agents (after M5, behind a flag that is off by default).** For a client that cannot sign in, such as a script or Claude Code, the invite form can show a `claude mcp add` command carrying a page-scoped token in an `Authorization` header for a separate endpoint, `/g/mcp`. The holder is a guest named by the label: observer only, one page, revocable, lasting 1 hour by default and 8 at most. The token is dormant until its first request, which raises an ordinary attach prompt naming the label and client, so a leak before use shows up. The endpoint never answers 401 or 403 and serves no resource metadata, so no client starts a sign-in, and a dead token gets 404. No-sign-in connector URLs for hosted Claude are not built: each would need a new connector against Free's single slot, and the URL would be a long-lived credential in synced settings that cannot rotate.

## Consequences

After one connector setup, an invitee joins from any device in a tap, and the operator spends a few. M3 builds no invites but lays the groundwork: `/pair` stores its nonce as a generic single-use ticket keyed by hash with a kind, the account mapping returns a kind and `/pair/claim` refuses non-members, the relay logs requests by route rather than raw path, and pairing limits on `/mcp` count per user. The owner runs ngrok with its traffic inspector off. Invites wait for M4 so invitees add a connector whose URL will not change, and `/i` avoids ngrok's warning page. Verify before M4: whether WorkOS can put a verified email in access tokens. S11 gains a carve-out for agent tokens: a credential, observer only, one page, revocable, never in a URL or a log.

## Notes after the M3 groundwork

M3 built the groundwork this record asks for. Single-use secrets live in a generic store keyed by a digest of the secret, each ticket with a kind (`pair` for now), its page, its lifetimes and a trace id, so M4's invites reuse it. The `oauth` plugin's one account mapping returns a member, with its user, or an invitee keyed by a digest of the `sub`; `/pair/claim` accepts members only and answers others 403 `not_allowed` until M4 turns that into `invite_required`. Unexpected request failures are logged by route, never by raw path or query. Pairing limits on `/mcp` and at `/pair` count per user and per page (`pairAttemptsPerPage`, 30 a minute); the relay no longer keys anything on a caller address for `/mcp` (its refusal log line still notes the socket address, which behind the tunnel is loopback), and per-address limits remain only on `/page`. After the section 9 review, `/pair` previews look a nonce up before counting it, so unknown, used and expired nonces get the one 404 and leave nothing behind, and only live nonces count against `pairPreviewsPerNonce`; the one relay-wide limit at `/pair` is the budget for code exchanges with the provider (ADR 0013's notes), which has no address in it. M4's `/i` reuses both rules.

## Notes from the A4.3 review (4 October 2026)

A reviewer found that the invitee pool kept out the people it exists for. A 2025-era session whose client holds its listening stream open is never idle, so it never idle-expires, and the pool evicted only idle sessions: accounts signed up at the provider, each holding one such session, filled the pool and answered every other invitee's `initialize` with 503, guests holding an invite-made attachment included, though hosted Claude speaks that era. Who gives way now follows a rank: a stranger, an invitee holding no attachment, below a guest, an invitee holding one, below a member (`rankOf` in `sessions.ts`). When the pool or the relay is full, the session closed is one held by someone ranked below the newcomer, the lowest rank first, idle before busy, then the least recently active; failing that, only an idle one of the newcomer's own rank. So a guest takes a stranger's place, busy or not; a member takes an invitee's when the relay is full, strangers' first; a stranger never closes a guest's session, idle or busy, nor a busy stranger's; and a member's session gives way to no one else. Before, a stranger could also close a guest's session when the relay was full. What remains: strangers holding busy sessions can still keep other strangers from opening a 2025-era session, which until they hold an attachment costs those only `pair_page` with a link, since `/i` and the 2026-07-28 leg need no session. The same review found the 2026-07-28 leg's listen streams outside the tier; ADR 0018's notes give their bounds, which follow the same rank. Tests: `invitee-tier.test.ts`, `listen-streams.test.ts`.

## Notes from ADRs 0025 and 0026 (5 October 2026)

ADR 0025 builds M5's first-class tools and keeps this record's rule. Invitees, and every attachment an invite made (a member's included), get no first-class names, and a call by such a name answers `tool_not_found`. ADR 0026 does the same for confirmation in the caller's client: on a page that opts in, invitees and every invite-made attachment still get the page prompt for a consequential call, and the adapter tells an invite-made grant by the invite it names.

## Notes from M6 (10 October 2026)

The fixed tools are nine from M6: `list_pages`, `pair_page`, `list_page_tools`, `call_page_tool` and `detach_page`, then `get_page_state` and `wait_for_page_state` (ADR 0040) and `get_proposal` and `withdraw_proposal` (ADR 0042). Where this record says invitees stay on "the five fixed tools", read "the fixed tools": invitees and invite-made attachments still get no first-class names. An invitee may read page state as any attached role may, and may propose only on a page whose `policy.proposals` is `'all'`.

"Use at most the page's user limit minus two seats" now holds for the people limit only (ADR 0044): invitees watching by invite sit in the page's watching seats, `TABDOCK_MAX_OBSERVERS_PER_PAGE`, apart from it, and with those at 0 the old rule returns. The no-account agent tokens on `/g/mcp` are built by ADR 0044, behind `TABDOCK_AGENT_TOKENS`, off by default: observer only, one page, 1, 4 or 8 hours, their first request always prompting, a deny or three timeouts burning them, named `agent <short id>` by the relay with the label the widget shows, and never a hosted connector.
