# 0029: The tour on GitHub Pages and the demo's choice of relay

Status: Accepted under the owner's standing instruction of 4 October 2026 (recorded 5 October 2026). Changes SPEC sections 4 (its layout and the demo paragraph) and 10 (the M5 line, from "At release"). Amends ADR 0021: the Pages publish leaves `deploy.yml` for a workflow of its own, `pages.yml`, which puts the demo at `/` and the tour at `/tour/`. Section 9 is unchanged. ADR 0031 adds the site build to section 10's acceptance tests (A5.5), and ADR 0028's banner is what the new README tells people to paste. This is decision D6 in `docs/notes/m5/m5-decisions.md`; the research is in `docs/notes/m5/pages-readme.md`, with three corrections from the fact checkers noted where they apply.

## Context

SPEC section 10 asks M5 to publish the `docs/tour` explainers on GitHub Pages beside the demo at release, and says the demo takes a relay URL so visitors point it at their own. Today the Pages publish is the last job of `deploy.yml` (its `pages` job), which runs only after a relay deploy and the owner's approval of the `production` environment, and publishes `apps/demo` alone from the demo's static build (`buildDemo` in `apps/demo/scripts/server.ts`). Its pins, `upload-pages-artifact` v5.0.0 (`fc324d35`) and `deploy-pages` v5.0.1 (`368f8252`), were still the newest tags on 5 October, and nothing is live: the repository has no Deploy run and no deployment. `upload-pages-artifact` tars one directory and `deploy-pages` posts one artifact per deployment, so demo and tour must be built into one directory in one job; a tour-only publish would drop the demo. With an Actions source the custom domain lives in the repository's settings and a `CNAME` file is ignored. Live Pages responses carry `cache-control: max-age=600` and `access-control-allow-origin: *` (the fact checkers added the second) and no `Content-Security-Policy` or `X-Frame-Options`, and CSP3 says a policy delivered in `<meta>` ignores `frame-ancestors` and `sandbox`. The static `index.html` loads `/main.js` by an absolute path and carries no policy; the dev server's headers (`SECURITY_HEADERS` in `server.ts`) do not travel to a static host.

Each tour page holds one Mermaid block, which GitHub renders in the repository and Pages does not. Five ways were weighed. (a) A build script with `marked`, drawing Mermaid to SVG at build time: in Playwright's Chromium 141 with every request aborted, all seven Mermaid blocks in the repository rendered in 30 to 470 ms each, 26 to 50 KB, with no script, no `on*` attribute and, under `htmlLabels: false`, no `foreignObject`. (b) `jekyll-build-pages` v1.0.13 runs its image by a mutable tag, so a SHA pin no longer fixes what runs, and draws no Mermaid. (c) Mermaid at runtime from jsDelivr with SRI costs each reader 1.57 MB gzipped and needs `style-src 'unsafe-inline'`. (d) `beautiful-mermaid` 1.1.3 needs no browser, but its SVGs import Google Fonts and its labels overlap lines. (e) GitHub's Markdown API needs the network at build time (not a token, as the note first said; the fact checkers corrected it) and leaves Mermaid open. Option (c) has a worse flaw: tour pages share the demo's origin, which the relay's allowlist vouches for (S2), and in one tab the `sessionStorage` where the adapter keeps its resume token, grants and invite records (`packages/adapter/src/index.ts`, `storageKey` in `packages/adapter/src/core.ts`). No S-rule's wording breaks, but S2's origin check would vouch for code the project does not ship.

The demo reads its relay in `relayFromQuery` (`apps/demo/src/relay.ts`), which takes it only from `?relay=` and refuses a scheme other than `ws:` and `wss:`, a user name or password, and `ws:` off loopback on an https page. `attachToRelay` (`apps/demo/src/main.ts`) refuses inside a frame and otherwise calls `attach()` as soon as the tools are registered, naming the host in the status line. Against a hostile relay the adapter still holds S4 to S6 (its own grant record, the least role, prompts denied on timeout); what it lacks is the visitor's knowledge. A crafted link makes a published copy dial a relay nobody chose, which then shows names of its own making in attach prompts and a QR code for any https host. A query on the relay URL is accepted today (by the demo and by the adapter's `checkRelayUrl`) and would travel in the page socket's request line, which Tabdock's relay logs only by route but a tunnel, a host edge or another relay may log whole. Under a candidate meta policy with loopback hosts named, the static board registered six tools, linked to a local-mode relay, drew its widget and ran `?busy` with no violation; `ws://[::1]:*` did not match, since CSP's host grammar has no IPv6 literal, while Chromium itself refuses `ws:` to a host off loopback from an https page and allows 127.0.0.1, localhost and [::1]. From Chrome 147, Local Network Access asks before a public site opens a WebSocket to a loopback address; the note marked this unprobed, but the fact checkers ran Chrome for Testing 154, where `ws://127.0.0.1` from a public https page failed without the loopback-network permission and opened with it.

## Decision

**The site.** A new private package, `apps/site`, builds the Pages site into `apps/site/dist`: the demo's own static build at the root; each `docs/tour/*.md` rendered with `marked` as `tour/NN-title.html`, plus `tour/index.html`; each Mermaid block drawn as `tour/img/NN-k.svg` and shown through `<img>`; and the PNGs under `docs/tour/img` copied. Mermaid draws in Playwright's Chromium (`playwright-core` at the workspace's Playwright version, so it drives the browser CI already installs), from mermaid's self-contained `dist/mermaid.min.js`, with `securityLevel: 'strict'`, `htmlLabels: false` and every request aborted. Links between tour pages become `.html` links, and other repository paths become GitHub links at the commit built. Each tour page carries no script, a `tour.css`, a `no-referrer` meta and the policy `default-src 'none'; img-src 'self'; style-src 'self'; base-uri 'none'; form-action 'none'`; wide diagrams scroll sideways so a phone can read them. The build fails if a tour page holds `<script` or an `on*=` attribute or lacks that policy, or if an SVG holds a script or a URL outside the site. The demo stays at `/`, so M4's URLs and the relay's origin list are unchanged; the tour is at `/tour/`, and each links to the other by relative paths.

`marked` 18.0.14 (MIT, no dependencies) and `mermaid` 12.1.0 (MIT, no install scripts) are dev dependencies outside CLAUDE.md's pre-approved list, accepted under the standing instruction. I departed from the note in one respect: mermaid brings about 117 packages (about 200 MB in a scratch install), so `apps/site` stays out of the pnpm workspace (`!apps/site` in `pnpm-workspace.yaml`) with its own `pnpm-lock.yaml`. A root script, `pnpm site:build`, runs `pnpm install --frozen-lockfile --ignore-workspace` in `apps/site` and then the build, so a clean clone's `pnpm install` stays as it was and pays for mermaid only when someone builds the site.

**Publishing.** A new `.github/workflows/pages.yml`, started only by `workflow_dispatch`, with every job conditioned on `refs/heads/main`, `permissions: {}` at the top and one concurrency group that never cancels a deploy half way. Its build job holds only `contents: read`: it checks out without persisted credentials, installs what the demo needs and Playwright's Chromium, runs `pnpm site:build` and uploads `apps/site/dist` with `upload-pages-artifact`. Its deploy job holds `pages: write` and `id-token: write`, names the `github-pages` environment, whose deployment branch rule admits only `main` as GitHub recommends, and runs only `deploy-pages`, so no npm package runs in a job that can publish. Every action is pinned by full SHA, as in `deploy.yml`: `checkout` v7.0.1 (`3d3c42e5`), `setup-node` v7.0.0 (`82076278`), `upload-pages-artifact` v5.0.0 (`fc324d35`) and `deploy-pages` v5.0.1 (`368f8252`). `deploy.yml` loses its `pages` job and ends with the live relay check, so a tour fix needs no relay deploy and a relay deploy no longer republishes the site. CI runs `pnpm site:build` after its Playwright install. ADR 0021's guards for the custom domain (verify the domain first, no wildcard record, retire the origin before the record) hold unchanged.

**The demo dials only a relay its visitor chose.** In every build, without `?relay` the board offers a Connect form; with a valid `?relay` it shows a bar reading `Connect to <host>`, the host taken from `URL.host` (so an internationalised name shows as punycode, with its port), and calls `attach()` only after a click whose event `isTrusted`. The form checks what is typed with the same rules and, on a trusted submit, records the choice exactly as the bar's click does and navigates to `?relay=`, keeping the page's other parameters; it is handled in script, so `form-action 'none'` below holds. The choice is remembered in `sessionStorage` for that tab and that relay URL alone, under a key of the demo's own apart from the adapter's records and holding no secret, so a reload reconnects and resumes without a second click. Only the dev and test bundle's `?e2e` hook skips the click; `__TABDOCK_E2E_HOOK__` is false in the static build, so a published copy never can. `relayFromQuery` also refuses a relay URL with a query or a fragment, even an empty one, since a query leaves in the socket's request line, where S11 would have no credential ride, and the WebSocket constructor refuses a URL with a fragment outright; the adapter's own check is unchanged. The refusal to link inside a frame stays as it is.

**The demo's static build.** `buildDemo` writes a meta policy into `dist/index.html`: `default-src 'none'; script-src 'self'; style-src 'self' 'sha256-<hash>'; img-src 'self'; connect-src wss: ws:; worker-src blob:; base-uri 'none'; form-action 'none'`, where the hash is computed at build time from `index.html`'s one inline style block, which also styles the bar and the form. `index.html` loads `./main.js`, so a fallback at `<user>.github.io/<repository>/` works too. `connect-src` names `ws:` as a scheme because CSP cannot name `[::1]`, which costs nothing: the browser already refuses `ws:` from an https page to anything but loopback. The widget's QR code is inline SVG and its styles an adopted sheet (`packages/adapter/src/qr.ts`, `widget.ts`), so neither needs more. The dev and test server keeps its headers and no meta policy, since its `?mcpb` frames MCP-B's widget, which the static build leaves out. A meta policy cannot carry `frame-ancestors`, so the board's refusal to link in a frame remains its framing defence.

**README.** The 0.1.0 README shrinks to about 650 words: what Tabdock is in three sentences; where to try it, through the repository's About website field rather than a committed URL, keeping the owner's domain out of files as M4 did; local mode with Claude Code through `pnpm dev`, pasting the command the relay prints (ADR 0028) and checking with `claude mcp list`, never `claude mcp get`; Claude on the web, desktop and phone through a public URL and a custom connector; one's own page, with section 8's snippet; security in brief, linking the threat model; a Mermaid architecture flowchart, which GitHub renders; the docs; status and licence. The full command list moves to a new `docs/develop.md`. The local path uses `pnpm dev` because its board is itself on loopback, while the published board would need Chrome's loopback-network permission to reach a local relay.

**SPEC wording.** Section 4's layout gains, after the `apps/demo` line: "`apps/site           Builds the GitHub Pages site: the demo's static build at / and docs/tour at /tour/, Mermaid drawn to SVG at build time; kept out of the pnpm workspace, with its own lockfile`".

Section 4's demo paragraph gains, after "`clear_board` (consequential).": "It dials only a relay its visitor chose (ADR 0029). `?relay=` names a `ws:` or `wss:` URL with no user name, password, query or fragment, and `wss:` on an https page unless the relay is on loopback; the board then shows a bar reading `Connect to <host>` and attaches only after a trusted click on it, or on the Connect form it offers when `?relay` is absent, a choice remembered for that tab and relay URL alone. Only the dev and test bundle's `?e2e` hook skips the click. The board never links inside a frame. Its static build carries a CSP in a `<meta>` element (`default-src 'none'`, scripts from its own origin only) and loads its script by a relative path."

Section 10, the M5 line, from "At release" to its end: "At release, publish the `docs/tour` explainers on GitHub Pages in one site with the demo page, the demo at `/` and the tour at `/tour/`, on the demo's own custom domain if the owner gave it one (ADRs 0021 and 0029). Tour pages carry no script, since they share the origin the relay's allowlist names for the demo. The relay is never hosted there; the demo takes a relay URL so visitors point it at their own, and dials it only after the visitor clicks to connect (section 4). Project sites under one account share a single origin, so without a custom domain the relay's allowlist entry for the demo covers all of them."

Section 9 stays: S1 and S2 are untouched, and the tour's lack of script keeps S2's origin check vouching only for the demo's own code; S4 to S6 are unchanged, the click being an extra step before the adapter starts; and refusing a query or fragment narrows what a relay URL can leak, as S11 asks.

## Consequences

Demo and tour share one origin, which is safe only while tour pages carry no script; the build enforces that, and a tour page that wants script needs an ADR of its own. Publishing no longer waits on the relay's production approval: `github-pages` admits only `main`, so `pages.yml` publishes only what review already let into `main`, and mermaid's packages run only in jobs that hold `contents: read`. Each publish replaces the whole site, so the build always includes both halves.

A visitor now clicks once before the board dials, and a crafted link can show the bar but cannot make the board dial; a remembered choice can reconnect a tab only to a relay its visitor already chose in that tab. The Playwright specs and demo scripts open the board with `?e2e` (`demoPageUrl` in `tests/e2e/src/tabdock-harness.ts`) and need no change; manual steps gain a click, and the `pnpm dev` banner says the board waits for one. A relay whose page URL needs a query cannot be used from the demo; no Tabdock relay needs one. Residual risks stay as the threat model's B10 row has them: a framing site can still draw a look-alike page, and Pages lets any site read the site's files, none of which is secret. The build's Chromium runs mermaid's code on the repository's own text with the network blocked.

Files that change with the build, beyond the code above: `docs/deploy.md` ("The workflows", the Pages step and the deploy description), the threat model's B10 row, `apps/demo/README.md`, `docs/checklists/M4.md` (the published board link now needs a click), and `tests/e2e/test/deploy-files.test.ts`, which today expects `deploy.yml`'s jobs to be `verify`, `deploy` and `pages` and gains checks for `pages.yml`. `pnpm lint` and `pnpm typecheck` must pass on a clean clone without `apps/site`'s packages installed.

## Notes from the M5 site review (5 October 2026)

A review of the published board found four ways round the click; each is fixed, with tests in `tests/e2e/specs/connect.spec.ts`, `tests/e2e/test/demo-static-build.test.ts` and `apps/demo/src/connect.test.ts` that fail without the fix. These notes amend the Decision under the owner's standing instruction of 4 October and replace the sentences above that they contradict; section 9 is unchanged, and the SPEC's demo paragraph follows them.

**A link sets the policy as well as the relay.** `?confirm=client` turns on the one trust ADR 0026 adds, and `?invites=all` offers Can control invites with two driver seats, yet the bar showed only the host and the choice was remembered for the relay URL alone. A crafted link could therefore pair a relay with a looser policy than its visitor saw, and any page able to navigate a tab that once chose relay R could link it to R again under a looser policy with no click. Now the bar names each policy setting the link makes beyond the defaults, the status area keeps naming them once linked, and a choice is remembered for the tab, the relay URL and the policy, read strictly and in one order (`policyTag` in `apps/demo/src/policy.ts`), so a link that changes the policy, looser or narrower, asks again. The Connect form sets `?confirm` and `?invites` only as its visitor ticks its two boxes, which start unticked whatever the page's own query says.

**A click that comes too soon.** The bar took a click the moment it appeared, so a double click begun on a popup that closes on its first press could land its second half on the bar. Its button now arms as the widget's boxes do: it takes a trusted click only once it has held still for 500 ms in a visible tab whose window has focus; a window regaining focus, the tab coming into view, `pageshow`, a resize, a scroll, a move or a refused click starts the wait again; and a press that began before it armed does not count when it ends after. `data-armed` shows the state. Headless Chromium fires no focus event when a popup closes, so the sandbox checks the refocus rule with dispatched events, and `docs/checklists/M5.md` asks for one check on a real browser.

**A long host.** At phone width an unbroken host pushed the bar and the status line past the screen's edge, hiding the end of the host, which says who runs it, and scrolling the page sideways. The host now sits in an element of its own, and the bar, its button and the status line wrap anywhere, so the whole host stays on screen. The bar does not single out the registrable domain, which would need the Public Suffix List, a new dependency.

**MCP-B's embed.** The static bundle still held the `?mcpb` loader, which appends `/vendor/webmcp-local-relay/embed.js` by a path at the origin's root; under a `<user>.github.io/<repository>/` fallback that path belongs to another site, and `script-src 'self'` would run whatever it serves, chosen by a link and with no click. A build-time define, `__TABDOCK_MCPB_EMBED__`, false in `buildDemo` and true only for the dev and test server, now drops the loader from the static bundle as `__TABDOCK_E2E_HOOK__` drops the `?e2e` hook.

SPEC section 4's demo paragraph, from "the board then shows a bar" to "skips the click.", now reads: "the board then shows a bar reading `Connect to <host>`, its host wrapping within the screen, that also names each policy setting the link makes beyond the defaults (`?confirm`, `?invites`), and attaches only after a trusted click on it once it has held still for half a second in a visible, focused tab, or on the Connect form it offers when `?relay` is absent, which sets `?confirm` and `?invites` only as its visitor ticks them. A choice is remembered for that tab, that relay URL and that policy alone. Only the dev and test bundle's `?e2e` hook skips the click, and only that bundle loads MCP-B's embed for `?mcpb`."
