# 0013: OAuth in M3: WorkOS issues tokens, the relay checks them

Status: Accepted by the owner, 3 October 2026 (decisions D1, D2, D3 and D7 of the M3 plan). Refines ADR 0006; changes SPEC section 7.

## Context

ADR 0006 planned a minimal `oauth` plugin that "accepts Claude's hosted callback and Claude Code's loopback redirect". The M3 research (`docs/notes/verified.md`, 3 October) showed how Claude actually signs in: it starts only on an HTTP 401 whose `WWW-Authenticate` carries `resource_metadata`, reads RFC 9728 protected resource metadata, registers itself with the authorization server it names (a client ID metadata document, or dynamic registration), always uses S256 PKCE and the RFC 8707 `resource` parameter, and treats any 403 other than `insufficient_scope` as final. The SDK has resource-server helpers but no authorization server and no token verifier. Of twelve identity providers checked, only WorkOS AuthKit offered everything Claude needs from dashboard switches. The auth plugin contract (`authenticate(request)` returns a User or null) cannot express a challenge or serve metadata, and the QR flow (S11) needs the relay to sign a phone's browser in as well.

## Decision

WorkOS AuthKit is the authorization server: it registers Claude, checks redirects (Claude's hosted callback and Claude Code's loopback), runs sign-in and issues access tokens whose audience is the relay's public MCP URL. The relay is a resource server only. The auth plugin contract becomes: `authenticate(request)` returns a user, or a refusal carrying its status and challenge (401 with `resource_metadata` to sign in, 403 for a signed-in person not on the allowlist), and a plugin may serve GET routes. The `oauth` plugin serves `/.well-known/oauth-protected-resource/mcp`, checks the provider's metadata at startup (issuer, S256, and client metadata documents or registration), and verifies each token's signature, issuer, audience and expiry with `jose` 6.2.12 under the SDK's `verifyBearerToken`; a valid token's `sub` maps to a user through an allowlist in `.env`, and anyone else gets 403. The QR page `/pair` signs the phone's browser in with `openid-client` 6.8.8 (and its dependency `oauth4webapi` 3.8.8) against the same provider, holding a short session in a `__Host-` cookie. Tests use `oauth2-mock-server` 9.2.0 as a stand-in provider. The owner approved these three runtime packages and one dev package. The runtime three are MIT, by one maintainer, with nothing else beneath them; `oauth2-mock-server` is MIT by another maintainer and brings `jose` and `basic-auth` 3.0.0 (MIT).

## Consequences

The relay holds no signing keys and no client registrations; swapping providers later changes only the issuer, key URL and audience. A vendor holds the owner's sign-ins, and since strangers may be able to sign up with it, the relay's allowlist is the real gate. Some facts are confirmed only on the owner's first run (Claude Code's loopback port, hosted Claude's metadata document), with dynamic registration as the fallback.

Corrected by ADR 0020: moving between providers, or between one provider's environments, also changes the `/pair` client and every member's `sub`, so the allowlist is redone and the connector added again.

## Notes after the build

A refusal may also be 503, with `Retry-After`, when the plugin cannot check a token because the provider's key set cannot be fetched, so a provider outage does not send Claude into a sign-in loop. A plugin may have a `start()`, run before the relay listens (the `oauth` plugin checks the provider's metadata there, with `fetch` and zod rather than `openid-client`, whose discovery is built for clients), and declares the `resource` it accepts tokens for, which public URL mode requires to equal `<public URL>/mcp`. Error descriptions in the challenge are fixed phrases, never library text. The relay serves only the protected resource metadata, not a mirror of the provider's. The `/pair` sign-in is a confidential client of the same provider (`TABDOCK_PAIR_CLIENT_ID` and `TABDOCK_PAIR_CLIENT_SECRET`, redirect URI `<public URL>/pair/callback`, scope `openid`, and `openid email` from M4 under ADR 0020), using `client_secret_post` when the provider lists it, checking the ID token's signature as well, and reusing the provider metadata the plugin already checked rather than discovering it again. WorkOS's documentation says that ID token carries the same `sub`, the user ID, as Claude's access tokens; the owner's first run confirms it. A test proves the ID token's signature is checked: a flipped bit, or a signature by an unpublished key under the provider's `kid`, fails the sign-in.

The section 9 review added three bounds. After a failed key set fetch, a cold start's first included, the plugin answers 503 and fetches again no sooner than its `Retry-After` of 5 s, whatever tokens arrive, because `jose` remembers no failure; meanwhile keys `jose` still holds as fresh check tokens without a fetch, so no key is trusted longer than `jose` alone would trust it (keeping an older key set through an outage was built and then dropped for that reason). Code exchanges at `/pair/callback`, each a request to the provider carrying the client secret that anyone can set off with a login cookie of their own making, are bounded for the whole relay: 8 at once and 60 a minute (`TABDOCK_MAX_PAIR_SIGNINS_IN_FLIGHT`, `TABDOCK_MAX_PAIR_SIGNINS_PER_MINUTE`), past which the sign-in fails without asking the provider. The cost is that someone who knows the public URL can keep QR sign-in failing for everyone at about a request a second; pairing by code from Claude, whose sign-in never touches `/pair`, still works, and a budget per client address waits for M4's trusted proxy address.
