# 0022: Local mode by default

Status: Accepted by the owner, 3 October 2026. Changes SPEC sections 2, 7, 10 and 11, and frames the hosted parts of ADRs 0018 to 0021 as the project's reference deployment. Section 9 is unchanged.

## Context

A first run needs setup before anything works: `loadConfigFromEnv` throws without `TABDOCK_DEV_TOKENS` (`config.ts:619-624`), `pnpm dev` refuses to start without it (`scripts/dev.ts:55`), and the `claude mcp add` line it prints holds a placeholder (`scripts/dev.ts:103`). The M4 drafts also read as if Fly.io, WorkOS and a personal domain were part of Tabdock. On 3 October the owner asked for a simple, batteries-included local relay "so that we don't dictate how users set this type of infrastructure up themselves and to reduce complexity", keeping the hosted setup as one worked example (`docs/notes/m4/local-mode-decision.md`). Claude Code 2.1.288 keeps a server's headers in `~/.claude.json` (mode 0600) for the `local` and `user` scopes and in the repository's `.mcp.json` only for `project`; `claude mcp add` prints them redacted, `claude mcp get` in full (`docs/notes/verified.md`, 3 October, M4).

## Decision

**When.** The relay runs in local mode when none of `TABDOCK_DEV_TOKENS`, `TABDOCK_PUBLIC_URL`, `TABDOCK_OAUTH_ISSUER`, `TABDOCK_OAUTH_USERS`, `TABDOCK_PAIR_CLIENT_ID` and `TABDOCK_PAIR_CLIENT_SECRET` is set and `TABDOCK_ENV` is unset or `development`. Explicit settings win, with M1's and ADR 0014's rules. A setting that means nothing in the resulting mode is refused by name, as `config.ts` already refuses OAuth settings without a public URL: `TABDOCK_OAUTH_CLIENT_IDS` without OAuth, and `TABDOCK_CLIENT_ADDRESS_HEADER` or `TABDOCK_TRUSTED_PROXY_CIDR` outside hosted mode. Production without auth settings refuses to start and never falls back to local mode. Pages keep S1 and S2's development default, and local mode mints no invites, which need a public URL (ADR 0017).

**Commands.** `pnpm relay`, a new root script, runs the relay alone and `pnpm dev` adds the demo board; both read `.env` when present and need none. The refusal in `scripts/dev.ts` goes and `pnpm dev:public` is unchanged. `npx @tabdock/relay` waits for the 0.1.0 release in M5.

**The token file.** `owner-token` lives in `TABDOCK_HOME` when set (absolute only), else in the per-user configuration directory: `$XDG_CONFIG_HOME/tabdock` or `~/.config/tabdock` on Linux and other Unix systems (XDG Base Directory 0.8), `~/Library/Application Support/Tabdock` on macOS, and `%LOCALAPPDATA%\Tabdock` on Windows, the local profile, since the token is good only on this machine. It holds `tabdock_` and 43 base64url characters encoding 32 bytes from `node:crypto`'s `randomBytes`. The first start creates the directory 0700 and links a synced 0600 temporary file into place, so two racing starts never read an empty token. Every start refuses, naming the path and the fix, a directory inside the checkout (compared by `realpath`), and a file or directory that another user owns, that grants group or others any permission, or that is not a regular, well-formed file. Like ssh with a private key, it refuses rather than repairs: a readable file may already be copied, and rewriting a bad one would hide tampering. On Windows, where Node reports identical owner, group and other bits and lacks `O_NOFOLLOW`, the owner and mode checks give way to another: the directory must lie under `%LOCALAPPDATA%` or `%USERPROFILE%`, whose default access list admits only the user, SYSTEM and Administrators, as a Windows run on the checklist confirms. The M4 plan states the exact rules.

**User and plugin.** The token maps to one fixed user, `you`, shown as `You`, through `createDevTokenAuth`, so authentication is M1's code path and the relay keeps only the token's digest. The plugin carries a new `AuthPlugin` field, `loopbackOnly: true`, and `resolveConfig` refuses any plugin so marked, whatever its name, with a public URL, in production or off loopback, so neither hosted mode (ADR 0018) nor a later rename can widen it. Local mode decides who may call `/mcp`, never who reaches a page: the operator still approves each attachment (S4), roles, revoke and S13 hold for `you`, and S7 records every call in an audit log kept in `audit/` beside the token unless `TABDOCK_AUDIT_DIR` names another (ADR 0019). Several local users still come from `TABDOCK_DEV_TOKENS`.

**This machine only.** Without a public URL, in local mode and with dev tokens alike, an `/mcp` request or `/page` upgrade carrying `Forwarded` or any `X-Forwarded-*` header gets 403 through M3's `madeLocally`, so a tunnel that rewrites `Host` cannot expose a loopback relay. Claude on the web, desktop and phone connects from Anthropic's cloud and needs public URL mode, through a tunnel (ADR 0014) or on a host (ADR 0018). Local mode also trusts every account on its machine: nothing authenticates the relay to its clients, so an account that binds the port while the relay is down receives Claude Code's token and the pages' `hello` frames and can raise attach requests of its own, and every local process shares the per-address page limits. On a machine shared with accounts one does not trust, run the relay on a host with sign-in instead.

**Banner.** The relay prints that it serves this computer only, the MCP and page socket URLs, the token's path and whether it was just created, and a command for the current shell that reads the file; for POSIX shells:

`claude mcp add --transport http --scope user tabdock-local http://127.0.0.1:8787/mcp --header "Authorization: Bearer $(cat '<path>')"`

It names the path, never the token, so shell history holds none. User scope offers the relay in every project, and any scope but `project` keeps the token out of repositories; the name `tabdock-local` leaves `tabdock` for a hosted connector and avoids an M1-era `tabdock` entry, which would win inside the checkout. The banner suggests `claude mcp list`, never `claude mcp get`, to check the connection, and its last line sends those wanting Claude on the web or phone to the top of `docs/deploy.md`, which offers a tunnel (`pnpm dev:public`) or a host before its worked example. Tabdock never prints or logs the token, any part or digest of it, or the file's contents. To rotate, stop the relay, delete the file and start again, then replace the Claude Code entry (`claude mcp remove --scope user tabdock-local` and the printed add); the old token gets 401.

**Reference deployment.** Everything past local mode is opt-in. `docs/deploy.md` is the reference deployment, Fly.io with WorkOS behind a subdomain of the owner's domain: one worked example, each platform-specific step marked, of a host meeting section 11 (ADR 0018) and a provider meeting section 7 (ADR 0020). The owner's D1, D2, D4 and D6 choose it, and no code depends on them.

**SPEC wording.** Section 2 gains a row after Relay trust: "| Default setup | Local mode: with no settings the relay binds loopback, keeps an owner token in a private per-user file and prints a ready Claude Code command. Public URL mode, the identity provider and the host are the user's choice; the project's own hosted relay is a reference deployment (ADR 0022) | Owner's call: Tabdock does not dictate how people run infrastructure |".

Section 7, in the auth paragraph, the sentence "M1 ships `dev-token` (users and bearer tokens from `.env`)." becomes: "M1 ships `dev-token` (users and bearer tokens from `.env`). From M4 a relay given no auth settings runs in local mode (ADR 0022): `dev-token` with one user, `you`, whose 256-bit token the relay draws on first run into a private per-user file outside the repo and never prints or logs; local mode binds loopback only, refuses proxied requests, trusts every account on its machine, is refused in production and with a public URL, and gives way to explicit dev tokens or OAuth settings."

Section 10 gains "A4.4 From a clean clone with no `.env`, `pnpm relay` starts in local mode, stores its token only in a private per-user file outside the repo (0600 where POSIX modes apply), and Claude Code, added with the command it prints, connects to it." The M4 line names local mode in ADR 0021's wording.

Section 11 splits in two. The first paragraph reads: "Laptop: Node 22+, pnpm, Chrome. `pnpm relay` (the relay alone) and `pnpm dev` (with the demo board) need no `.env`: with no settings they run local mode, which serves MCP clients on the same machine, such as Claude Code, and trusts every account on it (ADR 0022). The demo uses the polyfill, so no origin trial token is needed; test native WebMCP too when the flag is available. Claude Code cloud session: M1 and M2 automated tests run headless with the sim page and Playwright; no phone tests." The second, from "Public URL", takes ADR 0021's wording.

Section 9 stays: local mode keeps S1 and S2's localhost-only default and S12's loopback bind, keeps a persistent audit log for S7, and has one named user, so S4 to S8 and S13 hold on a machine whose accounts are trusted; S11 covers the owner token. Each rule above gets a test, listed in the M4 plan.

## Consequences

A first run is `pnpm install` and `pnpm relay`, with no account, tunnel or host, and a newcomer meets the trust model before any infrastructure. The token has a second private copy in Claude Code's `~/.claude.json`, which `claude mcp get` prints in full, and while the printed command runs it sits in `claude`'s argument list, which other accounts can see and command-line auditing (auditd, Windows event 4688, EDR agents) records; "never logged" covers Tabdock's own output only. Claude Code's `headersHelper` would avoid both but needs JSON configuration and the project trust dialog, so it waits for the M5 package. User scope lets a prompt injected into any Claude Code session act on pages `you` is attached to, within the granted roles and prompts, though any process of the user could read the token file anyway. The threat model's local-mode row records these exposures, port squatting and the shared per-address limits. `.env.example`, both READMEs and the M1 tour say every setting is optional; CLAUDE.md's "Dev tokens come from `.env`" is the owner's to update. SPEC requires only what a host and a provider must do: Fly.io, WorkOS and the owner's domain appear only in section 3's facts and where sections 4, 7 and 11 name the reference deployment as an example, never as a requirement.

## Notes after the build (4 October 2026)

Step 0's own findings are in `docs/plans/M4.md`. The workstreams finished what it left: `TABDOCK_OAUTH_CLIENT_IDS` and `TABDOCK_OAUTH_MAX_TOKEN_AGE` are refused by name without a public URL, `TABDOCK_CLIENT_ADDRESS_HEADER` outside hosted mode, `TABDOCK_TRUSTED_PROXY_CIDR` without that header, `TABDOCK_INVITES` in local mode, `TABDOCK_MAX_REQUESTS_PER_INVITEE` without invites, and the audit bounds with neither an audit directory nor local mode; the `/page` local check gives way only in hosted mode, and then to the public host alone; and local mode keeps its audit log in `audit/` beside the token unless `TABDOCK_AUDIT_DIR` names another, which `pnpm audit:log` reads with no flag. That directory is locked while a relay writes it, so a second relay sharing the token directory refuses to start, naming the lock, rather than fork the chain.
