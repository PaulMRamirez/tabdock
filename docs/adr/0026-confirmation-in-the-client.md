# 0026: Consequential confirmation in the caller's client

Status: Accepted under the owner's standing instruction of 4 October 2026 (recorded 5 October 2026). Changes SPEC sections 5 (the Client row and the roles paragraph), 6 (the `tools` and `invoke` rows), 7 (the error codes and a new paragraph on the call flow), 8 and 9 (S6, S7 and one phrase of S9); amends ADR 0019's `call` record and adds notes to ADRs 0002 and 0016. ADR 0031 adds the acceptance test, A5.3, to section 10 and the elicitation facts to section 3.

## Context

SPEC section 10 asks M5 for "consequential confirmation through `input_required` where the client supports it". Today only the page can confirm. When a consequential call gets the page, the adapter's `proceed` (`packages/adapter/src/core.ts:2061`) raises the on-page prompt through `askConfirm` (line 2205) while the call holds the page, and `onDeadline` (line 1860) turns silence into `denied_by_operator`, as S6 and ADR 0007 require. Whether a tool is consequential is ADR 0002's rule, `isConsequential` (`packages/adapter/src/tools.ts:188`), whose inputs (whether the runtime reports `consequentialHint`, and `policy.consequentialTools`) only the adapter has; the relay sees `readOnlyHint` alone, which is all its S5 check in `#call` reads (`packages/relay/src/hub.ts:3916`). An operator away from the laptop cannot answer, so a phone user's consequential call just times out.

The wire now offers a way to ask the caller (`docs/notes/m5/input-required.md`, checked 5 October). On 2026-07-28 a server may answer `tools/call` with `resultType: "input_required"`, carrying `inputRequests` (here an embedded `elicitation/create`) and an opaque `requestState`; the client retries under a new id with `inputResponses` and the state echoed. The server must treat that state as attacker controlled, protect its integrity, bind it to the principal and enforce single use itself; it must not ask for a capability the request's `io.modelcontextprotocol/clientCapabilities` omits, nor assume the client answers or retries. The 2025 revisions push `elicitation/create` during the call, declared in `initialize`, and 2025-11-25 and 2026-07-28 say servers MUST bind elicitations to the client and user identity. The relay's SDK, server 2.3.0, offers `inputRequired()`, `ctx.mcpReq.inputResponses` and `createRequestStateCodec`, an HMAC-SHA256 codec with a TTL and a `bind` callback whose `verify` plugs into the server's `requestState.verify` option; per the package's typings, read on 5 October, a hook that throws becomes a frozen `-32602 Invalid or expired requestState` before any handler runs. On a sessionful 2025 connection a default-on legacy shim turns `input_required` into real `elicitation/create` legs and answers a missing capability or a leg timeout with an `isError` result in the SDK's own words; `ctx.mcpReq.elicitInput` still works there.

Claude Code 2.1.289 declares `elicitation: {form: {}, url: {}}` on both revisions and answered a form inside `input_required` correctly in a live probe. The probe also showed what a client's yes is worth: headless `claude -p` without a hook answered `cancel` at once, and an `Elicitation` hook answered `accept` with no dialog. Claude's connector docs never mention elicitation, so whether hosted Claude declares it is unknown. The research weighed four options: (A) keep only the page prompt; (B) ask the caller wherever the client can answer, which would weaken S6, since a page that never chose it would lose its operator's prompt to something an agent can answer; (C) let a page opt in to confirmation in its members' own clients, with the page prompt everywhere else; (D) ask both, doubling prompts. D2 in `docs/notes/m5/m5-decisions.md` takes C.

## Decision

**Opt-in, and who may confirm.** `PolicySchema` (`packages/protocol/src/page-link.ts:79`) gains `confirmVia: 'page' | 'client'`, default `'page'`, set in `attach()` or by the script tag's `data-confirm-via` (`packages/adapter/src/script-options.ts`). It matters only under `consequential: 'confirm'`: `allow` still runs and `deny` still refuses. On a page that keeps `'page'` nothing changes, and S6 holds word for word. On a page that chose `'client'`, a consequential call by a member driver is confirmed by that member, through the client that made the call, wherever that client declares form elicitation; everyone else gets the on-page prompt as today, every invitee, every observer and every attachment an invite made among them, and so does every call from a client without the capability. "Member" is the account's kind (ADR 0017), "driver" is the attachment's role, and the attachment must be one the operator approved directly: as ADR 0016 keeps every invite-made attachment, a member's included, off first-class names (ADR 0025), this record keeps them on the page prompt, and the adapter can tell them apart by its own grant, which names the invite that made it. A client's yes proves only that the signed-in account's client said yes, since a hook can answer with no person present; that is why it is opt-in, for members only, and marked in the page's activity log. The option sits strictly between `confirm` and `allow`, which pages can already choose.

**When the relay asks.** Only when all of these hold: the page's hello policy says `consequential: 'confirm'` and `confirmVia: 'client'`; its latest `tools` frame marks the tool `consequential: true`; the caller's account is a member and its attachment a driver's that no invite made; and the request declares form elicitation, meaning an `elicitation` capability that is empty or names `form`, read on 2026-07-28 from the request's own `io.modelcontextprotocol/clientCapabilities` and on a 2025-era session from `initialize`. Otherwise the call goes out without a confirmation and the page decides as today, so the relay never asks a client that did not declare the capability and never provokes `-32021`. Since only the adapter can apply ADR 0002's rule, it sends the result: each tool it classes consequential carries `consequential: true` in the `tools` frame (`PageToolSchema`, line 57), whatever `confirmVia` says. A wrong mark fails safe both ways: a missing one leaves the call to the page prompt, and a spare one costs one question in the client before the page runs a tool its own rule calls harmless. The relay uses the mark only for this and shows it to no client. Confirmation lives in the one call path that `call_page_tool` and ADR 0025's first-class names share, so both confirm alike.

**The question.** The relay writes it: the tool name, the page id, the origin's host without its scheme, and the call's arguments as JSON cut to 500 characters, never a page title or description (S10). When the arguments are cut, the text ends `... (N more characters not shown)`, N the count left out, so nobody confirms what looks like a whole call while the part that matters lies past the cut; the confirmation still binds every argument through the digest below. The form has one boolean field, `confirm`, false by default, and asks for nothing secret. Only `accept` with `confirm` exactly `true`, read through a zod schema from what the SDK hands over, confirms; `decline`, `cancel`, `accept` with `false`, and a missing, wrapped or malformed answer do not.

**On 2026-07-28.** The first round runs every check `#call` makes before a call goes to its page (access, the call limit, held bytes, the tool, the role, the frame size and the argument check), so nobody is asked about a call the relay would refuse; it holds its request's bytes while those checks run, as `#call` does, releases them when it answers, and takes no queue place. It then stores a record under a random 128-bit id: the user, the page, the MCP tool name as called (`call_page_tool` or a first-class name), the page tool, a SHA-256 digest of the arguments as canonical JSON, an expiry 120 s out, and, for its audit line, the client's name and version. It answers `input_required` with the question under the key `confirm` and a `requestState` minted by `createRequestStateCodec` under a per-process 256-bit key from `node:crypto`, with its TTL also 120 s, its payload only the record's id (the codec signs but does not encrypt, so nothing secret goes in), and its `bind` the user id, the token's OAuth client id (empty for a dev token) and the method. The relay's `requestState.verify` hook calls the codec's `verify` and, on any failure (a bad MAC, expiry, another binding, a malformed state), resolves a refusal marker rather than throwing: a throw would become the SDK's `-32602` before any handler ran, leaving that call attempt without its call line (S7) and answering it unlike a reused state. A `tools/call` that carries a `requestState` is a retry. Before anything else, the budget included, the relay's dispatcher takes its record out of the store, so a retry refused for any reason has spent it; the dispatcher then spends the request budget as it does for every call (ADR 0025, which moves ADR 0018's spend from `packages/relay/src/mcp.ts:358` into the dispatcher), and the handler requires a live record matching the user, page, MCP tool, page tool and digest, and an answer that confirms. A forged, expired, reused or mismatched retry, or one whose answer does not confirm, answers `not_confirmed`, and the page never hears of it, unless the access check would refuse the call as well, when it answers as that check does: `not_attached` once its caller holds no attachment to the page, as S8 asks of every later call, or `page_gone`. A retry that passes goes the usual way from the access check onwards, the queue included. Just before it goes out, the relay checks the conditions for asking again: the page's current hello policy still says `confirm` and `client`, its latest `tools` frame still marks the tool, and the caller is still a member driver on an attachment no invite made. If any has changed, as after a reload that switched the page to `'page'`, the invoke goes without `confirmation`, the page decides as it would for any call, and the call record carries no `confirmedBy`, so the audit never credits the client with a call the operator decided. A restart draws a new key and drops every record, failing closed.

**On a 2025-era session.** The relay calls `ctx.mcpReq.elicitInput` inside the request, with its own 120 s timer and the request's signal, and sets `inputRequired.legacyShim: false`, so every outcome stays in the relay's handler: the shim would answer a timeout or a missing capability in the SDK's words, with no code and no audit line. The open request is the binding. The request's byte charge is taken before the question is asked, as `#holdBytes` charges any call that may wait, and held until the call ends or is refused, so up to four open questions per member hold nothing uncharged. After a confirming answer the call passes every check again, and the conditions for asking again as on 2026-07-28, and goes the usual way, with `confirmation` only if those still hold; any other outcome, a request its client closed included, answers `not_confirmed`. With the 45 s call deadline that follows, the request stays under hosted Claude's 240 s per tool call.

**A revoke while a question waits.** A revoke, any other end of the caller's attachment and the page's end drop that user's pending records for the page at once, and a 2025-era call waiting on its question abandons the elicitation and answers at once: `not_attached` after a revoke or the attachment's end, as S8 requires and as a call waiting on the page prompt answers, and `page_gone` when the page ends. A retry on 2026-07-28 after such a change finds no record and fails the access check, so it answers `not_attached` or `page_gone`; one after a revoke and a fresh approval finds no record either and answers `not_confirmed`, so a confirmation never outlives the attachment it was given under. A downgrade to observer needs nothing more, since the retry and the 2025-era answer pass the role check and the conditions for asking again.

**Bounds.** At most four questions wait per user across both revisions; a further call that would be asked answers `rate_limited` until one is answered or expires. Each round on 2026-07-28 is its own request and spends one of the caller's request budget and one of the per-page call limit, so a confirmed call costs two. A call takes its place in its page's write queue only once confirmed, so its arrival is that of its confirmation and no write waits while someone decides; unlike the on-page prompt, a client confirmation never holds the page. `requestState`, `inputResponses` and the argument digest never appear in logs, like arguments and tokens (S7, S11).

**How the page learns it.** `InvokeFrameSchema` (line 443) gains `confirmation?: { by: 'client', confirmationId, at }`, where `confirmationId` is a fresh relay id, never the record's, and `at` the epoch milliseconds at which the confirming answer arrived. The adapter skips its prompt only when its own `attach()` policy says `consequential: 'confirm'` and `confirmVia: 'client'`, the tool is consequential by its own rule, the caller's id is a member's (an invitee's id says so, ADR 0017), its own grant for the caller names no invite (`inviteId`), and the least of its own grant, the roster and the invoke's role is driver (`callerRole`, `core.ts:1338`); otherwise it prompts exactly as today, so a crafted frame skips no prompt on a page that did not opt in, nor for an invitee, an invite-made attachment or an observer. The activity log shows the call as "confirmed in <client> by <name>". `tabdock.v1` stays: every addition is optional, an adapter older than this drops the field and prompts, and a relay older than this drops `confirmVia` and the mark and never asks.

**Audit.** `CallShape` (`packages/protocol/src/audit.ts:118`) gains an optional `confirmedBy: 'client'`, present exactly when the call went out confirmed in its client. `not_confirmed` joins `ERROR_CODES` (`packages/protocol/src/errors.ts:2`) and with it the audit outcomes. A `not_confirmed` call reached no page, so its call record goes within the refusal budget (ADR 0019); a record that expires with no retry writes one such refusal when the sweep removes it, so a question nobody answered leaves a line while the relay runs. Asking writes nothing, so a question pending when the relay restarts leaves no line unless its client retries, which then answers `not_confirmed` and writes one; S7's lines are for calls that reach a page or are refused, and such a call was neither, but the threat model records the gap. The format stays at version 1, since 0.1.0 is unreleased.

**Not taken.** Claude Code's `_meta['anthropic/requiresUserInteraction']`, which the fact checker raised, forces Claude Code's own permission prompt on a tool; it binds that one client, the relay cannot see whether it was honoured, and on a page that prompts it would double every prompt.

**SPEC wording.** Section 5, the Client row: "| Client | MCP client name, version and declared capabilities, taken from each request | Self-declared and unauthenticated: the name and version are attribution only, and a declared form elicitation capability only decides where a page that opted in asks for confirmation (ADR 0026). All of a user's clients share that user's attachments |".

Invitees, observers, invite-made attachments and clients without that capability always get the on-page prompt. ## Consequences

An operator away from the laptop can let their own phone or Claude Code confirm instead of letting the page time out, and a confirmed write no longer holds the page while someone decides. A page that never opts in behaves exactly as in M4. What an opted-in page gives up is the operator's eye on each consequential call by a member driver: it trusts that member's client, which an `Elicitation` hook, or a future client that answers by default, can answer with no person present, and it trusts the relay's word that the client said yes. The threat model's B5 row says the adapter does not trust the relay; for an opted-in page and a member driver's consequential calls that no longer holds, as it never held under `allow`, so a relay that lies can run such calls attributed to a member who holds the driver role there. The B5 row and a residual-risk line record both, and the activity log and the audit's `confirmedBy` show every such call after the fact. Invitees, invite-made attachments, observers, pages that did not opt in and clients without the capability keep the page prompt whatever the relay says.

A confirmed call costs two requests on 2026-07-28 and up to four small records per member, and a restart turns pending questions into `not_confirmed`, after which the client asks again. An M4 `pnpm audit:log` refuses lines that carry `confirmedBy`, since every record type is strict; reader and relay ship together in 0.1.0. Hosted Claude's support is unverified: if it does not declare form elicitation, its calls keep the page prompt, so nothing fails open. `docs/checklists/M5.md` lists as owner steps Claude Code's real dialog on both revisions and hosted Claude's declared capabilities, read from ADR 0027's per-client line on the reference deployment. A question pending when the relay restarts leaves no audit line unless its client retries; the threat model's B5 row records that beside the trust above. ADR 0031's A5.3 covers, on both revisions, accept, decline, cancel, expiry, replay, a forged `requestState`, another user and another OAuth client, changed arguments, a fifth question, a restart and a revoke while a question waits, and the page prompt for a page that did not opt in, an invitee, an observer, an invite-made attachment and a client without the capability; the adapter's own suite sends a crafted `confirmation` under each failing condition and expects a prompt. Beside A5.3, the relay's tests check that no question is ever sent to a member observer, an invitee driver or an invite-made member driver (S6), that a retry after the page switched to `'page'` goes out without `confirmation` and its record without `confirmedBy`, that cut arguments end with the count left out, and, in `request-bytes.test.ts`, that a 2025-era call holds its byte charge while its question waits.

## Notes from the M5 Step 1 review (5 October 2026)

Two facts for the build, from ADR 0032. A `requestState` that is present and not a string never reaches `requestState.verify`: the SDK refuses it `-32602 Invalid or expired requestState` in `_invokeInputRequiredCapableHandler`, before any handler, on both eras. Such a request still spends the budget as it arrives (ADR 0032), but a forged retry of that shape would get the SDK's frozen error with no `not_confirmed` answer and no call line (S7), so B2 answers it `not_confirmed`, with its call record, ahead of the SDK: in `relay.ts`'s 2026-07-28 leg, and in `sessions.ts` for a 2025-era call that carries one, which that leg never asks for. And every invoke now keeps room for its confirmation: `MAX_CONFIRMATION_FRAME_BYTES` (137, the longest confirmation encoded) is counted in `#encodeInvoke`'s size check and in `invokeBytes` for every call, so a call that fits when it arrives still fits once confirmed and nobody is asked about one the relay would refuse; `mcp.test.ts` holds it, and B2 keeps that test. The audit schemas refuse a `not_confirmed` call record that carries `confirmedBy`.

## Notes from M5 Step 2 (5 October 2026)

B1 built the adapter's half as decided, with these departures. The adapter also asks when the roster lists the caller's attachment as an invite's, though its own grant names none, so the relay's word can only add a prompt here, never remove one; `core.test.ts` sends each crafted `confirmation` beside the same invoke without one and expects the same prompt. The tools frame marks a tool `consequential` by the page's own rule whatever `confirmVia` and the `consequential` policy say, so the relay sees the same mark on every page. The widget's activity line reads "confirmed in <client> by <name>", the sim page passes `confirmVia` through and lists every consequential prompt it raised in `sim.prompts`, and at integration the demo board read `?confirm=client` into `confirmVia: 'client'`. The relay's half is B2's, in Step 3: until it lands the relay never sends `confirmation`, so a page set to `confirmVia: 'client'` still prompts for every consequential call, and the threat model's B5 row says so beside the carve-out this record makes. The plan's Tests section lists the clauses of A5.3 that B2 still owes.
