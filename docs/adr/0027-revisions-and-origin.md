# 0027: MCP revisions served, the conformance suite, and Origin on /mcp

Status: Accepted under the owner's standing instruction of 4 October 2026 (recorded 5 October 2026). Changes SPEC sections 7 (its first paragraph) and 9 (S12). Adds a note to ADR 0018 (the `Origin` check beside the Host check that record keeps), and replaces M1's choice, recorded in `docs/notes/verified.md`, to check only `Host` on `/mcp`. ADR 0031 adds the facts below to section 3 (the conformance suite, Claude Code's negotiation, the SDK recheck) and A5.2 to section 10. This is decision D3 in `docs/notes/m5/m5-decisions.md`; the research is in `docs/notes/m5/revisions.md`, with one correction from the fact checkers.

## Context

SPEC section 10 asks M5 for "both MCP revisions verified", and section 7 still reads as M1 found it: use the official SDK, preferring the v2 packages "if they cover revision 2026-07-28 and still serve session-based clients". They do (ADR 0005). `/mcp` has two legs behind one set of checks (`legs` in `packages/relay/src/relay.ts`): `isLegacyRequest` sends 2025-era traffic to the sessionful leg in `sessions.ts` (ADR 0009) and everything else to `createMcpHandler` with `legacy: 'reject'`, the strict 2026-07-28 handler.

Probes of a local-mode relay on 5 October showed what each leg accepts. The sessionful leg answers `initialize` with the version asked for when it is on the SDK's list (2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05 and 2024-10-07, `SUPPORTED_PROTOCOL_VERSIONS` in core 2.3.0) and with 2025-11-25 otherwise, 2026-07-28 included; on a session a missing `MCP-Protocol-Version` passes, and an unknown one or 2026-07-28 gets 400. The strict leg answers `server/discover` with `supportedVersions: ["2026-07-28"]`, refuses any other envelope version with 400 and `-32022`, and a header that disagrees with the envelope with 400 and `-32020`. Through a recording proxy, SDK 1.10.2 spoke 2024-11-05 over Streamable HTTP, 1.12.3 spoke 2025-03-26, 1.13.0 to 1.24.0 spoke 2025-06-18, 1.24.1 onward and `client` 2.x by default spoke 2025-11-25 on a session, and `client` 2.x in `auto` or pinned mode spoke 2026-07-28 without one; every one listed tools and called `list_pages`. SDK 1.9 and older ship only an HTTP+SSE client, a transport the relay has never served. The repository's own tests cover only 2025-11-25 and 2026-07-28.

Two answers fall short of the revisions. Both 2025-11-25 and 2026-07-28 say a server MUST validate `Origin` and answer 403 to a present, invalid one, yet `/mcp` answers a foreign `Origin` with 200 on both legs when the token is valid (401 without one). M1 checked only `Host`, on the belief that hosted Claude sends no `Origin`, and the Host allowlist (`validateHost` in `relay.ts`, ADRs 0014 and 0018) is what stops DNS rebinding today. And 2026-07-28 says a server MUST answer an unsupported version with an error listing the versions it supports, while the relay's `-32022` names only 2026-07-28 though the same endpoint serves 2025 revisions: the SDK fills `data.supported` from its modern list (`serveModern` and `modernOnlyStrictRejection` in the server package's `dist`), and `CreateMcpHandlerOptions` offers no way to change it. The fact checkers corrected `revisions.md` here: this is a MUST, not a difference from an example.

The official conformance suite, `@modelcontextprotocol/conformance`, has a `latest` (0.1.16) that knows no 2026-07-28 and an alpha, 0.2.0-alpha.12 of 1 October, with frozen requirement sets for 2025-11-25 and 2026-07-28. Most of its scenarios call the referee's fixture tools and so fail against the relay by design; the protocol scenarios (`server-initialize`, `ping`, `tools-list`, `server-session-lifecycle`, `server-sse-multiple-streams`, `dns-rebinding-protection`, `http-header-validation`, `server-stateless`, the tools part of `caching` and four `input-required` structure scenarios) pass, and with a baseline both requirement runs exit 0 in seconds. Server mode takes no header, and the relay never takes a token in a URL (S11), so the run needs a proxy that adds the bearer; with the default 20 sessions per user the 2025 run got 429, since the referee leaves streams open. Its npm license field says MIT, while the LICENSE file in that alpha is a notice of a move from MIT to Apache-2.0. It brings express, octokit and a v1 SDK of its own (`@modelcontextprotocol/sdk` at `^1.29.0`, a floating range beside the four exact aliases below), all outside CLAUDE.md's pre-approved dev tooling.

Claude Code 2.1.289 (`latest`) negotiates 2026-07-28 by default from 2.1.274: `server/discover`, then every request with the envelope, naming itself `claude-code` and declaring `roots.listChanged` and form and URL elicitation, and sending no `Origin`. With `MCP_PROTOCOL_NEGOTIATION=legacy`, or after a legacy-looking 400 to `server/discover`, it initializes at 2025-11-25 on a session and never sends DELETE. `revisions.md` said headless runs opened no notification stream; the fact checkers found otherwise. `claude -p` opened `subscriptions/listen` (200) right after `server/discover` in two runs, and under the legacy setting opened a GET stream on its session after `notifications/initialized`; since the relay holds back a GET stream's response headers, a proxy that logs on the upstream response never records that GET. Which revision hosted Claude speaks, and whether it sends `Origin`, cannot be seen from a sandbox: its connector docs name only the 2025 authorization specs.

The relay pins `@modelcontextprotocol/server` 2.3.0 and `@modelcontextprotocol/node` 2.1.1 exactly (`packages/relay/package.json`), server 2.3.0 pins `core` 2.3.0 exactly, and `client` 2.3.0 is an exact dev dependency; all were `latest` on 5 October, with no pending changesets on the SDK's `main`. The SDK offers `validateOriginHeader`, which matches a hostname at any port over http or https, and lets a request without `Origin` pass.

## Decision

**Revisions served.** The relay claims 2025-03-26, 2025-06-18 and 2025-11-25 on the sessionful leg and 2026-07-28 on the strict leg. 2024-11-05 over Streamable HTTP is best effort: one matrix row (SDK 1.10.2) keeps it in view, the suite has no requirement set for it, and the relay adds no code of its own for it. The SDK also echoes 2024-10-07, which is not one of MCP's published revisions, and the relay does not claim it. The deprecated HTTP+SSE transport is not served, so a client that speaks only that cannot connect. Every version answer stays the SDK's except the one below, and `server/discover` keeps the SDK's answer.

**The unsupported-version answer.** When the strict leg answers `-32022`, the relay rewrites the error's `data.supported` to every revision it serves, 2024-11-05 included, in the order 2026-07-28, 2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05, and changes nothing else. The rewrite sits in `modern` in `relay.ts`, beside `refusedBySdk`, which already reads that answer's status, so it shapes a refusal the SDK has made and touches no part of the transport. If a later SDK fills the list itself, the rewrite goes. If the build finds it cannot be done without reaching into the transport, it stops, records the deviation in this ADR's notes, and a new record changes the SPEC sentence.

**Origin on `/mcp`.** Every request to `/mcp`, of any method and on either leg, that carries an `Origin` header is answered 403 unless the value is exactly an allowed origin. The check runs after the Host check and before `madeLocally` and the auth plugin, so a refused request gets no challenge, spends no budget (ADR 0030's included) and reaches neither leg. Without a public URL (local mode and dev tokens) the allowed origins are http and https on `localhost`, `127.0.0.1` and `[::1]` at any port, the same set as S2's development default for pages; with a public URL (public and hosted mode) the public origin alone, the value `/pair` already demands of its POSTs (`sameOrigin` in `pair.ts`); and in every mode the origins listed in `TABDOCK_MCP_ALLOWED_ORIGINS`.

The value is compared as written, as S2 compares page origins (`parseOrigin` in `config.ts`): it must be a serialised http or https origin equal to an allowed one, so `null`, an empty value, a path, a trailing slash, upper case, or two `Origin` lines (which Node joins with a comma) are refused. The relay keeps this comparison rather than the SDK's `validateOriginHeader`, which would also pass the public host on another port or over http; it already matches `Host` and page origins exactly for the same reason. The 403 keeps the shape of the SDK's guard, a JSON-RPC error with code -32000, message `Invalid Origin` and no id, as `validateHost` does for `Invalid Host`. A request with no `Origin` passes, as the SDK's guard lets it: the header is a browser's, and Claude Code 2.1.289 sends none; whether hosted Claude sends one is an owner check after the deploy.

`TABDOCK_MCP_ALLOWED_ORIGINS` is a comma-separated list parsed like `TABDOCK_ALLOWED_ORIGINS`; an entry that is not an http or https origin stops the relay at start, naming the variable and the entry. It is allowed in every mode, empty adds nothing, and the `relay listening` line names the effective `/mcp` origin policy beside the page one. The two lists stay apart: `TABDOCK_ALLOWED_ORIGINS` names page origins for `/page` and admits nothing to `/mcp`, and the reverse holds. The relay sends no CORS headers, so with or without the list no page on another origin can read an `/mcp` answer or send a bearer token past a preflight; the list is for a client that sends an `Origin` anyway, hosted Claude included should it turn out to. A refusal writes `mcp request refused: origin not allowed` through the `/mcp` repeated-lines budget, once a window and counted after (A4.3), naming the origin cut to 200 characters, as `/page` does, and the client address.

**What "verified" means.** A5.2 (ADR 0031) holds when four checks pass. First, a client matrix in CI against the sim page on both legs: `@modelcontextprotocol/sdk` 1.10.2, 1.12.3, 1.24.0 and 1.32.0, installed as exact npm aliases in `tests/e2e`, and `client` 2.3.0 in `legacy`, `auto` and pinned mode. Each pairs with the sim page, lists and calls a page tool through `call_page_tool` and, with ADR 0025's flag on, by its first-class name, and receives `list_changed` on its own channel (a GET stream on a session, `subscriptions/listen` without one); the test asserts the revision, the leg (a session id or none) and the client name the roster shows. Second, raw probes in CI pin every answer above: `initialize` echoing each claimed 2025-era revision and answering 2025-11-25 to 2026-07-28 and to an unknown date, the session header rules, `server/discover`, `-32022` listing every revision served, 2024-11-05 included, `-32020`, and the Origin rule on both legs. Third, the suite's 2025-11-25 and 2026-07-28 requirement sets in CI, pinned exactly at 0.2.0-alpha.12 in `tests/e2e`, with checked-in baselines that list the fixture scenarios and the SHOULD-level warnings by check id; a stale entry, one whose scenario now passes, fails the run, so a baseline cannot outlive what it excuses. A baseline may excuse only a scenario that calls the referee's fixture tools, prompts or resources, named in a reviewed list kept beside the baselines, and a SHOULD-level warning: `dns-rebinding-protection`, `http-header-validation` and every MUST-level check of every other scenario must pass with no entry, and a test reads both baseline files and fails on any entry outside those two kinds, so a later change cannot excuse the scenarios that test S12. A script starts the relay with `TABDOCK_HOME` in a temporary directory, a `TABDOCK_DEV_TOKENS` token drawn for that run, and `TABDOCK_MAX_SESSIONS_PER_USER` at 200 and `TABDOCK_MAX_REQUESTS_PER_USER` at 10,000, both for that run alone, since the referee leaves sessions open and, with every 2026-07-28 request spending (ADR 0030), sends more than 240 requests a minute, and puts in front of it a loopback proxy that adds the bearer header, passes `Host` and `Origin` through untouched so the suite's rebinding scenario tests the relay itself, and logs nothing. Fourth, outside CI because it needs a signed-in CLI and spends model calls, `check:claude-code:m5` drives Claude Code in the sandbox through a page tool, by `call_page_tool` and, with ADR 0025's flag on, by its first-class name, once by default (2026-07-28) and once with `MCP_PROTOCOL_NEGOTIATION=legacy` (2025-11-25 on a session), recording requests as they arrive rather than as they are answered, and asserts that its listen stream or GET stream opens within the relay's bounds; its results go in `docs/notes/verified.md`. Hosted Claude's revision is an owner step in `docs/checklists/M5.md`, read from the line below on the reference deployment.

The suite, its own v1 SDK, whose `^1.29.0` range the lockfile pins to one version, the v1 SDK aliases and what they bring are dev dependencies of `tests/e2e`, never bundled or published (ADR 0028 ships three packages of the relay's own); the suite is outside CLAUDE.md's pre-approved list and is accepted under the standing instruction, and the M5 pull request says so.

**Which revision a client speaks.** The relay writes one info line, `mcp client`, per user, client name and leg an hour, naming the user id, the client's name and version as `parseClientInfo` caps them (`mcp.ts`), the leg, the revision, and whether the client declared form elicitation (ADR 0026); never a token, a session id or an argument. A 2025-era session's line comes when `initialize` completes, with the negotiated version; a 2026-07-28 client's with its first request in the hour, with the envelope's version. The line goes through a repeated-lines budget of its own (`repeated-lines.ts`): one line per key an hour, at most 256 keys an hour, and no summary line, so a client that renames itself on every request fills only that budget and never hides a refusal line. The hour, rather than the minute the other budgets use, keeps a busy client to one line an hour. This is how the owner reads hosted Claude's revision and capabilities off the reference deployment.

**SDK pins.** The SDK stays on exact pins: `server` 2.3.0 and `node` 2.1.1 in the relay, `client` 2.3.0 as a dev dependency, and `core` 2.3.0 through `server`'s own exact pin, since a floating range would let an unreviewed transport change in. On release day the pins are rechecked against npm and the SDK's changelogs, as a step of `docs/release.md` (ADR 0028), and a newer version comes in only through the matrix, the probes and the suite above.

**SPEC wording.** In section 7, the first paragraph, "Endpoint `/mcp`, Streamable HTTP, using the official MCP SDK. Do not hand-roll the transport. Prefer the v2 packages if they cover revision 2026-07-28 and still serve session-based clients; otherwise use the v1 SDK and record why in an ADR.", becomes:

"Endpoint `/mcp`, Streamable HTTP, using the official MCP SDK's v2 packages at exact versions, rechecked before each release (ADRs 0005 and 0027). Do not hand-roll the transport. The relay serves MCP revisions 2025-03-26, 2025-06-18 and 2025-11-25 on a session (ADR 0009) and 2026-07-28 without one, and 2024-11-05 over Streamable HTTP as best effort; it does not serve the deprecated HTTP+SSE transport, and its answer to an unsupported version lists every revision it serves. In every mode `/mcp` answers 403, after the Host check and before authentication, to a request whose `Origin` header is present and not exactly an allowed origin: without a public URL, http and https on `localhost`, `127.0.0.1` and `[::1]` at any port; with one, the public origin; and in either case the origins listed in `TABDOCK_MCP_ALLOWED_ORIGINS`. A request with no `Origin` passes: the header is a browser's, and Claude Code sends none. `TABDOCK_ALLOWED_ORIGINS` lists page origins for `/page` and admits nothing to `/mcp` (ADR 0027)."

S12 gains a second sentence, after "(ADRs 0014 and 0018).": "In every mode `/mcp`, `/pair` and the auth plugin's routes refuse a `Host` that is not, exactly as written, a loopback name or, in public URL mode, the public host (ADRs 0014 and 0018), and `/mcp` answers 403, before authentication, to a request whose `Origin`, when present, is not on the allowlist section 7 gives (ADR 0027)."

Section 9 never stated the Host check, though ADRs 0014 and 0018 built it and `mcp.test.ts` and `hosted.test.ts` test it, so S12 now states both guards against DNS rebinding and cross-site requests. ADR 0031 carries the section 3 rows and A5.2.

## Consequences

The relay meets both revisions' Origin rule and the unsupported-version MUST, and "verified" becomes something CI repeats on every push rather than a claim: four SDK generations and three client modes on both legs, the version answers, and two official requirement sets, with Claude Code checked by hand in the sandbox on both revisions. A web page the user visits can still address a loopback relay as `127.0.0.1`, which passes the Host check; it holds no token and gets no CORS, so before this record it could make the relay run the auth plugin and write its refusal lines, and now it is refused before the plugin. ADR 0016's `/g/mcp`, when built, takes the same Host and Origin checks.

No section 9 requirement is weakened. S12 gains the Host rule ADRs 0014 and 0018 built and the Origin rule. S9's per-user session cap and request budget are raised only for the relay the conformance script starts, through the same settings any operator has; the defaults and their tests are unchanged. S11 holds: the run's token is drawn fresh and sent only by a loopback proxy that logs nothing, and the `mcp client` line carries no token or session id. S7 is untouched, since the line goes to the log, not the audit.

The risk this adds is hosted Claude: if it sends an `Origin`, the reference deployment refuses it after the M5 deploy until the operator lists that origin in `TABDOCK_MCP_ALLOWED_ORIGINS`. The refusal line names the origin, and the first owner step in `docs/checklists/M5.md` after deploying is to connect from Claude on the web and read both lines. Since headless Claude Code holds a notification stream on both revisions, each Claude Code process counts one listen stream or session against its user's caps (ADR 0018's notes), and ADR 0025's notifications reach it. A pinned client asking for an unknown future revision now learns it may fall back to a 2025 one.

The suite is an alpha, so a new alpha may rename scenarios or checks; the exact pin makes each move a deliberate change with its baseline reviewed. CI gains the matrix, the probes and two suite runs of a few seconds each, and `tests/e2e` gains the suite, its express, octokit and own v1 SDK, and four v1 SDK aliases.

The tests: `mcp-origin.test.ts` in the relay covers each mode's allowed origins, the variable and its refusals at start, a foreign, `null`, empty, repeated, upper-case and wrong-port `Origin` answered 403 before the plugin on every method and both legs with a valid token and without one, no budget spent, a missing `Origin` passing, and the refusal line once a window; `revisions.test.ts` in `tests/e2e` runs the matrix and the probes; the suite runs as its own CI step, and `conformance-baselines.test.ts` beside it fails on any baseline entry that is neither a listed fixture scenario nor a SHOULD-level warning; `mcp-client-line.test.ts` covers the line's fields, its hour, its key cap and its silence about tokens; and `check:claude-code:m5` with the hosted rows of `docs/checklists/M5.md` are the manual part of A5.2. `.env.example` documents `TABDOCK_MCP_ALLOWED_ORIGINS`.

## Notes from M5 Step 1 (5 October 2026)

A bad `TABDOCK_MCP_ALLOWED_ORIGINS` entry stops the relay naming the variable and the entry's position (`entry 2`), never its text, so a token pasted into the wrong variable never reaches a log (S11); `TABDOCK_ALLOWED_ORIGINS` still quotes its entry, as it did in M4. `m5-config.test.ts` checks the message leaves the entry out, and workstream F's `mcp-origin.test.ts` asserts this wording rather than the Decision's "naming the variable and the entry".
