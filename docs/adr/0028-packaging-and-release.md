# 0028: Packaging and the 0.1.0 release

Status: Accepted under the owner's standing instruction of 4 October 2026 (recorded 5 October 2026). Changes SPEC sections 4 (a paragraph on the published packages), 7 (local mode's sentence in the auth paragraph), 8 (how a page loads the adapter) and 11 (its first paragraph). Amends ADR 0022, which gains a note from this record: the `tabdock-relay` command, `--new-token` in place of its rotation steps, a refusal of a token directory inside any git work tree, in a checkout and in the package alike, and a banner that hands Claude Code the token through a `headersHelper` on POSIX shells. Settles three rows of `docs/plans/backlog.md`: publishing the relay, slimming the adapter with `zod/mini`, and serving the adapter from the relay, which it declines. This is decision D5 in `docs/notes/m5/m5-decisions.md`, and the research behind it is in `docs/notes/m5/packaging.md`, with the fact checkers' corrections of 5 October. ADR 0031 adds the packaging facts to section 3 and the release test, A5.5, to section 10.

## Context

Nothing is published yet. Every workspace package is `private`, at version 0.0.0, and exports its TypeScript sources (`packages/*/package.json`), which ADR 0003 runs through Node's type stripping with no build between packages. That stops at an install: Node 22.22 refuses to strip types under `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), so a published package must ship JavaScript. ADR 0022 left `npx @tabdock/relay` for the 0.1.0 release, and the backlog carries three rows for it: publish the relay with a `bin`, the same token file, checks and banner and a flag that draws a new token; slim the script-tag build with `zod/mini`; and consider serving that build from the local relay.

The relay assumes a checkout in five places. The argument worker's URL names `argument-worker.ts` (`packages/relay/src/argument-checker.ts:51`). `CHECKOUT` in `local-token.ts:46` is `../../..` from the module, which in an install is a `node_modules` directory, so ADR 0022's refusal of a token directory inside the checkout would guard nothing. `main.ts:14-15` and `audit-cli.ts:310-311` load `../../../.env`. The banner's last line names `pnpm dev:public` and `docs/deploy.md` (`local-banner.ts:79`). `RELAY_VERSION` is a literal `0.0.0` (`mcp.ts:63`), which the server info and every `relay_start` record carry (`mcp.ts:366`, `relay.ts:392`). A prototype in a scratch copy bundled `main`, the worker and the audit reader with esbuild 0.28.2, dependencies external, into a 125,654-byte tarball; installed (11 packages, 22 MB), its bin started local mode, refused `/mcp` without the token and answered with it. tsup, the other candidate, now says it "is not actively maintained anymore". `npx` runs a package's sole bin, and npm recommends a published `npm-shrinkwrap.json` for command-line tools. `pnpm pack` 10.28 applies `publishConfig` overrides of `bin` and `exports`, rewrites `workspace:*` to the exact version and adds the root `LICENSE` but not `NOTICE`.

The banner's command (`claudeAddCommand`, `local-banner.ts:42-48`) reads the token file inside `$(cat ...)`, so the token sits in `claude`'s argument list while it runs and then in `~/.claude.json`, which `claude mcp get` prints in full. ADR 0022 kept it because a `headersHelper` "needs JSON configuration and the project trust dialog". Claude Code's docs now say the trust dialog applies only to a project's `.mcp.json` and to local scope, and that a helper prints one JSON object within 10 s, at each connection and reconnect and again after a 401 or 403. In a probe with Claude Code 2.1.289, the latest, `claude mcp add-json --scope user` with a helper at a path holding spaces connected, `~/.claude.json` (0600) held the helper's command and no token, and `claude mcp get` showed no header; the same entry at local scope printed "headersHelper not run" and failed.

The adapter's script-tag build, `dist/tabdock-adapter.js` from `packages/adapter/scripts/build.ts`, is 286,140 bytes minified (87,242 gzip), not M1's 213 KiB; zod is 192 KB of it, 29 KB being a compiler that jitless mode never runs. With the protocol on `zod/mini` the prototype built 126,658 bytes (43,536 gzip), and all 144 protocol tests, 1,057 relay and adapter tests (the one failure was the scratch copy's missing `docs/` link) and all 75 Playwright tests passed. The traps: arrays take `z.maxLength`; mini loads no locale; a classic object holding mini schemas throws from `~standard.jsonSchema`, which the MCP SDK reads; and the SDK imports classic `zod/v4`.

Serving that file from the local relay would spare a page a build step, but `http://127.0.0.1` is only exempt from mixed content: Chrome gates loopback subresources under Local Network Access from 142 and WebSockets from 147, and in Chrome 154 a page treated as public loaded neither the loopback script nor the page socket until the `loopback-network` permission was granted. With it, SRI worked only beside `crossorigin="anonymous"` and `Access-Control-Allow-Origin`. jsDelivr and unpkg already serve npm files with `Access-Control-Allow-Origin: *`, `Cross-Origin-Resource-Policy: cross-origin` and `nosniff`.

On npm, `@tabdock/relay`, `@tabdock/adapter`, `@tabdock/protocol` and unscoped `tabdock` were free on 5 October, and nobody held the `tabdock` scope; a free npm organization makes it. Trusted publishing needs npm 11.5.1 and Node 22.14 or later, a GitHub-hosted runner, `id-token: write`, the exact workflow file name and a matching `repository.url`, and gives automatic provenance from a public repository. Publishers configured after 3 September 2026 may only `npm stage publish` unless direct publishing is chosen, and a staged version goes live only when a maintainer approves it with 2FA after npm's malware scan. A trusted publisher can be added only to a package that exists; tokens are granular only, stage-only tokens exist, and staging a package that does not exist yet publishes a public placeholder `0.0.0-stage`. Node 22's bundled npm (10.9) is too old; Node 24.21.0 bundles npm 11.19.0, whose `npm stage publish` takes the same OIDC and provenance path as `npm publish` (read in its source, not yet seen live).

## Decision

**Three packages, one version.** `@tabdock/protocol`, `@tabdock/adapter` and `@tabdock/relay` are published at 0.1.0 and always move together: one version in all three `package.json` files, one root `CHANGELOG.md`, one tag `v0.1.0`. They live under the npm organization `tabdock`, which the owner creates before anything else; nothing is published under unscoped `tabdock`. Each sets `publishConfig.access` to `public`, `repository.url` to this repository exactly as trusted publishing compares it, and `license` to `Apache-2.0`, and carries `LICENSE` and `NOTICE`, which the pack step copies in since `pnpm pack` adds only the first. Dependencies keep the workspace's exact pins, the SDK's among them (ADR 0027), and `workspace:*` becomes the exact shared version. The sim page, the demo, the tour site (ADR 0029) and the tests stay private. Inside the workspace nothing changes: packages still export `.ts` sources and ADR 0003's no-build rule holds, since `publishConfig` swaps in the built `exports`, `types` and `bin` only when a package is packed. No dependency is added: esbuild and `tsc` are already dev tools.

**Protocol and adapter.** Both ship `tsc` output with declarations, emitted with `rewriteRelativeImportExtensions` so specifiers end in `.js`, and neither declares `sideEffects: false`, since `zod-config.ts` works only by running when it loads. The whole protocol moves to `zod/mini`: every schema accepts and refuses exactly what it does today, which the protocol's tests hold, and `zod-config.ts` keeps `jitless` and sets zod's English locale when none is set yet, so a page that chose its own keeps it. The relay keeps classic zod for its own schemas, the fixed tools' inputs among them, so no mini schema sits inside a schema the SDK converts; the nine call sites that use classic methods on protocol schemas (in the relay's `auth.ts`, `mcp.ts` and `oauth.ts`, and `IdSchema.array()` in the adapter's `core.ts`) change to the mini forms. The adapter publishes `.` (`attach` and its types) and ships the script-tag build and its source map in `dist/`; `./core` and `./qr` stay workspace-only. A test builds the script-tag file with `scripts/build.ts`'s options and fails at 150,000 bytes or more.

**The relay as a command.** esbuild bundles the relay's own source into ESM files under `dist/`, every npm dependency external, `@tabdock/protocol` included, and the package ships an `npm-shrinkwrap.json` so an install gets the tree CI tested. It has one bin, `tabdock-relay`, so `npx @tabdock/relay` runs it, and no library entry point: 0.1.0 publishes a command, and none of the test helpers the workspace exports (`./test/provider`, `./test/secrecy`, `./test/tunnel`). `tabdock-relay` starts the relay as `pnpm relay` does; `tabdock-relay audit [options]` is `pnpm audit:log` with the same options, its usage naming the command it runs under; `--new-token` is below; `--version` prints the version and `--help` the usage; any other argument is refused with the usage, so a mistyped flag never starts a relay. `engines.node` is `>=22.18`, the floor ADR 0003 sets, and the pack-install job below runs on Node 22.18 as well as on `.nvmrc`'s Node, so the published floor is the one CI tests. The build sets a constant that marks the bundle as packaged, never guessed from its path, and four things follow from it: the worker's URL names the built worker file; the command reads no `.env` file, so settings come from the environment alone, as on a host, and running `npx` inside someone's project never picks up that project's file (a checkout's `pnpm relay`, `pnpm dev` and `pnpm audit:log` keep reading the root `.env`, as ADR 0022 says); the banner's last line sends those wanting Claude on the web or phone to the deploy guide by its URL in the repository, since the package has no `pnpm dev:public` and no `docs/`; and the relay skips the checkout comparison below, which would name a `node_modules` directory, leaving the repository rule. `RELAY_VERSION` stays a constant, now kept equal to the package's version by a test, as `ADAPTER_VERSION` is (`packages/adapter/test/script-options.test.ts`, its `ADAPTER_VERSION` test), so the server info and `relay_start` name the release that runs. The container image is unchanged: it still runs the relay's sources from its own copy of the checkout (ADRs 0018 and 0019).

**The token directory and repositories.** In a checkout and in the package alike, the relay refuses a token directory that lies inside any git work tree: one any of whose ancestors, itself included and up to the filesystem root, holds a `.git` entry, a directory or a file (so linked worktrees and submodules count), found from the directory's realpath and folded for case as today. A relay run from a checkout also keeps ADR 0022's comparison with the checkout it runs from, which still guards a checkout that has no `.git`, such as an unpacked source archive. The rule keys on where the token would lie, not on where the code or the person is, so it covers every repository the token could be committed from: the work tree around the current directory, where `npx` usually starts and where a `TABDOCK_HOME` such as `$PWD/.tabdock` would put the token in reach of a commit; an outer repository around a submodule or nested work tree the person stands in; a project that installed `@tabdock/relay`, run from elsewhere with `TABDOCK_HOME` inside it; and a dotfiles repository whose work tree is the home directory or `~/.config`. Every check is therefore at least as strong as ADR 0022's, and every other check of that record applies unchanged. The refusal names the work tree and the fix, as the checkout's does.

**The banner and its header helper.** In local mode on every system but Windows, each start ensures `claude-headers` beside `owner-token`: a `#!/bin/sh` script of fixed text that reads the token file by its absolute path and prints `{"Authorization":"Bearer <token>"}`, failing when the file is missing, and that holds no token. It is written as the token is, a synced temporary file linked into place, with mode 0700, and checked at every start as the token is: a regular file opened without following a link, owned by the relay's account, granting nothing to group or others, and holding exactly the text this release writes. Anything else is refused, never repaired, naming the path and the fix ("delete it and start again"), except that a file holding an earlier release's exact text is replaced in one rename, so an upgrade that changes the text locks nobody out. The banner then prints, for POSIX shells:

`claude mcp add-json --scope user tabdock-local '{"type":"http","url":"http://127.0.0.1:8787/mcp","headersHelper":"/home/u/.config/tabdock/claude-headers"}'`

The JSON comes from `JSON.stringify` and reaches the shell through `quotePosix`. `headersHelper` is a command Claude Code runs through a shell, so a helper path holding anything outside `[A-Za-z0-9/._-]` goes inside double quotes, written `\"` in the JSON, as on macOS, whose path holds `Application Support`; a path holding `"`, `\`, `$`, a backtick or a control character, which double quotes cannot carry safely, makes the banner print ADR 0022's `--header` line instead. PowerShell on Windows keeps ADR 0022's `--header` line, and Windows gets no helper, until a Windows run shows which shell runs helpers there; `docs/checklists/M5.md` holds that run. Everything else ADR 0022 says of the banner stands: user scope, the name `tabdock-local`, the path and never the token, `claude mcp list` to check, and the step to remove an older entry, which now also removes an M4 entry's copy of the token from `~/.claude.json`.

**A new token.** `tabdock-relay --new-token` (and `pnpm relay --new-token` in a checkout) replaces the owner token and then starts as usual, the banner saying the token was created just now. It works only in local mode and is refused by name otherwise. The directory must pass ADR 0022's checks; the old file is never read, so a file refused for its mode or contents can be replaced this way, which is what that refusal's "delete it and start again" asks for; the new token goes into a fresh synced 0600 temporary file that is renamed over `owner-token` in one step, since a link cannot replace a name, so a reader sees the old token or the new, never part of one. It replaces the file only after the start holds its audit directory's lock, so a second start beside a running relay that shares the directory refuses before it changes anything (ADR 0022's notes). With the helper, Claude Code reads the new token at its next connection, or after the 401 the old one gets, so its entry stays as it is; with PowerShell's line the entry must be replaced, and the banner says so. This replaces ADR 0022's rotation steps.

**The relay never serves the adapter.** The adapter is the second layer of S5 and the place S6's prompts run; code served by the relay would let a compromised or squatting relay remove both, and pinned SRI would narrow that only for pages that check it. A route would also need CORS, a fixed content type and tests of its own, and still meet Chrome's local network prompt. So a bundled app imports `@tabdock/adapter` from npm, and any other page loads `dist/tabdock-adapter.js` from its own origin, or from a CDN copy of the npm file pinned to an exact version with its `integrity` and `crossorigin="anonymous"`. Each release publishes that file's SHA-384 digest and a ready tag for jsDelivr. The backlog row closes as declined.

**Publishing.** A new workflow, `.github/workflows/publish.yml`, runs when a GitHub release is published, with actions pinned by commit as elsewhere (threat model, B8). A pack job (`contents: read`, Node from `.nvmrc`) builds and packs the three packages and checks each tarball: its version equals the tag, its files match an allowlist, and it holds no tests, `.env` or token. A stage job in the GitHub environment `npm` (a required reviewer, `v*` tags only, self-review prevention off so a sole maintainer can approve, `id-token: write`) runs Node 24.21.0 with npm 11.19.0 and stages protocol, adapter and relay in that order with `npm stage publish` and provenance. A last job (`contents: write`) attaches the tarballs, `SHA256SUMS` and the script-tag file's `integrity` line to the release. Nothing goes live until the owner approves each staged version with 2FA on npm, so a release takes two approvals by the owner, one on GitHub and one on npm, and a stolen CI credential can at most stage. For the first versions, while no package exists to hold a trusted publisher, the environment's secret is a stage-only granular token for `@tabdock`, without 2FA bypass, that expires after one day; once 0.1.0 is live the owner adds a trusted publisher to each package (this repository, `publish.yml`, environment `npm`, stage only), deletes the token and sets each package to require 2FA and disallow tokens. After the release pull request merges, Claude drafts the GitHub release and the owner publishes it, from a phone if need be, which starts the workflow. `docs/release.md` gives these steps, and `docs/checklists/M5.md` holds the owner's: the npm account with 2FA and the organization, the environment and its secret, both approvals, the trusted publishers, and checking on npm that each version carries provenance.

**SPEC wording.** Section 4 gains a paragraph after the one ending "it only routes.": "Three packages are published to npm under the `@tabdock` scope, always at one shared version, from 0.1.0 (ADR 0028): `@tabdock/protocol` and `@tabdock/adapter` as compiled JavaScript with type declarations, the adapter also carrying its script-tag build, and `@tabdock/relay` as one bundled command, `tabdock-relay`, with its dependency tree pinned by a published `npm-shrinkwrap.json`. Nothing is published under the unscoped name `tabdock`; the sim page, the demo and the tests stay private. Inside the workspace the packages still export their TypeScript sources (ADR 0003), and only packing builds them."

Section 7, in the auth paragraph, "whose 256-bit token the relay draws on first run into a private per-user file outside the repo and never prints or logs;" becomes "whose 256-bit token the relay draws on first run into a private per-user file outside the checkout and outside any git work tree and never prints or logs; on POSIX systems Claude Code reads it at each connection through a helper script the relay keeps beside it, which holds no token, so Claude Code's configuration holds none either (ADR 0028);".

Section 8 gains a first paragraph, before the `attach()` example: "A page gets the adapter in one of two ways. An app with a build step installs `@tabdock/adapter` from npm and calls `attach()` as below. Any other page loads the package's script-tag build, `dist/tabdock-adapter.js`, one self-contained file kept under 150,000 bytes, from the page's own origin or from a CDN copy of that npm file pinned to an exact version, with the `integrity` digest each release publishes and `crossorigin="anonymous"`. The relay never serves the adapter: the adapter's own checks (S5's second layer, S6's prompts) must not come from the relay they check (ADR 0028)."

Section 11, its first paragraph, gains after "and trusts every account on it (ADR 0022).": "Without a clone, `npx @tabdock/relay` runs the same relay from npm with Node 22.18 or later and no pnpm; it reads settings only from the environment, never from a `.env` file, and `npx @tabdock/relay audit` reads its audit log as `pnpm audit:log` does (ADR 0028)."

**Section 9** is unchanged, and no rule weakens. S5 and S6 keep their code on the page's side, since the relay never serves it. S11 tightens in practice on POSIX systems: the token leaves `claude`'s argument list and Claude Code's configuration, and neither the helper, the banner nor `--new-token` prints, logs or holds it. S12's loopback bind, S1 and S2's development default and S7's audit log are local mode's as before. The protocol's schemas validate exactly what they did, so every boundary is still checked with zod schemas from `packages/protocol`. The repository rule keeps ADR 0022's refusal of a token directory inside the checkout and adds a refusal of one inside any git work tree, so in a checkout and in the package alike it is at least as strong as before.

## Consequences

Someone with Node and no clone runs `npx @tabdock/relay`, pastes one command and has Claude Code connected, with the token never in an argument list, a shell history or Claude Code's configuration on macOS and Linux. The threat model's B9 row changes to match, and its residuals stay: an account that binds the port while the relay is down still receives the token, since Claude Code sends whatever the helper prints to whoever answers; Windows keeps M4's exposures until its run; and a person who added M4's line keeps a copy in `~/.claude.json` until they remove that entry, which `--new-token` makes useless. The helper is code Claude Code runs at each connection, so whoever can write the token directory can run code as the user, but that account is already the user, and the 0700 directory and the exact-content check are what ADR 0022 already relies on; a change made while a relay runs is caught at the next start, not before. Claude Code's own logs are outside Tabdock's reach, as ADR 0022 said of "never logged".

The repository rule refuses the default token directory whenever the home directory or `~/.config` is itself a git work tree, as some dotfile setups make it, wherever the relay is run from, from npm or from a checkout; a `TABDOCK_HOME` outside it is the fix the message names, and a bare repository whose work tree is the home (its `GIT_DIR` elsewhere) is not seen, by this rule or the checkout's. A command that reads no `.env` means a person who keeps settings in a file loads it into the environment themselves.

The script tag costs about 44 KB gzipped instead of 87 KB, under a ceiling a test holds. Code that imports `@tabdock/protocol` gets `zod/mini` schemas, without classic methods; at 0.x that is acceptable, and inside the workspace the prototype found only the nine call sites above. Importing the adapter from npm still turns zod's jitless mode on for the whole page, as the script tag always has (`zod-config.ts`), but never changes a locale the page chose.

Publishing makes the name stick in practice: SPEC section 12 still lists "The final name", and after 0.1.0 a rename means deprecating three packages and pointing to new ones, which ADR 0031 should say where it refreshes section 12. Staging the first versions leaves a public `0.0.0-stage` placeholder for each package, which npm creates and this route cannot avoid. Provenance for those versions rests on reading npm's source, so the checklist confirms it on each package's page; if it is missing, 0.1.0 stands and the next release, from the trusted publisher, carries it. The shrinkwrap means a fixed transitive dependency reaches `npx` users only in a new relay release, so a security fix in the tree is a release, which Dependabot's pull requests prompt. A CDN copy of the script tag trusts jsDelivr only as far as SRI lets it, since a wrong digest is refused; a page that self-hosts trusts nobody else. A page on a public origin that dials a local relay meets Chrome's local network prompt for the page socket, whatever serves the script (ADRs 0029 and 0031).

The tests: `local-token.test.ts` gains the repository rule, in both modes (a token directory inside the work tree around the current directory, a `.git` file, a current directory inside a submodule with `TABDOCK_HOME` in the outer repository, a current directory outside any work tree with `TABDOCK_HOME` inside one, a package installed inside a repository and run from elsewhere, `~/.config` as a work tree, and no work tree at all) and `--new-token` (the rename, a refused directory, a bad old file replaced, a held lock, outside local mode); `local-banner.test.ts` gains the `add-json` line for Linux and macOS paths, the fallback for unsafe paths and PowerShell's unchanged line; a new helper test covers its text, mode, owner, a symlink, a changed copy and an earlier release's copy; and the relay's version test, the bin's arguments, the adapter's size test and the protocol's tests on `zod/mini` join them. Since the packaged constant exists only in the bundle, where unit tests on the sources never set it, CI also checks the packed tarball itself, which is part of A5.5 (ADR 0031): on Node 22.18 and on `.nvmrc`'s Node it packs the three tarballs and installs them in a scratch directory; there the installed `tabdock-relay`, started with no settings from inside a git work tree, keeps its token in a 0600 file outside that work tree, refuses a `TABDOCK_HOME` inside it, reads no `.env` placed there, writes a `claude-headers` helper that holds no token, and lets an MCP client connect with the header the helper prints. Claude Code connecting through the helper runs in the sandbox as `check:claude-code:local` (`tests/e2e`) does now, and the checklist keeps a macOS and a Windows run. `publish.yml` and `docs/release.md` cannot run before the owner's npm setup, so the first release is their test, staged and approved by hand.

## Notes from M5 Step 2 (5 October 2026)

Workstream C built the decision with these departures. Each package commits its own copy of `NOTICE` rather than having the pack step copy it in, so `pnpm pack` picks it up like any listed file; `release-check.ts` refuses a `LICENSE` or `NOTICE` that differs from the root's, so the copies cannot drift. `tabdock-relay` takes `-v` and `-h` beside `--version` and `--help`, and still refuses anything else with the usage, naming a flag by its name and anything else only by its place. npm follows a dependency's `npm-shrinkwrap.json` only for a package from the registry, whose version document carries `_hasShrinkwrap` (`docs/notes/verified.md`), never for a local tarball, so `pack-install.ts` installs the three tarballs with the shrinkwrap's versions as `overrides` and checks every one; "an install gets the tree CI tested" therefore rests on npm honouring the published file, which `docs/checklists/M5.md` and `docs/release.md` check after the first release. The pack-install job also typechecks a NodeNext consumer against the protocol and the adapter as installed, and `release-check.ts` refuses a header helper in a tarball beside a token and a `.env`. The banner's helper is a script of shell builtins only, so no `PATH` changes what it runs, and it accepts only a token of the shape the relay draws.

## Notes from the M5 Step 2 packaging review (5 October 2026)

Recorded under the owner's standing instruction of 4 October. These notes replace the sentences above that they contradict, and the sentence of ADR 0022's notes that says `--new-token` holds the audit directory's lock. SPEC is unchanged: every rule below refuses more than section 7's sentence names, which still holds, A5.5's wording covers the new install check, and no section 9 rule weakens; S11 holds where it did not.

**The shrinkwrap holds the protocol.** npm installs a registry package that carries `npm-shrinkwrap.json` from that file alone: Arborist skips such a node when it builds the tree and reads the file in its place, so a dependency the file leaves out is never installed. The shrinkwrap left out `@tabdock/protocol`, as the Decision's "every npm dependency external, `@tabdock/protocol` included" built it, and a reviewer's `npx @tabdock/relay` through a registry stand-in failed with `ERR_MODULE_NOT_FOUND` on npm 10.9.4 and 11.21.0, while CI passed, since an install from local tarballs never sets the registry's `_hasShrinkwrap`. Now `release-pack.ts` packs the protocol first and `shrinkwrap.ts` has npm resolve it from that tarball, then names its registry URL and npm's sha512 of it, so an install fetches exactly the bytes the stage job publishes (it stages the packed files, checked against `SHA256SUMS`) or fails. `release-check.ts` refuses a shrinkwrap that leaves out any dependency of any package in its tree, the relay's own included, or that pins a sibling other than the tarball packed beside it. `pack-install.ts` runs `npx --yes @tabdock/relay@<version>` with a fresh cache through `scripts/local-registry.ts`, which serves the tarballs with `_hasShrinkwrap` read from each and sends every other request to the npm registry, on both Node legs, and installs the libraries the same way; `shrinkwrap-install.test.ts` shows npm's behaviour with two small packages. Bundling the protocol into the command was the other route, not taken, since the image and the workspace run the relay's sources with the protocol as a package.

**The token directory has a lock of its own.** `--new-token` was guarded only by the audit directory's lock and committed before the relay listened, so beside a running relay with another `TABDOCK_AUDIT_DIR` it replaced the token and then failed on the port, or ran on another port, while the first relay kept the old, perhaps leaked, token valid. Every local-mode relay now holds `owner-token.lock` beside the token from its plugin's start, before it listens, to its stop (`token-lock.ts`), whatever its audit directory or port, so a second relay sharing the directory and `--new-token` beside one both refuse, naming the lock; and the new token is renamed into place only once the relay listens, so a start that fails on its way up leaves the old one as it was. A lock is judged by its pid on this boot and in this pid namespace: one whose pid is gone, or from an earlier boot, is broken; one from another pid namespace, or that cannot be read, is refused with the file named for the person to delete if no relay runs. The residual: a relay on another machine sharing the directory over a network file system leaves a lock that looks like one from an earlier boot, and is not seen, which local mode, serving one machine, accepts.

**No token directory below a directory another account could change.** The Consequences say that whoever can write the token directory is already the user. That held only while nobody else could make the directory again: under `/tmp`, once it was cleared, any account could create `<TABDOCK_HOME>/claude-headers`, and Claude Code, which keeps the helper's path in `~/.claude.json` and runs it at every connection with no check of its own, would run it as the user. On POSIX systems a start now refuses a token directory below any directory that its group or others may write, sticky or not, or that an account other than this one or root owns, as OpenSSH's StrictModes refuses a key's path; the message names that directory and the fix (`chmod go-w` where it is the user's own and not sticky, else a `TABDOCK_HOME` under the home directory). Tests keep their scratch space in a private root (`test/helpers/private-tmp.ts`), which `vitest.setup.ts` points `TMPDIR` at, and `pack-install.ts` checks that a `TABDOCK_HOME` under the shared temporary directory is refused. The residual, for the threat model's B9: a directory made shared after the relay's last start is caught only at its next start, and a Claude Code entry left naming the helper of a token directory since removed runs whatever is there.

**Every repository counts.** The repository rule also looks for `.jj`, `.hg`, `.sl`, `.svn` and `.bzr`, a directory or a file, beside `.git`, and names the tool: Jujutsu snapshots new files into its working-copy commit without an `add`, so a token there reaches `jj git push`, and the rule's purpose, that the token cannot be committed, is the same for Mercurial, Sapling, Subversion and Bazaar. A colocated Jujutsu repository is named as git's.

**The audit subcommand repeats no argument.** `tabdock-relay audit` and `pnpm audit:log` passed node's parser messages on, which quote a stray argument, so a token pasted after `audit` was echoed. The reader now walks its arguments first and names a flag by its name and anything else only by its place, as the command does (`argument-names.ts`), and never prints node's message.

**The npm pages name only what is published.** The relay's and adapter's READMEs named `createRelay` and the `./test/*`, `./core` and `./qr` subpaths as imports, which the packed manifests do not export; they now mark those as the workspace's alone, and `release-check.ts` refuses a packed README that names a `@tabdock/<package>/<subpath>`, or imports a package root, that the packed manifest does not export.
