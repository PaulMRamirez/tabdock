# 0037: Move the MCP SDK pins to 2.3.1, and keep them together

Status: Accepted, 8 October 2026, under the owner's standing instruction to take the recommended option. Changes the SPEC's dated line, section 3 (its heading, the MCP SDK row and the sentence under the table) and section 10 (the `client` version in A5.2). Amends the "SDK pins" paragraph of ADR 0027, which gains a note pointing here; its rule stands: exact pins, and a newer version comes in only through the client matrix, the probes and the conformance suite. No relay behaviour changes, and section 9 is untouched.

## Context

ADR 0027 keeps the SDK on exact pins: `server` 2.3.0 and `node` 2.1.1 in the relay, `client` 2.3.0 as a dev dependency of the relay and of `tests/e2e`, and `core` 2.3.0 through `server`'s own exact pin. ADR 0031 wrote them into section 3 as `latest` on 5 October. npm dates `server`, `client` and `core` 2.3.1 to 11:50 to 11:52 UTC that same day, and the v1 line's `sdk` 1.32.1 to 11:47 UTC. `node` is still 2.1.1 and `latest`, and its peer range, `^2.3.0`, accepts server 2.3.1. `server` 2.3.1 and `client` 2.3.1 each pin `core` 2.3.1 exactly.

2.3.1 changes no code. Against 2.3.0, every `dist` file of `server`, `client` and `core` is byte for byte the same; only `package.json` and the `server` and `client` READMEs differ: `core` changes its version alone, and `server` and `client` their version, their exact `core` pin and the range of a development-only dependency, `core-internal`. The release's one source change, `expectedResource` for `server-legacy`'s `requireBearerAuth` (the SDK's pull request #2952; its changelog names no advisory), is in a package the relay does not use; `server` has had that check since 2.3.0, and the relay passes `expectedResource` to it. No advisory names `server`, `client`, `core` or `node` at 2.3.0 (`docs/notes/verified.md`, 8 October).

Dependabot's run of 8 October split the move in two. Pull request #13 bumps `server`, a production dependency, in the `runtime` group; pull request #14 bumps `client`, a development dependency, in the `tooling` group beside eslint. Either alone leaves `core` 2.3.0 and 2.3.1 side by side in `pnpm-lock.yaml`, so CI would test the relay through a client built on a `core` the relay does not ship with. #14 also failed `doc-installs.test.ts`, since the guide's install line named `client@2.3.0`. Section 3's SDK row and A5.2 name 2.3.0, as do `docs/release.md`, the guide, `tests/e2e/README.md`, the unpublished 0.1.0 entry in `CHANGELOG.md`, two relay comments and the tests' labels, and CLAUDE.md changes the SPEC only through a record.

## Decision

**The pins move together.** The SDK releases `server`, `client` and `core` at one version, and this tree keeps them at one version; `node` has its own numbers; it is in the same group, so a `node` release found in the same Dependabot run moves in the same pull request. One pull request takes `server`, `client` and `core` to 2.3.1 and keeps `node` at 2.1.1, changing both manifests, the lockfile and every statement of the current pin. It passes CI, whose client matrix, probes and conformance runs are ADR 0027's gate, and the check of 8 October is recorded in `docs/notes/verified.md`. Pull request #13 gives way to it, and #14, which also carries an eslint bump, is regenerated by Dependabot without the SDK.

`.github/dependabot.yml` gains a group, `mcp-sdk`, naming the four packages. It is written before `runtime` and `tooling`, since Dependabot puts a dependency in the first group it matches, and `tests/e2e/test/site-files.test.ts` holds that order and those names. The names are exact rather than `@modelcontextprotocol/*`, which would also pull the conformance alpha, a test tool whose new versions can move the baselines, into the SDK's pull request; it stays in `tooling`. A security update still comes as one pull request per advisory; a person completes it with the other pins before it merges, as `docs/release.md` and `docs/develop.md` now say.

**What says 2.3.1, and what keeps 2.3.0.** Every statement of the current pin changes: section 3 and A5.2, `docs/release.md`, the guide's client program (whose install line `doc-installs.test.ts` holds to the workspace pin), `tests/e2e/README.md`, the 0.1.0 entry in `CHANGELOG.md`, the comments in `mcp.ts` and `first-class.ts`, and the tests' labels and comments, including the line `pnpm demo:m5` prints. Dated records keep 2.3.0: ADRs 0004, 0025, 0026, 0027 and 0031, `docs/notes/`, the dated rows of `verified.md`, `docs/plans/M5.md` and the M5 checklist. The client matrix keeps `sdk` 1.32.0 as its v1 row; Dependabot ignores the matrix's aliases on purpose.

**SPEC wording.** The dated line becomes "Draft 1, 2 October 2026; last amended 8 October 2026 by ADR 0037." Section 3's heading becomes "## 3. Facts verified on 2, 3, 5 and 8 October 2026 (re-verify before relying on them)". Its MCP SDK row begins "MCP SDK packages, `latest` on 8 October and pinned exactly, all moving in one pull request (ADRs 0027 and 0037): `@modelcontextprotocol/server`, `client` and `core` 2.3.1 (published 5 October) with `@modelcontextprotocol/node` 2.1.1 (v2 line, serves 2026-07-28 and 2025-era clients), and `@modelcontextprotocol/sdk` 1.32.1 (v1 line, 2025-era only; the client matrix keeps 1.32.0; 1.9 and older have only an HTTP+SSE client). 2.3.1 changes no code: every `dist` file of the three is byte for byte that of 2.3.0, and only the versions, the exact `core` pin, a development-only `core-internal` range and the `server` and `client` READMEs differ. Server 2.3.1 offers", continues as before, and names "the 2.3.0 and 2.3.1 tarballs and changelogs" among its sources. The sentence under the table begins "Rows refreshed by ADRs 0004, 0015, 0021, 0031 and 0037". In section 10, A5.2's "`client` 2.3.0 in legacy, auto and pinned modes" becomes "`client` 2.3.1 in legacy, auto and pinned modes".

## Consequences

The relay and its tests resolve one `core`, so the matrix, the probes and the suite test the pairing a release ships, and a later SDK release arrives as one pull request rather than two that each fail or mislead alone. A bump still touches about twenty lines of prose, comments and labels; `doc-installs.test.ts` catches the guide's install line and the group test a split group, but nothing checks the rest, so the pull request that moves the pins greps for the old version. If 0.1.0 is published after this lands, it ships on 2.3.1 and its changelog entry says so.
