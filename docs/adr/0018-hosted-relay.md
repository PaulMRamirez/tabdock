# 0018: The relay on a host behind a TLS-terminating edge

Status: Accepted by the owner, 3 October 2026. Changes SPEC sections 2, 4 (its layout) and 9 (S9, S12) and ADR 0014's rule that pages attach only locally; completes the per-address budget ADR 0013's notes deferred and revisits ADR 0009's limits for a public relay.

## Context

From M4 the relay can run on a host rather than behind a tunnel. The owner chose Fly.io and a DNS-only `relay.<domain>` for the project's reference deployment (D1 and D2 in `docs/notes/m4/m4-decisions.md`): one `shared-cpu-1x` 512 MB Machine with a 1 GB volume. ADR 0022 asks that SPEC name what a host must do, never which host. On any host TLS ends at the platform's edge, and four M3 guards assume a laptop and a tunnel: the relay binds only loopback (`config.ts:403-406`); in public mode `/page` refuses upgrades that came through a proxy; per-address limits key on the TCP peer, which behind a proxy is the proxy; and `/pair` code exchanges share one relay-wide budget, so anyone who knows the URL can keep QR sign-in failing. ADR 0009's limits suit a laptop: the credential-free `/page` allows 1000 page sessions and 20 per address, each holding up to 1 MiB of tools, while an idle relay already uses 137 MB, and refused calls are never rate limited, since the access check runs before the call limit (`hub.ts:1942-1956`). A client-address header is only as good as the proxy that sets it; in a live probe Fly's proxy replaced a forged `Fly-Client-IP` with the real peer, which is the property every host must have.

## Decision

**Hosted mode.** The relay is in hosted mode when `TABDOCK_ENV` is `production`, `TABDOCK_PUBLIC_URL` is set (https, per ADR 0014) and `TABDOCK_CLIENT_ADDRESS_HEADER` names one header. Only then may `TABDOCK_HOST` be `0.0.0.0`, which a platform's proxy and health checks need; any other address, `::` included, stays refused, because an IPv6 wildcard can also listen on a platform's private network (on Fly, the one every Machine in the organisation shares) and would need its own ADR. The Host check for `/mcp`, the metadata route and `/pair` stays on in every mode, no longer tied to `config.loopback`, and the allowlist names only the public host and loopback names, so a platform's own name for the app (on Fly, `<app>.fly.dev`) gets 403 everywhere but `/healthz`, which keeps its M1 behaviour and serves a platform's health check.

**What a host must provide.** The relay and its image name no host: every hosted setting is an environment variable. A host qualifies when it terminates TLS for the public URL's host and passes plain HTTP and WebSocket upgrades to the container's port with the original `Host` unchanged; lets a request wait at least 60 s for its first byte and passes streamed responses through unbuffered, since `pair_page` waits 50 s and a call up to 47 s; has its proxy set the configured client-address header on every request, replacing any value a client sent, and connect from addresses `TABDOCK_TRUSTED_PROXY_CIDR` can name, from which nothing else can reach the container's port (so narrowing the range to the proxy's is a deploy step); runs exactly one instance, stopping the old before starting the new, with a persistent directory for `TABDOCK_AUDIT_DIR` (ADR 0019); does not close a connection that carries a ping every 15 s; and gives the public hostname a public IPv4 `A` record, as Claude requires. A host whose header cannot be trusted cannot run hosted mode; a tunnel in front of a loopback relay (ADR 0014) remains the alternative. SPEC section 11 carries this list (ADR 0021).

**Client address.** In hosted mode the client address comes from the configured header alone, and only when the TCP peer lies in `TABDOCK_TRUSTED_PROXY_CIDR`, by default the RFC 1918 ranges; the relay logs the first proxy address it sees and every untrusted peer, so a first deploy shows the range the proxy uses and the operator narrows the setting to it. The header must appear once and parse as an IP address, or the request gets 400 on every route that counts by address (`/page`, `/pair`, `/i`). Other forwarding headers are ignored. IPv4-mapped and IPv4-compatible forms count as their IPv4 address, IPv4 counts whole, and native IPv6 counts by its /56, the delegation a home connection commonly gets. Outside hosted mode M3's rules stay.

**Pages through the edge.** In hosted mode `/page` accepts upgrades whose `Host` is exactly the public host. S1 and S2 are unchanged: the origin comes only from the `Origin` header and must be listed.

**Limits for a public relay.** Hosted mode's defaults are 100 page sessions, and 5 page sockets and 5 page sessions per address, sized for the reference deployment's 512 MB; each is an environment variable, so a larger host raises them. A relay-wide budget for bytes held in tool lists and prepared schemas (`TABDOCK_MAX_TOOL_BYTES`) refuses a `tools` frame that would pass it with 1008, counted against its address, and Node starts with an explicit `--max-old-space-size`; integration sizes both so that a test holding the most pages at the largest tool list stays under a fixed heap ceiling beside the argument worker's 256 MB. Each user has a request budget on `/mcp`, covering every tool and checked right after authentication, before the access check: 240 a minute for a member and 60 for an invitee (`TABDOCK_MAX_REQUESTS_PER_USER`, `TABDOCK_MAX_REQUESTS_PER_INVITEE`), past which the answer is `rate_limited`. Each address gets 10 sign-ins a minute and 2 in flight across `/pair` and `/i`, sized for carrier NAT, under the relay-wide 60 and 8. `/mcp` counts nothing per address, since all hosted Claude traffic shares one range.

**The reference deployment.** `docs/deploy.md` shows one host meeting the list above, Fly.io, as a worked example with each Fly-specific step marked, so another host is a new section of the guide, not a code change. There `TABDOCK_CLIENT_ADDRESS_HEADER` is `fly-client-ip`; `deploy/fly/fly.toml` uses `[http_service]`, whose ports carry the HTTP handler that rewrites `Fly-Client-IP`, names no app or domain and holds only non-personal settings, and a CI check fails if that handler goes; one Machine with a volume (which makes Fly refuse the `bluegreen` and `canary` strategies), `auto_stop_machines = "off"`, and deploys that stop the old Machine before starting the new meet the one-instance rule.

**SPEC wording.** Section 2, Relay trust: "The relay sees plaintext calls and results, and so does a tunnel or host edge that terminates TLS in front of it (ADRs 0014 and 0018). Self-host first". S9: "Limits exist for users per page, requests and calls per user per minute, queue depth, frame size, result size and the memory page tool lists may hold, and, behind a host edge, page sessions and sign-ins per client address (ADR 0018)." S12: "The relay binds to loopback, unless it runs in production behind a host edge that terminates TLS and names the client address in one configured header; then it binds `0.0.0.0`, and every public URL in front of it is https (ADRs 0014 and 0018)." Section 4's layout gains the line "`deploy/` The reference deployment: one folder per documented host (`fly/` for Fly.io); the image's Dockerfile at the root names no host".

## Consequences

S12's wording changes, and the owner accepts that knowingly with this record: a plaintext listener faces the platform's proxy, never the internet directly, and the threat model puts that proxy, like the tunnel before it, inside the relay's trust boundary. Pages on any machine can attach through the public URL, bounded by the origin list and the caps; 20 addresses can still hold every page slot, which costs availability, not memory. With a hostname of one's own, a later host move changes only DNS. Every deploy is a restart (ADR 0019). Whether an address header can be trusted is a property of the platform, so SPEC states it as a host requirement and the deploy guide shows how each documented host meets it.

## Notes from the interface review (4 October 2026)

`client-address.ts` exports `createClientAddresses(config, log)`, built once per relay, whose `of(request)` gives `{ ok: true, address, key }`, the address for log lines and the key that limits count by (an IPv4 address, or an IPv6 /56), or `{ ok: false, problem }` with `missing`, `repeated` or `malformed`. relay.ts answers 400 itself on `/page` and on the `/pair` routes, and `/i`'s once they exist, when `ok` is false, and never on `/mcp`, which only names the address in its refusal line. Until workstream C reads the header, every mode counts by the TCP peer, and a hosted relay says so once at start.

A request in hosted mode whose TCP peer lies outside `TABDOCK_TRUSTED_PROXY_CIDR` counts as that peer: its header is ignored, so nothing it sends is believed, and the peer is logged. A range set too narrow then degrades to limits shared behind the proxy, with a log line naming the proxy's address, rather than refusing every page and sign-in; a client that reaches the port directly, which a qualifying host never allows, is counted as itself.

The sign-in budget lives in `sign-in-gate.ts`, which C owns: `pair.ts` asks it once per code exchange with the address key relay.ts hands to `PairFlow.handle`, and it holds today's relay-wide 60 a minute and 8 in flight, to which C adds the per-address share, checked first. `/i` signs in through `/pair/login` and `/pair/callback`, so the one gate covers both routes.

## Notes after the build (4 October 2026)

Workstream C built hosted mode, A the request budget, and integration joined `/i` to the client address rule.

**Binding and Host.** Hosted mode alone may bind `0.0.0.0` (loopback stays allowed there too); `::` and every other address are refused. The Host allowlist runs in every mode, and hosted `/page` takes upgrades for the public host alone. `Relay.url` reports `127.0.0.1` for a wildcard bind, the address the machine itself reaches it by.

**Client address.** Header lines are counted on `rawHeaders`, so a repeated header is seen however Node would merge it. IPv4-compatible forms exclude `::` and `::1`. A peer outside `TABDOCK_TRUSTED_PROXY_CIDR` is never answered 400, even with no header, since nothing it sends is read; untrusted peers are logged once each, up to 256, and the first proxy address once. `/i` sits behind the same rule as `/pair`: 400 when the edge names no client or names two, and a sign-in started at `/i` returns there and spends the same per-address share, which applies in hosted mode only and is checked before the relay-wide 60 and 8 (`hosted.test.ts`).

**Request budget.** It counts calls to the five fixed tools, `pair_page` included, never protocol housekeeping such as `initialize` or `tools/list`, and runs before the access check and before a tool's own arguments are checked: the tools register a Standard Schema that shows clients the same JSON Schema and leaves the zod check to the handler, so a malformed call costs budget and, past it, is answered `rate_limited`. Malformed arguments now answer `invalid_arguments: these arguments do not fit the tool's input schema (...)` in place of the SDK's own text.

**Tool budget.** `TABDOCK_MAX_TOOL_BYTES` charges `heldBytes`, an upper bound on the heap a list holds, not the frame's size on the wire: 128 bytes for each value or key of the cut copy, 2 bytes for each character kept (a cut string's original and the prepared schema included) and 1024 bytes a tool, checked once the list is built and before anything changes. The review showed why: a small frame of empty objects holds twenty times its size, and 100 hosted pages of 123 kB frames crashed `main.ts` under the image's heap cap at 12 MiB charged. Measured under `--expose-gc`, no shape held more than 0.9 of its charge, and with every hosted slot filled from 20 addresses the relay refused the rest with 1008 and kept serving even at a 96 MB heap, so 64 MiB, 100 page sessions and `--max-old-space-size=192` are the sized values (`tool-heap.test.ts`, which reads the Dockerfile's flag). The minimum stays 1 MiB, now meaning one page of ordinary tools rather than one whole frame of any tools. A refused `tools` frame has already counted against its address's frame budget.

**What the shares leave.** The A4.3 review measured it: about six client keys, six IPv4 addresses as readily as six /56s from one IPv6 /48 (which holds 256), together spend the relay-wide 60 sign-ins a minute and stall QR and `/i` sign-in for everyone, and twenty can hold every page slot, after which a further key can end the page asleep longest (ADR 0009); both follow from the numbers above and cost availability only, keying IPv6 by /48 would stop neither and would count unrelated customers of one provider as one, and `docs/threat-model.md` records both under B2 and B3.

## Notes from the A4.3 review (4 October 2026)

**Listen streams.** The 2026-07-28 leg answered `subscriptions/listen` from the SDK's one relay-wide set of 1024 streams, each held open by keep-alives and none counted per user, so one signed-up account opened all 1024 and every member's listen got `Subscription limit reached`. The relay now reads each 2026-07-28 POST's body before the SDK, hands the SDK that parsed body so both route the same value, and passes a listen through `listen-streams.ts` first. A listen spends one request of its caller's budget before anything else, so the budget counts calls to the five fixed tools and every `subscriptions/listen`, refused or not, still never `initialize` or `tools/list`; past it the listen gets a JSON-RPC error in the budget's own words and no audit record, since it asks nothing of a page. Streams are then bounded by the session numbers, counted apart from sessions: `TABDOCK_MAX_SESSIONS_PER_USER` for a member, one for a stranger and `sessionsPerInvitee` for a guest, `inviteeSessions` for all invitees and `TABDOCK_MAX_SESSIONS` in all, with the SDK's own cap set to that total so it never binds first. A newer stream of the same user ends that user's oldest, so a reconnecting client keeps listening. Past the pool or the total a stream ends only for a newcomer ranked above its holder (ADR 0016's notes), the lowest rank first and then the oldest; anyone else gets the SDK's own answer at its cap, `Subscription limit reached`. A refusal writes one line per reason a window. One stranger now holds one stream however many it opens, at most 60 listens a minute, and strangers together hold at most the pool. Tests: `listen-streams.test.ts`.

**Frames that change nothing.** `/page` takes no credential, and every frame the relay ignored or refused wrote a warn or info line, while only `tools` frames were budgeted: one socket wrote 200,000 lines in about a second, `hello` or not. Now a frame that changes nothing counts against `ignoredFramesPerSocket`, 20 a minute, and `ignoredFramesPerAddress`, 60 a minute across an address's sockets and reconnects; past either the socket is closed with 1008 and the page sleeps, to resume as after any close. Such a frame is one of unknown type, before `hello` too; a decision for no request of the page; a `set_role` for no one attached or one that leaves the role as it was; a revoke that ends nothing; an invite frame on a relay with invites off; a refused `invite_create`; and an `invite_cancel` naming no live invite. So a socket writes at most 22 lines through them: the budget, the frame that passed it and the close. A result for no call, a ping and `rotate_pairing` write no line at the production level and are not counted, and frames that act stay bounded by what they act on, promotions and mints by `OPERATOR_GRANTS_PER_PAGE`. What remains comes per connection, not per frame: each socket a script opens can still write a line or two (an upgrade refused, a close for a malformed or first frame, or its first such frame past the address budget, beside `page connected` and `page asleep`), bounded only by how fast it can connect, since ADR 0020's collapsing of repeated 401 lines has no counterpart at `/page`. Tests: `limits.test.ts`, `invites.test.ts`.

## Notes from the second A4.3 pass (4 October 2026)

Two skeptics re-checked the first pass's fixes. These notes replace the sentences above that they contradict; ADR 0023 (Accepted) replaces the paragraph on frames that change nothing.

**Listen streams, as served.** The relay read a listen's body through a clone and handed the SDK the parsed value, so nothing ever read the request's own copy, which stayed queued for the stream's life beside what the stream already held: fifty strangers with bodies padded to the 2 MiB cap pinned about 100 MiB of heap and 100 MiB of buffers, 300 MiB of RSS on a 512 MB host. Now the 2026-07-28 leg reads each POST body once and hands the SDK the parsed value for every request, not only listens, and a `subscriptions/listen` whose body is over 16 KiB (a real one is about 300 bytes) is answered 413 before it spends anything but its budget request or touches any stream; with the full pool held, the relay's heap and buffers stay within 16 MiB of where they started (`listen-heap.test.ts`).

**Who gives way, and when.** The gate made room before the SDK answered, so a listen the SDK then refused (a `text/plain` body, params with no filter, a malformed filter) or answered without a stream (one sent as a notification) still ended someone's stream, its own sender's oldest included. Now whose stream gives way is settled when the listen arrives, by the same rules, but that stream only ends once the SDK has answered the listen with an event stream; until then it counts for nothing and cannot be chosen again, and the listen being answered counts in its place, so overlapping listens never overshoot a cap. So "a newer stream of the same user ends that user's oldest" holds only for a newer stream the SDK served. A listen whose filter asks for nothing the relay sends gets a stream that ends at once, and still counts as served: a guest or member can churn the streams of those ranked below it at one budget request each, as it always could by opening a stream and dropping it. Since a stream marked to give way stays open until its newcomer is served, and each listen being answered marks at most one, the SDK's own cap is twice `TABDOCK_MAX_SESSIONS`, so it never binds before the relay's total (`listen-streams.test.ts` opens 1,100 streams to show the SDK's default of 1,024 no longer binds).

**Requests the SDK refuses.** A 2026-07-28 request the SDK answers with a 4xx before any tool runs (its validation ladder, a Content-Type it refuses, a body over the cap, an unknown method; any 4xx but its 499 for a client gone mid-call) now spends one request of its caller's budget, as a tool call does, so a flood of them runs the account dry; still never `initialize`, `tools/list` or any request the SDK serves. A JSON-RPC error the SDK answers with 200, such as a `tools/call` with no tool name, writes no line and is not counted, as `tools/list` is not. The lines the 4xx refusals write are bounded too (ADR 0019's notes).

**Frames that change nothing.** ADR 0023 holds their lines back past the budgets instead of closing the socket, makes the first frame `hello` or a 1008 close, and stops counting decisions the page is expected to send. A newer adapter's frame type is ignored and logged within the budget and never disconnects a page; a page frame type whose effect matters ships with a relay that knows it. What remains per connection is as the paragraph above says. Tests: `limits.test.ts`, `invites.test.ts`, `operator-controls.test.ts`.

## Notes from the final A4.3 pass (4 October 2026)

Two skeptics re-checked the second pass. These notes replace the sentences above that they contradict.

**Per connection.** The line or two each page connection writes now has the counterpart to ADR 0020's collapsing that it lacked: such lines are written up to 60 a minute per client address (`connectionLinesPerAddress`) and counted past it into one line per address (ADR 0023's notes), so one sequential client no longer writes about 2,400 lines a second, and a client that opens connections from many addresses writes at most 60 lines a minute from each, with the addresses tracked in a minute capped at 10,000.

**A page that stops reading.** Nothing bounded what the relay held for a page socket that stopped reading while it sent frames the relay answers, and `/page` needs no credential: one such socket held hundreds of MiB, past the reference host's 512 MB. ADR 0024 (Proposed) holds at most 256 frames, or 2 MiB, past what the kernel took for one page, and closes the socket with 1008 past either. The memory this leaves per page socket is bounded by those numbers and the kernel's own per-socket buffers, so `pageSessions` and `pageSocketsPerAddress` bound it in all. Tests: `page-backpressure.test.ts`, `hub.test.ts`.

**A call's body, while it waits.** A test now holds what the second pass's single read saves: ten 2026-07-28 calls padded toward the 2 MiB cap and left waiting on a page that never answers hold about one copy of their bodies (22 MiB), where reading a clone again held two (42 MiB) (`listen-heap.test.ts`). The one copy left is the SDK's: its Node adapter reads a body whole into one string and builds the web `Request` from it, and that request lives as long as its call. So a member, or a guest calling a tool the page is slow to answer, holds up to 2 MiB per call in flight, padding included, bounded by the request budget and the call deadline. Handing the adapter a body the relay parsed itself would leave only the compact JSON, but it moves how every `/mcp` request is read on both legs and is left for the backlog.
