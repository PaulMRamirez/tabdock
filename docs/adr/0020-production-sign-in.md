# 0020: Production sign-in

Status: Accepted by the owner, 3 October 2026. Changes SPEC section 7; corrects ADR 0013's consequences and notes; plans how ADR 0016's "verify before M4" is settled on the owner's first production run, with an unverified fallback.

## Context

The owner chose a WorkOS production environment (D4 in `docs/notes/m4/m4-decisions.md`): email sign-in by password or one-time code, sign-up open, no Google or GitHub button for now. Staging and production share nothing (keys, client ids, users, redirect URIs), so the move changes every `sub`, which ADR 0013's consequence ("swapping providers changes only the issuer, key URL and audience") misses. Production needs a card and accepts only https redirect URIs apart from `http://127.0.0.1`. WorkOS documents no access-token lifetime, no key rotation, and nothing saying that revoking a session or a consent ends issued tokens. Connect access tokens carry no email; a JWT template can add `user.email` and a boolean `user.email_verified`, though no example shows a rendered boolean. Today the relay requires only `exp` and `sub`, leaves jose's key caching at its defaults, reads the provider's metadata once, never checks a token's `client_id`, asks `/pair` for scope `openid`, answers 403 to accounts off the allowlist and does not redact `email`. With sign-up and dynamic registration open, anyone can register a client and ask a member to consent to it.

## Decision

**Provider.** The checks below are provider-neutral: any provider meeting the requirements in the section 7 wording below works, and one without the email claims shows invitees as unverified accounts. The reference deployment (ADR 0022, `docs/deploy.md`) uses a WorkOS production environment, $0 with a card on file while SSO, a custom domain and Radar stay off. Sign-up stays open: the relay's allowlist and invites are the gate, and closing it would need a WorkOS invitation per guest. The owner's own Google app can come later without changing any `sub` (backlog). The sign-in page stays on the environment's `*.authkit.app` name, since a custom domain costs $99 a month. The deploy guide redoes `TABDOCK_OAUTH_USERS` with the new `sub` values, and the connector is re-added in the same step as leaving ngrok.

**Token checks.** Beyond M3's: `iat` and `jti` are required; jose's `maxTokenAge` is 2 hours (`TABDOCK_OAUTH_MAX_TOKEN_AGE`, in minutes, 120 by default, refused above 1440 at startup), which also refuses an `iat` in the future; and a token whose `exp - iat` exceeds the same cap is refused, so a provider setting cannot mint day-long tokens. `typ` stays unpinned because WorkOS sends none. If the first production token shows a longer lifetime, the cap is raised within that ceiling and noted here, never removed. An optional `TABDOCK_OAUTH_CLIENT_IDS` names the OAuth clients whose tokens the relay accepts and refuses others with 401; once the owner's first run shows hosted Claude and Claude Code registering through client ID metadata documents, the checklist turns dynamic registration off at WorkOS and sets the list to the URLs seen.

**Keys and metadata.** jose's `cacheMaxAge` (10 minutes) and `cooldownDuration` (30 s) are set explicitly at today's defaults, so an upgrade cannot change them unseen; the runbook notes up to about 330 s of 401s after a key rotation. The relay re-reads the provider's metadata hourly; a changed issuer or key URL is refused and logged, and the relay keeps what it checked at start.

**Claims for invites.** One JWT template with namespaced keys, `{ "urn:tabdock:email": {{ user.email }}, "urn:tabdock:email_verified": {{ user.email_verified }} }`, parsed with zod (an email of up to 320 characters, a boolean). A missing or mistyped claim shows as "unverified account", and identity stays `sub`. The first time the relay sees a token with a given `sid` (remembering the last 1,000), it logs the token's lifetime, its `client_id` and the types of the two claims, never their values or the `sid`, so the owner's first production run settles ADR 0016's question. `/pair` and `/i` ask for `openid email` and read `email` and `email_verified` from the ID token, falling back to `fetchUserInfo` from the approved `openid-client` 6.8.8.

**Invitees.** With `TABDOCK_INVITES` on, a valid token whose `sub` is not on the allowlist is admitted as an invitee (ADRs 0016 and 0017) where M3 answers 403; with it off, the 403 stays.

**Logs.** `email` and `displayName` join the redacted log fields, so an invitee's address reaches the page and the audit file's `attach` record but never stderr. A refusal line names the account kind and `client_id`, never token text, and repeated 401 lines collapse to one per client address a minute, with a count.

**Revocation.** M4 keeps no deny list. A token lives until its `exp`, at most the 2-hour cap. A deny list of revoked `sid` values needs a signed revocation feed from the provider and goes to the backlog; the allowlist, the widget's Revoke and the short lifetime cover the realistic cases, and the threat model records the gap.

**SPEC wording.** Section 7, in the auth paragraph, the sentence beginning "M3 adds a minimal `oauth` plugin and M4 hardens it" becomes: "M3 adds a minimal `oauth` plugin and M4 hardens it (ADRs 0006, 0013 and 0020): an external identity provider registers Claude, checks its hosted callback and Claude Code's loopback redirect, and issues tokens for the relay, which serves RFC 9728 metadata and verifies each token through a maintained library, requiring `iat` and `jti`, refusing a lifetime over a configured cap (2 hours by default), and re-reading the provider's metadata hourly without accepting a new issuer. Any provider will do that passes the plugin's start checks (its issuer, S256 PKCE, and client ID metadata documents or dynamic registration); issues access tokens as RS256-signed JWTs, never opaque ones, whose keys are at its `jwks_uri` and whose `aud` is the relay's MCP URL from the RFC 8707 `resource` parameter, with a stable `sub`, `iat`, `jti`, an `exp` within the cap and, when the client list is set, RFC 9068's `client_id`; and offers a confidential client for `/pair` and `/i` whose signed ID token carries the same `sub`. Without `email` and `email_verified` (in the ID token or from UserInfo, and as namespaced claims in access tokens), invitees show as unverified. The reference deployment uses a WorkOS AuthKit production environment as one example (`docs/deploy.md`)." ADR 0013 gains a line under its consequences: "Corrected by ADR 0020: moving between providers, or between one provider's environments, also changes the `/pair` client and every member's `sub`, so the allowlist is redone and the connector added again." In its notes, the `/pair` scope becomes `openid email`.

## Consequences

No new dependency. Members re-enter their user ids once and re-add the connector once. Tokens remain plain bearer tokens (Claude documents no sender-constrained tokens), so the lifetime cap is the main limit on a stolen one, and until the client list is set a third-party client can phish a member's consent, which the threat model records. Whether WorkOS production accepts Claude Code's `localhost` loopback redirect, when its rule names only `http://127.0.0.1`, is checked on the owner's first run; hosted Claude does not depend on it.

## Notes from the interface review (4 October 2026)

The plugin says who someone is and the relay decides whether they may in, so `TABDOCK_INVITES` has one home. The `oauth` plugin maps every valid token to a member or an invitee through `BrowserSignIn.userOf`, and relay.ts answers an invitee with M3's 403 unless it admits invitees, which it will only with `config.invites` on; until workstream A's invitee tier exists it admits none, whatever the setting. Every `AuthRefusal` carries `accountKind` and `oauthClientId`, null when the plugin knows neither, and one module owned by A, `auth-log.ts`, writes the refusal line: A adds those two fields to it and collapses repeated 401s by the client address's limit key. `AuthPlugin.start` receives `{ log }` for the first-sighting and metadata re-read lines, and `stop()` ends what `start` set going; the relay calls it once on close and on every failed start, its own included.

## Notes after the build (4 October 2026)

Workstream A built this record against `oauth2-mock-server`; what a real provider issues waits for the owner's first production run (`docs/checklists/M4.md`).

**Token checks.** `iat` and `jti` join `exp` and `sub` in jose's `requiredClaims`. `maxTokenAge` is measured from `iat`, and an older token fails as `JWTExpired` naming `iat`, one with a future `iat` its claim check; a lifetime `exp - iat` past the cap is refused after jose. `cacheMaxAge`, `cooldownDuration` and `timeoutDuration` (5 s) are passed to jose explicitly, which `oauth-jwks.test.ts` checks by wrapping jose. `OAuthAuthOptions.metadataRefreshMs`, an hour by default, lets tests drive the hourly re-read, and `stop()` clears its timer; a re-read that fails logs a fixed problem word, `unreachable`, `missing`, `malformed` or `unusable`, and a changed issuer or key URL has a line of its own, never the provider's text. The test provider puts a `jti` on every token.

**Logs.** The token-shape line is written once per `sid`, the newest 1,000 remembered; a token with no `sid` is logged once per `client_id`, never per `jti`, which is new on every token. It names the claim types, the `client_id`, whether a `sid` was present and the lifetime in seconds, nothing more. 401 lines collapse by the client address's limit key, so an IPv6 /56 behind a host edge is one sender: the first in a minute is written in full, and the rest become one `repeated` line carrying `{ address, repeated, reasons }`, the reasons counted by their fixed phrases, written when the minute ends or the relay closes (`AuthRefusalLog.close()`); past 10,000 addresses in a minute the rest share one count.

**Email.** `/pair` and `/i` read `email` and `email_verified` from the ID token and, when it names none, from UserInfo through `openid-client`'s `fetchUserInfo` with the expected subject, for invitees only, never for members, whom the owner's settings name; `ProviderEndpoints` gained an optional `userinfo_endpoint` for it. A UserInfo failure leaves the account unverified and is logged by its kind. On `/mcp` an invitee's email comes only from the two namespaced access-token claims.
