# 0023: Page frames that change nothing

Status: Accepted, 4 October 2026, from the second A4.3 pass, under the owner's standing instruction to take the recommended option. Changes SPEC section 6.

## Context

SPEC section 6 says unknown frame types are "ignored and logged", and its close codes give 1008 for malformed frames and for a page or address over its `tools` budget. `/page` takes no credential, so the first A4.3 pass found that a socket could write a log line per 16-byte frame to stderr, which carries the audit checkpoints and, while the audit disk fails, the records themselves (ADR 0019). That pass counted every frame that changes nothing (an unknown type, a decision for no request of the page, a `set_role` that changes no role, a revoke that ends nothing, a refused or unknown invite frame) against 20 a minute per socket and 60 per address, and closed the socket with 1008 past either (ADR 0018's notes). It changed no spec text.

The second pass found three things wrong with closing. The shipped adapter sends such frames itself: its own timeout denial reached the relay after the relay's timer had ended the request in every case the reviewer saw, and `revoke('*')` with 21 requests waiting sent 21 decisions for requests the relay's revoke had just ended, which closed the operator's page and so dropped its waiting requests and failed its calls in flight. Frames before `hello` counted against the address, so a script that never said hello could spend an address's 60 and have the next page on that address closed for one ordinary frame; every page shares loopback in local and public URL mode, and a NAT, carrier NAT or IPv6 /56 shares an address behind a host edge. And closing bounded nothing about the lines that holding them back does not, since the close cost the attacker only a reconnect. (This pass also argued that a socket could already send pings without limit, each answered with a pong, as if that were harmless. It was not: a page that stopped reading left every pong, and every answer to a frame that changes nothing, queued in the relay's memory, a hole the final pass found and ADR 0024 closes.) A newer adapter sending a frame type this relay does not know would also have been disconnected in a loop, since the address count survives reconnects.

## Decision

**Lines, not sockets.** A frame that changes nothing never closes its socket. Every line its handler writes is held until the relay knows whether it changed anything (`FrameLog` in `hub.ts`): written as usual if it did; otherwise written only within the socket's budget (`ignoredFramesPerSocket`, 20 in a sliding minute) and its address's (`ignoredFramesPerAddress`, 60 in each clock minute, across the address's sockets and reconnects). Past either, the lines are held back and counted by frame type into one warn line per address, `page frames that changed nothing went unlogged`, when the minute ends or the relay stops (`repeated-lines.ts`). Addresses tracked in one minute are capped at 10,000; past that they share one count.

**The first frame must be `hello`.** A first frame of any other type, an unknown one included, closes the socket with 1008 (`first frame must be hello`) and writes one line, as a known type there always has. So frames before `hello` spend nothing of the address's budget.

**Frames the page is expected to send.** The relay remembers each request it ends (its time run out, a revoke, its invite closed, the page full, an approval) for the request's lifetime plus 30 seconds, and a decision the page sends for one of them is ignored with a debug line and counts against nothing: the page's timer runs on its own clock, and an operator's click can cross the end on the wire. The adapter sends no decision for a request its own revoke ends, since the revoke frame, which goes first, ends it on the relay.

**Forward compatibility.** A newer adapter's frame type is ignored and logged within the budget and never disconnects the page. A page frame type whose effect matters ships with a relay that knows it.

**SPEC wording.** Section 6's first paragraph reads: "Transport: WebSocket at `/page`, subprotocol `tabdock.v1`, JSON text frames shaped `{ "t": "<type>", ... }`. Both sides validate every frame with zod. The first frame must be `hello`; any other closes the socket with 1008. After it, unknown types are ignored and logged: the lines of frames that change nothing, unknown types among them, are written up to a budget per socket and per address and past it counted in one line per address each minute, and such frames never close a socket (ADR 0023). Frames are capped at 1 MB. Tool results over 120,000 characters are truncated with a visible marker." The close-code paragraph keeps its 1008 for malformed frames, which now names a first frame that is not `hello`.

## Consequences

A flood of such frames writes at most 20 lines a minute from one socket and 60 from one address, then one summary line per address a minute; the frames still cost parsing, and whatever the relay answers them with is held only within what ADR 0024 lets it hold for a page that is not reading, past which the socket is closed. Whoever shares a page's address can spend that address's lines, so the operator's own lines for frames that change nothing may be counted rather than written, but can no longer end the page, its waiting requests or its calls. The line or two each connection a script opens writes (an upgrade refused, a first frame that is not `hello`, `page connected`, `page asleep`) is written within a budget per client address and counted past it (the notes below). Tests: `limits.test.ts`, `invites.test.ts`, `operator.test.ts` and `invite-records.test.ts` (adapter), `operator-controls.test.ts` (end to end).

## Notes from the final A4.3 pass (4 October 2026)

Two skeptics re-checked the second pass. These notes replace the sentences above that they contradict.

**Answers to frames that change nothing.** Keeping a socket open past its budget left the relay answering each such frame (a revoke of everyone with a roster and the page's invites, an `invite_cancel` with the invites) whether or not the page read the answers: with invites on, a million `invite_cancel` frames for no invite held 130 to 175 MiB of heap and a million revokes of everyone about 360 MiB, where the first pass's close had stopped the flood after 20. ADR 0024 bounds what the relay holds for a page that is not reading and closes the socket past it, so keeping such sockets open no longer costs memory, and their lines stay bounded as above. Tests: `page-backpressure.test.ts`.

**Lines per connection.** Each connection still wrote a line or two of its own, about 2,400 a second from one sequential client with no credential: `hello` then a close wrote `page connected` and `page asleep`, and at an address's cap the sleeper ended and `page gone`; a refused upgrade or a first frame that is not `hello` wrote one each. Now every such line goes through one budget per client address (`connectionLinesPerAddress`, 60 a minute), keyed as the per-address limits key the address, or by what was wrong when a host edge named no client: the upgrade refusals in `relay.ts` and `admitSocket`; closes for a first frame that is not `hello`, a malformed or binary frame, a second `hello`, no `hello` in time, silence, the `tools` budgets or unread frames; a refused resume token; `page connected`, `page asleep`, `page detached` and `page gone`; and a sleeper ended, or a session refused, for want of room. Past it they are counted by message into one warn line per address, `page connection lines went unlogged`, when the minute ends or the relay stops, with the addresses tracked in a minute capped at 10,000 as for frames. Whoever shares a page's address can spend these lines too, so the operator's own `page connected` may only be counted; audit records' stderr copies never pass through this budget. Tests: `limits.test.ts`.
