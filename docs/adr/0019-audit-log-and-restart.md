# 0019: The persistent audit log, and what a restart keeps

Status: Accepted by the owner, 3 October 2026. Changes SPEC sections 4 and 9 (S7); narrows S7 for refused calls, which the owner accepted explicitly on 3 October.

## Context

SPEC section 4 asks M4 to persist the audit log and S7 asks that every call be attributed in it, but nothing sets the log's format, retention, failure behaviour or contents, or says what a restart does. Today each call attempt goes to a 1000-entry memory ring and to stderr (`hub.ts:1888-1923`). Nothing bounds refusals: with invites on and sign-up open (ADR 0020), a stranger at 100 requests a second could write about 2.7 GB of audit a day and push every real record out of a bounded log. Every deploy restarts the process, and the adapter drops its grants on `resumed: false`. The owner took option A of D3 (`docs/notes/m4/m4-decisions.md`) by default.

## Decision

**Storage.** A `FileAuditLog` implements the existing `AuditLog`, whose `append` now takes an `AuditEvent`, a discriminated union with `v: 1` in `packages/protocol`, and stays synchronous and never throws. Records are JSON Lines in `TABDOCK_AUDIT_DIR` (on a host, its volume; directory 0700, files 0600): one `writeSync` per line on an `O_APPEND` descriptor, `fdatasync` at most once a second, at rotation and at close, which follows `hub.shutdown()` because shutdown audits the calls it fails (`relay.ts:490-493`). A torn last line is closed at start. Production refuses to start without the directory or if it cannot write and sync a `relay_start` record; local mode defaults it to `audit/` beside its owner token (ADR 0022), and dev tokens and tests keep the memory ring unless it is set. `node:sqlite` is out: on Node 22 it prints a warning into the JSON log stream.

**Contents.** Each line carries `v`, `seq`, `at`, `type` and `prev`. The types are `call`, `attach` (with `via`, role and the token's `client_id`), `attach_refused`, `role`, `revoke`, `detach`, `expire`, `invite_minted`, `invite_redeemed`, `invite_closed`, `sponsor_gone`, `relay_start`, `relay_stop`, `audit_gap` and `refused_summary`. A page is named only by `pageId` and its `Origin`-header origin, never by title or URL. Records never hold arguments, results, tokens, codes, nonces, invite secrets or their hashes, resume-token hashes, cookies, `sub`, addresses or page-written labels. An invitee's email, or `unverified`, appears only in the `email` field of its `attach` record. Client text that fails `IdSchema` or `ToolNameSchema` is stored as `(invalid, N chars)`. Each record also goes to stderr through the logger, whose redaction drops `email` (ADR 0020), so the stderr copy differs from the file only there and the platform's logs (7 days on Fly) never hold an email.

**Bounds.** Files rotate at 8 MiB or UTC midnight and are kept 30 days or 64 MiB in all, never deleting the current file (`TABDOCK_AUDIT_RETENTION_DAYS`, `TABDOCK_AUDIT_MAX_MB`). A call that reaches a page always writes its own line, as do records an attachment or the operator causes, including an `attach_refused` from a page, which the per-page pairing limit bounds. A refusal that never reaches a page (a call, code or redemption, or a request past ADR 0018's budget) writes its own line within a budget. A member, or an account holding an attachment, gets 10 such lines a minute, then one `refused_summary` a minute with its counts by outcome. Invitees holding no attachment also share a relay-wide 30 a minute; past either budget, their refusals go into one relay-wide `refused_summary` a minute naming the 20 busiest with counts by outcome and counting the rest together. However many accounts strangers open, they write at most about 31 lines a minute, about 16 MB a day, so the 64 MiB cap keeps about four days of records through such a flood.

**Failure.** If the disk fills or errors, the call still runs and its record still reaches stderr, and an `audit_gap` record counting what was lost follows once writing works again. Failing closed would let a full disk stop every page.

**Tamper evidence.** `prev` is the SHA-256 (`node:crypto`) of the previous line, chained across files, and a checkpoint (`seq` and head) goes to stderr every 15 minutes, at rotation and at stop. It uses no key and no new primitive, and shows edits made after the last checkpoint the platform's logs still keep; it prevents nothing. The section 9 reviewer decides whether it counts as hand-rolled cryptography; if it does, only `seq` stays.

**Reading.** `pnpm audit:log` (pnpm's own `audit` shadows that name) filters by user, page, time, outcome and type, checks the chain with `--verify`, validates each line and escapes control and bidi characters. On a host the operator runs it inside the container or on copied files; on the reference deployment that is `fly ssh console -C`, or `fly ssh sftp get` and a local run, from a computer either way. M4 adds no HTTP route.

**Restart.** Only the audit log persists, with local mode's owner token file (ADR 0022). A restart, every deploy included, ends every page session, attachment, pairing ticket, attach request, invite, `/pair` session and MCP session; pages reconnect as new sessions, everyone pairs again and live invite links die. OAuth tokens stay valid, and 2025-era clients start a new session after a 404. `relay_stop` and `relay_start` mark the gap, and deploys run on demand, never on merge. A snapshot at graceful shutdown (D3 option B) goes to the backlog.

**SPEC wording.** Section 4, replacing its first two sentences: "The relay is one process with an in-memory store, run as exactly one instance. Besides local mode's owner token (ADR 0022), only the audit log persists, as JSON Lines files on disk; a restart ends every page session, attachment, pairing ticket and invite, and pages pair again (ADRs 0018 and 0019)." S7: "Every call that reaches a page is attributed in the page activity log and in the relay audit log, which in production and local mode survives restarts: user, client, tool, time, outcome. Arguments are not logged by default. A call refused before it reaches a page has its own line up to a per-user budget; past it, the refusal is counted by user and outcome in a summary line each minute, except that accounts holding no attachment also share a relay-wide budget whose summary names only the 20 busiest. While the audit disk fails, records reach only stderr and an `audit_gap` record counts what the file missed (ADR 0019)."

## Consequences

S7 narrows in three ways, which the owner accepted explicitly on 3 October: past its budget a refused call keeps its user and outcome but loses tool and client; a stranger outside the 20 busiest keeps only its outcome; and during an `audit_gap` records survive only in the platform's logs (7 days on Fly). In exchange no stranger can flush the log, while members and the people the operator let in stay attributed and revocable. Every deploy costs the operator a re-pair and kills live invite links. The audit directory is the only state a hosted relay keeps on disk; on the reference deployment it is a Fly volume, $0.15 a month and snapshotted daily.

## Notes from the interface review (4 October 2026)

A sixteenth record type, `request_refused`, records a request ADR 0018's per-user budget refused for `list_pages`, `list_page_tools` or `detach_page`: `userId`, `kind`, `client`, the tool, the page as the client sent it (null for `list_pages`) and the outcome `rate_limited`, within the refusal budget like any refusal that reached no page. A `call_page_tool` past the budget stays a `call` record and a `pair_page` an `attach_refused` one, so every call attempt is a `call` line.

`AuditLog.append` returns what the file line added, `{ seq, prev }`, or null when no file took the record (the memory ring, or a disk that failed). `recordAudit(audit, log, event)` in `store.ts` appends and writes the stderr copy with those fields, so the copy is the file line less the email whatever log is in use, a test's own included. The hub's records, `relay_start` and `relay_stop` go through it; `FileAuditLog` writes to stderr only the records it makes itself, `audit_gap` and the checkpoints.

## Notes after the build (4 October 2026)

Workstream C built the log and its reader, A the refusal budget and every record the hub owns, and integration found they fit.

**Files.** Each is `audit-<UTC day>-<sequence number of its first line, 12 digits>.jsonl`, and only regular files so named are read. `prev` is the SHA-256 of the previous line's text without its newline. Retention goes by a file's UTC day; at start the newest file is kept however old, and retention runs after each rotation, with the new file current, and hourly. Every line is checked against `AuditLineSchema` and the checked record is what is written, so a key no schema lists is dropped even inside a nested field, keys follow the schema's order, and the stderr copy can differ from the file by such a key; a record that fails is kept out and counted in the next `audit_gap`. A write that lands every byte but the newline is kept as a record. One writer per directory: `audit.lock` is held from open to close, a second relay on the directory refuses to start before reading or writing a line, and a lock whose pid is gone, is this process's own or comes from another boot is replaced.

**Start and stop.** `relay_start` and `relay_stop` are written only with a persistent log, since a memory ring forgets everything at a restart. Production's directory rule is enforced in `createRelay`, not `resolveConfig`: production refuses to start without a directory or a store of its own, or when `relay_start` is not synced, and a directory with a store is refused as ambiguous. The checkpoint line reads `audit checkpoint`, with `seq` and `head`; `pnpm audit:log --verify` reports a torn line as a notice, and `--checkpoint` takes `seq:head`. Node's permission model refuses `fdatasync` and `fchmod`, so it cannot host the relay.

**The refusal budget.** A stranger is an invitee id holding no attachment. A call that reached the page, or failed with `relay_error`, is always written in full, and after shutdown the budget writes directly with no summary step. A malformed `call_page_tool` keeps a `call` line (`invalid_arguments`) within the budget; malformed `list_page_tools` and `detach_page` calls write nothing, since `request_refused` allows only `rate_limited`, nor does a malformed `pair_page`. Since a page needs no credential, promotions and invite mints share `OPERATOR_GRANTS_PER_PAGE`, 10 a rate-limit window per page: past it a promotion is refused and the roster shows the role unchanged, and `invite_create` is refused with `limit`, while demotions, revokes and cancels are never counted or refused. A page's role and invite lines are so bounded; a member attached to many pages can make each write its share, all attributed.

**Records.** The hub writes every type it owns, `expire` with `idle`, `ends_at`, `page_gone` or `sponsor_gone`, and an `attach` for every approval, which moved three of workstream C's counts in `audit-relay.test.ts` by one at integration. Local mode keeps its files in `audit/` beside the owner token (ADR 0022).

## Notes from the section 9 review (4 October 2026)

The reviewers found four ways the log could lose, hide or fork its records; each is fixed, with tests in `audit-file.test.ts` and `audit-relay.test.ts` that fail without the fix.

**A gap at close.** A log that closes with an `audit_gap` still owed tries it once more, then writes it to `audit.gap` beside the files as the line it owes (seq and prev included), synced and renamed into place, and logs the count as an error either way, so a relay stopped or redeployed while its disk fails no longer leaves a silent hole. The next open writes that `audit_gap` before anything else and removes the file, dropping one whose seq the log has passed so no gap counts twice. `--verify` names each `audit_gap` and each `relay_start` that follows neither `relay_stop` nor `audit_gap`, which marks a crash or a disk that took not even `audit.gap`, without failing.

**The lock.** `audit.lock` reads `<pid> <boot> <pid namespace> <owner id>`, the owner id 16 random bytes drawn at open, and its holder sets its mtime every 5 s. A pid counts only on the same boot and in the same pid namespace: there a live pid other than this process's refuses the start and any other lock is replaced at once. Elsewhere, as for a second container on one host and volume where both relays are pid 1, a lock is replaced only once it has gone 30 s without a refresh, and one refreshed while the new relay waits refuses it. A stale lock is broken by renaming it aside and checking it is still the one judged stale, so two relays breaking it at once cannot both win; a lock is released only when its text is the holder's own; and a holder that finds another relay's lock in its place stops writing the files.

**The start of the log.** Each checkpoint also names `first`, the seq the oldest file kept starts at, and retention writes a checkpoint after every deletion, so the newest checkpoint always names where the log starts. `--verify` fails when a file's first record is not the seq its name gives, and `--checkpoint <seq>:<head>:<first>` fails when the log starts after `first`.

**Durations.** A call's `durationMs` comes from `performance.now()`, so a wall clock stepped back during a call no longer fails the schema and costs the call its own line.

## Notes from the second section 9 review (4 October 2026)

A second round of reviewers found five more ways the log could hide a loss or fork its writer, and one test that meant less than it said; each is fixed, with tests in `audit-file.test.ts` and `audit-relay.test.ts` that fail without the fix. These notes replace the sentences above that they contradict.

**The start of the log.** Each retention pass used to read `first` back from the directory, so a file deleted from the start other than by retention was blessed by the next checkpoint. Now `first` moves only when the log's own retention deletes the oldest file. A retention pass (hourly, or at a rotation) that finds the oldest file starting after `first` logs an error naming the missing seqs (`from`, `to`) and keeps `first`, so `--checkpoint` with any later checkpoint of that run still fails. A start also writes a checkpoint at once, before retention runs, naming where it found the log starting: a file removed while no relay ran shows on the platform's logs as a start checkpoint whose `first` is past the stop checkpoint's before it, with no `audit file deleted by retention` line between, and against that stop checkpoint `--checkpoint` fails. Nothing on disk can show such a removal to a later start, since whoever deletes the file can edit any record of it there too.

**The lock and clocks.** A lock's mtime is its holder's clock, so a newcomer whose clock ran 30 s or more ahead judged a live, refreshed lock stale at first sight and broke it. A lock whose pid this relay cannot check is now never broken at first sight: the newcomer watches it on its own monotonic clock for at least two refresh intervals (10 s by default) and breaks it only if nothing changed meanwhile and it has gone 30 s without a refresh, by that watch or by its mtime. An old mtime may shorten the wait to the watch, never skip it, so a container restarted after a crash waits between 10 and 30 s.

**Gaps.** `--verify` now names every `relay_start` that follows no `relay_stop`, one just after an `audit_gap` included (`afterGap`), since an `audit_gap` written mid-run can be followed by losses only stderr counts, and the reader says so. `audit.gap` is now a 512-byte file written for real, spaces while nothing is owed, which each open makes or checks while the disk works and keeps open to its close. A close that owes a gap writes it over those bytes in place and syncs it, which takes no new blocks, so a full disk, which refuses a new file, still takes the count; failing that it tries a new file renamed over it, and failing both it removes `audit.gap`, so an older, smaller count left there is not written as if it were the whole. The error line on stderr says which of these happened, a removal that failed included. The next open writes the owed `audit_gap` before anything else, then writes spaces back over the file.

**Tests that meant it.** Mutations removing the holder's refresh timer, the overdue lock check in `append` and the checkpoint after a retention deletion each survived the suite. Now a real holder in another process sits idle past the stale interval and a newcomer that sees another pid namespace is refused; a holder whose loop stalled past a refresh finds another relay's lock at its next `append` and writes nothing; and the line right after a retention deletion must be a checkpoint naming the new oldest file.

## Notes from the third section 9 review (4 October 2026)

A third round found that `first` could still move past records nobody's retention deleted. These notes replace the sentences above that they contradict.

**The start of the log.** After any retention deletion, a pass set `first` to where the oldest file in its own listing of the directory started. So one deletion carried `first` past files removed by hand behind the oldest: in one run, days 2 to 4 deleted by hand and then day 1 by age gave a checkpoint naming day 5's first seq, with no error. It also carried `first` past files removed from the start when an empty file named for the old `first`, on a day long expired, was planted in their place and retention deleted it. Now `first` moves only along files the log knows: those its start found and those it made since, by name and the seq each name gives. When retention deletes the oldest of them, `first` becomes where the next one starts, never a seq read from the directory, and a file the log does not know, whatever its name, moves `first` neither by its name nor when retention deletes it. A known file gone from the directory that retention did not delete gets an error line at the next pass naming its seqs (`from`, `to`), as missing from the start or from the middle of the log, and `first` stops there for the rest of the run; so `--checkpoint` with any checkpoint since fails, by the break in the chain while the files before remain and by `first` after. A known file gone that held no record, since the next starts at its seq, lost nothing and stops nothing.

**Across a restart.** A start takes the files it finds as given. Its checkpoint, written before anything else, repeats the stop's exactly after a clean stop, so one that differs shows the files changed, and against the stop's checkpoint the log fails. A change that leaves the start's checkpoint the same can no longer be told from retention's own work once retention has deleted the files before it. Until then the log fails against the stop's checkpoint for a file removed from the middle, or for files removed from the start with another planted under the old `first`'s name, which keeps the start's `first` the stop's; the oldest file renamed to an older day, which retention then deletes early, shows only as the retention line naming it. So an `audit file deleted by retention` line between the stop's checkpoint and a later one does not by itself account for a jump in `first`, and the second review's rule, a start checkpoint whose `first` is past the stop's, shows files removed from the start while no relay ran but its absence proves nothing.

**Tests that meant it.** In `audit-file.test.ts`, a file removed from the middle before age retention deletes the oldest leaves the next checkpoint naming the start of the hole, and an expired empty file planted where the oldest files were leaves `first` where it was, with the missing seqs logged; both fail without the fix, and mutations that let a listed file move `first`, forget the files a start found or made, or move `first` to the oldest file left on disk each fail a test.

## Notes from the fourth section 9 review (4 October 2026)

A fourth round found two more ways a file the log did not make could decide what the log keeps. These notes replace the sentences above that they contradict.

**Size retention.** The cap summed the sizes the directory reported for every audit file, planted ones included, and deleted the oldest files the log knew until the sum fit. A sparse file takes no space yet reports any size, so a file planted while the relay ran, or one the log knew grown in place with `truncate`, made retention delete the start of the log as if by right: under the 64 MiB cap, one plant sized to fit moved `first` from 1 to 5 under ordinary retention lines and no error, and once the plant was gone `--verify` against the newest checkpoint passed. Now each file the log knows carries the bytes it knows it by, its size when the start found it plus every byte the log wrote to it since, and the cap counts those alone, so a file the log made under a name something else took first counts only the log's own bytes. A file the log neither found nor made, which only something else can put there while it runs, is left out of the total, never deleted for size, and named by an error line (`file`, `bytes`) at the next retention pass that finds it, once while it lasts; it still goes by its age, which moves nothing. A file the log knows whose size on disk no longer matches gets an error line too (`file`, `bytes`, `knownBytes`) and counts at the log's bytes. Each deletion for size names `total`, the bytes the log counted, and `maxBytes`. A start still takes the files it finds as given, sizes included: a file planted or grown while no relay ran counts at its size then, and the start's retention may delete the oldest files for it, under lines whose `total` runs far past what the files hold.

**A file that held no record.** A known file gone from the directory was dropped without an error when the next known file started at the same seq, on the reasoning that it held no record. That held only for files the log made: a start takes an empty file planted beside the oldest, with the same first seq, as one of its own, so the oldest file, removed by hand while the relay ran, went with no error line, and `first` stayed put until the plant expired a day after the real file would have. Now a gone file is dropped only when the log knows it held nothing: it was empty when the start found it, or the log made it and no line landed in it. A run of files gone is reported as missing up to the next known file that starts later, so a file with the same first seq beside it hides none of it.

**Tests that meant it.** In `audit-file.test.ts`, a sparse file past the cap planted mid-run, a closed file grown past the cap with `truncate`, and a sparse file under the name the next file takes each delete nothing and are named; a file planted before every file the log made is never deleted for size; and the oldest file removed beside an empty file with its first seq planted before the start is reported missing. Each fails without the fix, and mutations that count sizes from the directory, delete an unknown file for size, drop either error line or its once-only guard, prune by the next file's name, let a file with the same first seq end a hole, count a made file as holding a record before a line lands, take the size on disk when the log opens a file to append to it, or take the current file from the directory listing each fail a test.

## Notes from the fifth section 9 review (4 October 2026)

A fifth round found one more way a file the log did not make could shorten what its error line names, and two halves of the size guarantee no test held. These notes replace the sentence above that they contradict.

**A run of files gone.** A run was reported only up to the next known file that started after the run's first file, so an empty file planted before the start with the second file's seq, sorting after it, cut the line short: with the two oldest files removed by hand while the relay ran, the line named seqs 1 to 3, never 4 to 6, though `first` stayed at 1 and `--verify` against the newest checkpoint still failed. ## Notes from the A4.3 review (4 October 2026)

The stderr copy, which carries the checkpoints and, during an `audit_gap`, the only copy of each record, could be flooded by a page socket holding no credential at about one line per 16-byte frame, enough to drown or age those lines out of the platform's logs. ADR 0018's notes now budget the frames that wrote them: a socket writes at most 22 such lines before it is closed, and an address at most 60 a minute, then a line or two for each further connection it opens. A listen refused on the 2026-07-28 leg writes one line per reason a window. The audit files themselves were never affected. Whether a platform drops or ages out lines under a heavy flood is the platform's, and the sandbox could not test Fly's.

## Notes from the final A4.3 pass (4 October 2026)

These notes replace the sentences of the notes above that they contradict.

**A stolen session id.** The second pass sent `MCP session id presented by another user` through the per-kind budget for `/mcp` lines, without saying so: one line a minute for the whole relay, keyed only by the message, the rest counted with no user. Such a line is evidence that its sender holds someone else's live session id (S13), and a decoy pair of signed-up accounts could spend the minute's one line, leaving a real presenter only in the count. Now it has a budget of its own per presenting user: 3 lines a minute naming the user, then one `..., repeated` line a minute naming that user with the count, with the users tracked in a minute capped at 10,000, past which the rest share one count (`sessions.ts`, as `auth-log.ts` does for addresses). So every presenter is named at least once a minute however many others present ids. Tests: `mcp-log-budget.test.ts`.

**What the per-kind budget covers.** It covers the SDK's refusals (`mcp handler error`), the 2025-era leg's refused initializes and the sessions it closes or ends, refused listens, the Node adapter's errors (`mcp adapter error`) and, on a relay without a public URL, the refusals of proxied requests; a test now holds each of those kinds to one line a minute and a count. `/page`'s per-connection lines are budgeted per client address (ADR 0023's notes), and what the relay holds for a page that stops reading is bounded (ADR 0024).

## Notes from ADR 0026 (5 October 2026)

A `call` record gains an optional `confirmedBy: 'client'`, present exactly when the call went out confirmed in its caller's client, and `not_confirmed` joins the outcomes; a pending client confirmation that expires with no retry writes one `not_confirmed` call record within the refusal budget when the sweep removes it; asking writes nothing, so one still pending when the relay restarts leaves no record unless its client retries, and that retry writes the `not_confirmed` record. Records still never hold arguments, their digest or a `requestState`. The format stays at version 1, since 0.1.0 is unreleased; an M4 `pnpm audit:log` refuses lines that carry the new field.
