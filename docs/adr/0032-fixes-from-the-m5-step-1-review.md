# 0032: Fixes from the M5 Step 1 review

Status: Accepted, 5 October 2026, from the review of M5 Step 1, under the owner's standing instruction to take the recommended option. Changes SPEC section 7 (how often a user hears of a first-class list change) and S9 (the cut-off's measure, and each invitee's share of what invitees' waiting requests may hold). Amends ADR 0025 (the notifier's interval), ADR 0026 (a confirmation's room in every invoke, and what reaches `requestState.verify`) and ADR 0030 (how the 2026-07-28 leg spends the request budget, and the cut-off's measure); adds notes to ADR 0027.

## Context

Reviewers read Step 1 (`2a1f3ea` to `0c935b3`) against section 9 and found ten issues. Each was reproduced on branch `m5` before it was fixed, and each fix has a test that failed without it.

Four touch S9. The cut-off of ADR 0030 measured progress by `writableLength`, which shrinks only once the kernel has taken a whole write; the SDK builds every JSON answer with `Response.json`, one chunk, and the MCP Node adapter passes each chunk to one `res.write`, so a client reading a large result steadily showed no progress until its last byte went out. A probe on a Unix socket read a 1 MB answer at 400 KB/s and `writableLength` sat at 1,000,183 throughout; with 16 KiB writes it sat at 65,568 while bytes kept going out. So a reading client was cut, against S9's promise. The arrival spending of ADR 0030 let through, unspent, every `tools/call` the SDK's `isSpecType.CallToolRequest` takes: one naming no tool the relay serves got the SDK's error in a 200, and one whose `requestState` is a number or `null` got the SDK's `-32602` before any handler ran (`_invokeInputRequiredCapableHandler`, before `requestState.verify`), so twenty and six of them passed a budget of 3, each building a server. ADR 0030's notes deferred the first to Step 2, while S9 already called it closed. `#holdBytes` checked an invitee against a user's share (24 MiB) and then the invitees' pool (16 MiB), so one guest calling a page that holds calls filled the pool alone: nine 1.5 MiB calls waited, and every other invitee on every page met `page_busy`. And ADR 0025's notifier, at one change a second, let one page that keeps changing its tools make each of a member's clients list again sixty times a minute; every 2026-07-28 `tools/list` spends the budget (ADR 0030), so four clients spent all of a member's 240.

Six are smaller. The invoke's size was fixed before a call waits, but ADR 0026's `confirmation` adds up to 137 bytes just before dispatch, so a call within 137 bytes of the frame cap would be confirmed and then refused. The audit schema accepted a `not_confirmed` call record crediting a client with `confirmedBy`. Both MCP-B local relays declare the bin `webmcp-local-relay`, and in `tests/e2e` pnpm linked the 6.0 beta's, so `pnpm exec webmcp-local-relay` there ran the beta. `attach()` with a bad policy threw zod/mini's internal `$ZodError`, about to become public API at 0.1.0. And ADR 0027 says a bad `TABDOCK_MCP_ALLOWED_ORIGINS` entry is named, while the code names its position only.

## Decision

**Progress is what the kernel takes.** `relay.ts` hands the Node adapter every `/mcp` answer in slices of at most 16 KiB (`inSlices` in `response-stalls.ts`), views of the chunk with nothing copied, so the adapter writes a few and waits for `drain`. The check counts progress as the socket's bytes whose writes have finished, `bytesWritten` less `writableLength`, both documented `net.Socket` properties, a count that only grows. A response with bytes waiting and no more finished than at the last check counts a stall, and any growth starts over; one with no socket yet, queued behind another response on its connection, counts none, since the one ahead is watched. Three stalls after the check that first saw it waiting cut it off, logged as before. The kernel takes more of a response only once its reader has freed a good part of the socket's buffer, about 200 to 260 KB at a time on a Linux Unix socket (212,992 bytes), so a client keeps any answer it reads faster than that much in 30 s, and a held stream's 13-byte keep-alives cost nothing until its buffer is full. S9's sentence becomes: "An `/mcp` response with bytes waiting, of which its client lets no more be sent for 30 s, is cut off and logged; a client that reads enough for more to be sent within every 30 s is never cut (ADRs 0030 and 0032)." Tests, in `response-stalls.test.ts`: on a real Unix socket through the adapter, a 3 MB `Response.json` answer and 200 ms checks, a reader at 1.5 MB/s keeps it and one that stops after 500 KB is cut with its line; the first fails without the slices and without the new measure; no `/mcp` write through the relay passes 16 KiB; and the stand-in now models a socket.

**Every 2026-07-28 request spends as it arrives.** `arrivalOf` in `relay.ts` spends one request for every JSON-RPC request but a `subscriptions/listen`, `tools/call` included, and records the outcome under the request's own auth object (`paidOnArrival`, as the byte charge is keyed); a fixed tool then spends nothing more for a request already paid. Past the budget the request is answered 429 there, except a `tools/call` the SDK's schema takes that names one of the five fixed tools (`FIXED_TOOL_NAMES` in `mcp.ts`, held to the server's list by a test) with `requestState` absent or a string, which goes on so that tool refuses it `rate_limited` with its record (S7), as in M4. So neither an unknown name, nor the spike's marker, whose handler never spent, nor params the SDK refuses before a handler runs, whatever checks it adds there, make a request free. Step 2's dispatcher keeps the rule: on the 2026-07-28 leg it spends nothing for a request already paid and refuses one that arrived past the budget; on the 2025-era leg it spends for every call. Tests, in `mcp-log-budget.test.ts`: against a budget of 3, a run of `tools/call` naming `nope`, and a run with `requestState` 5 then `null`, are refused 429 past the budget with `list_pages` refused after them, and a fixed tool spends once and refuses the fourth call in its own words with its record.

**Each invitee holds a share of the invitees' pool.** In `#holdBytes` an invitee is refused `rate_limited` past `min(requestBytesPerUser, max(MIN_REQUEST_BYTES, floor(pool / 4)))`, where the pool is ADR 0030's quarter: 4 MiB at the default total, so one call of the largest arguments still fits and four invitees are needed to fill the pool. The refusal says "your requests waiting on pages already hold ... and one invited account's may hold ...". With invites on, a total under twice `MIN_REQUEST_BYTES` (8 MiB) stops the relay at start, so invitees never hold more than half the total. S9's phrase becomes: "invitees together hold at most a quarter of the total, or one call of the largest arguments where a quarter is less, and each invitee at most a quarter of that, or one such call where that is less (ADRs 0018, 0030 and 0032)". Tests, in `request-bytes.test.ts`: the review's probe at the default limits, where one guest padding calls to 1.5 MiB on a page that holds them is refused at her own share after two while another page's guest and a member are still served; ADR 0030's quarter test, now filled by three guests; and the start refusal in `m5-config.test.ts`.

**A user hears of list changes at most every 10 s.** `FIRST_CLASS_NOTIFY_INTERVAL_MS` becomes 10,000, the list's own `ttlMs`: a change goes at once when none went to that user in the last 10 s, and otherwise one goes at the interval's end if the list's digest still differs from the last one sent. Four clients that list again on each change then spend 24 requests a minute and twenty spend 120, half a member's 240. I considered one uncharged `tools/list` per notification instead and did not take it: the 2026-07-28 leg has no sessions, so a list cannot be tied to the stream that heard the change. SPEC section 7's "at most once a second" becomes "at most once every 10 s". Tests: the constant in the protocol's `m5-interfaces.test.ts`, and the budget arithmetic in `m5-config.test.ts`. Workstream A adds the behaviour test to `page-tools-notify.test.ts`: a page changing its tools every second, a member with four 2026-07-28 clients that list again on each change, and the member's `call_page_tool` on another page still served.

**The smaller six.** `MAX_CONFIRMATION_FRAME_BYTES`, 137, joins the protocol constants, held by a test that encodes the longest confirmation, and `#encodeInvoke` counts it on every call, in the size check and in `invokeBytes`, so a call that fits when it arrives fits once confirmed; `mcp.test.ts` refuses arguments 100 bytes under the cap `invalid_arguments` before any invoke and sends them with 137 bytes to spare. The call record's audit schemas refuse `confirmedBy` with outcome `not_confirmed`. The two 6.0 beta aliases move to a private workspace package, `tests/mcpb6` (`@tabdock/mcpb6`), which exports the beta's CLI and polyfill paths, so `tests/e2e`'s bare bin is 5.1.0 again; `mcpb-versions.test.ts` holds both. `attach()` throws a `TypeError` naming the policy's bad fields, never their values, as a bad relay URL does. And ADR 0027's notes record that the refusal names the entry's position.

## Consequences

No section 9 requirement is weakened. S9 gains a share per invitee and a start refusal, its cut-off now keeps the clients it promised to keep and still cuts those that stop, and its arrival spending now holds for every 2026-07-28 request, as it already said; S7's records gain the rule that a refused confirmation credits no client.

Visible changes: a client reading a large answer must let the kernel take a batch every 30 s, where before it had to read all that was left within 30 s; a guest's waiting requests hold at most 4 MiB at the default total, where one alone could hold 16 MiB, and a guest request charged more is refused `rate_limited`; a `.env` with `TABDOCK_INVITES` on and `TABDOCK_MAX_REQUEST_BYTES` under 8,388,608 no longer starts; a first-class list change may reach a client up to 10 s late; every invoke leaves 137 bytes less for arguments; and the workspace gains one private package.

Left for later steps, each named in `docs/plans/M5.md`: workstream A's notifier test; B2 answering a 2026-07-28 retry whose `requestState` is not a string `not_confirmed`, with its call record, ahead of the SDK, and likewise a 2025-era call that carries one, since `requestState.verify` never sees it (ADR 0026's notes); workstream C documenting `attach()`'s `TypeError` in the adapter's README; workstream E reaching the beta through `@tabdock/mcpb6`; and workstream F's `mcp-origin.test.ts` asserting ADR 0027's wording as noted.

## Notes from the A5.6 review (5 October 2026)

ADR 0030's notes from the same review replace the S9 sentence above: beside the stall rule, which stands as this record measures it, a user may have at most eight `/mcp` responses with bytes waiting, an invitee two, and the oldest past that are cut off as each answer of theirs is handed over and at every check, since any progress starts the stall count over and the rule alone bounded how long an unread answer lived, not how many one user held. A response with no socket, queued behind another on its connection, still counts no stall, but it now ends with its connection, which Node never did, so the response ahead going no longer leaves it held.
