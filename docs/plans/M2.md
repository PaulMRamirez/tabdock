# M2 plan: many clients, many users

Goal: several people and several MCP clients share one page safely. The operator sees who is attached and through which clients, changes roles and revokes from the widget, and sees every call in an activity log; the relay runs mutating calls one at a time per page, checks arguments, expires idle attachments and enforces the remaining section 9 limits. Built on M1 and ADRs 0005 and 0007; the owner's M2 choices are recorded in ADRs 0008 (argument validation) and 0009 (sessions, limits and idle expiry). SDK behaviour behind this plan was verified on 2 October 2026 and goes into `docs/notes/verified.md`.

## Relay: MCP sessions and attribution

`/mcp` keeps one endpoint and two legs, composed as the SDK documents: `isLegacyRequest` sends 2025-era traffic to a sessionful leg (one `WebStandardStreamableHTTPServerTransport` and one `McpServer` per session, created only for `initialize`), and everything else goes to `createMcpHandler` with `legacy: 'reject'`. Both legs sit behind the existing `toNodeHandler`, Host check and auth plugin. The SDK does not tie a session to a user, so the relay records each session's owner and answers 404 when another user presents its id (S13). Sessions end after 30 minutes with no open response; each user holds at most 20 (a new one evicts that user's least recently used idle session) and the relay at most 1000 (503 when full). A tool handler reads the caller's client from the session's `initialize` or the request's client info, so the roster names every client, and a client's cancellation now reaches the page as `cancel` with reason `client` on both legs. Revoke resolves the call with `not_attached` rather than closing the client's transport, which would leave it waiting.

## Relay: calls, limits and expiry

Mutating calls (any tool not marked read-only) wait in a per-page queue and run one at a time in arrival order; read-only calls go straight through. A queued call keeps its deadline, which counts from arrival, and leaves the queue on cancel, revoke or timeout; its role is checked again when it reaches the front. The limits (ADR 0009) are 10 users per page (`page_busy` at pairing or approval), 120 calls per user per page per minute (`rate_limited`), 32 queued mutating calls per page (`page_busy`), and 20 page sockets per address and 1000 in total, the oldest asleep page making way when full. Attachments expire after 8 hours without a call; each call moves `expiresAt`, the roster shows it, and an expired attachment behaves like a revoked one. Before forwarding, `call_page_tool` checks arguments against the tool's `inputSchema` with the SDK's bundled CfWorker validator, compiled once per tool from the page's uncut schema with regex keywords removed (ADR 0008); a mismatch returns `invalid_arguments` with relay-written text, and a schema the validator cannot handle skips the check.

## Adapter and widget

The `Dock` handle gains `setRole`, `revoke` (one user or everyone) and `pause`. Role changes are the operator's own, so they update the adapter's grant record before the frame goes out; the relay may still cap a driver at `maxDrivers`. The adapter runs mutating invokes one at a time even if a relay sends several, keeps the last 50 calls (time, user, client, tool, outcome, duration) as its activity log (S7), and while paused answers every call with `page_busy`. The widget's roster shows each user's role, clients and expiry with a role switch and Revoke, plus Revoke all; its buttons take clicks only once their row has held still, like the prompts. The panel adds the activity log and a pause switch. Everything relay-supplied still goes in through `textContent`.

## Tests and demo

Integration tests in `tests/e2e/test` run the relay, sim pages and MCP clients of both protocol eras: A2.1 (two users, three clients, roster lists them all), A2.2 (an observer refused by the relay, and by the adapter when a test relay skips its own check), A2.3 (twenty concurrent mutating calls from three clients run strictly one at a time in arrival order while reads interleave), A2.4 (revoke cancels an in-flight call and blocks the next) and A2.5 (a consequential tool prompts and deny returns `denied_by_operator`). Each new limit, session ownership, idle expiry, cancellation and argument validation gets its own test, and Playwright drives the roster controls, activity log and pause switch in Chromium. `pnpm demo:m2` narrates two users and three clients on one page, a refused observer, a burst of serialized writes, a revoke mid-call and a denied consequential call. The Claude Code check from M1 runs again against the new routing.
