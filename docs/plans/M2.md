# M2 plan: many clients, many users

Goal: several people and several MCP clients share one page safely. The operator sees who is attached and through which clients, changes roles and revokes from the widget, and sees every call in an activity log; the relay runs mutating calls one at a time per page, checks arguments, expires idle attachments and enforces the remaining section 9 limits. Built on M1 and ADRs 0005 and 0007; the owner's M2 choices are recorded in ADRs 0008 (argument validation) and 0009 (sessions, limits and idle expiry). SDK behaviour behind this plan was verified on 2 October 2026 and goes into `docs/notes/verified.md`.

## Relay: MCP sessions and attribution

`/mcp` keeps one endpoint and two legs, composed as the SDK documents: `isLegacyRequest` sends 2025-era traffic to a sessionful leg (one `WebStandardStreamableHTTPServerTransport` and one `McpServer` per session, created only for `initialize`), and everything else goes to `createMcpHandler` with `legacy: 'reject'`. Both legs sit behind the existing `toNodeHandler`, Host check and auth plugin. The SDK does not tie a session to a user, so the relay records each session's owner and answers 404 when another user presents its id (S13). Sessions end after 30 minutes with no open response; each user holds at most 20 (a new one evicts that user's least recently used idle session) and the relay at most 1000 (503 when full). A tool handler reads the caller's client from the session's `initialize` or the request's client info, so the roster names every client, and a client's cancellation now reaches the page as `cancel` with reason `client` on both legs. Revoke resolves the call with `not_attached` rather than closing the client's transport, which would leave it waiting.

## Relay: calls, limits and expiry

Mutating calls (any tool not marked read-only) wait in a per-page queue and run one at a time in arrival order; read-only calls go straight through. A queued call keeps its deadline, which counts from arrival, and leaves the queue on cancel, revoke or timeout; its role is checked again when it reaches the front. The limits (ADR 0009) are 10 users per page (`page_busy` at pairing or approval), 120 calls per user per page per minute (`rate_limited`), 32 queued mutating calls per page (`page_busy`), and 20 page sockets per address and 1000 in total, the oldest asleep page making way when full. Attachments expire after 8 hours without a call; each call moves `expiresAt`, the roster shows it, and an expired attachment behaves like a revoked one. Before forwarding, `call_page_tool` checks arguments against the tool's `inputSchema` with the SDK's bundled CfWorker validator, on a worker thread with a 50 ms budget (ADR 0010), over a copy of the page's uncut schema with its regexes, `format` and `uniqueItems` removed (ADR 0008); a mismatch returns `invalid_arguments` with relay-written text, and a schema or check the validator cannot handle in time lets the call through unchecked.

## Adapter and widget

The `Dock` handle gains `setRole`, `revoke` (one user or everyone) and `pause`. Role changes are the operator's own, so they update the adapter's grant record before the frame goes out; the relay may still cap a driver at `maxDrivers`. The adapter runs mutating invokes one at a time even if a relay sends several, keeps the last 50 calls (time, user, client, tool, outcome, duration) as its activity log (S7), and while paused answers every call with `page_busy`. The widget's roster shows each user's role, clients and expiry with a role switch and Revoke, plus Revoke all; its buttons take clicks only once their row has held still, like the prompts. The panel adds the activity log and a pause switch. Everything relay-supplied still goes in through `textContent`.

## Tests and demo

Integration tests in `tests/e2e/test` run the relay, sim pages and MCP clients of both protocol eras: A2.1 (two users, three clients, roster lists them all), A2.2 (an observer refused by the relay, and by the adapter when a test relay skips its own check), A2.3 (twenty concurrent mutating calls from three clients run strictly one at a time in arrival order while reads interleave), A2.4 (revoke cancels an in-flight call and blocks the next) and A2.5 (a consequential tool prompts and deny returns `denied_by_operator`). Each new limit, session ownership, idle expiry, cancellation and argument validation gets its own test, and Playwright drives the roster controls, activity log and pause switch in Chromium. `pnpm demo:m2` narrates two users and three clients on one page, a refused observer, a burst of serialized writes, a revoke mid-call and a denied consequential call. The Claude Code check from M1 runs again against the new routing.

## Deviations recorded during the build

The relay's schema copy drops `format` as well as the page's regexes, and loosens more than ADR 0008 lists so it never rejects what the page accepts (the ADR's notes say how). Invalid calls count toward the call limit, so nobody spins on them for free. A write takes its place in the queue on arrival, before its argument check answers, and the queue waits at a head still being checked, so arrival order holds whatever the checks cost. Queue depth counts waiting calls, so a page can have one write running and 32 waiting; a queued call that never ran times out at its deadline, with text saying it waited, while a running one keeps M1's grace. Users per page counts attachments, not pending requests, and is checked again at approval. The page-session limits count awake and asleep sessions per creating address and in total, with open sockets refused separately before the upgrade, and room is made only for a new page, never a resume (ADR 0009's notes). Roster frames sent only because an expiry moved are throttled (at most one a minute per page), since every roster change makes the widget's buttons wait again and a busy client could otherwise keep the operator from clicking Revoke; the shown expiry can therefore run up to that much early, never late. A 2025-era client keeps its session while its GET stream stays open, bounded by the 20-per-user cap. The SDK marks `getClientVersion()` deprecated, so the one `eslint-disable` in the repo says why it is still used.

On the page, pause also refuses calls that arrived but have not started (queued, reading tools or waiting on a prompt) and takes their prompts down, and it holds across reloads, new sessions and a detach of the same page in the same tab until the operator resumes; another page of the site starts with its own session, pause and approvals (ADR 0011). Revoke also ends the revoked user's calls on the page at once, without waiting for the relay, and is kept in `sessionStorage` and sent again on resume, across a reload too, if the relay still lists that user; a user revoked but still listed is refused meanwhile. A write answered early (a cancel, its deadline, a revoke) keeps the page until its handler ends, so writes never overlap even on the polyfill, which cannot stop a handler, unless the page unregisters a running write's tool there, in which case the page is held until that call's deadline plus 2 s (ADR 0001's notes). An invoke reusing the id of a call still listed or still holding the page is ignored. The roster shows the role the page enforces, the lesser of its own grant and the relay's claim; a row the page never approved says so and offers only Revoke, and a denial for a user the relay does not list withdraws any grant the relay never applied. A revoked call that was waiting on a prompt shows as `denied_by_operator` in the page's log and `not_attached` in the relay's audit. The page also caps waiting writes at 32, re-checks the role after the operator allows a consequential call, and logs calls it abandons on a dropped link as `cancelled`. The activity log lives in memory, so a reload starts it empty. Revoke all is not armed, as it only removes access; roster rows and the pause switch are, and the role switch is disabled while the link is down. The panel is wider (360 px) and may be as tall as the window, so two prompts and the new sections fit without scrolling on a laptop.
