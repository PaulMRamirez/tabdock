# M4 plan: local mode, real sign-in, a reference deployment and invites

Goal: with no settings the relay runs in local mode for clients on its own machine (A4.4); with settings it runs at a stable public URL on any host meeting SPEC section 11, where Claude on the web and the phone signs in through a production provider and a second account joins a page by watch and control invites (A4.2); S1 to S14 are tested (A4.1), with a persistent audit log, a container image, a deploy guide and a threat model; and a second reviewer pass leaves no high-severity issue open (A4.3). ADRs 0017 to 0022 make every SPEC change. The owner accepted all six on 3 October. The research and decisions are in `docs/notes/m4/`, the facts in `docs/notes/verified.md`.

## Local mode first

On 3 October the owner asked for a batteries-included local relay that dictates no infrastructure (ADR 0022). With no `.env`, `pnpm relay` runs the relay alone and `pnpm dev` adds the demo board. On first run the relay draws a 256-bit owner token into a private per-user file outside the repo and maps it to one user, `you`, through the existing `createDevTokenAuth`. It binds loopback only, refuses proxied requests, is refused in production and with a public URL, gives way to explicit settings, and trusts every account on its machine. The banner prints a ready `claude mcp add ... tabdock-local` that reads the file, never the token. Only clients on the same machine can use it; Claude on the web, desktop and phone needs public URL mode. It is workstream 0 and lands first, since it is small and every later test and demo can start from it: `local-token.ts`; `config.ts` with the `loopbackOnly` marker on `AuthPlugin`; the forwarded-header refusal in `relay.ts`; both banners and a root `relay` script; `scripts/spike/latency.ts`, which reads the token file (never creating it) when neither `TABDOCK_SPIKE_TOKEN` nor `TABDOCK_DEV_TOKENS` is set; `.env.example`, the READMEs and the M1 tour. Local mode gains its audit directory, `audit/` beside the token, when `FileAuditLog` lands in workstream C.

The token file in detail: the resolver reads `TABDOCK_HOME` (absolute only), `XDG_CONFIG_HOME` (used only when absolute), `HOME`, `LOCALAPPDATA` and `USERPROFILE` only from the environment object it is given, with platform, uid and home directory injected, and the vitest setup points all five at temporary directories. A new token goes to a temporary name (`O_CREAT | O_EXCL`, 0600), is synced and hard-linked to `owner-token`, which fails if the name exists, and the loser of a race reads the winner's file. A file over 64 bytes or not matching `^tabdock_[A-Za-z0-9_-]{43}\n?$` is malformed. Each start opens the file without following a symlink and checks it through the descriptor, and every refusal names the fix ("chmod 600", "chmod 700", "delete it and start again"), never the contents. Paths compare by `realpath`, case-insensitively on macOS and Windows. On Windows `lstat` checks for a regular file and the directory must lie under `%LOCALAPPDATA%` or `%USERPROFILE%`. PowerShell reads the file with `$(Get-Content -TotalCount 1 -LiteralPath '<path>')`, and each shell's form single-quotes the path.

## Decisions and defaults

The owner's hosted choices are the project's reference deployment, written up in `docs/deploy.md` as one worked example, not a requirement: Fly.io, one 512 MB Machine in `iad` with a 1 GB volume, deployed from GitHub Actions (D1); `relay.<domain>` on a DNS-only record, the domain kept out of the repo (D2); WorkOS production with email sign-in and open sign-up (D4); and `apps/demo` on GitHub Pages at `demo.<domain>` unless the owner picks `<user>.github.io` (D6). SPEC requires only what a host and a provider must do; Fly.io, WorkOS and the owner's domain appear only in section 3's facts and where SPEC names the reference deployment as an example (sections 4, 7 and 11), never as a requirement.

Defaults: D3 option A (only the audit log persists; a restart detaches everyone); D5 option A (a distroless runtime image, digests and action SHAs pinned, `anchore/scan-action`, never `trivy-action`); Node 22 until a move to 24 before 30 April 2027; deploys only by manual dispatch of an image digest behind a reviewed GitHub environment; an audit log that fails open, kept 30 days or 64 MiB; `TABDOCK_INVITES` off unless set; no revocation feed; `pnpm audit:log` as the reader. No new npm runtime dependency is needed.

Section 9 changes: S7 narrows for refused calls (0019); S9 adds per-user request limits, a budget for held tool lists, and per-address page sessions and sign-ins (0018); S12 allows a plaintext listener behind a TLS-terminating edge (0018); S14 grows to every invite rule (0017). The owner accepted ADR 0019's narrowing of S7 on 3 October: past a budget, a refused call that reached no page keeps only its user and outcome, and a stranger outside the 20 busiest only its outcome, so strangers cannot flush the log; a call that reaches a page is always logged in full. Local mode changes no section 9 text: it keeps S7's log on disk and holds S4 to S8 and S13 on a machine whose accounts are trusted.

## Workstreams

**A, relay:** invites, the invitee tier, `invite_required` and the role cap (0017); ADR 0020's token checks and email claims; `/i` beside `/pair`; the request and refusal budgets. A owns `pair.ts`, `/i` and the sign-in flow (the `openid email` scope, the email claims, the return target), `auth-log.ts`, the invitee session pool in `sessions.ts` and the invite paths of `hub.ts`. **B, adapter and widget:** the adapter's own invite record, the role cap and `endsAt`, and no redemption clearing a revoke (today any approval does, `core.ts:1783`); the Invite form, live list, Revoke and QR code; the demo's `?invites=all` and its refusal to attach in a frame. B owns `packages/adapter`, `packages/sim-page` and `apps/demo/**`; the frame refusal lives in the page code, in every build or behind a define B adds to `apps/demo/scripts/server.ts` itself. **C, host and audit:** hosted mode, the client address (`createClientAddresses`) and the per-address limits (0018), the sign-in share in `sign-in-gate.ts`; `FileAuditLog` (0019); an image that names no host, which CI builds, scans, smoke-tests and attests; and the reference deployment's `deploy/fly/fly.toml`, dispatch-only workflow and `docs/deploy.md`, the home of operational detail. C owns `.github/workflows`, including a new Pages workflow that runs the demo's existing static build and edits nothing under `apps/demo`. `docs/threat-model.md` follows OWASP's four questions with one STRIDE row per trust boundary, naming its S-numbers, tests and residual risks. Local mode's row records that it trusts every account on the machine (another can take the port while the relay is down, and all share the per-address page limits), that user scope gives every Claude Code session the relay's tools, and that `claude mcp get` and command-line auditing expose the token.

## Tests

Local mode: no settings give local mode, each explicit setting wins, each hosted-only setting is refused outside its mode, production without auth settings is refused, and a `loopbackOnly` plugin under any name is refused with a public URL, in production or off loopback (the `loadConfigFromEnv({})` test becomes a local-mode test). A first start creates a 0700 directory and a 0600 file, a second reuses it byte for byte, and two at once end with one token; each refusal above is tested with the fix named and nothing echoed, owner and readability through an injected `stat` and uid (the sandbox runs as root), paths and the Windows rule through an injected platform and environment. `pnpm relay` and `pnpm dev` run as children against a temporary `TABDOCK_HOME`, and no stdout, stderr or log sink line holds the token, its digest or any 8-character run of its 43 random characters. No token, a wrong one or a dev token gets 401, and the right one is `you`, whose pairing still waits for the operator. Without a public URL, `/mcp` and `/page` each refuse `Forwarded` and `X-Forwarded-For` with 403. The printed POSIX line runs through `sh -c` against a stub `claude`, from a path holding a space and a quote, and must pass exactly `Authorization: Bearer <token>`; the PowerShell line is checked as text, and run where `pwsh` exists. `check:claude-code:local` runs the line with an installed `claude` in a throwaway HOME until `claude mcp list` shows the relay connected, with no model calls (A4.4); with no `claude` on the PATH it skips and records a checklist item, since Claude Code is not a repo dependency.

S14 gets one test per clause, and S5, S7, S9 and S11 gain cases from ADRs 0017 to 0020. A4.1 runs in the sandbox with stand-ins for provider and edge; CI checks the image. For A4.3 a separate reviewer runs the section 9 lenses plus supply chain, a skeptic re-checks each finding, each fix lands with a test, and a fresh agent blind to the findings must find no unaddressed high-severity issue.
