# M3 plan: phone

Goal: Claude on the owner's phone attaches to a page on the laptop and calls its tools, through a public HTTPS address and real sign-in, and the spike measures whether that is good enough (A3.1 to A3.4). Built on M2 and the owner's M3 decisions, recorded in ADR 0013 (WorkOS AuthKit issues tokens, the relay checks them with `jose`, the phone signs in at `/pair` with `openid-client`, tests use `oauth2-mock-server`) and ADR 0014 (public URL mode behind an ngrok static domain, OAuth only when public, the page link kept local, a spike flag for A3.3). ADR 0015 proposes the SPEC section 3 and 12 facts. The research is in `docs/notes/m3/`, and its facts are in `docs/notes/verified.md`.

## Relay: sign-in and public URL mode

The auth plugin contract changes first, since everything else rests on it: `authenticate(request)` returns a user or a refusal with its status and challenge, and a plugin may serve GET routes. The `oauth` plugin checks the provider's RFC 8414 metadata at startup (matching `issuer`, S256, and client metadata documents with `none` or a registration endpoint), serves RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` naming the provider, and verifies each token with the SDK's `verifyBearerToken` over a `jose` verifier (signature by the provider's keys, RS256 only, `iss`, `aud` equal to the public MCP URL, `exp`), throwing the SDK's `OAuthError` so a bad token is a 401 and never a 500. A token's `sub` maps to a user through `TABDOCK_OAUTH_USERS`; anyone else gets a plain 403. Every unauthenticated `/mcp` request, on both legs, gets the 401 challenge with `resource_metadata` before the SDK runs. `TABDOCK_PUBLIC_URL` (https only) switches on public mode: its host joins the Host allowlist and sets the metadata `resource`, the token audience and the pairing URL; production rules apply; dev tokens are refused; and `/page` upgrades through the public host are refused, so only local pages attach. If the first tunnel check shows streamed responses do not pass, the 2025-era leg answers POSTs with plain JSON instead. Tokens, cookies, nonces and codes never reach a log.

## The QR flow at /pair

Each pairing ticket gains a 128-bit nonce, bound to its page, single use, 120 s, stored hashed, and the `pairing` frame's `url` becomes `<public URL>/pair#<nonce>`, so the nonce never appears in a server or tunnel log. `GET /pair` is a static page under a strict CSP that reads and clears the fragment. `/pair/login` and `/pair/callback` sign the phone in with `openid-client` (authorization code with PKCE) and set a `__Host-` session cookie. A preview, which consumes nothing, shows the page's origin, title and current code to match against the widget; `POST /pair/claim`, from a signed-in session on the same origin, consumes the nonce, rotates the ticket and sends the operator an attach request `via: 'qr'`, and the phone then waits on a status route until the operator decides. Unknown, used and expired nonces share one error, and rate limits count per user, since every request behind the tunnel arrives from the same address (S3, S11).

## Widget QR

The adapter draws the pairing URL as a QR code with `qrcode-generator` (already approved), level M, as one SVG path built with DOM calls inside the closed shadow root, never the library's SVG string or data URL, which pages with Trusted Types block. It appears only when the frame carries a URL, redraws on each new code, keeps the typed code beside it, and never logs the URL.

## Spike measurements

`scripts/spike/latency.ts` signs in once through OAuth and times 50 sequential `get_view` calls over the public URL after 5 warm-up calls, reporting p50 and p95 and, from relay timestamps, how much is tunnel and how much page. The same timestamps time a QR pairing from scan to first call. The spike flag adds a marker tool on demand and logs every tool list Claude fetches, for A3.3's question of whether hosted Claude sees a list change mid-chat. `scripts/spike/soak.ts` freezes the page through Chrome DevTools for a 60-minute hidden soak that checks reconnect and resume, and offers a CPU-busy page for the manual Energy Saver run. Results go to `docs/notes/spike.md`, which the owner's runs complete, ending in the A3.4 go or no-go note.

## Tests and demo

In the sandbox, against `oauth2-mock-server`: valid tokens; expired, wrong audience or issuer, unsigned, unknown key and missing expiry refused; an unknown user 403; no or malformed header 401 with `resource_metadata` on both legs; the metadata documents; a provider whose metadata does not match refused at startup; and the client SDK's whole OAuth flow through relay and mock provider. Public mode: an http public URL refused, the Host allowlist, dev tokens refused, `/page` refused through the public host. `/pair`: nonce single use, expiry and rotation; the nonce never in the log sink; a claim without a session or from another origin refused; a preview that consumes nothing; rate limits; approve, deny and timeout. Playwright: the widget QR under a Trusted Types CSP, decoding to the pairing URL; a phone-sized browser going from scan URL through mock sign-in, claim and approval to a first call; a frozen tab recovering. `pnpm demo:m3` runs all of it locally with the mock provider from a clean clone. Claude Code signs in against the mock provider if practical.

## For the owner

`docs/checklists/M3.md` holds what needs the laptop and phone: create the WorkOS and ngrok accounts and enter the settings `pnpm dev:public` prints; check a streamed response through the tunnel first; add the connector on claude.ai on the laptop and sign in; pair from the phone by code and by QR and call tools (A3.1, A3.2); run the latency and tool-list measurements; run the soaks (60 minutes in the background, Energy Saver, laptop sleep); and write the A3.4 note.
