# M3 plan: phone

Goal: Claude on the owner's phone attaches to a page on the laptop and calls its tools, through a public HTTPS address and real sign-in, and the spike measures whether that is good enough (A3.1 to A3.4). Built on M2 and the owner's M3 decisions, recorded in ADR 0013 (WorkOS AuthKit issues tokens, the relay checks them with `jose`, the phone signs in at `/pair` with `openid-client`, tests use `oauth2-mock-server`) and ADR 0014 (public URL mode behind an ngrok static domain, OAuth only when public, the page link kept local, a spike flag for A3.3). ADR 0015 proposes the SPEC section 3 and 12 facts. The research is in `docs/notes/m3/`, and its facts are in `docs/notes/verified.md`.

## Relay: sign-in and public URL mode

The auth plugin contract changes first, since everything else rests on it: `authenticate(request)` returns a user or a refusal with its status and challenge, and a plugin may serve GET routes. The `oauth` plugin checks the provider's RFC 8414 metadata at startup (matching `issuer`, S256, and client metadata documents with `none` or a registration endpoint), serves RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` naming the provider, and verifies each token with the SDK's `verifyBearerToken` over a `jose` verifier (signature by the provider's keys, RS256 only, `iss`, `aud` equal to the public MCP URL, `exp`), throwing the SDK's `OAuthError` so a bad token is a 401 and never a 500. A token's `sub` maps to a user through `TABDOCK_OAUTH_USERS`; anyone else gets a plain 403. Every unauthenticated `/mcp` request, on both legs, gets the 401 challenge with `resource_metadata` before the SDK runs. `TABDOCK_PUBLIC_URL` (https only) switches on public mode: its host joins the Host allowlist and sets the metadata `resource`, the token audience and the pairing URL; production rules apply; dev tokens are refused; and `/page` upgrades through the public host are refused, so only local pages attach. If the first tunnel check shows streamed responses do not pass, the 2025-era leg answers POSTs with plain JSON instead. Tokens, cookies, nonces and codes never reach a log.

## The QR flow at /pair

ADR 0016 (invites, built in M4) shapes this work: the pairing nonce is stored as a generic single-use ticket keyed by hash with a kind, so invites reuse it; the account mapping returns the account's kind and `/pair/claim` accepts members only; requests are logged by route rather than raw path; and pairing limits on `/mcp` count per user, since every caller behind the tunnel shares an address.

Each pairing ticket gains a 128-bit nonce, bound to its page, single use, 120 s, stored hashed, and the `pairing` frame's `url` becomes `<public URL>/pair#<nonce>`, so the nonce never appears in a server or tunnel log. `GET /pair` is a static page under a strict CSP that reads and clears the fragment. `/pair/login` and `/pair/callback` sign the phone in with `openid-client` (authorization code with PKCE) and set a `__Host-` session cookie. A preview, which consumes nothing, shows the page's origin, title and current code to match against the widget; `POST /pair/claim`, from a signed-in session on the same origin, consumes the nonce, rotates the ticket and sends the operator an attach request `via: 'qr'`, and the phone then waits on a status route until the operator decides. Unknown, used and expired nonces share one error, and rate limits count per user, since every request behind the tunnel arrives from the same address (S3, S11).

## Widget QR

The adapter draws the pairing URL as a QR code with `qrcode-generator` (already approved), level M, as one SVG path built with DOM calls inside the closed shadow root, never the library's SVG string or data URL, which pages with Trusted Types block. It appears only when the frame carries a URL, redraws on each new code, keeps the typed code beside it, and never logs the URL.

## Spike measurements

The spike flag is `TABDOCK_SPIKE` (refused in production): the owner adds or removes a marker tool by typing `add`, `remove` or `status` in the relay's terminal, never over HTTP, and each `call_page_tool` result carries its timings under `_meta['tabdock/spikeTiming']`. `scripts/spike/latency.ts` signs in once through OAuth and times 50 sequential `get_view` calls over the public URL after 5 warm-up calls, reporting p50 and p95 and, from relay timestamps, how much is tunnel and how much page. The same timestamps time a QR pairing from scan to first call. The spike flag adds a marker tool on demand and logs every tool list Claude fetches, for A3.3's question of whether hosted Claude sees a list change mid-chat. `scripts/spike/soak.ts` freezes the page through Chrome DevTools for a 60-minute hidden soak that checks reconnect and resume, and offers a CPU-busy page for the manual Energy Saver run. Results go to `docs/notes/spike.md`, which the owner's runs complete, ending in the A3.4 go or no-go note.

## Tests and demo

In the sandbox, against `oauth2-mock-server`: valid tokens; expired, wrong audience or issuer, unsigned, unknown key and missing expiry refused; an unknown user 403; no or malformed header 401 with `resource_metadata` on both legs; the metadata documents; a provider whose metadata does not match refused at startup; and the client SDK's whole OAuth flow through relay and mock provider. Public mode: an http public URL refused, the Host allowlist, dev tokens refused, `/page` refused through the public host. `/pair`: nonce single use, expiry and rotation; the nonce never in the log sink; a claim without a session or from another origin refused; a preview that consumes nothing; rate limits; approve, deny and timeout. Playwright: the widget QR under a Trusted Types CSP, decoding to the pairing URL; a phone-sized browser going from scan URL through mock sign-in, claim and approval to a first call; a frozen tab recovering. `pnpm demo:m3` runs all of it locally with the mock provider from a clean clone. Claude Code signs in against the mock provider if practical.

## For the owner

`docs/checklists/M3.md` holds what needs the laptop and phone: create the WorkOS and ngrok accounts and enter the settings `pnpm dev:public` prints; check a streamed response through the tunnel first; add the connector on claude.ai on the laptop and sign in; pair from the phone by code and by QR and call tools (A3.1, A3.2); run the latency and tool-list measurements; run the soaks (60 minutes in the background, Energy Saver, laptop sleep); and write the A3.4 note.

## Order of work

Plan and ADRs first; then the auth plugin contract; then three workstreams in parallel (relay sign-in and public mode, `/pair` and the widget QR, spike scripts and their tests); then integration, the section 9 review with adversarial verification, the explainer `docs/tour/03-phone.md`, the checklist, the pull request and the report.

## Notes after the build

The phone waits on `/pair` before claiming: the preview shows the page and its code, and the claim runs only when the person taps Join, so a link opened by accident spends nothing. Pairing limits count per user and per page (30 attempts a minute per page), never per address, since every request through the tunnel shares one; the relay no longer keys any `/mcp` limit on a caller address (only the line logged for a refused `/mcp` request still notes the socket address, which behind the tunnel is loopback). The widget draws a QR code only for the shape the relay builds, `<https origin>/pair#<22 base64url characters>`, spelled exactly as that shape rebuilt from the parsed URL, so the drawn text is the text that was checked; anything else shows the typed code alone. The drawing carries its own white ground and 124 px size as SVG attributes, and the widget's styles go in as a constructed stylesheet, which no `style-src` governs, with the `<style>` element only where a browser cannot adopt one, so a page whose CSP leaves out `unsafe-inline` still shows the widget and a code a phone can read. `pnpm dev:public` names every missing setting at once (the public URL, the issuer, the users, the `/pair` client id and secret, and `TABDOCK_ALLOWED_ORIGINS`, which public mode needs listed) and prints the values to enter at the provider and in Claude; it never prints a secret. `pnpm demo:m3` runs sign-in, code pairing and QR pairing from a phone-sized browser against the mock provider and an https stand-in for the public URL, and prints a sample of the scan-to-first-call milestones, which come only from the spike hooks in `spike.ts`. `pnpm spike:soak --quick` runs three 40 s freeze cycles in about three minutes, and CI runs one short cycle of the same logic in `tests/e2e/specs/soak.spec.ts`; the full 60-minute soak is the owner's. The Claude Code check (`pnpm --filter @tabdock/e2e check:claude-code:m3`) signs Claude Code 2.1.288 in through the relay's 401 and metadata via CIMD and finds it Connected; it needs the installed CLI, so it stays out of CI. The plain-JSON fallback for the 2025-era leg waits on the owner's first streamed response through ngrok and is built only if that fails.

The section 9 review (five lenses, each finding re-checked by a skeptic with its own probe, then each fix branch attacked by a second skeptic) confirmed one medium and eight low findings, all fixed with tests that fail without the fix. The medium one: `/pair/preview` recorded any well-formed nonce in its limiter before checking it, and the limiter then swept every key on every insert, so an anonymous flood could tie up the relay. Previews now look a nonce up first and count only live ones, and the limiter (`rate-limit.ts`) keeps its keys in two generations, so each call costs the same however many keys it holds. The low ones: code exchanges at `/pair/callback` are bounded relay-wide (8 at once, 60 a minute; ADR 0013's notes give the trade-off); a failed key set fetch is retried no sooner than its `Retry-After`; `Host` is parsed strictly and compared exactly, and more than one `Host` line is a 400, however many header lines come between them, as is a proxy header anywhere on a `/page` upgrade in public mode (ADR 0014's notes); the QR code draws only the canonical pairing URL and styles itself; a test now proves the `/pair` sign-in checks the ID token's signature; `demo:m3` checks that the relay, not the page, refused the observer's write; and the spike's milestone test runs on an injected clock.
