# M1 plan: walking skeleton

Goal: the first end-to-end Tabdock path. A page running the adapter dials the relay, shows a pairing code, and its operator approves an MCP client that paired with that code; the client then lists the page and calls its tools through the five fixed tools. Everything runs on one machine with dev tokens. Built on the M0 measurements and ADRs 0001 (runtime variance) and 0005 (pair_page wait and SDK mode); ADR 0002 option C, accepted by the owner during M1, decides which tools are consequential.

## Contract first

`packages/protocol` defines the page link (SPEC section 6) as zod schemas, with types inferred from them, plus every shared number: frame and result caps, ping and resume timings, pairing and attach lifetimes. Relay and adapter both parse every frame with it. Unknown frame types are ignored and logged; a malformed frame of a known type closes the socket with 1008. Logs and parse errors carry paths, never values.

## Relay (`packages/relay`)

One Node process on `node:http`: `ws` handles `/page` on upgrade, and the official MCP SDK v2 (`createMcpHandler` through `@modelcontextprotocol/node`) handles `/mcp`. It binds 127.0.0.1 and refuses any other address until TLS arrives in M4 (S12).

`/page` requires subprotocol `tabdock.v1` and an `Origin` header on the allowlist, checked before the upgrade: localhost and 127.0.0.1 origins by default in dev, and an explicit list in production, without which the relay refuses to start (S1, S2). A dev flag allows header-less sockets for the sim page only. The first frame must be `hello` within 10 s. A valid resume token from the same origin resumes the session with its page id and attachments, and every welcome rotates the token. A socket drop makes the page asleep; after ten minutes it is gone, its attachments are deleted, and a short tombstone lets callers see `page_gone`. Pings every 15 s; 30 s of silence closes the socket.

Pairing (S3): one live ticket per page, a 10-character Crockford base32 code (50 bits) shown as `XXXXX-XXXXX`, valid 120 s, single use, rotated on use and on expiry, looked up by hash and compared in constant time. Attempts are rate limited per user and per client address. A wrong and an expired code both return `pairing_expired`, because the spec has no separate code and telling them apart would confirm that a code once existed. A matched code creates an attach request (60 s, deny on silence) unless the page set `autoApprove: 'observer'`, which attaches at once as observer (S4). `pair_page` waits at most 50 s (ADR 0005); an approval after that still creates the attachment.

`/mcp` authenticates every request with the auth plugin (`authenticate(request)` returns a user or null; M1 ships `dev-token`, users and tokens from `.env`), validates `Host` against localhost, and serves `list_pages`, `pair_page`, `list_page_tools`, `call_page_tool` and `detach_page`. Every check is against the caller's attachments, so an unknown page and someone else's page give the same `not_attached` (S13). The relay enforces roles (observers call only read-only tools, S5), labels every page result with the untrusted header and passes JSON through as structured content, cuts descriptions to 1000 characters and results to 120,000 (S9, S10), and writes an audit record per call without arguments (S7). Tokens, codes and resume tokens never reach a log (S11). The store sits behind an interface so M4 can persist the audit log.

## Adapter (`packages/adapter`)

A core that knows nothing about the DOM, taking a socket factory, a model context, storage and a UI port, plus a browser entry that wires `WebSocket`, `document.modelContext`, `sessionStorage` and a widget in a closed shadow root. `attach()` returns the only control handle. The core reads tools with `getTools()`, normalises string schemas, re-sends the full list on every `toolchange` and on a 2 s poll when it changed, and runs calls with `executeTool`, detecting the input format per page (ADR 0001). It checks role and consequential policy again before running anything (S5, S6; a consequential tool prompts unless policy says otherwise, and silence denies), cuts results to the frame limit, aborts on `cancel` or deadline, reconnects with backoff from 0.5 to 30 s using the resume token, and holds a Web Lock while connected. The M1 widget is minimal: a badge with link state, attached count and the pairing code, and Allow as driver, Allow as observer and Deny on each attach request. A script-tag build reads the same options from data attributes.

## Sim page (`packages/sim-page`)

The adapter core in Node with a fake `document.modelContext` that can behave like the polyfill, Chrome 154 or Chrome 156 (from `docs/notes/baseline.md`), a `ws` client that sends an `Origin` header, and a scripted operator.

## Tests and demo

Vitest integration tests run the relay, sim pages and the MCP client in one process: A1.1 (pair, approve, list, call), A1.3 (reload inside the resume window keeps attachments), A1.4 (wrong code, expired code, denial), and a test for each S-requirement M1 can already prove (S1 to S4, S10 to S13, and the relay half of S5, S7 and S9). Playwright drives the real adapter on the demo page in Chromium. A1.2 is scripted with the real Claude Code CLI over HTTP with a bearer header, as A0.2 was. `pnpm dev` runs relay and demo together with dev tokens from `.env`; `pnpm demo:m1` generates its own tokens and narrates one pairing and a few calls.

## Order of work

Protocol, plan and ADR first; then relay and adapter with sim page in parallel, each with unit tests; then integration, demo and A1.2; then the section 9 review with adversarial checks; then the explainer `docs/tour/01-walking-skeleton.md`, checklist, pull request and report.

## Deviations recorded during the build

The relay leaves `structuredContent` out of a truncated result, so the full JSON cannot slip past the 120,000-character cap. It refuses arguments whose invoke frame would exceed 1 MB before sending them (ADR 0007 settles how that error reads). A refused resume (unknown token, gone page or another origin) starts a fresh session with `resumed: false` instead of closing the socket. `list_page_tools` on an asleep page returns `page_asleep`. `call_page_tool` sets `_meta['anthropic/maxResultSizeChars']` so Claude Code keeps results up to the cap inline. The listing tools start with a fixed untrusted-content line, and page schemas in `list_page_tools` have their descriptions cut like tool descriptions. Silence on an attach request returns `timeout` from `pair_page` (ADR 0007). The pairing code sits in the widget's panel, which opens on its own while nobody is attached, rather than on the badge itself. The protocol gained a close-code table (ADR 0007). After the M1 review: the adapter keeps its own record of the roles the operator granted (in `sessionStorage` beside the resume token, so a reload keeps it) and runs a call only under the least privileged of that grant, the roster and the claimed role; each widget prompt box takes clicks only 500 ms after it appears or last moves, and a click on a box that has moved since is ignored; page schemas are cut and capped and `list_page_tools` stays under the result cap with a visible count of tools left out; an asleep page holds no tools until it resumes; and the relay's call timer runs 2 s past the page's deadline. A second `pair_page` from a user with a request already pending waits on that request (one prompt per user per page), and the first approval sets the role (ADR 0007); a user the roster drops loses the adapter's grant. Page schemas have every string cut to 1000 characters, non-string descriptions replaced, and any key over that length removes the schema. A resumed page answers `page_asleep` (reconnecting) until its tools arrive, and `list_page_tools` carries the same result-size hint as `call_page_tool`. One edge stays: an approval clicked just as the request expires is ignored by the relay but kept by the page until the next welcome; because the first approval wins and the roster caps every call, it can never raise a role.
