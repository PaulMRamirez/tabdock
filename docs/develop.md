# Developing Tabdock

Node 22.18 or later (it runs TypeScript files directly, with no build step for the relay) and pnpm 10, which Corepack installs from the root `packageManager` field (`corepack enable pnpm`). The repository is a pnpm workspace: `packages/protocol`, `packages/relay`, `packages/adapter` and `packages/sim-page`, `apps/demo` and `apps/map-demo`, and `tests/*`. `apps/site`, which builds the GitHub Pages site, stays outside it with its own lockfile (ADR 0029), so a clean clone's `pnpm install` never fetches mermaid and its hundred-odd packages.

## Every command

```sh
pnpm install       # the workspace, from pnpm-lock.yaml
pnpm test          # unit and integration tests (vitest), no browser needed
pnpm lint          # eslint and prettier --check
pnpm format        # prettier --write
pnpm typecheck     # tsc over the root scripts and every workspace package
pnpm build         # each package's build, where it has one
pnpm test:e2e      # browser tests (Playwright; fetches Chromium on first run)
pnpm conformance   # the official MCP conformance suite's 2025-11-25 and 2026-07-28 sets against a local relay
pnpm ci-check      # tests/ci-check: the CI check's walk of the canvas map page in local mode, then its audit

pnpm relay         # the relay alone; local mode with no settings, printing the command for Claude Code
pnpm relay --new-token  # the same, after replacing local mode's owner token in one rename
pnpm dev           # relay and demo board together, local mode unless .env says otherwise
pnpm dev:public    # the same in public URL mode, for Claude on a phone through a tunnel
pnpm dev:demo      # the demo board alone at http://127.0.0.1:5173/
pnpm dev:map       # the canvas map page alone at http://127.0.0.1:5174/ (tests/map-page)
pnpm dev:map-demo  # the map demo alone at http://127.0.0.1:5175/ (apps/map-demo)
pnpm record:map-demo  # a captioned video of a client driving the map demo, kept in apps/map-demo/media/ within budget
pnpm audit:log     # read the persistent audit log, or --verify its chain

pnpm demo:m0       # the M0 baseline through MCP-B's local relay, narrated
pnpm demo:m1       # an MCP client pairs with the demo board through the Tabdock relay
pnpm demo:m2       # two users and three clients share the board: roles, the write queue, revoke
pnpm demo:m3       # sign-in, pairing by code and by the widget's QR code from a phone-sized browser
pnpm demo:m4       # local mode, then a page shared by watch and control invites, and the audit log
pnpm demo:m5       # first-class page tools on both MCP revisions, and a call confirmed in the client
pnpm demo:m6       # a class on one map tab: state, a capture, a proposal, members, a session, 40 watchers, an agent, a restart, the record

pnpm site:build    # the Pages site into apps/site/dist: the demo at /, the map demo at /map/, docs/tour at /tour/, docs/guide at /guide/

pnpm release:pack  # build and pack the three npm packages into dist/packages, publishing nothing
pnpm release:check # check those tarballs file by file (add --tag v0.1.0 to match a tag)
pnpm pack:install  # install those tarballs in a scratch directory and run tabdock-relay as A5.5 asks
pnpm spike:latency # the M3 spike's call timings against a running relay
pnpm spike:soak    # the M3 spike's long run with a busy page
pnpm measure:room  # ADR 0044's room measurement, by hand, as root: about 75 minutes (docs/notes/m6/room-measure.md)
```

`pnpm conformance` is what CI runs after the tests: it starts a relay of its own behind a loopback proxy that adds a token drawn for the run, and holds each requirement set to its checked-in baseline in `tests/e2e/conformance`. `pnpm ci-check` is what CI's `ci-check` job runs, with no secret (ADR 0041): `scripts/ci-check.ts` gives `tests/ci-check` a fresh `TABDOCK_HOME` (the job puts it under the runner's temporary directory and deletes it after), runs its Playwright walk of the canvas map page against local mode at its defaults, prints the output only after scanning it (any form of the owner token or an unmasked pairing code fails the run and withholds it), and then verifies the audit chain and holds its call records to the walk's page calls; `pnpm ci-check --advisory` runs the advisory walk with a signed-in Claude Code instead, by hand and never in CI. The three release commands are what CI's `pack-install` job and `publish.yml` run; `docs/release.md` says how a release is made. `pnpm --filter @tabdock/e2e <script>` runs the end-to-end package's own scripts: `baseline` re-measures the M0 baseline, and the `check:claude-code` scripts drive a real Claude Code against a relay in the sandbox, among them `check:claude-code:images` (an image result as Claude Code hands it to its model, against a stand-in for the Messages API, or with `-- --live` against your own sign-in) and `check:claude-code:agent` (an agent token's printed command, its prompt and a Cancel). One Playwright spec runs alone with `pnpm --filter @tabdock/e2e exec playwright test specs/<name>.spec.ts`; specs take free ports, so several can run at once. `pnpm measure:room` is the one command here that changes the machine: it needs root, Playwright's Chromium for the frames and about 75 minutes. It holds its relay to 512 MiB and one CPU in cgroup v1 groups under `/sys/fs/cgroup` named `tabdock-measure-<pid>-<room>` where it can, then a cgroup v2 group, then a systemd user scope, and otherwise the heap flag alone with only RSS measured, saying in its report which it used. It takes those 75 minutes for a class of 40, one of 80 and two of 40 on two pages, and about 7 more for each frame repeat past the first. It starts itself again in a network namespace of its own (`unshare --net`, bringing loopback up with `ip` or `perl`), so the 64 KiB TCP buffers its unread phases set never reach the host; where no namespace can be made it leaves the buffers alone unless `--narrow-host-tcp` asks it to narrow the host's for those minutes. Ctrl-C stops its relays and removes its groups, a run killed outright leaves only empty groups that the next run removes, and `--quick` is a smoke run of a few minutes with a class of 6.

## Settings

Every setting is optional and comes from the process environment or a `.env` at the root, which git ignores; a variable already set in the environment wins over `.env`, so `TABDOCK_FIRST_CLASS_TOOLS=1 pnpm dev` works whatever `.env` says. `.env.example` describes each setting, and `docs/guide/08-relay-settings.md` and `docs/guide/14-settings-for-rooms.md` list them as tables with their modes, defaults and bounds. With neither, `pnpm relay` and `pnpm dev` run local mode (ADR 0022): loopback only, one user, `you`, and an owner token drawn into a private file outside the repository (`TABDOCK_HOME`, or the platform's config directory). The relay prints a command for Claude Code that reads the token from that file, so the token never reaches the screen; check the result with `claude mcp list`, never `claude mcp get`. Settings in `.env` win over local mode. `DEMO_PORT` moves the demo board, and `MAP_DEMO_PORT` the map demo.

## The demo board

The board dials only a relay its visitor chose (ADR 0029): `pnpm dev` prints a link with `?relay=` set, and the board then waits behind a `Connect to <host>` bar until you click it; without `?relay` it offers a Connect form. The bar's button takes a click only once it has held still for half a second, and names any page policy the link sets; the choice is remembered for that tab, relay URL and policy, so a reload reconnects. The Playwright specs and demo scripts open it with `?e2e=<key>`, a hook only a dev or test server asked for it has, under a random key of that server's own, which skips the click and hands the script the adapter's control handle; `pnpm dev` has no hook unless a script names a key in `DEMO_E2E_KEY`, so no link from another site can skip the click (ADR 0029's notes). `apps/demo/README.md` lists the board's other parameters.

## The map demo

`pnpm dev:map-demo` serves `apps/map-demo` (ADR 0050) on port 5175, or `MAP_DEMO_PORT`, rebuilding as you edit, with its static build's own page and meta policy (and the policy again as a header, with `frame-ancestors`), and prints a link with `?relay=` set for `pnpm relay`. Like the board it waits behind a `Connect to <host>` bar until you click, and offers a Connect form without `?relay`; unlike the board it reads no policy from its link and has no test hook in any build, not even under a key, so a script drives it as a person would, clicking the bar and approving in the widget through `@tabdock/adapter/testing`. Its links to the board, the tour and the guide answer 404 on the dev server, since only the site holds them. `pnpm --filter @tabdock/map-demo build` writes the static build into `apps/map-demo/dist`, and its unit tests run in `pnpm test` (alone with `pnpm exec vitest run apps/map-demo`). `pnpm record:map-demo`, run by hand and by no CI job, starts `pnpm relay` in local mode with a throwaway `TABDOCK_HOME` whose `TABDOCK_ALLOWED_ORIGINS` names a loopback static host serving the build, films the page in headless Chromium at 1280 by 720, clicks Connect and Allow as driver as a person does, and has an SDK client list the walkthrough, go to each stop, read `get_page_state` and call `capture_view` once, under a caption bar naming each step. A shade over the widget's lane and the code's block hidden inside the widget keep the pairing code and its QR code out of every frame, each scene checks that before it goes on, and the run prints only file paths and sizes. It writes the take, its poster and a still of each scene into a `recording/` directory inside `apps/map-demo`, which git ignores, and copies a take within budget (4,000,000 bytes for the video, 300,000 for the poster) into `apps/map-demo/media/`, which the page links and the site serves at `/map/media/`; look at the stills and the video before committing it.

Its geography, `apps/map-demo/src/data/natural-earth-110m.ts`, is generated, never edited by hand. `pnpm --filter @tabdock/map-demo vendor`, run by hand and by no CI job, fetches Natural Earth's 110m land and lakes at tag v5.1.2 from raw.githubusercontent.com, stops unless each file's SHA-256 is the one `apps/map-demo/scripts/vendor-natural-earth.ts` pins, and rewrites the module, formatted by prettier; run from the root as `node apps/map-demo/scripts/vendor-natural-earth.ts --from <dir>`, it reads two files you already have instead. The same files give the same bytes, so a rerun at the tag changes nothing, and `apps/map-demo/test/vendor.test.ts` holds the module to its 24,000-byte budget. Moving to another tag means new pins in the script and a fresh check of Natural Earth's terms, recorded in `docs/notes/verified.md`.

## The site

`pnpm site:build` installs `apps/site` from its own lockfile (`pnpm install --frozen-lockfile --ignore-workspace` there), typechecks it, runs its tests with `node --test`, and builds: the demo's static build at the root and the map demo's at `/map/` (`buildMapDemo()`), each with its meta policy, each `docs/tour/*.md` rendered by `marked` as a page under `/tour/`, and each `docs/guide/*.md` as a page under `/guide/` (its `README.md` as the guide's index), each Mermaid block drawn to an SVG in Playwright's Chromium with the network blocked. It needs the workspace installed (for the demo's build) and that Chromium, which `pnpm --filter @tabdock/e2e exec playwright install chromium` fetches; `CHROMIUM_EXECUTABLE` points it at another build of Chromium. The build stops if `/map/` holds anything but its page, its script and the script's source map, under its policy, if a tour or guide page holds a script or an event handler attribute or lacks its policy, if a link names a tour or guide page that does not exist, or if a diagram holds a script or names anything outside the site. Serve `apps/site/dist` with any static server to read it as Pages will. Root lint, typecheck and unit tests leave `apps/site` out, since a clean clone cannot resolve its packages; CI runs `pnpm site:build` after it installs Chromium, and `.github/workflows/pages.yml` publishes the result (`docs/deploy.md`, "The workflows").

## Dependency updates

Dependabot proposes updates weekly (`.github/dependabot.yml`), and three kinds are left to a person on purpose. Node's major version is a recorded decision, not a bump: the runtime stays on Node 22 until the move to Node 24 before 30 April 2027 (`docs/plans/backlog.md`), so the image takes new digests of the `22` tag only, and `@types/node` follows the runtime's major, never a newer one. TypeScript, `@types/node` and Playwright are shared by the workspace and the Pages site, which must hold the same versions (`tests/e2e/test/site-files.test.ts`), and Dependabot proposes each directory's updates in a pull request of its own (Playwright even under a different name in each), so it cannot keep the two in step; both entries ignore every version of them. Bump them in one change: `pnpm add -D --save-exact -w typescript@<version>` (or `@types/node`) and `pnpm --filter @tabdock/e2e add -D --save-exact @playwright/test@<version>` in the workspace, then `pnpm --dir apps/site add -D --save-exact` with the same package at the same version for the site (`playwright-core` for Playwright), and run `pnpm install --frozen-lockfile`, `pnpm test` and `pnpm site:build`. A security alert against one of them is handled the same way: the alert still shows under the repository's Security tab, the ignore rules may keep Dependabot from opening a pull request for it, and any pull request it does open moves one lockfile, so a person finishes the bump in both places. A TypeScript major also waits for `typescript-eslint` to support it; TypeScript 7 failed lint on 5 October 2026 because it does not yet. The site's own packages, `marked` and `mermaid`, still come from Dependabot, which updates the site's lockfile now that `apps/site/pnpm-workspace.yaml` makes the site a pnpm project of its own. The root `pnpm-workspace.yaml` names `apps/demo` and `apps/map-demo` rather than `apps/*` with a `!apps/site` exclusion, since Dependabot reads its globs without pnpm's negation and its root job would otherwise edit the site's `package.json` too. The MCP SDK packages the relay pins (`@modelcontextprotocol/server`, `client`, `core` and `node`) come in a group of their own, `mcp-sdk`, written before the `runtime` and `tooling` groups because Dependabot puts a dependency in the first group it matches: `server` and `client` each pin `core` exactly, so a pull request that moved one alone would leave two copies of `core` in the tree (ADR 0037). A security update still comes one pull request per advisory; move the rest of the SDK pins in it by hand, as `docs/release.md` says, before it merges. MCP-B is pinned exactly in four places on purpose (ADR 0047): the demo, the map demo (ADR 0050) and the canvas map page on 5.1.0, whose behaviour the guide describes, and the private `tests/mcpb6` on 6.0.0, the release the `mcpb6` Playwright project runs the adapter on, whose ESM import no longer installs the polyfill, so its harness calls `installWebMCP()`. A Dependabot pull request that moves the demo or the map page to 6 fails `tests/e2e/test/mcpb-versions.test.ts` or `tests/map-page/test/package.test.ts`, while no test yet holds the map demo's pin, so read one that moves it as you would the board's; one that moves `tests/mcpb6` within 6 is taken once that project passes on it and its notes are read.

## Conventions

TypeScript strict mode and ESM throughout; every message that crosses a boundary is checked by the zod schemas in `packages/protocol`. Comments say why, not what. `CLAUDE.md` has the rest, and `SPEC.md` is the source of truth: a change to it goes through an ADR in `docs/adr/`.
