# @tabdock/e2e

End-to-end tests and milestone demos. `src/harness.ts` starts the demo page in Chromium, MCP-B's local relay as a stdio MCP server, and an MCP client from the official SDK (M0). `src/tabdock-harness.ts` starts the Tabdock relay with throwaway dev tokens beside the demo page, opens the page with `?relay` and the `?e2e` test hook under the demo server's own key, connects MCP clients with a bearer header, and clicks inside the adapter's closed shadow root through the DevTools protocol (M1).

## Tests without a browser

`test/*.test.ts` run in `pnpm test` without a browser: the relay, sim pages running the real adapter core, and MCP clients in one process, covering A1.1 and A1.4 (`pairing.test.ts`) and A1.3 (`resume.test.ts`) on the default sim profile (Chrome 156), with `link-close.test.ts` holding how the page link ends and `policy.test.ts` the roles, page policy and isolation checks (S1, S2, S5, S6, S13), and `runtimes.test.ts` runs the pair, list and call path on every profile the sim page plays (MCP-B polyfill 5.1, Chrome 154, Chrome 156). The M2 acceptance tests sit beside them: `many-clients.test.ts` (A2.1, A2.3), `role-checks.test.ts` (A2.2, with `stand-in-relay.ts` playing a relay that skips its own check), `operator-controls.test.ts` (A2.4, A2.5, pause) and `call-lifecycle.test.ts` (idle expiry, argument checks, client cancellation on both protocol eras).

`test/dev-public.test.ts` runs `pnpm dev:public` as a child process against the relay tests' stand-in provider, and `test/local-mode.test.ts` runs `pnpm relay` and `pnpm dev` the same way in local mode (ADR 0022) against a throwaway `TABDOCK_HOME`, through `src/local-harness.ts`, which runs pnpm in a process group of its own and reads the banner back: the first start draws a 0700 directory and a 0600 token file, the next keeps it byte for byte, the printed `claude mcp add-json` line hands Claude Code the header helper beside the token (ADR 0028), which prints the header a client connects with, only the owner token gets in and only from this machine, `pnpm spike:latency` reads the file without ever creating it, and no line either command prints holds the token, its digest or any 8 characters of it. `test/deploy-files.test.ts` reads `deploy/fly/fly.toml`, the Dockerfile, `.dockerignore` and the workflows as text with their comments left out, and fails if a pin, a default permission, Fly's HTTP handler, the audit mount or a step the image and deploy rely on goes (`docs/deploy.md`); `test/doc-pointers.test.ts` checks that every `docs/` path the code names exists.

## Browser specs

`pnpm test:e2e` (from the root) runs the Playwright specs in `specs/`: the M0 baseline through MCP-B (`mcpb-relay.spec.ts`, A0.2, and `demo-page.spec.ts`), the real adapter on the demo page against the Tabdock relay (`tabdock-relay.spec.ts`, M1 and M2), the operator's widget against a scripted relay (`widget.spec.ts`), what a page script that runs after `attach()` can catch by patching built-ins (`later-scripts.spec.ts`), the demo's Connect bar and form and its static build (`connect.spec.ts`, ADR 0029), and (`pair.spec.ts`, M3) the QR flow, where a phone-sized browser opens the widget's pairing URL, signs in at the relay tests' stand-in provider, joins, and sees the operator's click approve it. `src/public-harness.ts` runs that relay in public URL mode and plays the tunnel with Playwright routing: `https://relay.test` reaches the loopback relay with the public Host, so the phone has a real https origin with no certificate and no http allowance in the relay; since Playwright never routes a request a redirect produced, each redirect becomes a page that navigates on at once, and the browser still applies its own cookie and Origin rules to every hop. The spec turns the relay's spike flag on and reads its scan-to-first-call milestones back from the log.

From M4, `specs/invites.spec.ts` drives the widget's invites (the Invite form, the live list, Revoke and the QR code) against a scripted relay under Trusted Types and a strict style-src, along with the demo's refusal to link inside a frame, and `specs/invite-journey.spec.ts` runs the whole journey against the real relay in public URL mode, with invites on and the audit log on disk: the widget mints a Can watch link, a second account joins at `/i` on a phone-sized page, reads and is refused a write; a Can control link redeemed through `pair_page` raises a prompt naming the account, is approved and writes; Revoke all ends both and closes the links; and `pnpm audit:log --verify` finds the record intact, with no secret in any log.

## Milestone demos and the baseline

`pnpm demo:m0` to `pnpm demo:m5` narrate one session each; add `-- --headed` to watch or `-- --screenshot` (M0 to M2) to refresh `docs/tour/img/m0-board.png`, `m1-board.png` or `m2-board.png`. `demo:m3` runs public URL mode entirely on this machine: the stand-in provider, `src/public-harness.ts` for the browsers and the relay tests' `tunnelFetch` for MCP clients, which sign in with the SDK's OAuth flow; it prints codes and the pairing URL only masked and checks every line it prints against the secrets it has seen. `demo:m4` starts with local mode, running `pnpm dev` against a throwaway `TABDOCK_HOME` and pairing an MCP client that reads the owner token file as the printed line's header helper does, then runs that invite journey in public URL mode, narrated, ending with `pnpm audit:log` and its `--verify`; it masks invite links the same way and also checks every line against the owner token in each form `leakIn` knows. `demo:m5` runs `pnpm dev` in local mode with `TABDOCK_FIRST_CLASS_TOOLS=1` and a throwaway `TABDOCK_HOME`: a client on 2026-07-28 and one on 2025-11-25 each pair, list and call a first-class tool, then confirm `clear_board` on a `?confirm=client` board in their own elicitation handlers (by `input_required` and by an elicitation inside the request), while a client that declares no form elicitation gets the board's prompt instead; it ends with `pnpm audit:log` and its `--verify`, and checks every line against the owner token and the pairing codes. `pnpm --filter @tabdock/e2e baseline` re-measures the WebMCP runtime into `docs/notes/baseline.raw*.json`; with `BASELINE_MCPB=6` it measures MCP-B's 6.0 beta instead, the demo on the beta polyfill beside the beta local relay and its own embed, into `baseline.raw.mcpb6-beta.json`, and refuses to record if a native context was already there.

## Claude Code checks

`check:claude-code` (A0.2), `check:claude-code:m1` (A1.2) and `check:claude-code:m2` (Claude Code named in the page's roster and activity log) run the real Claude Code CLI; it must be installed and signed in, and each spends a few model calls. `check:claude-code:m3` spends none: it runs `claude mcp add`, `claude mcp login --no-browser` (in a pseudo-terminal from `script`) and `claude mcp list` in a throwaway HOME against the public-mode relay and the stand-in provider, reaching `https://relay.test` through a CONNECT proxy and a TLS front with a certificate the openssl CLI makes for that run, handed to Claude Code through `HTTPS_PROXY` and `NODE_EXTRA_CA_CERTS`; it also records what Claude Code says for a plain loopback URL, which cannot sign in. `check:claude-code:local` (A4.4) spends none either: it starts `pnpm relay` in local mode with a throwaway `TABDOCK_HOME` whose path holds a space and a quote, runs the printed `claude mcp add-json` line (ADR 0028) through `sh -c` in a throwaway HOME until `claude mcp list` shows the relay connected through the header helper, checks that Claude Code's configuration holds the helper and no token, then restarts the relay with `--new-token` and sees the same entry connect with the new token and the old one refused; with no `claude` on the PATH it skips and says so.

## From M5

From M5 the acceptance tests of A5.1 and A5.3 run in `pnpm test` against the sim page. `test/first-class-calls.test.ts` (A5.1) holds what only the adapter decides for a call by a first-class name: it prompts the operator exactly as `call_page_tool`'s does, Deny answers `denied_by_operator` in the same words with the same record, and a client's cancellation reaches the handler. `test/first-class-schemas.test.ts` holds which page schemas reach a member's list at all, since a client rejects a whole `tools/list` over one entry it cannot take: every client of the matrix lists the fixed tools and the plain tool alone. `test/confirm-in-client.test.ts` (A5.3) runs confirmation in the client on both revisions with the SDK client's own elicitation handler: a member driver confirms a consequential call with no page prompt, while every declined, dismissed, expired, replayed, forged or mismatched confirmation answers `not_confirmed` and the page never hears of the call; `specs/confirm-in-client.spec.ts` does the same on the demo board in a browser, where the widget's activity log names the client that confirmed.

From M5 (A5.4, ADR 0031) `playwright.config.ts` has two projects. `chromium` runs every spec but one, as before. `mcpb6` runs `specs/mcpb6.spec.ts` alone: `src/mcpb6-page.ts` installs MCP-B's 6.0 beta polyfill (reached only through `@tabdock/mcpb6`) before the demo's own scripts, so the demo and its bundled adapter run on 6 unchanged, and each test first checks that the page really is on 6 before it trusts a result; it covers a call, cancellation by revoke and by the client, and the consequential prompt with its mark in the tools frame. `pnpm test:e2e` runs both; `playwright test --project mcpb6` runs the leg alone, and `test/mcpb6-leg.test.ts` holds the split.

From M5 (A5.2, ADR 0027) three checks hold the MCP revisions the relay serves. `test/revisions.test.ts` runs the client matrix in `pnpm test`: `@modelcontextprotocol/sdk` 1.10.2, 1.12.3, 1.24.0 and 1.32.0, installed as exact npm aliases (`mcp-sdk-<version>`), and `client` 2.3.0 in legacy, auto and pinned mode, each pairing with the sim page, listing and calling its tools through `call_page_tool` and by first-class name, and hearing its list change on its own channel, behind `src/mcp-proxy.ts`, a loopback proxy that records each request as it arrives, with the tool a `tools/call` names and the names a `tools/list` answer gives, so the revision, the leg and the route each call took are read off the wire; `test/mcp-proxy.test.ts` holds the proxy to its rules (Host and every Origin line passed up as written unless a run leaves one rebinding guard alone, the run's bearer in place of the client's, each request recorded as it arrives with no token, session id or argument, and nothing logged). `pnpm conformance` (from the root, and in CI) runs `src/conformance.ts`: `pnpm relay` with a dev token drawn for the run and its session and request caps raised for that run alone, the same proxy adding the bearer header and logging nothing, and the official suite's 2025-11-25 and 2026-07-28 requirement sets against the baselines in `conformance/`, which may excuse only what `conformance/reviewed.json` names (fixture scenarios, checks that cannot reach the relay, in the suite's exact words, SHOULD-level warnings and unscored scenarios of extensions the relay does not offer; never `dns-rebinding-protection`, `http-header-validation`, `server-session-lifecycle`, a `wire-schema-valid` check or any other MUST, ADR 0027's notes). After each set it holds the unscored scenarios the suite does not score to the same baseline, and it runs `dns-rebinding-protection` again with each of the relay's two rebinding guards left alone, since the suite's probe trips both at once; `test/conformance-baselines.test.ts` holds both files to those rules, and `-- --results <dir>` keeps each scenario's `checks.json`. `check:claude-code:m5` drives the real Claude Code twice in a throwaway HOME, by default and with `MCP_PROTOCOL_NEGOTIATION=legacy`, through `call_page_tool` and a first-class name against a local relay and the sim page, reading which name each `tools/call` asked for off the wire (the audit names the page tool whatever the route), and spends a few model calls, so it stays out of CI. `check:claude-code:labels` drives Claude Code against a stand-in for the Messages API on loopback instead, so it needs `claude` on the PATH but no sign-in and makes no model call: it asks Claude Code for a hostile page's JSON result by both routes, its tool list and its page list, on both revisions, and fails if any `tool_result` its model is handed lacks the `[tabdock: ...]` line before the page's text, since Claude Code shows its model a result's structured content in place of the text (ADR 0025's notes).

The release and the site have checks of their own (A5.5, ADRs 0028 and 0029). `test/release-check.test.ts` runs `scripts/release-check.ts` on tarballs made for the test, each rule refusing the one thing it is there to catch; `test/publish-workflow.test.ts` reads `publish.yml` as text and runs its tag check against a scratch repository; `test/adapter-size.test.ts` holds the script-tag build under 150,000 bytes; `test/demo-static-build.test.ts` holds the demo's static build to its meta policy with no `?e2e` bypass; `test/site-files.test.ts` keeps `apps/site` out of the workspace with its own lockfile; and `test/mcpb-versions.test.ts` keeps the demo and the baseline on MCP-B 5.1.0 while the 6.0 beta is reached only through `@tabdock/mcpb6`.

The docs have sync tests of their own (ADR 0035), each reading the Markdown through `src/doc-files.ts` and failing when a doc drifts from the code: `test/doc-snippets.test.ts` typechecks every ts and js block in the guide, the README and the adapter's README against the workspace packages (a block after `<!-- fragment -->` is skipped) and runs each script tag's data attributes through the script-tag build's reader; `test/adapter-reference.test.ts` holds the adapter reference's tables to `AttachOptions`, `Dock`, `DockState`, `InviteOptions`, `PolicySchema` and the script-tag attributes; `test/doc-client-surface.test.ts` holds the troubleshooting table and SPEC section 7 to `ERROR_CODES`, and the guide's fixed tools to the relay's golden tool list; `test/doc-commands.test.ts` resolves every `pnpm` command and relay flag a doc names; `test/doc-pointers.test.ts` follows every link, path, file name, ADR number and code-shaped name; `test/doc-limits.test.ts` checks the limits table against the constants; `test/doc-style.test.ts` holds the house style; and `test/doc-release-state.test.ts` keeps install claims waiting for the npm publish while `CHANGELOG.md` says it has not happened. The settings page has its own in the relay's package, `packages/relay/test/settings-reference.test.ts`.

## Spike tooling

The M3 spike tooling lives in `src/spike/` behind two root commands. `pnpm spike:latency` (`scripts/spike/latency.ts`, `src/spike/latency.ts`) times 5 warm-up and 50 sequential `call_page_tool get_view` calls against a relay's MCP URL, with a dev token on loopback or the SDK's OAuth sign-in and a loopback redirect for an https URL, and prints nearest-rank p50 and p95 with min and max as a markdown table, split by the relay's timestamps when its `TABDOCK_SPIKE` is on; `--help` lists the options. `pnpm spike:soak` (`scripts/spike/soak.ts`, `src/spike/soak.ts`) freezes and thaws the demo page over raw CDP (`src/spike/cdp.ts`, since Playwright's focus emulation keeps a page from freezing) for 60 minutes, or a few with `--quick`, checking after each thaw that the page resumed with its attachment and a working call; `specs/soak.spec.ts` runs one quick cycle, and `test/spike-latency.test.ts` covers the latency run and its sign-in.

## Browsers

Browsers: the harness and the Playwright global setup download Playwright's Chromium on first use. Set `CHROMIUM_EXECUTABLE` to use another Chrome, for example one with native WebMCP; the harness and the `chromium` project always pass `--enable-features=WebMCPTesting`, and the `mcpb6` project never does, so the beta polyfill installs instead of a native context.
