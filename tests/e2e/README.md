# @tabdock/e2e

End-to-end tests and milestone demos. `src/harness.ts` starts the demo page in Chromium, MCP-B's local relay as a stdio MCP server, and an MCP client from the official SDK (M0). `src/tabdock-harness.ts` starts the Tabdock relay with throwaway dev tokens beside the demo page, opens the page with `?relay` and the `?e2e` test hook, connects MCP clients with a bearer header, and clicks inside the adapter's closed shadow root through the DevTools protocol (M1).

`test/*.test.ts` run in `pnpm test` without a browser: the relay, sim pages running the real adapter core, and MCP clients in one process, covering A1.1, A1.3 and A1.4 on the default sim profile (Chrome 156), with `runtimes.test.ts` running the pair, list and call path on every profile the sim page plays (MCP-B polyfill 5.1, Chrome 154, Chrome 156). The M2 acceptance tests sit beside them: `many-clients.test.ts` (A2.1, A2.3), `role-checks.test.ts` (A2.2, with `stand-in-relay.ts` playing a relay that skips its own check), `operator-controls.test.ts` (A2.4, A2.5, pause) and `call-lifecycle.test.ts` (idle expiry, argument checks, client cancellation on both protocol eras). `pnpm test:e2e` (from the root) runs the Playwright specs in `specs/`: the M0 baseline through MCP-B, the real adapter on the demo page against the Tabdock relay, and (`pair.spec.ts`, M3) the QR flow, where a phone-sized browser opens the widget's pairing URL, signs in at the relay tests' stand-in provider, joins, and sees the operator's click approve it. `src/public-harness.ts` runs that relay in public URL mode and plays the tunnel with Playwright routing: `https://relay.test` reaches the loopback relay with the public Host, so the phone has a real https origin with no certificate and no http allowance in the relay; since Playwright never routes a request a redirect produced, each redirect becomes a page that navigates on at once, and the browser still applies its own cookie and Origin rules to every hop. The spec turns the relay's spike flag on and reads its scan-to-first-call milestones back from the log. `test/dev-public.test.ts` runs `pnpm dev:public` as a child process against the same stand-in provider, and `test/local-mode.test.ts` runs `pnpm relay` and `pnpm dev` the same way in local mode (ADR 0022) against a throwaway `TABDOCK_HOME`, through `src/local-harness.ts`, which runs pnpm in a process group of its own and reads the banner back: the first start draws a 0700 directory and a 0600 token file, the next keeps it byte for byte, the printed line is the one that reads the file, only the owner token gets in and only from this machine, `pnpm spike:latency` reads the file without ever creating it, and no line either command prints holds the token, its digest or any 8 characters of it. `pnpm demo:m0`, `pnpm demo:m1`, `pnpm demo:m2` and `pnpm demo:m3` narrate one session each; add `-- --headed` to watch or `-- --screenshot` (M0 to M2) to refresh `docs/tour/img/m0-board.png`, `m1-board.png` or `m2-board.png`. `demo:m3` runs public URL mode entirely on this machine: the stand-in provider, `src/public-harness.ts` for the browsers and the relay tests' `tunnelFetch` for MCP clients, which sign in with the SDK's OAuth flow; it prints codes and the pairing URL only masked and checks every line it prints against the secrets it has seen. `pnpm --filter @tabdock/e2e baseline` re-measures the WebMCP runtime into `docs/notes/baseline.raw*.json`. `check:claude-code` (A0.2), `check:claude-code:m1` (A1.2) and `check:claude-code:m2` (Claude Code named in the page's roster and activity log) run the real Claude Code CLI; it must be installed and signed in, and each spends a few model calls. `check:claude-code:m3` spends none: it runs `claude mcp add`, `claude mcp login --no-browser` (in a pseudo-terminal from `script`) and `claude mcp list` in a throwaway HOME against the public-mode relay and the stand-in provider, reaching `https://relay.test` through a CONNECT proxy and a TLS front with a certificate the openssl CLI makes for that run, handed to Claude Code through `HTTPS_PROXY` and `NODE_EXTRA_CA_CERTS`; it also records what Claude Code says for a plain loopback URL, which cannot sign in. `check:claude-code:local` (A4.4) spends none either: it starts `pnpm relay` in local mode with a throwaway `TABDOCK_HOME` whose path holds a space and a quote, runs the printed `claude mcp add` line through `sh -c` in a throwaway HOME until `claude mcp list` shows the relay connected, then rotates the token as the docs say and sees the old entry refused and the new one connect; with no `claude` on the PATH it skips and says so.

The M3 spike tooling lives in `src/spike/` behind two root commands. `pnpm spike:latency` (`scripts/spike/latency.ts`, `src/spike/latency.ts`) times 5 warm-up and 50 sequential `call_page_tool get_view` calls against a relay's MCP URL, with a dev token on loopback or the SDK's OAuth sign-in and a loopback redirect for an https URL, and prints nearest-rank p50 and p95 with min and max as a markdown table, split by the relay's timestamps when its `TABDOCK_SPIKE` is on; `--help` lists the options. `pnpm spike:soak` (`scripts/spike/soak.ts`, `src/spike/soak.ts`) freezes and thaws the demo page over raw CDP (`src/spike/cdp.ts`, since Playwright's focus emulation keeps a page from freezing) for 60 minutes, or a few with `--quick`, checking after each thaw that the page resumed with its attachment and a working call; `specs/soak.spec.ts` runs one quick cycle, and `test/spike-latency.test.ts` covers the latency run and its sign-in.

Browsers: the harness and the Playwright global setup download Playwright's Chromium on first use. Set `CHROMIUM_EXECUTABLE` to use another Chrome, for example one with native WebMCP; the harness always passes `--enable-features=WebMCPTesting`.
