# @tabdock/e2e

End-to-end tests and milestone demos. `src/harness.ts` starts the demo page in Chromium, MCP-B's local relay as a stdio MCP server, and an MCP client from the official SDK (M0). `src/tabdock-harness.ts` starts the Tabdock relay with throwaway dev tokens beside the demo page, opens the page with `?relay` and the `?e2e` test hook under the demo server's own key, connects MCP clients with a bearer header, and clicks inside the adapter's closed shadow root through the DevTools protocol (M1).

## Tests without a browser

`test/*.test.ts` run in `pnpm test` without a browser: the relay, sim pages running the real adapter core, and MCP clients in one process, which `test/helpers.ts` sets up for each test with throwaway dev tokens, covering A1.1 and A1.4 (`pairing.test.ts`) and A1.3 (`resume.test.ts`) on the default sim profile (Chrome 156), with `link-close.test.ts` holding how the page link ends and `policy.test.ts` the roles, page policy and isolation checks (S1, S2, S5, S6, S13), and `runtimes.test.ts` runs the pair, list and call path on every profile the sim page plays (MCP-B polyfill 5.1, Chrome 154, Chrome 156). The M2 acceptance tests sit beside them: `many-clients.test.ts` (A2.1, A2.3), `role-checks.test.ts` (A2.2, with `stand-in-relay.ts` playing a relay that skips its own check), `operator-controls.test.ts` (A2.4, A2.5, pause) and `call-lifecycle.test.ts` (idle expiry, argument checks, client cancellation on both protocol eras).

`test/dev-public.test.ts` runs `pnpm dev:public` as a child process against the relay tests' stand-in provider, and `test/local-mode.test.ts` runs `pnpm relay` and `pnpm dev` the same way in local mode (ADR 0022) against a throwaway `TABDOCK_HOME`, through `src/local-harness.ts`, which runs pnpm in a process group of its own and reads the banner back: the first start draws a 0700 directory and a 0600 token file, the next keeps it byte for byte, the printed `claude mcp add-json` line hands Claude Code the header helper beside the token (ADR 0028), which prints the header a client connects with, only the owner token gets in and only from this machine, `pnpm spike:latency` reads the file without ever creating it, and no line either command prints holds the token, its digest or any 8 characters of it. `test/deploy-files.test.ts` reads `deploy/fly/fly.toml`, the Dockerfile, `.dockerignore` and the workflows as text with their comments left out, and fails if a pin, a default permission, Fly's HTTP handler, the audit mount or a step the image and deploy rely on goes (`docs/deploy.md`); `test/doc-pointers.test.ts` checks that every `docs/` path the code names exists.

## Browser specs

`pnpm test:e2e` (from the root) runs the Playwright specs in `specs/`: the M0 baseline through MCP-B (`mcpb-relay.spec.ts`, A0.2, and `demo-page.spec.ts`), the real adapter on the demo page against the Tabdock relay (`tabdock-relay.spec.ts`, M1 and M2), the operator's widget against a scripted relay (`widget.spec.ts`), what a page script that runs after `attach()` can catch by patching built-ins (`later-scripts.spec.ts`), the demo's Connect bar and form and its static build (`connect.spec.ts`, ADR 0029), and (`pair.spec.ts`, M3) the QR flow, where a phone-sized browser opens the widget's pairing URL, signs in at the relay tests' stand-in provider, joins, and sees the operator's click approve it. `src/public-harness.ts` runs that relay in public URL mode and plays the tunnel with Playwright routing: `https://relay.test` reaches the loopback relay with the public Host, so the phone has a real https origin with no certificate and no http allowance in the relay; since Playwright never routes a request a redirect produced, each redirect becomes a page that navigates on at once, and the browser still applies its own cookie and Origin rules to every hop. The spec turns the relay's spike flag on and reads its scan-to-first-call milestones back from the log.

From M4, `specs/invites.spec.ts` drives the widget's invites (the Invite form, the live list, Revoke and the QR code) against a scripted relay under Trusted Types and a strict style-src, along with the demo's refusal to link inside a frame, and `specs/invite-journey.spec.ts` runs the whole journey against the real relay in public URL mode, with invites on and the audit log on disk: the widget mints a Can watch link, a second account joins at `/i` on a phone-sized page, reads and is refused a write; a Can control link redeemed through `pair_page` raises a prompt naming the account, is approved and writes; Revoke all ends both and closes the links; and `pnpm audit:log --verify` finds the record intact, with no secret in any log.

## Claude Code checks

## Spike tooling

The M3 spike tooling lives in `src/spike/` behind two root commands. `pnpm spike:latency` (`scripts/spike/latency.ts`, `src/spike/latency.ts`) times 5 warm-up and 50 sequential `call_page_tool get_view` calls against a relay's MCP URL, with a dev token on loopback or the SDK's OAuth sign-in and a loopback redirect for an https URL, and prints nearest-rank p50 and p95 with min and max as a markdown table, split by the relay's timestamps when its `TABDOCK_SPIKE` is on; `--help` lists the options. `pnpm spike:soak` (`scripts/spike/soak.ts`, `src/spike/soak.ts`) freezes and thaws the demo page over raw CDP (`src/spike/cdp.ts`, since Playwright's focus emulation keeps a page from freezing) for 60 minutes, or a few with `--quick`, checking after each thaw that the page resumed with its attachment and a working call; `specs/soak.spec.ts` runs one quick cycle, and `test/spike-latency.test.ts` covers the latency run and its sign-in.

## Browsers

Browsers: the harness and the Playwright global setup download Playwright's Chromium on first use. Set `CHROMIUM_EXECUTABLE` to use another Chrome, for example one with native WebMCP; the harness and the `chromium` project always pass `--enable-features=WebMCPTesting`, and the `mcpb6` project never does, so the 6.0.0 polyfill installs instead of a native context.
