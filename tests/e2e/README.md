# @tabdock/e2e

End-to-end tests and milestone demos. `src/harness.ts` starts the demo page in Chromium, MCP-B's local relay as a stdio MCP server, and an MCP client from the official SDK (M0). `src/tabdock-harness.ts` starts the Tabdock relay with throwaway dev tokens beside the demo page, opens the page with `?relay` and the `?e2e` test hook, connects MCP clients with a bearer header, and clicks inside the adapter's closed shadow root through the DevTools protocol (M1).

`test/*.test.ts` run in `pnpm test` without a browser: the relay, sim pages running the real adapter core, and MCP clients in one process, covering A1.1, A1.3 and A1.4 on the default sim profile (Chrome 156), with `runtimes.test.ts` running the pair, list and call path on every profile the sim page plays (MCP-B polyfill 5.1, Chrome 154, Chrome 156). The M2 acceptance tests sit beside them: `many-clients.test.ts` (A2.1, A2.3), `role-checks.test.ts` (A2.2, with `stand-in-relay.ts` playing a relay that skips its own check), `operator-controls.test.ts` (A2.4, A2.5, pause) and `call-lifecycle.test.ts` (idle expiry, argument checks, client cancellation on both protocol eras). `pnpm test:e2e` (from the root) runs the Playwright specs in `specs/`: the M0 baseline through MCP-B, the real adapter on the demo page against the Tabdock relay, and (`pair.spec.ts`, M3) the QR flow, where a phone-sized browser opens the widget's pairing URL, signs in at the relay tests' stand-in provider, joins, and sees the operator's click approve it. `src/public-harness.ts` runs that relay in public URL mode and plays the tunnel with Playwright routing: `https://relay.test` reaches the loopback relay with the public Host, so the phone has a real https origin with no certificate and no http allowance in the relay; since Playwright never routes a request a redirect produced, each redirect becomes a page that navigates on at once, and the browser still applies its own cookie and Origin rules to every hop. The spec turns the relay's spike flag on and reads its scan-to-first-call milestones back from the log. From M4, `specs/invites.spec.ts` drives the widget's invites (the Invite form, the live list, Revoke and the QR code) against a scripted relay under Trusted Types and a strict style-src, along with the demo's refusal to link inside a frame, and `specs/invite-journey.spec.ts` runs the whole journey against the real relay in public URL mode, with invites on and the audit log on disk: the widget mints a Can watch link, a second account joins at `/i` on a phone-sized page, reads and is refused a write; a Can control link redeemed through `pair_page` raises a prompt naming the account, is approved and writes; Revoke all ends both and closes the links; and `pnpm audit:log --verify` finds the record intact, with no secret in any log. `test/dev-public.test.ts` runs `pnpm dev:public` as a child process against the same stand-in provider, and `test/local-mode.test.ts` runs `pnpm relay` and `pnpm dev` the same way in local mode (ADR 0022) against a throwaway `TABDOCK_HOME`, through `src/local-harness.ts`, which runs pnpm in a process group of its own and reads the banner back: the first start draws a 0700 directory and a 0600 token file, the next keeps it byte for byte, the printed line is the one that reads the file, only the owner token gets in and only from this machine, `pnpm spike:latency` reads the file without ever creating it, and no line either command prints holds the token, its digest or any 8 characters of it. `test/deploy-files.test.ts` reads `deploy/fly/fly.toml`, the Dockerfile, `.dockerignore` and the workflows as text with their comments left out, and fails if a pin, a default permission, Fly's HTTP handler, the audit mount or a step the image and deploy rely on goes (`docs/deploy.md`); `test/doc-pointers.test.ts` checks that every `docs/` path the code names exists. `pnpm demo:m0` to `pnpm demo:m4` narrate one session each; add `-- --headed` to watch or `-- --screenshot` (M0 to M2) to refresh `docs/tour/img/m0-board.png`, `m1-board.png` or `m2-board.png`. `demo:m3` runs public URL mode entirely on this machine: the stand-in provider, `src/public-harness.ts` for the browsers and the relay tests' `tunnelFetch` for MCP clients, which sign in with the SDK's OAuth flow; it prints codes and the pairing URL only masked and checks every line it prints against the secrets it has seen. `demo:m4` starts with local mode, running `pnpm dev` against a throwaway `TABDOCK_HOME` and pairing an MCP client that reads the owner token file as the printed Claude Code line does, then runs that invite journey in public URL mode, narrated, ending with `pnpm audit:log` and its `--verify`; it masks invite links the same way and also checks every line against the owner token in each form `leakIn` knows. `pnpm --filter @tabdock/e2e baseline` re-measures the WebMCP runtime into `docs/notes/baseline.raw*.json`; with `BASELINE_MCPB=6` it measures MCP-B's 6.0 beta instead, the demo on the beta polyfill beside the beta local relay and its own embed, into `baseline.raw.mcpb6-beta.json`, and refuses to record if a native context was already there. `check:claude-code` (A0.2), `check:claude-code:m1` (A1.2) and `check:claude-code:m2` (Claude Code named in the page's roster and activity log) run the real Claude Code CLI; it must be installed and signed in, and each spends a few model calls. `check:claude-code:m3` spends none: it runs `claude mcp add`, `claude mcp login --no-browser` (in a pseudo-terminal from `script`) and `claude mcp list` in a throwaway HOME against the public-mode relay and the stand-in provider, reaching `https://relay.test` through a CONNECT proxy and a TLS front with a certificate the openssl CLI makes for that run, handed to Claude Code through `HTTPS_PROXY` and `NODE_EXTRA_CA_CERTS`; it also records what Claude Code says for a plain loopback URL, which cannot sign in. `check:claude-code:local` (A4.4) spends none either: it starts `pnpm relay` in local mode with a throwaway `TABDOCK_HOME` whose path holds a space and a quote, runs the printed `claude mcp add-json` line (ADR 0028) through `sh -c` in a throwaway HOME until `claude mcp list` shows the relay connected through the header helper, checks that Claude Code's configuration holds the helper and no token, then restarts the relay with `--new-token` and sees the same entry connect with the new token and the old one refused; with no `claude` on the PATH it skips and says so.

The M3 spike tooling lives in `src/spike/` behind two root commands. `pnpm spike:latency` (`scripts/spike/latency.ts`, `src/spike/latency.ts`) times 5 warm-up and 50 sequential `call_page_tool get_view` calls against a relay's MCP URL, with a dev token on loopback or the SDK's OAuth sign-in and a loopback redirect for an https URL, and prints nearest-rank p50 and p95 with min and max as a markdown table, split by the relay's timestamps when its `TABDOCK_SPIKE` is on; `--help` lists the options. `pnpm spike:soak` (`scripts/spike/soak.ts`, `src/spike/soak.ts`) freezes and thaws the demo page over raw CDP (`src/spike/cdp.ts`, since Playwright's focus emulation keeps a page from freezing) for 60 minutes, or a few with `--quick`, checking after each thaw that the page resumed with its attachment and a working call; `specs/soak.spec.ts` runs one quick cycle, and `test/spike-latency.test.ts` covers the latency run and its sign-in.

From M5 (A5.4, ADR 0031) `playwright.config.ts` has two projects. `chromium` runs every spec but one, as before. `mcpb6` runs `specs/mcpb6.spec.ts` alone: `src/mcpb6-page.ts` installs MCP-B's 6.0 beta polyfill (reached only through `@tabdock/mcpb6`) before the demo's own scripts, so the demo and its bundled adapter run on 6 unchanged, and each test first checks that the page really is on 6 before it trusts a result; it covers a call, cancellation by revoke and by the client, and the consequential prompt with its mark in the tools frame. `pnpm test:e2e` runs both; `playwright test --project mcpb6` runs the leg alone, and `test/mcpb6-leg.test.ts` holds the split.

Browsers: the harness and the Playwright global setup download Playwright's Chromium on first use. Set `CHROMIUM_EXECUTABLE` to use another Chrome, for example one with native WebMCP; the harness and the `chromium` project always pass `--enable-features=WebMCPTesting`, and the `mcpb6` project never does, so the beta polyfill installs instead of a native context.
