# @tabdock/mcpb6

MCP-B 6.0.0 for the one test leg that runs the adapter on it (ADR 0047), kept in a private package of its own. The demo board, the canvas map page and the baseline stay on exact 5.1.0, whose behaviour the guide describes. Both releases of `@mcp-b/webmcp-local-relay` declare the same bin, and when both sat in one package pnpm linked 6's, so `pnpm exec webmcp-local-relay` in `tests/e2e` ran 6 without a word. Here 6.0.0 installs under aliases, `webmcp-polyfill-6` and `webmcp-local-relay-6`, so its bins never shadow 5.1.0's, and a test reaches it only through the paths `src/index.ts` exports, the package's one entry, `.`.

`MCPB6_POLYFILL_MODULE` is the polyfill's ESM entry, the file a page's `import { installWebMCP } from '@mcp-b/webmcp-polyfill'` loads. From 6.0.0, importing it installs nothing: a page that takes the polyfill from npm must call `installWebMCP()` itself, which is why the leg calls it too. `MCPB6_POLYFILL_SCRIPT` is the script-tag build, which still installs itself as it loads; the leg never runs it, since an npm page takes the ESM entry, and its tests use the path to show which build they did not inject. `mcpb6ModuleScript(binding)` wraps the ESM entry in a classic script with esbuild, as a page's own bundler would, since an init script that runs before the page's scripts cannot be a module, and returns the files it read, so a test can show it bundled 6.0.0's entry alone. `MCPB6_LOCAL_RELAY_CLI` is MCP-B's local relay command at 6.0.0, which its package's exports do not expose.

The `mcpb6` project in `tests/e2e/playwright.config.ts` runs `mcpb6.spec.ts` and, from M6, `mcpb6-images.spec.ts` against this package; `tests/e2e/test/mcpb-versions.test.ts` holds the demo on 5.1.0 and this package on exact 6.0.0. A Dependabot pull request that moves this package within 6 is taken once that project passes on it and the release's notes are read. `pnpm --filter @tabdock/mcpb6 typecheck` checks it.
