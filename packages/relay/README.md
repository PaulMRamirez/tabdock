# @tabdock/relay

The relay at the centre of [Tabdock](https://github.com/PaulMRamirez/tabdock). Web pages dial out to it over a WebSocket at `/page`, and MCP clients such as Claude Code and Claude add its one URL, `/mcp`. It signs clients in, asks the person at each page to approve whoever attaches, checks and routes calls, queues writes and keeps a hash-chained audit log. It never runs a page's tools, but it sees every call and result in plain text, so run your own.

## Run it

From a clone, with Node 22.18 or later and pnpm 10:

```sh
git clone https://github.com/PaulMRamirez/tabdock.git
cd tabdock
pnpm install
pnpm relay
```

Once 0.1.0 is on npm, `npx @tabdock/relay` runs the same command, `tabdock-relay`, without a clone. With no settings the relay runs local mode on `127.0.0.1:8787` for this computer only, keeps a private owner token outside any repository, and prints how to add it to Claude Code. On macOS and Linux that is a `claude mcp add-json` command whose header helper reads the token at each connection, so the token is in neither the command nor Claude Code's settings; in PowerShell, or where the helper's path cannot be quoted, it is a `claude mcp add ... --header` line, which leaves a copy of the token in Claude Code's settings. A page joins with `@tabdock/adapter`.

| Mode       | Selected by                                                                | Who reaches it                                                       |
| ---------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Local      | no sign-in settings                                                        | clients and pages on this computer, one user holding an owner token  |
| Dev tokens | `TABDOCK_DEV_TOKENS`                                                       | clients and pages on this computer, several named users              |
| Public URL | `TABDOCK_PUBLIC_URL` with an OAuth identity provider                       | clients anywhere through a tunnel, signed in; pages on this computer |
| Hosted     | a public URL, `TABDOCK_ENV=production` and `TABDOCK_CLIENT_ADDRESS_HEADER` | clients and pages anywhere, behind a host edge that terminates TLS   |

| Command                           | What it does                                    |
| --------------------------------- | ----------------------------------------------- |
| `tabdock-relay`                   | starts the relay from the environment           |
| `tabdock-relay --new-token`       | replaces local mode's owner token, then starts  |
| `tabdock-relay audit [options]`   | reads the audit log; `--help` lists its options |
| `tabdock-relay --version` or `-v` | prints the version                              |
| `tabdock-relay --help` or `-h`    | prints the usage                                |

In a clone, `pnpm relay` takes the same arguments and `pnpm audit:log` is the audit reader, so `pnpm relay audit --help` prints its usage as `pnpm audit:log`. Any other argument is refused with the usage, naming a flag by its name and anything else only by its place, so a mistyped flag never starts a relay and a token pasted in the wrong place is never echoed.

Clients see five fixed tools: `list_pages`, `pair_page`, `list_page_tools`, `call_page_tool` and `detach_page`; with `TABDOCK_FIRST_CLASS_TOOLS=1`, members' clients also see each attached page's tools by name. The guide covers the rest: [Connect clients](https://github.com/PaulMRamirez/tabdock/blob/main/docs/guide/05-connect-clients.md), [Run a relay](https://github.com/PaulMRamirez/tabdock/blob/main/docs/guide/07-run-a-relay.md) for tunnels and hosts, and [Relay settings](https://github.com/PaulMRamirez/tabdock/blob/main/docs/guide/08-relay-settings.md) for every setting with its modes, default and bounds. The rest of this file describes the relay in full, for operators who want the detail and for contributors.

## Settings in detail

### Where settings come from

Every setting is optional. A checkout loads the repo-root `.env` when present, where a variable already set in the environment wins; the published command reads no `.env` file at all, so its settings come from the environment alone, as on a host, and running it inside someone's project never picks up that project's file. Flags take `1`, `true`, `0` or `false`; counts are whole numbers from 1 to 999999999; settings in minutes are at most 35791. Anything else stops the relay at start with a message naming the variable and the rule but not the value, except that a `TABDOCK_HOME` path, a `TABDOCK_HOST` off loopback and a `TABDOCK_ALLOWED_ORIGINS` entry are quoted back. The relay prints its URLs on stdout and JSON log lines on stderr, never a token, a code or a session id.

Besides the sign-in, audit and feature settings in the sections below, it reads `TABDOCK_HOME` (local mode's token directory, below), `TABDOCK_DEV_TOKENS` (`alice=<token>,bob=<token>`, tokens of 24 or more characters, which turns local mode off), `TABDOCK_HOST` (loopback only, or `0.0.0.0` in hosted mode below; the relay resolves a name such as `localhost` itself and refuses to start unless every address it gives is loopback, then listens on that address), `TABDOCK_PORT` (default 8787) and `TABDOCK_ENV` (`development` or `production`).

Origins are two lists. `TABDOCK_ALLOWED_ORIGINS` (comma list; required in production; in development the default is http and https on localhost, 127.0.0.1 and [::1]) names the page origins `/page` takes, and `TABDOCK_DEV_ALLOW_NO_ORIGIN` (local mode and dev tokens only, refused in production and with a public URL) lets a page socket without an Origin header in. `TABDOCK_MCP_ALLOWED_ORIGINS` is a comma list of origins `/mcp` accepts in an `Origin` header besides its own, in every mode, each written as a browser sends it, lower case with no path and no trailing slash, any other entry stopping the relay at start; empty adds nothing, and it admits nothing to `/page`, as `TABDOCK_ALLOWED_ORIGINS` admits nothing to `/mcp`.

`TABDOCK_FIRST_CLASS_TOOLS` (`1`) also lists each attached page's tools to members' clients as tools of their own, named `<page id>__<tool>`, beside the five fixed tools, which always remain; off unless set, in every mode, local mode included, and allowed in production.

The section 9 limits and idle lifetimes (ADR 0009) are optional: `TABDOCK_MAX_SESSIONS_PER_USER` (20), `TABDOCK_MAX_SESSIONS` (1000), `TABDOCK_MAX_USERS_PER_PAGE` (10), `TABDOCK_MAX_QUEUE_DEPTH` (32), `TABDOCK_MAX_PAGE_SOCKETS_PER_ADDRESS` (20 open), `TABDOCK_MAX_PAGE_SESSIONS_PER_ADDRESS` (20, asleep ones included), `TABDOCK_MAX_PAGE_SESSIONS` (1000; hosted mode defaults these three to 5, 5 and 100), `TABDOCK_MAX_REQUESTS_PER_USER` (240 requests a minute per member: every tool call, every 2026-07-28 request, and while first-class tools are on every 2025-era `tools/list`) and `TABDOCK_MAX_REQUESTS_PER_INVITEE` (60), `TABDOCK_MAX_CALLS_PER_MINUTE` (120 per user per page), `TABDOCK_MAX_PAIR_SIGNINS_PER_MINUTE` (60 for the whole relay), `TABDOCK_MAX_PAIR_SIGNINS_IN_FLIGHT` (8 at once), `TABDOCK_SESSION_IDLE_MINUTES` (30) and `TABDOCK_ATTACHMENT_IDLE_MINUTES` (480).

The three heap budgets are in bytes, never MiB, so `TABDOCK_MAX_TOOL_BYTES=64` stops the relay at start: `TABDOCK_MAX_TOOL_BYTES` (default 67108864, which is 64 MiB, at least 1048576; an upper bound on the heap all pages' tool lists hold), `TABDOCK_MAX_REQUEST_BYTES` (default 67108864, 64 MiB) and `TABDOCK_MAX_REQUEST_BYTES_PER_USER` (default 25165824, 24 MiB, at most the total), what the requests waiting on pages are measured to hold, in all and per user, each at least 4194304, and the total at least 8388608 with invites on. The container image's heap cap holds these defaults; raise it with them.

### Local mode

Local mode (ADR 0022) is what the relay runs with none of `TABDOCK_DEV_TOKENS`, `TABDOCK_PUBLIC_URL`, `TABDOCK_OAUTH_ISSUER`, `TABDOCK_OAUTH_USERS`, `TABDOCK_PAIR_CLIENT_ID` and `TABDOCK_PAIR_CLIENT_SECRET` set (blank counts as unset) and `TABDOCK_ENV` unset or `development`; explicit settings always win, and production without them refuses to start rather than fall back. One user, `you` (shown as You), holds an owner token through the ordinary `dev-token` plugin, which keeps only its digest; the plugin carries `loopbackOnly: true`, and `resolveConfig` refuses any plugin so marked, whatever its name, with a public URL, in production or off loopback.

`local-token.ts` keeps the token in `owner-token` inside `TABDOCK_HOME` (absolute only) or the per-user configuration directory: `$XDG_CONFIG_HOME/tabdock` (when absolute) or `~/.config/tabdock` on Linux and other Unix systems, `~/Library/Application Support/Tabdock` on macOS, `%LOCALAPPDATA%\Tabdock` on Windows. The first start makes the directory 0700 and draws `tabdock_` plus 43 base64url characters (32 bytes from `randomBytes`) into a temporary 0600 file opened with `O_CREAT | O_EXCL`, syncs it and hard-links it to `owner-token`, so a second start racing it reads the winner's complete file rather than an empty one.

Every start opens the file without following a symlink and checks it through the descriptor, and refuses, naming the path and the fix ("chmod 700", "chmod 600", "delete it and start again") and never the contents: a directory inside the work tree of any repository, found by walking up from its realpath to the file system's root for a `.git`, `.jj`, `.hg`, `.sl`, `.svn` or `.bzr` entry, a directory or a file, so linked worktrees, submodules and Jujutsu's working copy, which snapshots new files on its own, all count (ADR 0028 and its notes; the message names the tool, the work tree and `TABDOCK_HOME` as the fix, and an entry it cannot look for is refused too); on POSIX systems, a directory below any directory that its group or others may write, sticky or not, or that an account other than this one or root owns, as OpenSSH asks of a key's path, since Claude Code keeps running the header helper by its path and another account that could make the directory again once it is gone, as anyone can under `/tmp` after a reboot, would have its own helper run as you (the message names that directory, and `chmod go-w` where it is yours and not sticky); in a checkout, a directory inside the checkout itself (compared by `realpath`, case-insensitively on macOS and Windows), which still guards an unpacked source archive with no `.git`, a comparison the published command, which has no checkout, leaves to the work tree rule; a directory or file another account owns or that grants its group or others any permission, and anything that is not a regular file of at most 64 bytes matching `^tabdock_[A-Za-z0-9_-]{43}\n?$`. Like ssh with a private key it refuses rather than repairs.

On Windows, where Node reports no owner and lacks `O_NOFOLLOW`, `lstat` checks for a regular file and the directory must lie under `%LOCALAPPDATA%` or `%USERPROFILE%`. The resolver reads its variables only from the environment object it is given, with the platform, uid, home directory and stat calls injectable for tests. `readOwnerToken` reads without ever creating, for tools such as `pnpm spike:latency`.

On every system but Windows each start also keeps `claude-headers` beside the token (ADR 0028): a `#!/bin/sh` script of fixed text, holding no token, that reads the token file by its absolute path, checks its shape with shell builtins alone and prints `{"Authorization":"Bearer <token>"}`, failing when the file is missing or malformed. It is written as the token is, a synced temporary file linked into place with mode 0700, and checked at every start as the token is: a regular file opened without following a link, this account's, granting nothing to group or others, runnable by its owner and holding exactly the text this release writes; anything else is refused and left alone, except a file holding an earlier release's exact text, which is replaced in one rename.

The banner (`local-banner.ts`, shared with `pnpm dev`) says the relay serves this computer only, names the MCP and page socket URLs, the token's path and the helper's, says whether the token was just drawn, and prints `claude mcp add-json --scope user tabdock-local '{"type":"http","url":"<url>","headersHelper":"<helper>"}'`, the JSON from `JSON.stringify` single-quoted by `quotePosix`, with the helper's path bare when it holds only letters, digits and `/._-` and in double quotes otherwise, as on macOS. Claude Code runs the helper at each connection, so the token is never in `claude`'s argument list, a shell history or `~/.claude.json`. A helper path holding `"`, `\`, `$`, a backtick or a control character falls back to `claude mcp add --transport http --scope user tabdock-local <url> --header "Authorization: Bearer $(cat '<path>')"`, and Windows keeps the PowerShell form with `$(Get-Content -TotalCount 1 -LiteralPath '<path>')` and gets no helper until a Windows run shows which shell runs one; both name the path, never the token.

Every start also says how to remove an older `tabdock-local` entry, which Claude Code refuses to replace: a token kept from an earlier start may be one no relay ever served, if that start could not listen, and an M4 entry keeps a copy of the token in `~/.claude.json` until it is removed. The published command's last line sends people wanting Claude on the web or phone to [docs/deploy.md](https://github.com/PaulMRamirez/tabdock/blob/main/docs/deploy.md) by its URL in the repository, since the package has neither the file nor `pnpm dev:public`. It suggests `claude mcp list` to check the connection, never `claude mcp get`, which prints a stored header in full.

To rotate, start with `--new-token`: the old file is never read, so one refused for its mode or contents can be replaced this way; the directory must pass every check above; a new token goes into a fresh synced 0600 temporary file that is renamed over `owner-token` only once the relay holds the token directory's own lock and listens. Every local-mode relay holds `owner-token.lock` beside the token from its start to its stop, whatever audit directory or port it uses (`token-lock.ts`), so a second relay sharing the directory, or `--new-token` beside one, refuses naming the lock, and a start that fails on its way up, on that lock or a port in use, leaves the old token as it was; a lock whose relay is gone is broken, and one it cannot judge, such as another pid namespace's, is refused with the file named for you to delete if no relay runs. The old token then gets 401, and a helper entry in Claude Code needs no change, since the helper reads the new token at its next connection; a `--header` entry must be replaced, and the banner says so. Outside local mode `--new-token` is refused by name.

Local mode decides who may call `/mcp`, never who reaches a page: the operator still approves each attachment. It trusts every account on its machine, since nothing authenticates the relay to its clients.

### Host and Origin checks

Without a public URL, in local mode and with dev tokens alike, an `/mcp` request or `/page` upgrade whose Host is not a loopback name as written, or that carries `Forwarded` or any `X-Forwarded-*` header, gets 403 before the auth plugin runs, so a tunnel pointed at a loopback relay, even one that rewrites Host, cannot expose it.

In every mode `/mcp` also answers 403, after the Host check and before the auth plugin or the budget, to a request whose `Origin` header is present and not exactly an allowed origin: without a public URL, http and https on `localhost`, `127.0.0.1` and `[::1]` at any port; with one, the public origin; and in either case those in `TABDOCK_MCP_ALLOWED_ORIGINS` (ADR 0027). A request with no `Origin` passes, since the header is a browser's and Claude Code sends none. A refusal writes one line a window naming the origin, so if a client you trust, hosted Claude say, is refused for the `Origin` it sends, add that origin to the list.

### First-class tools

With `TABDOCK_FIRST_CLASS_TOOLS=1` (ADR 0025), a member's `tools/list` holds, beside the five fixed tools, the tools of each page they hold other than through an invite, a driver's all of them and an observer's those marked read-only, named `<page id>__<tool>` with a `.` made `_`, at most 64 page tools and 100,000 characters of them, each description behind a relay prefix that calls the page's text untrusted, with `call_page_tool`'s annotations; a call by such a name runs `call_page_tool`'s very path, and invitees and attachments an invite made keep the five fixed tools. On 2026-07-28 the list carries `ttlMs` 10,000 with `cacheScope` `private`, and a change to it reaches only that user's own sessions and listen streams, at most once every 10 s.

### Confirmation in the client

A page whose hello chose `confirmVia: 'client'` lets its member drivers confirm a consequential call in their own client (ADR 0026, `confirm.ts`): the relay asks only a member on a driver's attachment no invite made, whose request declares form elicitation, about a tool the page's adapter marked `consequential`, and sends every other call for the page to prompt. On 2026-07-28 a first round, once every check before dispatch has passed, answers `input_required` with the relay's own question and a `requestState` from the SDK's codec, signed under a key drawn at start and bound to the user, the token's OAuth client and the method, that carries only the id of a single-use record of the user, page, tool as called, page tool and a SHA-256 of the canonical arguments, good for 120 s; the retry takes that record out before anything else and must match it.

On a 2025-era session the relay asks inside the request under its own 120 s timer, the SDK's legacy shim off, holding the request's byte charge. A declined, dismissed, expired, reused, forged or mismatched confirmation answers `not_confirmed`, and the page never hears of the call; at most four questions wait per user and a fifth is `rate_limited`; a revoke, the attachment's end or the page's end drops them at once, and a restart voids them all. The invoke then carries `confirmation`, and the call's audit record `confirmedBy: 'client'`, only while the page's policy, its mark and the caller's standing still call for asking as it goes out. No `requestState`, record id, digest or confirmation id reaches a log line.

### Sign-in

Auth is a plugin (`auth.ts`, ADR 0013): `authenticate(request)` returns a user, or a refusal that carries its own status, body and headers (401 with `WWW-Authenticate` to sign in, 403 for someone signed in but not allowed, 503 when the plugin cannot check anyone just now); the relay checks that answer with zod before acting on it. A plugin may also serve GET routes, may need `start({ log })` before the relay listens and `stop()` when it closes or fails to start, and says only who someone is: the relay itself decides whether to admit an invitee, which it does only with `TABDOCK_INVITES` on (ADR 0020). `dev-token` answers exactly as it has since M1.

The `oauth` plugin (`oauth.ts`) makes the relay a resource server for an external identity provider: at start it reads the provider's RFC 8414 metadata (OpenID Connect discovery as the fallback, as Claude does) and refuses to start unless the metadata names `TABDOCK_OAUTH_ISSUER` exactly, lists S256, and offers client ID metadata documents with `none` or a registration endpoint; it serves RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` naming the provider as the only authorization server, with no scopes; and it checks each token with the SDK's `verifyBearerToken` over `jose` (RS256 only, the provider's published keys, issuer, audience equal to the public MCP URL, a required expiry, 5 s of clock tolerance).

Every refused `/mcp` request, on both legs, gets the SDK's 401 challenge with `resource_metadata` before any MCP code runs; a valid token whose `sub` is not in `TABDOCK_OAUTH_USERS` gets a plain 403, unless invites are on and it is admitted as an invitee; keys that cannot be fetched give 503 with `Retry-After: 5`, and after a failed fetch (a cold start's first one included) the plugin fetches again no sooner than that, whatever tokens arrive, while the keys `jose` still holds as fresh (fetched at most 10 minutes earlier) keep checking tokens with no fetch, so no key is trusted longer than `jose` alone would trust it (a key missing from them is a 503 then, not a 401).

From M4 (ADR 0020) it also requires `iat` and `jti`, refuses a token older or longer-lived than `TABDOCK_OAUTH_MAX_TOKEN_AGE` (120 minutes, at most 1440), accepts only the clients in `TABDOCK_OAUTH_CLIENT_IDS` when that is set, passes jose its key cache (10 minutes), cooldown (30 s) and timeout (5 s) explicitly, re-reads the provider's metadata hourly without adopting a new issuer or key URL, names an invitee by the namespaced claims `urn:tabdock:email` and `urn:tabdock:email_verified`, and logs each token session's shape once (claim types, `client_id` and lifetime, never a value).

Refusals are logged with a fixed reason, the account kind and the `client_id`, never a token or a subject, by one module (`auth-log.ts`), which collapses repeated 401s from one client address into one count a minute. One account mapping decides who a `sub` is, for `/mcp` and `/pair` alike (ADR 0016): a member (on the allowlist, with a user) or an invitee (anyone else the provider signs in, `g_` and a digest of the `sub`, named by verified email or as an unverified account), and invitees get in only with invites on.

### Public URL mode

Public URL mode (ADR 0014) starts when `TABDOCK_PUBLIC_URL` is set: the https origin a tunnel serves, such as `https://relay.example`, with no path. The relay still binds loopback. It needs `TABDOCK_OAUTH_ISSUER` and `TABDOCK_OAUTH_USERS` (comma-separated `sub=userId:Display Name`, the name optional and free of commas, the user id never starting `g_`; `sub` is the person's subject at the provider, in WorkOS the user's ID), and ignores `TABDOCK_DEV_TOKENS`, so a dev token is refused on every request.

`<public URL>/mcp` is the connector URL, the metadata `resource` and the audience tokens must carry, so register it at the provider as the resource; the public host joins the loopback names in the Host check for `/mcp` and the metadata; the production rules apply (an explicit `TABDOCK_ALLOWED_ORIGINS`, no `TABDOCK_DEV_ALLOW_NO_ORIGIN`); and `/page` refuses any upgrade whose Host is not a loopback name or that carries a `Forwarded` or `X-Forwarded-*` header, so only pages on the relay's machine attach. The OAuth settings without a public URL are refused, since tokens are issued for that address.

Public URL mode also needs `TABDOCK_PAIR_CLIENT_ID` and `TABDOCK_PAIR_CLIENT_SECRET`, the relay's own confidential client at the same provider with `<public URL>/pair/callback` as its redirect URI, for the QR flow below; they are refused without a public URL.

### Hosted mode

Hosted mode (ADR 0018) is public URL mode on a host: `TABDOCK_ENV=production`, a public URL and `TABDOCK_CLIENT_ADDRESS_HEADER`, the one header the host's edge overwrites with the client's address. Only then may `TABDOCK_HOST` be `0.0.0.0`, never `::`.

`client-address.ts` believes the header only from a peer inside `TABDOCK_TRUSTED_PROXY_CIDR` (the RFC 1918 ranges unless set), counting IPv4-mapped and IPv4-compatible forms as IPv4 and native IPv6 by its /56; a missing, repeated or malformed header is a 400 on `/page`, `/pair` and `/i`, and a peer outside the ranges counts as itself and is logged. `/page` then takes upgrades for the public host alone, the Host allowlist still answers the platform's own name for the app with 403 everywhere but `/healthz`, and the sign-in gate (`sign-in-gate.ts`) adds 10 sign-ins a minute and 2 in flight per address, checked before the relay-wide 60 and 8. [Run a relay](https://github.com/PaulMRamirez/tabdock/blob/main/docs/guide/07-run-a-relay.md) runs the image behind nginx or Caddy, and [docs/deploy.md](https://github.com/PaulMRamirez/tabdock/blob/main/docs/deploy.md) is the reference deployment on Fly.io.

### The QR flow

The QR flow (`pair.ts`, public URL mode only; without a public URL no `/pair` route exists and the pairing frame has no URL). Each pairing code gets a QR nonce: 128 random bits, bound to the page, single use, living as long as the code (120 s) and replaced with it, stored only as a SHA-256 digest in the store's generic single-use tickets (kind `pair`; invites keep records of their own). The `pairing` frame's `url` is `<public URL>/pair#<nonce>`; the fragment never reaches the relay, the tunnel or a log. `GET /pair` is a static page under a strict CSP (`default-src 'self'`, its script and style as files, no inline script, `frame-ancestors 'none'`, Trusted Types required) with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; its script reads the fragment, clears it with `history.replaceState`, keeps it in `sessionStorage` across sign-in, and claims only when the person taps Join.

`POST /pair/preview` (`{"nonce"}` as JSON, never in a URL) uses nothing up and returns the page's origin (from its socket's Origin header), its title (capped at 120 characters, controls stripped, shown as written by the page) and its current code to compare with the widget, plus whether the browser is signed in.

`/pair/login` and `/pair/callback` run `openid-client`'s authorization code flow, asking for `openid email`, with PKCE S256, state and nonce against the oauth plugin's provider (the metadata its `start()` checked), with `client_secret_post` when the provider offers it and `client_secret_basic` otherwise; the ID token's signature is checked against the provider's keys as well, its `sub` goes through the account mapping, and the browser gets a `__Host-tabdock-pair` cookie (Secure, HttpOnly, SameSite=Lax, Path=/) naming an in-memory session that lasts 15 minutes (`timings.pairSessionMs`), at most 4 per account and 200 in all (`limits.pairSessions`, strangers ended first). The sign-in in progress (state, nonce, verifier) lives in the browser's own `__Host-tabdock-pair-login` cookie for 10 minutes, so nobody can fill the relay with half-finished sign-ins.

`POST /pair/claim` needs the session, an `Origin` equal to the public origin and JSON; with invites off a non-member gets 403 `not_allowed`, and with them on an invitee's claim goes to the hub, which counts it against the per-user pairing limit, records it and answers `invite_required` before the nonce is read; a member's claim then uses the nonce up, rotates the code and nonce, and raises an attach request `via: 'qr'` exactly as `pair_page` does (one pending request per user and page, the operator's approval, silence as denial), returning a claim id; `POST /pair/status` answers `pending`, `approved` with the role, `denied` or `expired` for the claimant's own claim only. Unknown, used and expired nonces get one answer (404 `pairing_expired`).

Pairing limits never count by address, since behind the tunnel every caller shares one (S3, ADR 0016): `pair_page` and QR claims share `rateLimits.pairAttemptsPerUser` (10 a minute), every pairing that lands on a page counts against `pairAttemptsPerPage` (30), and previews of one live nonce against `pairPreviewsPerNonce` (30); an unknown, used or expired nonce is answered without being counted, so made-up nonces leave nothing behind.

Each sign-in that comes back to `/pair/callback` costs a code exchange, a request to the provider carrying the `/pair` client's secret, and anyone can send one with a login cookie of their own making, so the whole relay makes at most `limits.pairSignInsInFlight` (8) at once and `rateLimits.pairSignIns` (60) a window; past either the sign-in fails (`/pair?signin=failed`, a warn line) and the provider hears nothing. The limiter behind all of these (`rate-limit.ts`) costs the same per call however many keys it holds and holds at most a bounded number, dropping those recorded longest ago past its cap.

Outside hosted mode per-address limits remain only on `/page`, where the address is the page's own; in hosted mode the sign-in gate also counts by client address. Requests are logged by route (`/mcp`, `/pair/claim`, `/i/claim`, `(other)`), never by raw path or query. Scan to first call (A3.3) is timed by the spike's pairing milestones below, which `/pair/preview` and `/pair/claim` report through the hub.

### Invites

Invites (ADRs 0016 and 0017) need a public URL and `TABDOCK_INVITES=1`. A page mints one with `invite_create` while a member is attached, the member attached longest becoming its sponsor; the relay keeps only the secret's hash and terms, at most 10 live per page, each for at most 24 hours and 20 uses (Can control: 1), and sends the page an `invites` frame after each welcome and change. `/i` is served beside `/pair`, under the same CSP and sign-in, and previews the page, its title and the invite's label as the page wrote them, and the sponsor, joining only on a click; `pair_page` takes a one-use link instead of a code.

Every redemption reaches the page with the secret presented, and the page decides: a Can watch link lets an observer in without a prompt, a Can control one prompts, one at a time, and burns after three refusals or timeouts. The relay grants no more than the invite's role, ends what an invite made after 24 hours, with the page session, on revoke or when the sponsor leaves, keeps members two seats, and bars a revoked invitee's `sub` and verified email from that invite.

Invitees hold one 2025-era MCP session, and one 2026-07-28 listen stream, until they hold an attachment, in pools of their own where a session or stream gives way only to someone ranked above its holder (a stranger, an invitee holding no attachment, below a guest, one holding an attachment, below a member) or, a session only and when idle, to someone of its holder's rank (`sessions.ts`, `listen-streams.ts`); a stream gives way only once the SDK has answered the listen that needs its place with a stream, so a listen it refuses ends nobody's, and a listen whose body is over 16 KiB is refused with 413 before it touches any stream, spending only its one budget request. They see only the pages they hold and get `invite_required` for a pairing code. Each user's tool calls, listens and 2026-07-28 requests the SDK refuses count against a request budget before the access check (ADR 0018).

### The audit log

The audit log (ADR 0019): with `TABDOCK_AUDIT_DIR`, which production requires, or in local mode (`audit/` beside the owner token), `audit-file.ts` writes one JSON line per record into 0600 files in a 0700 directory, each line checked against the protocol's schema and chained to the SHA-256 of the one before, with a checkpoint on stderr every 15 minutes, at rotation and at stop; files rotate at 8 MiB or UTC midnight and are kept 30 days or 64 MiB (`TABDOCK_AUDIT_RETENTION_DAYS`, `TABDOCK_AUDIT_MAX_MB`), and the log holds `audit.lock` while it writes, so a second relay on the directory refuses to start. It fails open: a failing disk leaves records on stderr and an `audit_gap` counting what the file missed. Without a directory, dev tokens and tests keep a 1000-entry memory ring.

Refusals that reach no page pass through `audit-budget.ts`, 10 lines a minute per account and 30 shared by accounts holding no attachment, then a summary a minute. Each record's stderr copy drops an invitee's email.

Lines someone can cause at will without spending a budget share that stderr, so `repeated-lines.ts` bounds them: on `/mcp` (the SDK's refusals, refused or evicted 2025-era sessions, refused listens, the Node adapter's errors and, without a public URL, refusals of proxied requests) one line per kind a minute and a count of the rest, and a session id presented by someone other than its owner (S13) 3 lines a minute per presenting user, each user's rest counted in a line naming them (ADR 0019's notes); on `/page` the lines of frames that change nothing up to 20 a minute per socket and 60 per address, the rest counted per address, never closing the page, and the lines each connection writes (an upgrade refused, a socket closed for its first frame, its silence or its unread frames, a page connected, asleep or gone, a sleeper ended) up to 60 a minute per address, the rest counted per address (ADR 0023 and its notes); an error's message is cut to 200 characters. `pnpm audit:log` (`audit-cli.ts`) filters and prints the files and checks the chain with `--verify`.

### The spike

`TABDOCK_SPIKE=1` turns on the M3 spike's measurements (`spike.ts`, ADR 0014, SPEC A3.3); production refuses to start with it, and public URL mode allows it, since hosted Claude is what it measures. The relay then logs every `tools/list` and every stream a client opens or ends (a 2025 session's GET stream, a 2026-07-28 `subscriptions/listen`) with the client's own name and a short session label, puts its timestamps for each `call_page_tool` (request in, invoke out, result in, response out) into the result's `_meta` under `tabdock/spikeTiming` and a log line, and logs pairing milestones up to the first call: `spike: pairing milestone` lines with a `stage` of `issued` (debug), `scanned` (the first `/pair` preview of a nonce), `claimed` (a code or nonce matched, with `via`), `approved` or `refused`, and `first_call`, each with the milliseconds since the earlier stages and a `trace` id (`tr_...`) the spike draws for each ticket, random and unrelated to its code or nonce, so one pairing can be followed through the log.

Typing `add`, `remove` or `status` in the relay's own terminal adds a numbered marker tool beside the five fixed tools, or removes it, and tells open sessions the list changed: `notifications/tools/list_changed` on 2025 sessions' streams and on 2026-07-28 clients' `subscriptions/listen` streams, through the relay's own notifier, telling every member itself, since a first-class list change reaches only its own user. Nothing over HTTP controls it, so no web page and nothing behind the tunnel can.

## Internals

The design is in [SPEC.md](https://github.com/PaulMRamirez/tabdock/blob/main/SPEC.md), sections 4 to 7, and the decisions in the repository's [ADRs](https://github.com/PaulMRamirez/tabdock/tree/main/docs/adr). Pages dial out to a WebSocket at `/page`; MCP clients reach the five fixed tools at `/mcp`, and with first-class tools on each attached page's tools by name, over Streamable HTTP through the official MCP SDK v2; `/healthz` answers `ok`. The relay only routes calls and never runs page tools itself.

### Requests and calls

A request or page upgrade whose `Host` is not a host and an optional port (RFC 9110: a name of unreserved characters, a dotted IPv4 address or a bracketed IPv6 one, a port up to 65535; no userinfo, path, query, fragment or percent-encoding), or that carries more than one `Host` line, gets 400 before anything reads it; the relay counts every header line, since Node would otherwise drop those past 2000 entries without saying so.

The Host check for `/mcp`, the plugin's routes and `/pair`, and the loopback test for `/page` (and, without a public URL, for `/mcp`), compare the lower-cased host without its port exactly with `localhost`, `127.0.0.1`, `[::1]` and the public host, so forms the URL parser would rewrite into one of them, such as `2130706433` or `127.1`, get 403. An unexpected failure inside the SDK's Node adapter is logged as `mcp adapter error` with the error's class only, since its message can quote the URL.

`/mcp` has two legs behind the Host check and the auth plugin, composed as the SDK documents: 2025-era traffic (`isLegacyRequest`) goes to a sessionful leg with one transport and one server per session, the SDK's low-level `Server`, which answers `tools/list` and dispatches `tools/call` itself so no page-chosen name is ever registered (ADR 0025), bound to the user who opened it, and everything else to `createMcpHandler` with `legacy: 'reject'`.

Mutating calls wait in a per-page queue and run one at a time in arrival order; read-only calls go straight to the page. Arguments are checked against the tool's own `inputSchema` with the SDK's CfWorker validator, after every regex, `format` and `uniqueItems` in it is removed (ADR 0008), on a worker thread with a 50 ms budget (`timings.argumentCheckMs`, ADR 0010): a check that cannot finish in time lets the call through unchecked, and the relay's main thread never runs the validator.

### A page that stops reading

A page that stops reading cannot make the relay hold what it sends (ADR 0024): the hub counts each frame it hands a page's socket until the kernel takes it, and past 256 such frames still queued, or once that queue, what the kernel has not yet taken, would pass 2 MiB, closes the socket with 1008 (`page is not reading`) and cuts it off 2 s later; the page sleeps and may resume. A call's invoke goes out only while the queue holds at most 1 MiB with it, and otherwise waits for room until its deadline, so calls never close a page, and neither do cancels, while a page that reads, however slowly, is never closed for what it is sent (ADR 0024's notes). The hub answers WebSocket ping control frames itself, within the same bound, and `ws` never does on its own.

### What waiting requests hold

A call or a pairing that waits on a page is charged what its request is measured to hold on the heap, counted from the body before either MCP leg parses it (`request-heap.ts`): a measure set above what every shape in `test/helpers/call-shapes.ts` was measured to hold on both legs, keys of digits alone included, not a bound proven for every shape. It is held within `TABDOCK_MAX_REQUEST_BYTES_PER_USER` (25165824 bytes, 24 MiB, by default) per user, past which it is refused `rate_limited`, a quarter of the total for invitees together (16 MiB by default, never under 4 MiB), and `TABDOCK_MAX_REQUEST_BYTES` (67108864 bytes, 64 MiB, by default) for the relay, past either of which a call is refused `page_busy` and a pairing `rate_limited`; a body whose charge alone passes a user's share is answered 413 unparsed, and a share above the total stops the relay at start (ADRs 0018 and 0030).

On the 2026-07-28 leg every request spends one of its caller's requests a minute as it arrives, `tools/list`, `server/discover`, `initialize` and every `tools/call` included, whatever it names; a `subscriptions/listen` spends in `listen-streams.ts` instead. Past the budget, a `tools/call` naming one of the five fixed tools, or while first-class tools are on a first-class name, whose `requestState` the SDK will not refuse first, is answered `rate_limited` in that tool's words with its audit record (a first-class call with `call_page_tool`'s), and any other request gets 429 with no audit record and one line a minute (ADRs 0030 and 0032). On a 2025-era session the relay's own dispatcher spends one request for every `tools/call` before it resolves the name, and while first-class tools are on so does every `tools/list`; past the budget a fixed or first-class call is refused as on 2026-07-28, and anything else gets a JSON-RPC error with one line a minute and no record.

An `/mcp` response whose unsent bytes stop shrinking for three checks 10 s apart (`response-stalls.ts`) is cut off, freeing what it held and cancelling a call still waiting on it, with one warn line a minute naming the user; a client that keeps reading is never cut (ADR 0030). A user may have at most eight responses with bytes waiting, an invitee two, and the oldest past that are cut off the same way, with a line of their own, as each answer of theirs is handed over and at every check, so unread answers of up to about 0.72 MB each hold about 6.5 MB for a member however fast they are opened; and a response queued behind another on a connection that closes, as a client that pipelines leaves it, ends with that connection (ADR 0030's notes).

### Layout, build and tests

Inside this repository's workspace, and never from npm (the published package is a command with no library entry point, ADR 0028), `createRelay(options)` in `src/relay.ts` starts one on a chosen or free port and returns its URLs, its audit log and `close()`; `options.timings`, `options.rateLimits` and `options.limits` shorten lifetimes and shrink limits for tests. A call's deadline goes to the page as `callDeadlineMs`, counted from the call's arrival, while the relay's own timer waits `callDeadlineGraceMs` (2 s) longer, so a page's answer at its deadline, such as `denied_by_operator` for an unanswered prompt, reaches the client instead of a bare `timeout`.

The layout of `src/`: `relay.ts` (HTTP, upgrade checks, MCP mount), `sessions.ts` (the 2025-era session leg), `hub.ts` (page sessions, pairing, attachments, the write queue, calls), `mcp.ts` (the tool surface: the five tools and first-class names), `first-class.ts` (a page tool's first-class entry), `schema-keywords.ts` (the schema keyword positions the cut and a first-class entry share), `page-tool-notifier.ts` (each user's list change notices), `validate.ts` (preparing schemas and describing failures), `argument-checker.ts` and `argument-worker.ts` (the checks on a worker thread), `cfworker.ts` (the only module that loads the validator), `check-messages.ts` (messages to and from the worker), `store.ts` (storage interfaces and in-memory implementations), `audit-file.ts`, `audit-budget.ts` and `audit-cli.ts` (the audit log, its refusal budget and its reader), `auth.ts` (the auth plugin contract and dev-token), `auth-log.ts` (sign-in refusal lines), `client-address.ts` and `sign-in-gate.ts` (the client address and the sign-in budget), `local-token.ts`, `token-lock.ts`, `local-banner.ts` and `shell-quote.ts` (local mode's owner token, its directory's lock, its header helper and what it prints), `oauth.ts` (the OAuth plugin), `pair.ts` and `pair-page/` (the QR flow at `/pair`, the invite page at `/i` and their static files), `secrets.ts` (ids, codes, digests), `config.ts` (options, public URL mode, the environment), `spike.ts` (the M3 spike's measurements), `origin-refusals.ts` (the `/mcp` Origin refusal's lines), `log.ts`, `rate-limit.ts`, `cli.ts` and `argument-names.ts` (the command, `tabdock-relay`, and how it and the audit reader name an argument they refuse), `main.ts` (what `pnpm relay` and the image run) and `packaged.ts` (the mark only the bundle carries).

`scripts/build.ts` bundles `cli.ts` and the worker with esbuild into `dist/`, every npm dependency external and `@tabdock/protocol` among them, `TABDOCK_PACKAGED` defined there alone, which names the bundle's worker file, drops the `.env` and the checkout comparison and points the banner at the deploy guide's URL; `scripts/shrinkwrap.ts` makes the published `npm-shrinkwrap.json` from the versions this workspace resolved, `@tabdock/protocol` included, pinned by the registry URL and sha512 of the very tarball packed beside the relay, since npm installs a shrinkwrapped package's dependencies from that file alone; and `scripts/pack-install.ts` runs `npx @tabdock/relay@<version>` through `scripts/local-registry.ts`, which serves the packed tarballs as the npm registry will after the publish, `_hasShrinkwrap` and all, then runs the installed command as A5.5 asks (ADR 0028 and its notes; [docs/release.md](https://github.com/PaulMRamirez/tabdock/blob/main/docs/release.md)). Only packing builds anything: in the workspace the package still exports its TypeScript sources (ADR 0003), and the published package has one bin and no library entry point.

Tests in `test/` drive it with a hand-written page client over `ws`, the SDK's own MCP client and, for session edge cases, raw HTTP; the OAuth tests use `oauth2-mock-server` as the identity provider (`test/helpers/provider.ts`) and play the tunnel with `test/helpers/tunnel.ts`, which sends requests for `https://relay.test` to the relay with that Host, and `test/helpers/phone.ts` plays a phone's browser at `/pair` and `/i` with a cookie jar; `test/helpers/invites.ts` runs it in public URL mode with invites on and mints as the adapter does, and `test/helpers/main-process.ts` runs `main.ts` as a child, as the image does. In the workspace alone, the end-to-end tests import the provider, tunnel, secrecy and result helpers through the package's `./test/provider`, `./test/tunnel`, `./test/secrecy` and `./test/results` exports, which the published package leaves out.
