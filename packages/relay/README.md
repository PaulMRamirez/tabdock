# @tabdock/relay

The Node service at the centre of Tabdock (SPEC.md sections 4 to 7). Pages dial out to a WebSocket at `/page`; MCP clients reach the five fixed tools at `/mcp` over Streamable HTTP through the official MCP SDK v2; `/healthz` answers `ok`. The relay only routes calls and never runs page tools itself.

Run it with `pnpm relay` at the root (or `node packages/relay/src/main.ts`, or `pnpm --filter @tabdock/relay start`). Every setting is optional. It loads the repo-root `.env` when present and reads `TABDOCK_HOME` (local mode's token directory, below), `TABDOCK_DEV_TOKENS` (`alice=<token>,bob=<token>`, tokens of 24 or more characters, which turns local mode off), `TABDOCK_HOST` (loopback only, or `0.0.0.0` in hosted mode below; the relay resolves a name such as `localhost` itself and refuses to start unless every address it gives is loopback, then listens on that address), `TABDOCK_PORT` (default 8787), `TABDOCK_ENV` (`development` or `production`), `TABDOCK_ALLOWED_ORIGINS` (comma list; required in production; in development the default is http and https on localhost, 127.0.0.1 and [::1]) and `TABDOCK_DEV_ALLOW_NO_ORIGIN` (development only, lets a page socket without an Origin header in). The section 9 limits and idle lifetimes (ADR 0009) are optional: `TABDOCK_MAX_SESSIONS_PER_USER` (20), `TABDOCK_MAX_SESSIONS` (1000), `TABDOCK_MAX_USERS_PER_PAGE` (10), `TABDOCK_MAX_QUEUE_DEPTH` (32), `TABDOCK_MAX_PAGE_SOCKETS_PER_ADDRESS` (20 open), `TABDOCK_MAX_PAGE_SESSIONS_PER_ADDRESS` (20, asleep ones included), `TABDOCK_MAX_PAGE_SESSIONS` (1000; hosted mode defaults these three to 5, 5 and 100), `TABDOCK_MAX_REQUESTS_PER_USER` (240 tool calls a minute per member) and `TABDOCK_MAX_REQUESTS_PER_INVITEE` (60), `TABDOCK_MAX_TOOL_BYTES` (64 MiB, an upper bound on the heap all pages' tool lists hold), `TABDOCK_MAX_CALLS_PER_MINUTE` (120 per user per page), `TABDOCK_MAX_PAIR_SIGNINS_PER_MINUTE` (60 for the whole relay), `TABDOCK_MAX_PAIR_SIGNINS_IN_FLIGHT` (8 at once), `TABDOCK_SESSION_IDLE_MINUTES` (30) and `TABDOCK_ATTACHMENT_IDLE_MINUTES` (480). It prints its URLs on stdout and JSON log lines on stderr, never a token, a code or a session id.

Local mode (ADR 0022) is what the relay runs with none of `TABDOCK_DEV_TOKENS`, `TABDOCK_PUBLIC_URL`, `TABDOCK_OAUTH_ISSUER`, `TABDOCK_OAUTH_USERS`, `TABDOCK_PAIR_CLIENT_ID` and `TABDOCK_PAIR_CLIENT_SECRET` set (blank counts as unset) and `TABDOCK_ENV` unset or `development`; explicit settings always win, and production without them refuses to start rather than fall back. One user, `you` (shown as You), holds an owner token through the ordinary `dev-token` plugin, which keeps only its digest; the plugin carries `loopbackOnly: true`, and `resolveConfig` refuses any plugin so marked, whatever its name, with a public URL, in production or off loopback. `local-token.ts` keeps the token in `owner-token` inside `TABDOCK_HOME` (absolute only) or the per-user configuration directory: `$XDG_CONFIG_HOME/tabdock` (when absolute) or `~/.config/tabdock` on Linux and other Unix systems, `~/Library/Application Support/Tabdock` on macOS, `%LOCALAPPDATA%\Tabdock` on Windows. The first start makes the directory 0700 and draws `tabdock_` plus 43 base64url characters (32 bytes from `randomBytes`) into a temporary 0600 file opened with `O_CREAT | O_EXCL`, syncs it and hard-links it to `owner-token`, so a second start racing it reads the winner's complete file rather than an empty one. Every start opens the file without following a symlink and checks it through the descriptor, and refuses, naming the path and the fix ("chmod 700", "chmod 600", "delete it and start again") and never the contents: a directory inside the checkout (compared by `realpath`, case-insensitively on macOS and Windows), a directory or file another account owns or that grants its group or others any permission, and anything that is not a regular file of at most 64 bytes matching `^tabdock_[A-Za-z0-9_-]{43}\n?$`. Like ssh with a private key it refuses rather than repairs. On Windows, where Node reports no owner and lacks `O_NOFOLLOW`, `lstat` checks for a regular file and the directory must lie under `%LOCALAPPDATA%` or `%USERPROFILE%`. The resolver reads its variables only from the environment object it is given, with the platform, uid, home directory and stat calls injectable for tests. `readOwnerToken` reads without ever creating, for tools such as `pnpm spike:latency`. The banner (`local-banner.ts`, shared with `pnpm dev`) says the relay serves this computer only, names the MCP and page socket URLs and the token's path, says whether the token was just drawn, and prints `claude mcp add --transport http --scope user tabdock-local <url> --header "Authorization: Bearer $(cat '<path>')"`, or on Windows the PowerShell form with `$(Get-Content -TotalCount 1 -LiteralPath '<path>')`, so the line names the path, never the token. Every start also says how to remove an older `tabdock-local` entry, which `claude mcp add` refuses to replace: a token kept from an earlier start may be one no relay ever served, if that start could not listen. It suggests `claude mcp list` to check the connection, never `claude mcp get`, which prints the header. To rotate, stop the relay, delete the file and start again, then replace the Claude Code entry; the old token gets 401. Local mode decides who may call `/mcp`, never who reaches a page: the operator still approves each attachment. It trusts every account on its machine, since nothing authenticates the relay to its clients.

Without a public URL, in local mode and with dev tokens alike, an `/mcp` request or `/page` upgrade whose Host is not a loopback name as written, or that carries `Forwarded` or any `X-Forwarded-*` header, gets 403 before the auth plugin runs, so a tunnel pointed at a loopback relay, even one that rewrites Host, cannot expose it.

Auth is a plugin (`auth.ts`, ADR 0013): `authenticate(request)` returns a user, or a refusal that carries its own status, body and headers (401 with `WWW-Authenticate` to sign in, 403 for someone signed in but not allowed, 503 when the plugin cannot check anyone just now); the relay checks that answer with zod before acting on it. A plugin may also serve GET routes, may need `start({ log })` before the relay listens and `stop()` when it closes or fails to start, and says only who someone is: the relay itself decides whether to admit an invitee, which it does only with `TABDOCK_INVITES` on (ADR 0020). `dev-token` answers exactly as it has since M1. The `oauth` plugin (`oauth.ts`) makes the relay a resource server for an external identity provider: at start it reads the provider's RFC 8414 metadata (OpenID Connect discovery as the fallback, as Claude does) and refuses to start unless the metadata names `TABDOCK_OAUTH_ISSUER` exactly, lists S256, and offers client ID metadata documents with `none` or a registration endpoint; it serves RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` naming the provider as the only authorization server, with no scopes; and it checks each token with the SDK's `verifyBearerToken` over `jose` (RS256 only, the provider's published keys, issuer, audience equal to the public MCP URL, a required expiry, 5 s of clock tolerance). Every refused `/mcp` request, on both legs, gets the SDK's 401 challenge with `resource_metadata` before any MCP code runs; a valid token whose `sub` is not in `TABDOCK_OAUTH_USERS` gets a plain 403, unless invites are on and it is admitted as an invitee; keys that cannot be fetched give 503 with `Retry-After: 5`, and after a failed fetch (a cold start's first one included) the plugin fetches again no sooner than that, whatever tokens arrive, while the keys `jose` still holds as fresh (fetched at most 10 minutes earlier) keep checking tokens with no fetch, so no key is trusted longer than `jose` alone would trust it (a key missing from them is a 503 then, not a 401). From M4 (ADR 0020) it also requires `iat` and `jti`, refuses a token older or longer-lived than `TABDOCK_OAUTH_MAX_TOKEN_AGE` (120 minutes, at most 1440), accepts only the clients in `TABDOCK_OAUTH_CLIENT_IDS` when that is set, passes jose its key cache (10 minutes), cooldown (30 s) and timeout (5 s) explicitly, re-reads the provider's metadata hourly without adopting a new issuer or key URL, names an invitee by the namespaced claims `urn:tabdock:email` and `urn:tabdock:email_verified`, and logs each token session's shape once (claim types, `client_id` and lifetime, never a value). Refusals are logged with a fixed reason, the account kind and the `client_id`, never a token or a subject, by one module (`auth-log.ts`), which collapses repeated 401s from one client address into one count a minute. One account mapping decides who a `sub` is, for `/mcp` and `/pair` alike (ADR 0016): a member (on the allowlist, with a user) or an invitee (anyone else the provider signs in, `g_` and a digest of the `sub`, named by verified email or as an unverified account), and invitees get in only with invites on.

Public URL mode (ADR 0014) starts when `TABDOCK_PUBLIC_URL` is set: the https origin a tunnel serves, such as `https://<name>.ngrok-free.app`, with no path. The relay still binds loopback. It needs `TABDOCK_OAUTH_ISSUER` and `TABDOCK_OAUTH_USERS` (comma-separated `sub=userId:Display Name`, the name optional and free of commas; `sub` is the person's subject at the provider, in WorkOS the user's ID), and ignores `TABDOCK_DEV_TOKENS`, so a dev token is refused on every request. `<public URL>/mcp` is the connector URL, the metadata `resource` and the audience tokens must carry, so register it at the provider as the resource; the public host joins the loopback names in the Host check for `/mcp` and the metadata; the production rules apply (an explicit `TABDOCK_ALLOWED_ORIGINS`, no `TABDOCK_DEV_ALLOW_NO_ORIGIN`); and `/page` refuses any upgrade whose Host is not a loopback name or that carries a `Forwarded` or `X-Forwarded-*` header, so only pages on the relay's machine attach. The OAuth settings without a public URL are refused, since tokens are issued for that address. Public URL mode also needs `TABDOCK_PAIR_CLIENT_ID` and `TABDOCK_PAIR_CLIENT_SECRET`, the relay's own confidential client at the same provider with `<public URL>/pair/callback` as its redirect URI, for the QR flow below; they are refused without a public URL.

Hosted mode (ADR 0018) is public URL mode on a host: `TABDOCK_ENV=production`, a public URL and `TABDOCK_CLIENT_ADDRESS_HEADER`, the one header the host's edge overwrites with the client's address. Only then may `TABDOCK_HOST` be `0.0.0.0`, never `::`. `client-address.ts` believes the header only from a peer inside `TABDOCK_TRUSTED_PROXY_CIDR` (the RFC 1918 ranges unless set), counting IPv4-mapped and IPv4-compatible forms as IPv4 and native IPv6 by its /56; a missing, repeated or malformed header is a 400 on `/page`, `/pair` and `/i`, and a peer outside the ranges counts as itself and is logged. `/page` then takes upgrades for the public host alone, the Host allowlist still answers the platform's own name for the app with 403 everywhere but `/healthz`, and the sign-in gate (`sign-in-gate.ts`) adds 10 sign-ins a minute and 2 in flight per address, checked before the relay-wide 60 and 8. `docs/deploy.md` covers the image and the reference deployment.

The QR flow (`pair.ts`, public URL mode only; without a public URL no `/pair` route exists and the pairing frame has no URL). Each pairing code gets a QR nonce: 128 random bits, bound to the page, single use, living as long as the code (120 s) and replaced with it, stored only as a SHA-256 digest in the store's generic single-use tickets (kind `pair`; invites keep records of their own). The `pairing` frame's `url` is `<public URL>/pair#<nonce>`; the fragment never reaches the relay, the tunnel or a log. `GET /pair` is a static page under a strict CSP (`default-src 'self'`, its script and style as files, no inline script, `frame-ancestors 'none'`, Trusted Types required) with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; its script reads the fragment, clears it with `history.replaceState`, keeps it in `sessionStorage` across sign-in, and claims only when the person taps Join. `POST /pair/preview` (`{"nonce"}` as JSON, never in a URL) uses nothing up and returns the page's origin (from its socket's Origin header), its title (capped at 120 characters, controls stripped, shown as written by the page) and its current code to compare with the widget, plus whether the browser is signed in. `/pair/login` and `/pair/callback` run `openid-client`'s authorization code flow, asking for `openid email`, with PKCE S256, state and nonce against the oauth plugin's provider (the metadata its `start()` checked), with `client_secret_post` when the provider offers it and `client_secret_basic` otherwise; the ID token's signature is checked against the provider's keys as well, its `sub` goes through the account mapping, and the browser gets a `__Host-tabdock-pair` cookie (Secure, HttpOnly, SameSite=Lax, Path=/) naming an in-memory session that lasts 15 minutes (`timings.pairSessionMs`), at most 4 per account and 200 in all (`limits.pairSessions`, strangers ended first). The sign-in in progress (state, nonce, verifier) lives in the browser's own `__Host-tabdock-pair-login` cookie for 10 minutes, so nobody can fill the relay with half-finished sign-ins. `POST /pair/claim` needs the session, an `Origin` equal to the public origin and JSON; with invites off a non-member gets 403 `not_allowed`, and with them on an invitee's claim goes to the hub, which counts it against the per-user pairing limit, records it and answers `invite_required` before the nonce is read; a member's claim then uses the nonce up, rotates the code and nonce, and raises an attach request `via: 'qr'` exactly as `pair_page` does (one pending request per user and page, the operator's approval, silence as denial), returning a claim id; `POST /pair/status` answers `pending`, `approved` with the role, `denied` or `expired` for the claimant's own claim only. Unknown, used and expired nonces get one answer (404 `pairing_expired`).

Pairing limits never count by address, since behind the tunnel every caller shares one (S3, ADR 0016): `pair_page` and QR claims share `rateLimits.pairAttemptsPerUser` (10 a minute), every pairing that lands on a page counts against `pairAttemptsPerPage` (30), and previews of one live nonce against `pairPreviewsPerNonce` (30); an unknown, used or expired nonce is answered without being counted, so made-up nonces leave nothing behind. Each sign-in that comes back to `/pair/callback` costs a code exchange, a request to the provider carrying the `/pair` client's secret, and anyone can send one with a login cookie of their own making, so the whole relay makes at most `limits.pairSignInsInFlight` (8) at once and `rateLimits.pairSignIns` (60) a window; past either the sign-in fails (`/pair?signin=failed`, a warn line) and the provider hears nothing. The limiter behind all of these (`rate-limit.ts`) costs the same per call however many keys it holds and holds at most a bounded number, dropping those recorded longest ago past its cap. Outside hosted mode per-address limits remain only on `/page`, where the address is the page's own; in hosted mode the sign-in gate also counts by client address. Requests are logged by route (`/mcp`, `/pair/claim`, `/i/claim`, `(other)`), never by raw path or query. Scan to first call (A3.3) is timed by the spike's pairing milestones below, which `/pair/preview` and `/pair/claim` report through the hub.

Invites (ADRs 0016 and 0017) need a public URL and `TABDOCK_INVITES=1`. A page mints one with `invite_create` while a member is attached, the member attached longest becoming its sponsor; the relay keeps only the secret's hash and terms, at most 10 live per page, each for at most 24 hours and 20 uses (Can control: 1), and sends the page an `invites` frame after each welcome and change. `/i` is served beside `/pair`, under the same CSP and sign-in, and previews the page, its title and the invite's label as the page wrote them, and the sponsor, joining only on a click; `pair_page` takes a one-use link instead of a code. Every redemption reaches the page with the secret presented, and the page decides: a Can watch link lets an observer in without a prompt, a Can control one prompts, one at a time, and burns after three refusals or timeouts. The relay grants no more than the invite's role, ends what an invite made after 24 hours, with the page session, on revoke or when the sponsor leaves, keeps members two seats, and bars a revoked invitee's `sub` and verified email from that invite. Invitees hold one 2025-era MCP session, and one 2026-07-28 listen stream, until they hold an attachment, in pools of their own where a session or stream gives way only to someone ranked above its holder (a stranger, an invitee holding no attachment, below a guest, one holding an attachment, below a member; `sessions.ts`, `listen-streams.ts`), see only the pages they hold and get `invite_required` for a pairing code. Each user's tool calls and listens count against a request budget before the access check (ADR 0018).

The audit log (ADR 0019): with `TABDOCK_AUDIT_DIR`, which production requires, or in local mode (`audit/` beside the owner token), `audit-file.ts` writes one JSON line per record into 0600 files in a 0700 directory, each line checked against the protocol's schema and chained to the SHA-256 of the one before, with a checkpoint on stderr every 15 minutes, at rotation and at stop; files rotate at 8 MiB or UTC midnight and are kept 30 days or 64 MiB (`TABDOCK_AUDIT_RETENTION_DAYS`, `TABDOCK_AUDIT_MAX_MB`), and the log holds `audit.lock` while it writes, so a second relay on the directory refuses to start. It fails open: a failing disk leaves records on stderr and an `audit_gap` counting what the file missed. Without a directory, dev tokens and tests keep a 1000-entry memory ring. Refusals that reach no page pass through `audit-budget.ts`, 10 lines a minute per account and 30 shared by accounts holding no attachment, then a summary a minute. Each record's stderr copy drops an invitee's email. `pnpm audit:log` (`audit-cli.ts`) filters and prints the files and checks the chain with `--verify`.

`TABDOCK_SPIKE=1` turns on the M3 spike's measurements (`spike.ts`, ADR 0014, SPEC A3.3); production refuses to start with it, and public URL mode allows it, since hosted Claude is what it measures. The relay then logs every `tools/list` and every stream a client opens or ends (a 2025 session's GET stream, a 2026-07-28 `subscriptions/listen`) with the client's own name and a short session label, puts its timestamps for each `call_page_tool` (request in, invoke out, result in, response out) into the result's `_meta` under `tabdock/spikeTiming` and a log line, and logs pairing milestones up to the first call: `spike: pairing milestone` lines with a `stage` of `issued` (debug), `scanned` (the first `/pair` preview of a nonce), `claimed` (a code or nonce matched, with `via`), `approved` or `refused`, and `first_call`, each with the milliseconds since the earlier stages and a `trace` id (`tr_...`) the spike draws for each ticket, random and unrelated to its code or nonce, so one pairing can be followed through the log. Typing `add`, `remove` or `status` in the relay's own terminal adds a numbered marker tool beside the five fixed tools, or removes it, and tells open sessions the list changed: `notifications/tools/list_changed` on 2025 sessions' streams, the SDK's `subscriptions/listen` bus for 2026-07-28 clients. Nothing over HTTP controls it, so no web page and nothing behind the tunnel can.

A request or page upgrade whose `Host` is not a host and an optional port (RFC 9110: a name of unreserved characters, a dotted IPv4 address or a bracketed IPv6 one, a port up to 65535; no userinfo, path, query, fragment or percent-encoding), or that carries more than one `Host` line, gets 400 before anything reads it; the relay counts every header line, since Node would otherwise drop those past 2000 entries without saying so. The Host check for `/mcp`, the plugin's routes and `/pair`, and the loopback test for `/page` (and, without a public URL, for `/mcp`), compare the lower-cased host without its port exactly with `localhost`, `127.0.0.1`, `[::1]` and the public host, so forms the URL parser would rewrite into one of them, such as `2130706433` or `127.1`, get 403. An unexpected failure inside the SDK's Node adapter is logged as `mcp adapter error` with the error's class only, since its message can quote the URL. `/mcp` has two legs behind the Host check and the auth plugin, composed as the SDK documents: 2025-era traffic (`isLegacyRequest`) goes to a sessionful leg with one transport and one `McpServer` per session, bound to the user who opened it, and everything else to `createMcpHandler` with `legacy: 'reject'`. Mutating calls wait in a per-page queue and run one at a time in arrival order; read-only calls go straight to the page. Arguments are checked against the tool's own `inputSchema` with the SDK's CfWorker validator, after every regex, `format` and `uniqueItems` in it is removed (ADR 0008), on a worker thread with a 50 ms budget (`timings.argumentCheckMs`, ADR 0010): a check that cannot finish in time lets the call through unchecked, and the relay's main thread never runs the validator.

In code, `createRelay(options)` starts one on a chosen or free port and returns its URLs, its audit log and `close()`; `options.timings`, `options.rateLimits` and `options.limits` shorten lifetimes and shrink limits for tests. A call's deadline goes to the page as `callDeadlineMs`, counted from the call's arrival, while the relay's own timer waits `callDeadlineGraceMs` (2 s) longer, so a page's answer at its deadline, such as `denied_by_operator` for an unanswered prompt, reaches the client instead of a bare `timeout`. The layout: `relay.ts` (HTTP, upgrade checks, MCP mount), `sessions.ts` (the 2025-era session leg), `hub.ts` (page sessions, pairing, attachments, the write queue, calls), `mcp.ts` (the five tools), `validate.ts` (preparing schemas and describing failures), `argument-checker.ts` and `argument-worker.ts` (the checks on a worker thread), `cfworker.ts` (the only module that loads the validator), `check-messages.ts` (messages to and from the worker), `store.ts` (storage interfaces and in-memory implementations), `audit-file.ts`, `audit-budget.ts` and `audit-cli.ts` (the audit log, its refusal budget and its reader), `auth.ts` (the auth plugin contract and dev-token), `auth-log.ts` (sign-in refusal lines), `client-address.ts` and `sign-in-gate.ts` (the client address and the sign-in budget), `local-token.ts` and `local-banner.ts` (local mode's owner token and what it prints), `oauth.ts` (the OAuth plugin), `pair.ts` and `pair-page/` (the QR flow at `/pair`, the invite page at `/i` and their static files), `secrets.ts` (ids, codes, digests), `config.ts` (options, public URL mode, the environment), `spike.ts` (the M3 spike's measurements), `log.ts`, `rate-limit.ts` and `main.ts` (what `pnpm relay` runs). Tests in `test/` drive it with a hand-written page client over `ws`, the SDK's own MCP client and, for session edge cases, raw HTTP; the OAuth tests use `oauth2-mock-server` as the identity provider (`test/helpers/provider.ts`) and play the tunnel with `test/helpers/tunnel.ts`, which sends requests for `https://relay.test` to the relay with that Host, and `test/helpers/phone.ts` plays a phone's browser at `/pair` and `/i` with a cookie jar; `test/helpers/invites.ts` runs it in public URL mode with invites on and mints as the adapter does, and `test/helpers/main-process.ts` runs `main.ts` as a child, as the image does. The provider, tunnel and secrecy helpers are also exported as `@tabdock/relay/test/provider`, `@tabdock/relay/test/tunnel` and `@tabdock/relay/test/secrecy` for the end-to-end tests.
