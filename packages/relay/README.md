# @tabdock/relay

The Node service at the centre of Tabdock (SPEC.md sections 4 to 7). Pages dial out to a WebSocket at `/page`; MCP clients reach the five fixed tools at `/mcp` over Streamable HTTP through the official MCP SDK v2; `/healthz` answers `ok`. The relay only routes calls and never runs page tools itself.

Run it with `node packages/relay/src/main.ts` (or `pnpm --filter @tabdock/relay start`). It loads the repo-root `.env` when present and reads `TABDOCK_DEV_TOKENS` (required unless the relay has a public URL, `alice=<token>,bob=<token>`, tokens of 24 or more characters), `TABDOCK_HOST` (loopback only until M4 brings TLS), `TABDOCK_PORT` (default 8787), `TABDOCK_ENV` (`development` or `production`), `TABDOCK_ALLOWED_ORIGINS` (comma list; required in production; in development the default is http and https on localhost, 127.0.0.1 and [::1]) and `TABDOCK_DEV_ALLOW_NO_ORIGIN` (development only, lets a page socket without an Origin header in). The section 9 limits and idle lifetimes (ADR 0009) are optional: `TABDOCK_MAX_SESSIONS_PER_USER` (20), `TABDOCK_MAX_SESSIONS` (1000), `TABDOCK_MAX_USERS_PER_PAGE` (10), `TABDOCK_MAX_QUEUE_DEPTH` (32), `TABDOCK_MAX_PAGE_SOCKETS_PER_ADDRESS` (20 open), `TABDOCK_MAX_PAGE_SESSIONS_PER_ADDRESS` (20, asleep ones included), `TABDOCK_MAX_PAGE_SESSIONS` (1000), `TABDOCK_MAX_CALLS_PER_MINUTE` (120 per user per page), `TABDOCK_SESSION_IDLE_MINUTES` (30) and `TABDOCK_ATTACHMENT_IDLE_MINUTES` (480). It prints its URLs on stdout and JSON log lines on stderr, never a token, a code or a session id.

Auth is a plugin (`auth.ts`, ADR 0013): `authenticate(request)` returns a user, or a refusal that carries its own status, body and headers (401 with `WWW-Authenticate` to sign in, 403 for someone signed in but not allowed, 503 when the plugin cannot check anyone just now); the relay checks that answer with zod before acting on it. A plugin may also serve GET routes and may need `start()` before the relay listens. `dev-token` answers exactly as it has since M1. The `oauth` plugin (`oauth.ts`) makes the relay a resource server for an external identity provider: at start it reads the provider's RFC 8414 metadata (OpenID Connect discovery as the fallback, as Claude does) and refuses to start unless the metadata names `TABDOCK_OAUTH_ISSUER` exactly, lists S256, and offers client ID metadata documents with `none` or a registration endpoint; it serves RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` naming the provider as the only authorization server, with no scopes; and it checks each token with the SDK's `verifyBearerToken` over `jose` (RS256 only, the provider's published keys, issuer, audience equal to the public MCP URL, a required expiry, 5 s of clock tolerance). Every refused `/mcp` request, on both legs, gets the SDK's 401 challenge with `resource_metadata` before any MCP code runs; a valid token whose `sub` is not in `TABDOCK_OAUTH_USERS` gets a plain 403; keys that cannot be fetched give 503. Refusals are logged with a fixed reason, never a token or a subject.

Public URL mode (ADR 0014) starts when `TABDOCK_PUBLIC_URL` is set: the https origin a tunnel serves, such as `https://<name>.ngrok-free.app`, with no path. The relay still binds loopback. It needs `TABDOCK_OAUTH_ISSUER` and `TABDOCK_OAUTH_USERS` (comma-separated `sub=userId:Display Name`, the name optional and free of commas; `sub` is the person's subject at the provider, in WorkOS the user's ID), and ignores `TABDOCK_DEV_TOKENS`, so a dev token is refused on every request. `<public URL>/mcp` is the connector URL, the metadata `resource` and the audience tokens must carry, so register it at the provider as the resource; the public host joins the loopback names in the Host check for `/mcp` and the metadata; the production rules apply (an explicit `TABDOCK_ALLOWED_ORIGINS`, no `TABDOCK_DEV_ALLOW_NO_ORIGIN`); and `/page` refuses any upgrade whose Host is not a loopback name or that carries a `Forwarded` or `X-Forwarded-*` header, so only pages on the relay's machine attach. The OAuth settings without a public URL are refused, since tokens are issued for that address.

`/mcp` has two legs behind the Host check and the auth plugin, composed as the SDK documents: 2025-era traffic (`isLegacyRequest`) goes to a sessionful leg with one transport and one `McpServer` per session, bound to the user who opened it, and everything else to `createMcpHandler` with `legacy: 'reject'`. Mutating calls wait in a per-page queue and run one at a time in arrival order; read-only calls go straight to the page. Arguments are checked against the tool's own `inputSchema` with the SDK's CfWorker validator, after every regex, `format` and `uniqueItems` in it is removed (ADR 0008), on a worker thread with a 50 ms budget (`timings.argumentCheckMs`, ADR 0010): a check that cannot finish in time lets the call through unchecked, and the relay's main thread never runs the validator.

In code, `createRelay(options)` starts one on a chosen or free port and returns its URLs, its audit log and `close()`; `options.timings`, `options.rateLimits` and `options.limits` shorten lifetimes and shrink limits for tests. A call's deadline goes to the page as `callDeadlineMs`, counted from the call's arrival, while the relay's own timer waits `callDeadlineGraceMs` (2 s) longer, so a page's answer at its deadline, such as `denied_by_operator` for an unanswered prompt, reaches the client instead of a bare `timeout`. The layout: `relay.ts` (HTTP, upgrade checks, MCP mount), `sessions.ts` (the 2025-era session leg), `hub.ts` (page sessions, pairing, attachments, the write queue, calls), `mcp.ts` (the five tools), `validate.ts` (preparing schemas and describing failures), `argument-checker.ts` and `argument-worker.ts` (the checks on a worker thread), `cfworker.ts` (the only module that loads the validator), `check-messages.ts` (messages to and from the worker), `store.ts` (storage interfaces and in-memory implementations), `auth.ts` (the auth plugin contract and dev-token), `oauth.ts` (the OAuth plugin), `secrets.ts` (ids, codes, digests), `config.ts` (options, public URL mode, the environment), `log.ts` and `rate-limit.ts`. Tests in `test/` drive it with a hand-written page client over `ws`, the SDK's own MCP client and, for session edge cases, raw HTTP; the OAuth tests use `oauth2-mock-server` as the identity provider (`test/helpers/provider.ts`) and play the tunnel with `test/helpers/tunnel.ts`, which sends requests for `https://relay.test` to the relay with that Host.
