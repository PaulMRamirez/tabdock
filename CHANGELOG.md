# Changelog

`@tabdock/protocol`, `@tabdock/adapter` and `@tabdock/relay` share one version, so this one file covers all three, one entry per release, each tagged `v<version>` (ADR 0028). `docs/release.md` says how a release is made. Versions follow semantic versioning; while they start with 0, a minor version may change the page link, the relay's settings or the packages' API.

## Unreleased (M6)

Milestone M6, a class on one tab (ADRs 0038 to 0049), and the map demo (ADR 0050), for the release after 0.1.0, expected to be 0.2.0, since M6 adds frames to the page link (ADR 0049). 0.1.0 is M5's code, tagged on `main` before M6 merges; nothing here is on npm yet.

**Map and globe pages.** A shared tool profile, `tabdock.map.v1`, of fourteen tools for map and globe pages, a core of `get_view` and `set_view` and six optional groups, with one view shape for maps and globes, worked over in-memory state in `@tabdock/sim-page/map` and in a canvas page with no map library for Playwright and the CI check, `pnpm dev:map` (ADR 0038).

**Images.** A tool the page names in the new `policy.imageTools` (`data-image-tools`) may return one still PNG, JPEG or WebP in an envelope, `{ image: { mimeType, data }, text }`, of at most `TABDOCK_MAX_IMAGE_BYTES` decoded bytes (65,536 by default, 524,288 at most, 0 for none) and 8,192 pixels a side. One strict check in the protocol serves the adapter and the relay, which checks it again, and refuses an animated PNG or WebP with the call record's `imageRefused: 'animated'` and "the image is animated; only a still image passes", since a file within the byte cap could decode to far more pixels than the dimension caps allow (ADR 0039's notes); a client gets the label, a relay line calling the image untrusted and the page's text in one text block, then the image, never structured content. Nobody re-encodes. The adapter starts image calls one at a time, 250 ms apart, with 8 waiting, after any consequential prompt, and the audit records each image's type, size and SHA-256. The adapter exports the cap's default and ceiling as `DEFAULT_IMAGE_BYTES` and `MAX_IMAGE_BYTES`. The demo gains `capture_board` (ADR 0039).

**Page state.** `dock.publishState(value)`, or a `tabdock:state` event (`STATE_EVENT`) on a script-tag page, shares a JSON object of at most 16,384 bytes, at most twice a second, which the new fixed tools `get_page_state` and `wait_for_page_state` read and wait on behind their own label, without running a tool; a user holds two waits at once. `TABDOCK_MAX_STATE_BYTES` (4 MiB) caps what every page holds, past which a value is withheld (ADR 0040).

**CI checks.** `@tabdock/adapter/testing` reads the widget's pairing code and clicks its armed buttons through the DevTools protocol, with no browser driver, only where a hit test at the very point of the press, in view and on a scrolled page too, reaches the button, and `@tabdock/protocol/devtools` holds the schemas it checks replies with. `tests/ci-check` is a copyable check that walks a map page's every stop against local mode; `pnpm ci-check` runs it, and CI's new `ci-check` job runs it with no secret (ADR 0041).

**Proposals.** Under a policy's `proposals` (`'off'` by default, `'members'` or `'all'`; `data-proposals`), an observer's write answers `proposed` with an id instead of `role_denied`, the widget queues it with Accept, Dismiss and Dismiss all, and Accept is that call's confirmation; the page runs it only against its own record of the Accept. The new fixed tools `get_proposal` and `withdraw_proposal` follow it, and the new error `proposal_not_found` answers an unknown id and another user's alike. A user holds 3 pending on a page and a page 20; a proposal withdrawn, refused or dropped by its proposer's detach keeps its place for a minute; one user's proposals hold at most an eighth of `TABDOCK_MAX_PROPOSAL_BYTES` (16 MiB); and a proposal goes out only where the page link has room. Page code answers the queue as the widget does, with `dock.acceptProposal(proposalId)`, `dock.dismissProposal(proposalId)` and `dock.dismissAllProposals()` (ADR 0042).

**Time-boxed sessions and the members file.** The operator starts a session of 30 to 240 minutes in the widget or with `dock.startSession()`, narrowing driver seats and proposals within the policy, with one watch invite for every 20 observers shown one QR at a time, warnings at 5 minutes and 1, Extend and an End that asks first; its end, on the relay's clock and the page's, closes every live invite and every agent token on the page and ends every attachment an invite or agent token made, those from before the session included. Beside `dock.startSession()`, page code has `dock.extendSession(minutes)`, `dock.endSession()` and `dock.renewSessionLink()`, which mints the next observers' link. `TABDOCK_MEMBERS_FILE` lists the members in a file the relay polls every 2 s and applies within about 4 s of a change, in place of `TABDOCK_OAUTH_USERS`; a removal ends what the old id held as it applies (ADR 0043).

**Larger rooms and agent tokens.** Invitees watching by invite take watching seats, `TABDOCK_MAX_OBSERVERS_PER_PAGE` (40, 0 for M5's rule), apart from the people limit, shown in a compact Watching section that closes past 8 rows, filters, and has one "Revoke closes their link" box; join notices by one invite merge into one line from the third, Revoke and Revoke all ask first while a sponsor's invites have let people in, and a promotion a full people limit refuses says so. Watchers share 60 calls a minute per page, 15 per watcher, 4 running and 2 per watcher, options set by the room measurement. `TABDOCK_MAX_RESPONSE_BYTES` (96 MiB) caps unread answers relay-wide, cutting strangers' and then guests', never a member's. Behind `TABDOCK_AGENT_TOKENS`, which needs invites (and minting needs a public URL), the widget mints a token for 1, 4 or 8 hours and shows a `claude mcp add` command once, its Invite form opening at Can watch each time; its first request at `/g/mcp` raises an ordinary prompt, observer only, a deny or three timeouts burn it, every miss is a 404, and it is for Claude Code and scripts, never a hosted connector; page code mints one with `dock.agentToken(options)` and closes it with `dock.cancelAgent(tokenId)`. `pnpm measure:room` measured a class of 40 and of 80 on a 512 MiB relay (ADR 0044). `pnpm dev:public`'s banner says whether invites, agent tokens and the restart snapshot are on.

**Session records.** The widget keeps an in-memory record of who attached and every call that reached the page, never arguments or results, offers it when a session ends, and saves it as JSON and a Markdown summary only on the operator's click, after saying how many people it names and how many by email address. `tabdock-relay audit --match <file>` (`pnpm audit:log --match`) holds a saved record to the audit log call by call through the call record's new `callId`, and `--call <id>` finds the call records with that `callId`. Page code copies the current, previous or ended record with `dock.sessionRecord(which)` and drops one with `dock.discardRecord(which)`, and `sessionRecordJson`, `sessionRecordMarkdown` and `sessionRecordFileName` write a record as the widget saves it (ADR 0045).

**Restart snapshot.** With `TABDOCK_RESTART_SNAPSHOT` on (off by default, needing an audit directory), a graceful stop writes a snapshot, holding digests in place of every secret, token and code beside names, emails and page titles, and a start within 10 minutes resumes pages under their same ids, attachments, invites, agent tokens and time-boxed sessions, never pairing codes, pending requests, proposals or published state. The snapshot is bound to the audit log's last two records and to the `/pair` client, so rotating its secret ends everything; leave the setting off while rotating anything else. Names follow the member list in force, a member comes back only where it gives the same subject, the seats and origins must still fit, an invitee keeps two clients, no snapshot is written while a member list change is owed, and every start removes a stop's leftover temporary files (ADR 0046).

**Deploy.** `deploy/fly/fly.toml`'s `kill_timeout` rises from 5 to 30 seconds, since stopping the fullest hosted relay and writing its snapshot took 6.2 to 8.7 s at the baseline share, and its volume at `/data` holds the members file and the snapshot beside the audit log once you choose them. `.github/workflows/deploy.yml` takes `TABDOCK_MEMBERS_FILE` as a variable of the `production` environment beside the secret `TABDOCK_OAUTH_USERS`, refuses both at once, and unsets whichever is not in use, since Fly keeps a secret until it is unset. `pnpm dev:public` accepts a members file in place of `TABDOCK_OAUTH_USERS`.

**The map demo.** `apps/map-demo`, private and never on npm, draws Earth as a flat map and a globe on a plain canvas with no map library, from Natural Earth's public-domain 1:110m land and lakes at v5.1.2, vendored by a generator run by hand that stops unless each file's SHA-256 matches its pin. It registers fourteen tools, every tool of the map profile but the clock group's two, with `edit_stop` and `reset_edits`, under `MAP_PAGE_POLICY` with `capture_view` as its image tool; it walks a six-stop tour of Earth, captures its own map again for `capture_view` and publishes its view as page state. Like the board it dials only a relay its visitor chose, through a Connect bar or form with a remembered choice of its own, reads no policy from its link and has no test hook in any build. The Pages site builds it at `/map/` under the board's meta policy with `worker-src 'none'` and `media-src 'self'`, and `pnpm dev:map-demo` serves it on port 5175 (`MAP_DEMO_PORT`). The board's relay check and armed Connect button are now `@tabdock/demo/relay` and `@tabdock/demo/arming`, which both pages use (ADR 0050). `pnpm record:map-demo` films it by hand beside a local relay, with the pairing code kept out of every frame, while an SDK client standing in for Claude takes the tour, and sets a pane of that client's real calls and answers beside the page, joined with ffmpeg; the take, under a minute, is kept in `apps/map-demo/media/` as an MP4 and a WebM, which the page plays from its poster and the site serves at `/map/media/`, and a looping GIF, which the README shows, each held to a budget. Both pages now build with zod's English messages alone, leaving out its other languages: the map's script fell from 707,027 bytes to about 447,000 (148,000 gzipped) and the board's from 1,087,634 to about 742,000.

**Changed.** The page link stays `tabdock.v1` with every new field optional: the hello's policy gains `imageTools` and `proposals`, the welcome `maxImageBytes`, `maxStateBytes`, `usersPerPage` and `observersPerPage`, the result `image`, the invoke `proposal`, and `attach_request` `via: 'agent'` with its `agent` part; the frames `state`, `proposal`, `proposal_decision`, `proposal_end`, `session_start`, `session_extend`, `session_end`, `session`, `agent_create`, `agent_cancel` and `agents` are new, so an M5 peer meets frame types it does not know. `@tabdock/protocol` names its one side effect, `zod-config`, in `sideEffects`, so a bundler may drop the modules a page never imports (ADR 0048's notes).

The fixed tools are nine: M4's five first and unchanged in name, schema and annotations, then `get_page_state`, `wait_for_page_state`, `get_proposal` and `withdraw_proposal`. `detach_page`'s description now says that attachments your invites let in end with yours, and `call_page_tool`'s mentions proposals. A first-class tool's prefix now says "untrusted page content" where it said "untrusted page text". `list_page_tools`'s description mentions proposals, and its result marks a tool the caller may propose `proposable: true`. The relay's MCP instructions name page state reads, proposals and an agent's `pair_page` with no arguments; `pair_page`'s and `detach_page`'s descriptions gain a clause for an agent, and an agent's empty `list_pages` says to call `pair_page` with no arguments (ADR 0049). The widget gives each refusal of a session a sentence of its own, opening the form again to show it where the relay refused or never answered, and says that New link closes the session's earlier links, and `/i` says to add the connector in Claude on the web or the desktop app.

Invitees watching by invite no longer count against `TABDOCK_MAX_USERS_PER_PAGE`, which is now refused above 50, and every other invite-made attachment still leaves members two of its seats. An invitee's roster row lists two clients. `TABDOCK_MAX_INVITEE_SESSIONS` is a setting, and its default rises from 50 to 100; it, `TABDOCK_MAX_OBSERVERS_PER_PAGE` and `TABDOCK_AGENT_TOKENS` are refused without `TABDOCK_INVITES`. The script-tag build's ceiling rises from 150,000 to 200,000 bytes (ADR 0048). The audit log adds optional fields to the call record (`callId`, an image's type, size and digest, `imageRefused`, a proposal's id and `acceptedOnPage`) and to `relay_start` (`agentTokens`, `restartSnapshot`), and records for proposals, sessions, member reloads, the snapshot and agent tokens; `AUDIT_VERSION` stays 1 while 0.1.0 is unpublished, and moves to 2 with a reader for both if 0.1.0 publishes first (ADR 0045).

The MCP-B 6 test leg runs on the released 6.0.0, whose ESM import no longer installs the polyfill, so a page using it from npm calls `installWebMCP()`; the demo stays on exact 5.1.0 (ADR 0047). The demo board publishes its view as page state, reads `?proposals` with a third box on its Connect form, and gains `capture_board`; `pnpm demo:m6` narrates a lesson on the canvas map page. `tests/ci-check` stops at once when `CI_CHECK_PAGE_URL` is unset or empty.

## 0.1.0 (prepared 5 October 2026, not yet published)

The first release, from the work of milestones M0 to M5.

**Added.** `npx @tabdock/relay` runs the relay as one command, `tabdock-relay`, with Node 22.18 or later: with no settings it runs local mode for this computer only, keeps a private owner token outside any git work tree and prints a `claude mcp add-json` command whose header helper reads the token at each connection, so the token is in neither the command nor Claude Code's settings (ADRs 0022 and 0028). `tabdock-relay --new-token` replaces the token in one rename, `tabdock-relay audit` reads the hash-chained audit log (ADR 0019), and `tabdock-relay --version` prints the version. The relay serves several clients and people on one page with the operator approving each (S4), observers and drivers, and invites for guests at a public URL (ADRs 0016 and 0017). `@tabdock/adapter` links a page's WebMCP tools to a relay, enforces roles and consequential-call prompts again on the page, and shows the operator's widget, which says when `maxDrivers` seats someone the operator chose as driver as an observer; `attach()` throws a `TypeError` naming a bad policy's fields, never their values (ADR 0032). Its script-tag build, `dist/tabdock-adapter.js`, is one self-contained file under 150,000 bytes for pages without a build step, which logs one `[tabdock]` line and attaches nothing for a bad attribute or a `data-relay` other than `ws:` or `wss:`, and whose hint notice names `data-consequential-tools`, and passes its call, cancel and consequential specs on the MCP-B 6.0 beta as well as on 5.1.0, which the demo keeps. `@tabdock/protocol` holds the page link's types and `zod/mini` schemas, which both sides validate every frame with.

**First-class page tools.** With `TABDOCK_FIRST_CLASS_TOOLS=1`, off by default in every mode, a member's client lists the tools of each page they hold as `<page id>__<tool>` beside the five fixed tools, a driver every tool and an observer the read-only ones; invitees and attachments an invite made keep the five fixed tools. Each description starts with a relay prefix calling the page's name, title, description, schema and results untrusted text, and a call by such a name takes the very path `call_page_tool` takes, with the same checks, prompts, audit records and errors. A user hears of changes to their own pages only, at most once every 10 s, and on 2026-07-28 the list is cached privately for 10 s (ADRs 0025 and 0032).

**Confirmation in the client.** A page that sets `policy.confirmVia: 'client'` (`data-confirm-via="client"` on the script tag) lets a member driver whose attachment no invite made, and whose client declares form elicitation, confirm a consequential call in that client instead of on the page: through `input_required` on 2026-07-28, bound to one exact call by a signed request state and a single-use record, and through an elicitation inside the request on a 2025-era session. The page raises no prompt, its activity log says the call was confirmed in the client, and the audit record carries `confirmedBy: 'client'`. Decline, cancel, expiry, replay and changed arguments answer the new error `not_confirmed`; a page that did not opt in, an observer, an invitee, an invite-made attachment and a client without form elicitation all get the page's prompt as before (ADR 0026).

**MCP revisions.** The relay serves 2025-03-26, 2025-06-18, 2025-11-25 and 2026-07-28 over Streamable HTTP, with 2024-11-05 as best effort. CI verifies both eras with a client matrix (`@modelcontextprotocol/sdk` 1.10.2, 1.12.3, 1.24.0 and 1.32.0, and client 2.3.1 in legacy, auto and pinned modes) and with the official conformance suite's 2025-11-25 and 2026-07-28 requirement sets against checked-in baselines; Claude Code 2.1.289 was checked on both revisions in a sandbox. One `mcp client` log line per user, client and leg an hour names the revision each client speaks (ADR 0027).

**The tour site and the demo.** `apps/site` builds the demo board at `/` and the `docs/tour` explainers at `/tour/` as one static site for GitHub Pages, its Mermaid diagrams drawn at build time so tour pages carry no script, published by dispatching `.github/workflows/pages.yml` on `main`. The demo board dials only a relay its visitor chose: a linked relay shows a "Connect to <host>" bar that connects after the visitor's own click, no relay shows a Connect form, a relay URL with a query or fragment is refused, and the static build carries a Content-Security-Policy meta (ADR 0029).

**The guide.** `docs/guide/` is a user guide beside the tour: concepts, a quick start, adding Tabdock to an app, the adapter and relay references, connecting clients, sharing, running a relay, use cases, security, troubleshooting, and setup problems and limits (ADR 0035), published on the Pages site at `/guide/` beside the tour under the tour's no-script rules, and held to the code by doc sync tests. The relay's own tool text now points an account that joins pages by invite to an invite link where it named only a pairing code: `detach_page`'s description and the answer `list_pages` gives when you hold no page.

**Security.** SPEC section 9's rules S1 to S14 hold, each with its tests; the threat model is `docs/threat-model.md`. `/mcp` refuses a request whose `Origin` is present and off its allowlist with 403 before auth: loopback origins in local and dev-token mode, the public origin in public and hosted mode, plus `TABDOCK_MCP_ALLOWED_ORIGINS` (ADR 0027). From the last M4 review and the M5 Step 1 review (ADRs 0030 and 0032): invitees together hold at most a quarter of the relay's request bytes and each invitee a quarter of that; an `/mcp` response its client leaves unread, so that no more of it can be sent for 30 s, is cut off and logged, as are a user's oldest responses with bytes waiting past eight (two for an invitee), and a response queued behind another on a connection that closes ends with it; every 2026-07-28 request spends its user's request budget, and while first-class tools are on so does every 2025-era `tools/list`; the relay refuses a per-user request share above its total; an invite past its end can no longer be approved; and the adapter caps a relay's call deadline at the timer maximum. From the M5 section 9 review (A5.6, ADRs 0025 and 0029): page text reaches a client only as text behind its `[tabdock: ...]` label, never as structured content, which Claude Code shows its model in place of the text; a first-class entry's title and schema text defuse every opening bracket, opening quote and `<` before `tabdock`, accents on its letters or not; and the demo board's `?e2e` test hook, which skips the Connect click, exists only on a dev or test server asked for it, under a random key, so `pnpm dev` cannot be made to dial by another site's link. An empty `policy.consequentialTools`, or an empty `data-consequential-tools`, names no tool, so where the runtime drops `consequentialHint` (MCP-B 5.1.0, Chrome 153) every tool that is not read-only still prompts on the page, carries the `consequential` mark to the relay and brings the widget's notice; the README and SPEC examples no longer show `consequentialTools: []` (ADR 0034). A refusal at start never repeats a setting's value, since a token may sit in the wrong variable: a list entry is named by its place, two that clash by both places, the identity provider by `TABDOCK_OAUTH_ISSUER`, and a directory `TABDOCK_HOME` or `TABDOCK_AUDIT_DIR` gives, with what lies in or above it, by its setting, since a token starting with `/` passes as a path (ADR 0028's notes).
