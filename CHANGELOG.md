# Changelog

`@tabdock/protocol`, `@tabdock/adapter` and `@tabdock/relay` share one version, so this one file covers all three, one entry per release, each tagged `v<version>` (ADR 0028). `docs/release.md` says how a release is made. Versions follow semantic versioning; while they start with 0, a minor version may change the page link, the relay's settings or the packages' API.

## 0.1.0 (prepared 5 October 2026, not yet published)

The first release, from the work of milestones M0 to M5.

**Added.** `npx @tabdock/relay` runs the relay as one command, `tabdock-relay`, with Node 22.18 or later: with no settings it runs local mode for this computer only, keeps a private owner token outside any git work tree and prints a `claude mcp add-json` command whose header helper reads the token at each connection, so the token is in neither the command nor Claude Code's settings (ADRs 0022 and 0028). `tabdock-relay --new-token` replaces the token in one rename, `tabdock-relay audit` reads the hash-chained audit log (ADR 0019), and `tabdock-relay --version` prints the version. The relay serves several clients and people on one page with the operator approving each (S4), observers and drivers, and invites for guests at a public URL (ADRs 0016 and 0017). `@tabdock/adapter` links a page's WebMCP tools to a relay, enforces roles and consequential-call prompts again on the page, and shows the operator's widget; `attach()` throws a `TypeError` naming a bad policy's fields, never their values (ADR 0032). Its script-tag build, `dist/tabdock-adapter.js`, is one self-contained file under 150,000 bytes for pages without a build step, and passes its call, cancel and consequential specs on the MCP-B 6.0 beta as well as on 5.1.0, which the demo keeps. `@tabdock/protocol` holds the page link's types and `zod/mini` schemas, which both sides validate every frame with.

**First-class page tools.** With `TABDOCK_FIRST_CLASS_TOOLS=1`, off by default in every mode, a member's client lists the tools of each page they hold as `<page id>__<tool>` beside the five fixed tools, a driver every tool and an observer the read-only ones; invitees and attachments an invite made keep the five fixed tools. Each description starts with a relay prefix calling the page's name, title, description, schema and results untrusted text, and a call by such a name takes the very path `call_page_tool` takes, with the same checks, prompts, audit records and errors. A user hears of changes to their own pages only, at most once every 10 s, and on 2026-07-28 the list is cached privately for 10 s (ADRs 0025 and 0032).

**Confirmation in the client.** A page that sets `policy.confirmVia: 'client'` (`data-confirm-via="client"` on the script tag) lets a member driver whose attachment no invite made, and whose client declares form elicitation, confirm a consequential call in that client instead of on the page: through `input_required` on 2026-07-28, bound to one exact call by a signed request state and a single-use record, and through an elicitation inside the request on a 2025-era session. The page raises no prompt, its activity log says the call was confirmed in the client, and the audit record carries `confirmedBy: 'client'`. Decline, cancel, expiry, replay and changed arguments answer the new error `not_confirmed`; a page that did not opt in, an observer, an invitee, an invite-made attachment and a client without form elicitation all get the page's prompt as before (ADR 0026).

**MCP revisions.** The relay serves 2025-03-26, 2025-06-18, 2025-11-25 and 2026-07-28 over Streamable HTTP, with 2024-11-05 as best effort. CI verifies both eras with a client matrix (`@modelcontextprotocol/sdk` 1.10.2, 1.12.3, 1.24.0 and 1.32.0, and client 2.3.0 in legacy, auto and pinned modes) and with the official conformance suite's 2025-11-25 and 2026-07-28 requirement sets against checked-in baselines; Claude Code 2.1.289 was checked on both revisions in a sandbox. One `mcp client` log line per user, client and leg an hour names the revision each client speaks (ADR 0027).

**The tour site and the demo.** `apps/site` builds the demo board at `/` and the `docs/tour` explainers at `/tour/` as one static site for GitHub Pages, its Mermaid diagrams drawn at build time so tour pages carry no script, published by dispatching `.github/workflows/pages.yml` on `main`. The demo board dials only a relay its visitor chose: a linked relay shows a "Connect to <host>" bar that connects after the visitor's own click, no relay shows a Connect form, a relay URL with a query or fragment is refused, and the static build carries a Content-Security-Policy meta (ADR 0029).

**The guide.** `docs/guide/` is a user guide beside the tour: concepts, a quick start, adding Tabdock to an app, the adapter and relay references, connecting clients, sharing, running a relay, use cases, security, troubleshooting, and setup problems and limits (ADR 0035), published on the Pages site at `/guide/` beside the tour under the tour's no-script rules, and held to the code by doc sync tests. The relay's own tool text now points an account that joins pages by invite to an invite link where it named only a pairing code: `detach_page`'s description and the answer `list_pages` gives when you hold no page.

**Security.** SPEC section 9's rules S1 to S14 hold, each with its tests; the threat model is `docs/threat-model.md`. `/mcp` refuses a request whose `Origin` is present and off its allowlist with 403 before auth: loopback origins in local and dev-token mode, the public origin in public and hosted mode, plus `TABDOCK_MCP_ALLOWED_ORIGINS` (ADR 0027). From the last M4 review and the M5 Step 1 review (ADRs 0030 and 0032): invitees together hold at most a quarter of the relay's request bytes and each invitee a quarter of that; an `/mcp` response its client leaves unread, so that no more of it can be sent for 30 s, is cut off and logged, as are a user's oldest responses with bytes waiting past eight (two for an invitee), and a response queued behind another on a connection that closes ends with it; every 2026-07-28 request spends its user's request budget, and while first-class tools are on so does every 2025-era `tools/list`; the relay refuses a per-user request share above its total; an invite past its end can no longer be approved; and the adapter caps a relay's call deadline at the timer maximum. From the M5 section 9 review (A5.6, ADRs 0025 and 0029): page text reaches a client only as text behind its `[tabdock: ...]` label, never as structured content, which Claude Code shows its model in place of the text; a first-class entry's title and schema text defuse every opening bracket, opening quote and `<` before `tabdock`, accents on its letters or not; and the demo board's `?e2e` test hook, which skips the Connect click, exists only on a dev or test server asked for it, under a random key, so `pnpm dev` cannot be made to dial by another site's link. An empty `policy.consequentialTools`, or an empty `data-consequential-tools`, names no tool, so where the runtime drops `consequentialHint` (MCP-B 5.1.0, Chrome 153) every tool that is not read-only still prompts on the page, carries the `consequential` mark to the relay and brings the widget's notice; the README and SPEC examples no longer show `consequentialTools: []` (ADR 0034).
